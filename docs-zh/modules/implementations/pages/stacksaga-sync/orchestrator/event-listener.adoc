= 事务事件监听器 (Transaction Event Listener)

[[event_listener_for_stage_change_events]]
== 事务状态变更监听器 (Transaction State Change Listeners)

在通过调用 `StackSagaTemplate` 的 `execute` 或 `executeAsync` 方法将事务交由 StackSaga 引擎接管后，事务便开始在流转中执行，并在事务流程的每个执行步骤（主执行与补偿执行）完成后随时更新其状态。
如果您希望持续监听事务状态的变化并基于其执行相应动作，框架提供了完善的监听机制。

根据运行环境的不同，可以选择对应的实现方式：

. **`TransactionEventListener`**：适用于非响应式（命令式，Imperative）环境。
. **`ReactiveTransactionEventListener`**：适用于响应式（Reactive）环境。

如果您希望获取事务状态变更的通知，框架提供了两种主要途径：

. 使用 `StackSagaTemplate.getCurrentState`
. 使用 `TransactionEventListener` 或 `ReactiveTransactionEventListener`

IMPORTANT: 通过提供 `transactionId` 调用 `StackSagaTemplate.getCurrentState` 方法获取事务当前状态的方式效率较低，因为每当您调用此方法时，引擎都必须从事件存储 (Event Store) 中实时读取事务状态。
而如果使用监听器，在事务流中的每次步骤执行之后，您都会实时收到状态变更通知，无需主动轮询调用任何方法，因为事务的当前状态会实时传递给监听器的回调方法。
在下单示例中，执行完成后，您可以通过这些监听器即时推送通知以更新用户的订单状态。
但在某些情况下，您可能希望在事务完成后主动查询当前状态（例如用户在下单后进入页面查看订单详情），此时便可以通过 `SagaTemplate.getCurrentState` 并传入 `transactionId` 进行查询。
这两种方式的适用场景截然不同，您可以根据实际需求灵活选用。

[IMPORTANT]
====
*顺序执行与延迟影响 (Sequential Execution and Latency Impact)：* +
在使用监听器的 `onStateChanged` 方法时，请注意该方法是在每个跨度执行完毕后作为事务生命周期的一部分**顺序同步调用的**。Saga 流程中的下一个跨度只有在当前 `onStateChanged` 执行完成后才会被触发。避免在此方法中直接执行繁重的计算或阻塞式 I/O，因为这会直接延缓整个分布式事务的流转速度。如果需要进行重型处理，请将其异步转交至独立的线程池。

*可暂停长事务 (Pausable LRT) 中的至少一次通知（重复调用风险）：* +
在 xref:stacksaga-sync/index.adoc#pausable-lrt[可暂停长事务 (Pausable LRT)] 中，如果执行器配置了超时时长 (`Duration`) 并暂停等待外部回调，在执行器最初成功执行完毕时会触发一次 `onStateChanged`。如果外部回调在超时过期前未到达，框架将重新执行该暂停的执行器，从而为同一步骤**再次**调用 `onStateChanged`。参见 xref:stacksaga-sync/orchestrator/stacksaga_template.adoc#pausable-lrt-timeout-reexecution[超时重新执行机制]。

*至关重要的设计原则 —— 使用 `QueryExecutor` 处理业务逻辑：* +
切勿使用 `TransactionEventListener` 执行核心业务状态变更或非幂等性操作。如果某个无需补偿的操作必须紧随某个执行器执行（例如生成内部收据或审计记录），请在 Saga 流程中将其建模为合法的 **`QueryExecutor`**，而不是放在事件监听器中。
====

[[transaction_event_listener]]
=== TransactionEventListener

您可以实现 `TransactionEventListener` 接口，在非响应式环境中监听事务事件，如下所示：

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class PlaceOrderHandler implements TransactionEventListener<OrderDomainEntity> {
    @Override
    public void onStateChanged(TransactionState<OrderDomainEntity, SyncExecutionEvent<OrderDomainEntity>> state) {
        TransactionCompleteStatus currentStatus = state.getCurrentStatus();
        log.info("当前事务状态: {}", currentStatus);
        NavigableMap<Integer, ? extends SyncExecutionEvent<OrderDomainEntity>> executionHistory = state.getExecutionHistory();
        log.info("事务执行历史: {}", executionHistory);
        OrderDomainEntity currentDomainEntity = state.getCurrentDomainEntity();
        log.info("当前领域实体状态: {}", currentDomainEntity);
        ZonedDateTime startedDateTime = state.getStartedDateTime();
        log.info("事务启动时间: {}", startedDateTime.toLocalDateTime());
    }
}
----

NOTE: 此处的 `onStateChanged` 是在框架专用的 `blockingExecutionScheduler`（专为阻塞式、非响应式监听器代码保留的有界弹性调度器）上调用的，绝不会运行在驱动事务步骤本身的线程上。这防止了缓慢或阻塞的 `TransactionEventListener` 拖慢不相关的事务。可通过 `stacksaga.scheduler.blocking-execution.*` 对其进行调优，参见 xref:stacksaga-sync/orchestrator/properties.adoc[配置属性]。

[[reactive_transaction_event_listener]]
=== ReactiveTransactionEventListener

您可以实现 `ReactiveTransactionEventListener` 接口，在响应式环境中监听事务事件，如下所示：

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class ReactivePlaceOrderHandler implements ReactiveTransactionEventListener<OrderDomainEntity> {
    @Override
    public Mono<Void> onStateChanged(TransactionState<OrderDomainEntity, SyncExecutionEvent<OrderDomainEntity>> transactionState) {
        return Mono
                .just(transactionState)
                .doOnNext(state -> {
                    TransactionCompleteStatus currentStatus = state.getCurrentStatus();
                    log.info("当前事务状态: {}", currentStatus);
                    NavigableMap<Integer, ? extends SyncExecutionEvent<OrderDomainEntity>> executionHistory = state.getExecutionHistory();
                    log.info("事务执行历史: {}", executionHistory);
                    OrderDomainEntity currentDomainEntity = state.getCurrentDomainEntity();
                    log.info("当前领域实体状态: {}", currentDomainEntity);
                    ZonedDateTime startedDateTime = state.getStartedDateTime();
                    log.info("事务启动时间: {}", startedDateTime.toLocalDateTime());
                })
                .flatMap(orderDomainEntityTransactionState -> {
                    // 在此处模拟异步处理逻辑
                    return Mono.delay(Duration.ofSeconds(1))
                            .then();
                });
    }
}
----

NOTE: 此处的 `onStateChanged` 不会插入额外的调度器切换 —— 它直接继承驱动进行中 Saga 处理的框架共享非阻塞 `executionScheduler`。因此，在其中进行的任何阻塞调用都可能导致不相关的事务发生饥饿；请确保此实现保持完全响应式/非阻塞。可通过 `stacksaga.scheduler.execution.*` 对该调度器进行调优，参见 xref:stacksaga-sync/orchestrator/properties.adoc[配置属性]。

== 推荐的处理程序模式 (Recommended Handler Pattern)

StackSaga 团队建议将 Saga 事务相关的操作集中在一个名为 `Handler` 的独立类中实现，该类专门负责启动、监听和检查 Saga 事务的状态。
以下代码展示了 Handler 的推荐架构：

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class PlaceOrderHandler implements TransactionEventListener<OrderDomainEntity> {

    private SagaTemplate<OrderDomainEntity> sagaTemplate;

    public String handle(String username, double amount, List<String> items) { //<1>
        return this
                .sagaTemplate
                .init(() -> {
                  // 初始化领域实体....
                })
                .....
    }

    public CustomOrderStatusView getCurrentState(String orderId) { //<2>
        return this
                .sagaTemplate
                .getCurrentState(orderId)
                ......

    }
    @Override
    public void onStateChanged(TransactionState<OrderDomainEntity, SyncExecutionEvent<OrderDomainEntity>> transactionState) { //<3>
        // 处理状态变更通知....
    }
}
----

<1> `handle` 方法负责使用 `SagaTemplate` 并提供启动事务所需的必要参数来发起 Saga 事务。
<2> 使用 `SagaTemplate` 获取事务的当前聚合状态。
<3> 实现 `TransactionEventListener` 接口并重写 `onStateChanged` 方法，以监听事务状态的实时变更。
