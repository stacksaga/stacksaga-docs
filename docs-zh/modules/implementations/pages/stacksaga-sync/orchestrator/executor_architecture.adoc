= Saga 执行器 (Saga Executors)

== 概述 (Overview)

在 StackSaga 中，Saga 执行器 (Saga Executor) 是一个专用组件，负责在分布式 Saga 工作流中封装并执行单个原子事务 (Atomic Transaction)。
它充当业务逻辑与 Saga 编排引擎之间的桥梁，确保长事务 (LRT - Long-Running Transaction) 中的每个步骤都能可靠且一致地执行。

Saga 执行器分为两类：**命令执行器 (Command Executors)**（处理修改状态的操作，同时支持主执行与补偿执行）与 **查询执行器 (Query Executors)**（处理只读操作）。
通过将每个原子事务隔离在独立的执行器中，StackSaga 实现了精确的控制、自动重试与补偿机制，彻底消除了分布式数据异常，并保证了跨微服务的最终一致性 (Eventual Consistency)。

IMPORTANT: 如果您刚接触 Saga 模式，建议先阅读 xref:foundations:idempotency.adoc[]，了解分布式系统中的幂等性 (Idempotency) 和原子操作概念。

通常，一个原子执行包含两个阶段：**主执行 (Primary Execution)** 与 **补偿执行 (Compensating Execution)**。

1. **主执行 (Primary Execution / Main Forward Execution)**：
主执行代表长事务中的核心业务前向操作。
每个主执行都是整体业务工作流中的独立步骤，推动流程向最终完成演进。
这些操作具备幂等性与隔离性，确保它们可以独立且安全地执行，不会产生意外的副作用。
+
例如，在下单工作流中，主执行可能包括获取用户详情、初始化订单、进行预授权、扣减库存以及处理最终支付。
+
这些主执行推动流程向前演进。[icon:arrow-circle-right[1x,role=green]]

2. **补偿执行 (Compensating Execution / Revert Execution)**：
补偿执行旨在当后续步骤发生失败时，撤销先前已成功完成的主执行所产生的影响。
每个命令执行都有一个对应的补偿动作来逆转其影响，确保系统在发生故障时能够恢复到一致状态。
+
补偿执行推动流程向后回滚。[icon:arrow-circle-left[1x,role=green]]

=== 真实业务场景：电商下单 Saga 工作流

以典型的电商下单场景为例：顾客购买一台价值 \$1,500 的笔记本电脑。为了完成这一笔业务请求，编排器必须按序协同 4 个相互独立的微服务：

1. **用户服务** (`CheckCustomerEligibilityExecutor`)：验证客户账户状态并检查授信额度（只读查询）。
2. **订单服务** (`CreateOrderCommandExecutor`)：在数据库中创建处于 `PENDING`（待处理）状态的订单并保存商品条目。
3. **支付服务** (`ProcessPaymentCommandExecutor`)：与外部支付网关或银行对接，对客户的信用卡进行预授权并完成扣款。
4. **库存服务** (`ReserveStockCommandExecutor`)：在仓库数据库中扣减并锁定实物库存。

=== 为什么单体 `@Transactional` 在分布式微服务中失效

在传统的单体架构中，整个流程往往被包裹在一个单一的 Spring `@Transactional` 本地事务方法中。
若步骤 3 的支付网关拒绝了扣款，本地数据库事务会自动回滚：订单记录被丢弃，库存未曾变动，数据一致性自然得到保障。

然而，在现代分布式微服务架构中：

* 订单服务写入自身独立的 **PostgreSQL** 数据库。
* 库存服务写入自身独立的 **Oracle** 或 **MySQL** 数据库。
* 支付服务通过 HTTP 调用外部第三方 API（**Stripe、PayPal 或核心银行清算网关**）。

由于每个微服务均拥有完全隔离的私有持久化存储，**跨服务的单一数据库事务在物理上是无法成立的**。
传统的分布式事务方案（如两阶段提交 2PC 或 XA 事务）需要在所有参与者之间维持全局悲观锁，导致极高的网络延迟、单点故障隐患，并且在跨公网网络时极其脆弱。

这正是 **StackSaga 执行器 (Executors)** 旨在彻底解决的核心问题。

=== 原子事务的边界法则：“一个执行器 = 一个原子操作”

在 StackSaga 中，一个 **Saga 执行器 (Executor)** 被严格定义为：**在单个微服务边界内封装的一笔原子事务**。

[IMPORTANT]
.基本架构法则：一个执行器 = 一个原子操作
====
一个执行器应当且仅应当与**一个微服务或一个数据库边界**交互。
绝不要在单个执行器内部混合多个修改外部状态的动作（例如：在同一个 `doProcess()` 方法中既创建订单记录又调用信用卡扣款）。
====

为什么必须严格执行原子边界划分？

1. **故障隔离与爆炸半径控制 (Blast Radius Control)**：
若某个执行器在同一个方法内先在订单服务创建了记录，随后调用外部 Stripe 扣款，一旦在调用 Stripe 时发生网络超时，系统将陷入不可知的“灰度状态”（无法确定卡到底扣成功没有）。
将其拆解为 `CreateOrderCommandExecutor` 与 `ProcessPaymentCommandExecutor` 两个执行器后，StackSaga 能以 100% 的确定性得知：步骤 2 已成功提交，而步骤 3 失败。

2. **细粒度幂等性与重试机制 (Granular Idempotency)**：
每个执行器在运行时都会获得一个为该次执行跨度专门生成的确定性 `idempotencyKey`。
若支付服务由于瞬时网络抖动发生超时，StackSaga 的重试引擎可以安全地利用该稳定的 `idempotencyKey` 重试 `ProcessPaymentCommandExecutor`，而绝不会意外重走一遍订单服务造成重复下单。

3. **边界清晰的反向补偿 (Clean Compensating Boundaries)**：
当发生故障触发补偿时，StackSaga 只需补偿那些**已经成功提交**的步骤。
若步骤 3（支付）失败，库存服务（步骤 4）由于从未被执行，因而完全不需要任何库存回滚。SEC 引擎只需调用 `CreateOrderCommandExecutor.doRevert()` 来取消待处理订单即可。

=== 执行器如何构建并主导 Saga 链路

在 StackSaga 中，执行链路不需要配置在沉重的外部 XML 文件、静态数据表或中心化的 BPMN 编排器中。相反，Saga 链路是由执行器**以类型安全、去中心化且编程式的方式动态驱动的**：

==== 1. 前向链路编排 (去中心化流式路由)
每一个执行器通过 `ProcessStepManager` 自主指定前向流程中的下一个接棒者：

[source,java]
----
// 前向交接：步骤 2 移交至步骤 3
return stepManager
        .success("ORDER_INITIALIZED")
        .noPause()
        .nextExecutor(ProcessPaymentCommandExecutor.class);
----

==== 2. 动态条件分支路由 (Dynamic Branching)
由于路由逻辑是编程式的，执行器可以直接读取 `currentDomainEntity` 中的最新聚合状态，并在运行时做出动态条件分支决策：

[source,java]
----
// 基于聚合状态做出的运行时动态路由：
if (currentDomainEntity.isVipCustomer()) {
    // VIP 优质客户走极速专属扣款通道：
    return stepManager
            .success("ORDER_INITIALIZED")
            .noPause()
            .nextExecutor(ExpressPaymentCommandExecutor.class);
} else {
    return stepManager
            .success("ORDER_INITIALIZED")
            .noPause()
            .nextExecutor(StandardPaymentCommandExecutor.class);
}
----

==== 3. 终结完成 (Terminal Completion)
正向链路中的最后一个执行器通过调用 `.complete()` 通知 SEC 引擎该长事务已圆满结束：

[source,java]
----
// 终结成功：在事件存储中将整个长事务标记为已完成
return stepManager
        .success("STOCK_RESERVED")
        .noPause()
        .complete();
----

==== 4. 逆向补偿链路的自动化协调 (由 SEC 全权接管)
StackSaga 最具颠覆性的架构优势之一在于：**开发者永远不需要编写反向补偿的路由跳转代码**。
您**不需要**在配置中声明“若支付失败，请跳转至取消订单”。

**StackSaga 引擎如何自动调度回滚？**

1. 当事务向前推进时，Saga 执行协调器 (SEC) 会在事件存储表 (`es_transaction_execution_tryout`) 中为每一个成功提交的命令执行器追加写入不可变的溯源日志。
2. 若任何步骤抛出 `NonRetryableExecutorException`（如支付被拒），SEC 会立即刹车，终结正向推进。
3. SEC 引擎逆序读取历史执行日志，并**按照严格的时间逆序**依次调用各个命令执行器的 `doRevert()` 方法：
+
[source,text]
----
Failed Step N (失败步骤 N) ──> doRevert(步骤 N-1) ──> doRevert(步骤 N-2) ... ──> doRevert(步骤 1)
----
+
4. 在调用每一个 `doRevert()` 之前，SEC 会精准还原该执行器当时运行前夕的领域实体聚合快照，确保补偿逻辑基于纯净、准确的历史事实运行。

== 执行器类型与参数解构 (Executor Types & Method Parameters)

基于执行性质，StackSaga 中的 Saga 执行器主要分为核心执行器与专用子执行器：

image:implementations:executor/stacksaga-diagram-executor-types-in-stacksaga.svg[alt="Stacksaga 执行器类型",width=100%,opts=interactive,scaledwidth=100%]

* **xref:#command-executors[命令执行器]** (`CommandExecutor` / `ReactiveCommandExecutor`)：用于修改业务状态且需要补偿的操作。
* **xref:#query-executors[查询执行器]** (`QueryExecutor` / `ReactiveQueryExecutor`)：用于无需补偿的只读操作。
* **xref:#sub-executors[子执行器]**：用于将复杂的多阶段补偿拆分为原子步骤：
** **xref:#sub-before-executors[前置补偿子执行器]** (`RevertBeforeExecutor` / `ReactiveRevertBeforeExecutor`)
** **xref:#sub-after-executors[后置补偿子执行器]** (`RevertAfterExecutor` / `ReactiveRevertAfterExecutor`)

IMPORTANT: 上述每种执行器类型均提供了阻塞式 (Imperative / Blocking) 与非阻塞响应式 (Reactive via Project Reactor) 两种实现。您可以在同一个 Saga 中根据技术栈自由选用或混合搭配。

[TIP]
.密封接口架构与编译期类型安全 (Sealed Interface Foundation)
====
StackSaga 的所有执行器契约均建立在现代 Java 21 **密封接口 (sealed interfaces)** 体系之上，以 `SagaExecutor<DE>` 为根契约。
中间层契约如 `SagaCommandExecutor<DE>` 统一了同步 (`CommandExecutor`) 与响应式 (`ReactiveCommandExecutor`) 命令，并作为子执行器钩子 (`@RevertBefore` 与 `@RevertAfter`) 的通用目标泛型上限 `<E extends SagaCommandExecutor<DE>>`。
同理，`SagaQueryExecutor<DE>` 统一定义只读查询，而 `SagaReactiveExecutor<DE>` 标识所有基于 Project Reactor `Mono` 的非阻塞流。
====

=== 标准方法签名与参数解构

StackSaga 为所有执行器提供了编译期类型安全、统一清晰的方法签名。
所有前向主执行 (`doProcess`) 统一接收 4 个参数，所有命令补偿执行 (`doRevert`) 统一接收 6 个参数：

.标准方法签名结构
[source,java]
----
// 前向执行 (CommandExecutor 与 QueryExecutor):
ProcessStepManager<DE> doProcess(
        @NonNull DE currentDomainEntity,
        @NonNull String idempotencyKey,
        @NonNull ResumeContext resumeContext,
        @NonNull ProcessStepManager<DE> stepManager
) throws RetryableExecutorException, NonRetryableExecutorException;

// 补偿执行 (CommandExecutor):
RevertStepManager doRevert(
        @NonNull NonRetryableExecutorException processException,
        @NonNull DE finalDomainEntityState,
        @NonNull RevertHintStore revertHintStore,
        @NonNull String idempotencyKey,
        @NonNull ResumeContext resumeContext,
        @NonNull RevertStepManager stepManager
) throws RetryableExecutorException;
----

* **`currentDomainEntity` / `finalDomainEntityState`**：事件存储 (Event Store) 还原至当前执行步骤的聚合根状态快照。
* **`idempotencyKey`**：框架为当前执行跨度 (Execution Span) 生成的确定性、重试稳定的全局唯一幂等键。调用下游服务时透传该键（通过 Header、Body 或 Query 参数），以保证跨服务调用的幂等性。
* **`resumeContext`**：当暂停的事务通过 `sagaTemplate.resume(...)` 恢复时，用于安全传递外部回调 Webhook 载荷的只读键值存储 (`Map<String, String>`)。
* **`revertHintStore`** _(仅在补偿中有效)_：在补偿步骤之间传递诊断线索与追踪标识（例如外部退款请求会话 ID）的持久化键值存储。
* **`stepManager`**：阶段式流式构建器接口，用于声明本步骤的执行结果并精确引导 Saga 引擎的下一步路由。

为了清晰解耦设计，StackSaga 将执行器的应用划分为两大核心模式：

1. *xref:#usage-1-continuous-lrt[模式 1：连续长事务 (Continuous LRT)]* -- 无断点、直通式的顺序编排（绝大多数业务场景）。
2. *xref:#usage-2-pausable-lrt[模式 2：可暂停长事务 (Pausable LRT / Wait-State / Callback-Driven)]* -- 涉及外部异步回调、人工介入的主动等待状态。

'''

[[usage-1-continuous-lrt]]
== 模式 1：连续长事务 (Continuous Long-Running Transactions)

在 **连续长事务 (Continuous LRT)** 中，所有步骤自始至终无中断顺序执行，无需进入持久化等待状态。
这代表了微服务编排中最常见的主流场景（例如订单同步创建、账户扣款、库存预留）。

在连续长事务中：

* **主执行 (Primary Execution)**：完成业务后，直接调用 `.noPause().nextExecutor(...)` 或 `.noPause().complete()`。
* **补偿执行 (Compensating Execution)**：撤销业务后，直接调用 `.noPause()`。
* **恢复上下文 (Resume Context)**：由于事务未曾暂停，`resumeContext` 参数自然为空 (`resumeContext.isEmpty() == true`)。

[[command-executors]]
=== 连续 LRT 中的命令执行器 (Command Executors)

如果某个原子操作修改了系统状态，且在下游步骤失败时必须执行逆向补偿，请实现 `CommandExecutor`（阻塞式）或 `ReactiveCommandExecutor`（响应式）。

[[blocking-command-executors]]
==== 阻塞式命令执行器 (Blocking Command-Executor)

[source,java]
----
@SagaExecutor(executeFor = "order-service", value = "initializeOrderExecutor") //<1>
@AllArgsConstructor
public class InitializeOrderExecutor implements CommandExecutor<OrderDomainEntity> { //<2>

    private final OrderService orderService;

    @Override //<3>
    public @NonNull ProcessStepManager<OrderDomainEntity> doProcess(
            @NonNull OrderDomainEntity currentDomainEntity,
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext,
            @NonNull ProcessStepManager<OrderDomainEntity> stepManager
    ) throws RetryableExecutorException, NonRetryableExecutorException {

        try {
            //<4>
            String orderId = this.orderService.initializeOrder(
                    currentDomainEntity.getUsername(),
                    currentDomainEntity.getProductItems(),
                    currentDomainEntity.getTotalAmount(),
                    idempotencyKey
            );
            currentDomainEntity.setOrderId(orderId);

            //<5>
            return stepManager
                    .success("INITIALIZED_ORDER")
                    .noPause()
                    .nextExecutor(ReserveItemsExecutor.class);

        } catch (OperationAlreadyExecutedException alreadyExecutedException) {
            //<6>
            return stepManager
                    .success("INITIALIZED_ORDER")
                    .noPause()
                    .nextExecutor(ReserveItemsExecutor.class);

        } catch (FeignException.ServiceUnavailable unavailableException) {
            //<7>
            throw RetryableExecutorException.of(unavailableException);

        } catch (FeignException.BadRequest badRequestException) {
            //<8>
            throw NonRetryableExecutorException
                    .buildWith(badRequestException)
                    .put("time", LocalDateTime.now())
                    .put("reason", "BadRequest")
                    .build();
        }
    }

    @Override
    @RevertBefore(startFrom = OrderInitializeSubBeforeExecutor.class) //<12>
    @RevertAfter(startFrom = OrderInitializeSubAfterExecutor.class) //<13>
    public @NonNull RevertStepManager doRevert(
            @NonNull NonRetryableExecutorException processException,
            @NonNull OrderDomainEntity finalDomainEntityState,
            @NonNull RevertHintStore revertHintStore,
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext,
            @NonNull RevertStepManager stepManager
    ) throws RetryableExecutorException {

        try {
            //<9>
            this.orderService.cancelOrder(finalDomainEntityState.getOrderId(), idempotencyKey);
            return stepManager
                    .success("CANCELLED_ORDER")
                    .noPause(); //<10>

        } catch (OperationAlreadyExecutedException alreadyExecutedException) {
            return stepManager
                    .success("CANCELLED_ORDER")
                    .noPause(); //<10>

        } catch (FeignException.ServiceUnavailable unavailableException) {
            //<11>
            throw RetryableExecutorException.of(unavailableException);

        } catch (FeignException.BadRequest badRequestException) {
            // 不可恢复的补偿异常：记录至提示存储并平稳推进回滚，避免挂起事务
            revertHintStore.put("InitializeOrderExecutor:FAILED", processException.getMessage());
            return stepManager
                    .success("CANCEL_ORDER_TOLERATED")
                    .noPause();
        }
    }
}
----

<1> `@SagaExecutor` 将执行器注册为 Spring Bean 并声明元数据（`executeFor` 目标服务与执行器全局唯一标识）。
<2> 实现 `CommandExecutor<OrderDomainEntity>` 并绑定对应的领域聚合实体类型。
<3> 重写 `doProcess`，接收标准的 4 个参数。
<4> 执行主业务逻辑，并将 `idempotencyKey` 透传给下游接口。
[[stepManager_navigation]]
<5> **阶段式流式 Step Manager 导航 (`stepManager`)**： +
*阶段 1*：`.success("INITIALIZED_ORDER")` 记录业务执行成功的事件名称。 +
*阶段 2*：`.noPause()` 声明本次执行为直通式连续推进，不进入暂停状态。 +
*阶段 3*：`.nextExecutor(ReserveItemsExecutor.class)` 指定下一个要调用的执行器类。若该步骤为 Saga 的最后一步，调用 `.complete()` 终结事务。
<6> **妥善处理幂等重复执行**：当下游微服务返回操作已执行的标识（例如 HTTP `409 Conflict`）时，**必须视为成功**并返回 `stepManager.success(...).noPause().nextExecutor(...)`。切勿在已完成的操作上抛出错误。
<7> 捕获瞬时网络抖动并包装为 `RetryableExecutorException.of(...)`，触发重试调度器自动重试。
<8> 捕获不可恢复的业务失败（例如数据不合法、余额不足）并包装为 `NonRetryableExecutorException`，触发逆向回滚。
<9> 在 `doRevert` 中实现回滚补偿逻辑：反向撤销 `doProcess` 所做的修改。
<10> 调用 `stepManager.success("CANCELLED_ORDER").noPause()` 结束当前步骤的补偿。SEC 引擎将自动按照逆序调用前一个命令执行器的补偿。
<11> 补偿中的瞬时故障通过 `RetryableExecutorException` 触发自动重试。
<12> `@RevertBefore`：声明在调用当前执行器的 `doRevert()` 之前执行的前置子补偿执行器。
<13> `@RevertAfter`：声明在调用当前执行器的 `doRevert()` 之后执行的后置子补偿执行器。

[[reactive-command-executors]]
==== 非阻塞响应式命令执行器 (Non-Blocking Reactive Command-Executor)

[source,java]
----
@SagaExecutor(executeFor = "order-service", value = "reactiveInitializeOrderExecutor")
@AllArgsConstructor
public class ReactiveInitializeOrderExecutor implements ReactiveCommandExecutor<OrderDomainEntity> {

    private final OrderService orderService;

    @Override
    @NonNull
    public Mono<ProcessStepManager<OrderDomainEntity>> doProcess(
            @NonNull OrderDomainEntity currentDomainEntity,
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext,
            @NonNull ProcessStepManager<OrderDomainEntity> stepManager
    ) {
        return this.orderService
                .createOrder(
                        currentDomainEntity.getUserData(),
                        currentDomainEntity.getOrderDetails(),
                        idempotencyKey
                )
                .map(orderId -> {
                    currentDomainEntity.setOrderId(orderId);
                    return stepManager
                            .success("INITIALIZED_ORDER")
                            .noPause()
                            .nextExecutor(ReactiveReserveItemsExecutor.class);
                })
                .onErrorResume(throwable -> {
                    if (throwable instanceof OperationAlreadyExecutedException) {
                        return Mono.just(stepManager
                                .success("INITIALIZED_ORDER")
                                .noPause()
                                .nextExecutor(ReactiveReserveItemsExecutor.class));
                    } else if (throwable instanceof ResourceUnavailableException) {
                        return Mono.error(RetryableExecutorException.of(throwable));
                    } else {
                        return Mono.error(NonRetryableExecutorException.buildWith(throwable)
                                .put("time", String.valueOf(System.currentTimeMillis()))
                                .put("reason", "BadRequest")
                                .build());
                    }
                });
    }

    @Override
    @NonNull
    public Mono<RevertStepManager> doRevert(
            @NonNull NonRetryableExecutorException processException,
            @NonNull OrderDomainEntity finalDomainEntityState,
            @NonNull RevertHintStore revertHintStore,
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext,
            @NonNull RevertStepManager stepManager
    ) {
        return this.orderService
                .cancelOrder(finalDomainEntityState.getOrderId(), idempotencyKey)
                .thenReturn(stepManager
                        .success("REVERTED_ORDER_INITIALIZATION")
                        .noPause())
                .onErrorResume(throwable -> {
                    if (throwable instanceof OperationAlreadyExecutedException) {
                        return Mono.just(stepManager
                                .success("REVERTED_ORDER_INITIALIZATION")
                                .noPause());
                    } else if (throwable instanceof ResourceUnavailableException) {
                        return Mono.error(RetryableExecutorException.of(throwable));
                    } else {
                        revertHintStore.put("InitializeOrderExecutor:FAILED", processException.getMessage());
                        return Mono.just(stepManager
                                .success("IGNORED")
                                .noPause());
                    }
                });
    }
}
----

IMPORTANT: 在响应式执行器中，Reactive 流决不能返回 `null` 或 `Mono.empty()`。必须始终通过 `Mono.just(stepManager...)` 或 `Mono.error(...)` 返回。

[[sub-executors]]
=== 连续 LRT 中的子执行器 (Sub-Executors)

子执行器是 StackSaga 中专门用于在父命令执行器的主要补偿 (`doRevert`) 之外，执行**额外原子补偿操作**的专用组件。

牢记核心法则：**一个执行器 = 一个原子事务**。
若取消订单需要执行两个彼此独立的外部操作（例如：(1) 取消内部预约，(2) 通知外部第三方快递服务），将它们混在一个 `doRevert()` 中将违背原子性边界。
子执行器完美解决了这一难题：

[source,text]
----
前置子执行器 Sub-Before (1..N) ──> 父执行器 Parent doRevert() ──> 后置子执行器 Sub-After (1..N)
----

image:executor/Architecture-Stacksaga-command-executor-with-revert-executors.drawio.svg[alt="Stacksaga 执行器架构",width=100%,opts=interactive,scaledwidth=100%]

[[sub-before-executors]]
==== 前置补偿子执行器 (Sub-Before-Executor)

在父命令执行器的 `doRevert()` 运行*之前*执行：

[source,java]
----
@SagaExecutor(executeFor = "order-service", value = "orderInitializeSubBeforeExecutor")

public class OrderInitializeSubBeforeExecutor implements RevertBeforeExecutor<OrderDomainEntity, InitializeOrderExecutor> {

[[usage-2-pausable-lrt]]
== 模式 2：可暂停长事务 (Pausable LRT / Wait-State / Callback-Driven)

在企业级微服务中，分布式事务往往无法自始至终不间断地执行完毕。现实业务强制要求持久化的等待状态：

* **支付网关 (Payment Gateways)**：3D-Secure 异步银行重定向或跨行结算延迟。
* **人工介入 (Human-in-the-Loop)**：异步人工审批（KYC 实名审查、信贷审批、主管授权）。
* **实体操作 (Physical Operations)**：物理线下操作（后厨备餐、仓库拣货打包）。

StackSaga 通过 `stepManager` 上的 `.pause(Duration retentionDuration)` 操作符，为**可暂停长事务 (Pausable LRT)** 提供了原生一等公民支持。

[[pausable_lrt_lifecycle]]
=== 生产实战混合流程：连续与可暂停执行器统一编排

在企业级生产架构中，同一个业务长事务往往在同一个编排器微服务内同时涵盖同步连续执行与异步等待状态。

下图清晰展示了 `Order-service` 作为编排器，如何借助 StackSaga 将本地/远程同步执行步骤与外部第三方异步回调无缝融合：

.生产实战长事务流程参考指南（图示编号详解）

[.properties-table.google-anno-skip]
|===
| 编号 | 流程组件 | 架构角色与执行机制

| **1**
| `exe-1 (no pause)` +
`CheckCustomerEligibility`
| **连续查询执行 (Continuous Query)**：`Order-service` 编排器调用 `service-1` (`User Service`) 校验客户状态、授信额度与下单资格。作为只读操作，其实现为 `QueryExecutor`。步骤同步执行完毕，直接返回 `.noPause().nextExecutor(CreateOrderCommandExecutor.class)`，无任何等待阻塞，立即连续推进至步骤 2。

| **2**
| `exe-2 (no pause)` +
`CreateOrder`
| **连续命令执行 (Continuous Command)**：编排器通过本地 JPA 在本地数据库 (`service-2: Order DB`) 中创建状态为 `PENDING` 的初始订单。涉及本地状态持久化，其实现为 `CommandExecutor`（具备 `doRevert` 以备补偿）。本地事务提交后返回 `.noPause().nextExecutor(ProcessPaymentCommandExecutor.class)`。

| **3**
| `exe-3 (pause)` +
`ProcessPayment`
| **可暂停等待状态发起 (Wait-State Initiation)**：编排器向外部支付网关 (`service-3: Payment Gateway API`) 发起异步支付请求，透传 `idempotencyKey` 作为幂等关联键。执行完成后声明暂停： +
`stepManager.success("PAYMENT_DISPATCHED").pause(Duration.ofMinutes(15)).nextExecutor(DispatchDeliveryCommandExecutor.class)`。 +
*线程即时释放*：SEC 引擎将事务快照持久化至事件存储后，**立即将工作线程和数据库连接归还线程池**。在等待外部网关回调期间，StackSaga 在内存中零线程挂起、零连接占用，轻松支撑海量并发。

| **4**
| **Webhook 接入端点 (胶囊形)** +
`/resume-to 4` +
`sagaTemplate.resume()`
| **异步 Webhook 回调握手 (Callback Handshake)**：在图示中采用紧凑的胶囊形状呈现，用于将外部 HTTP 控制器端点与内部 Saga 执行器鲜明区分。客户完成支付后，支付网关向 `/resume-to 4` 接口发起异步 HTTP POST 回调。Controller 执行： +
`sagaTemplate.resume(transactionId, resumeKey).put("authCode", authCode).execute();` +
SEC 引擎严格校验关联密钥，将 `is_paused` 重置为 `0`，把回调数据注入 `ResumeContext`，分配新的工作线程调度激活 `exe-4`。

| **5**

`sagaTemplate.resume(transactionId, resumeKey).put("trackingNumber", trackingNumber).execute();` +

[NOTE]
.对称等待状态架构：补偿流程中的可暂停执行 (`doRevert()`)
====
上述图表展示的 **“执行 -> 暂停 / 等待 -> 回调恢复 (Process -> Pause / Wait -> Resumption)”** 模式并不仅限于正向业务流程 (`doProcess()`)。
StackSaga 为逆向回滚补偿流程 (`doRevert()`) 提供了完全对称的等待状态支持：

* **回滚中的等待状态**：若某个原子补偿步骤需要依赖外部异步操作（例如向银行网关提交异步退款清算申请，或向航空 GDS 系统提交取消客票申请），`doRevert()` 同样可以声明暂停：
+
[source,java]
----
return stepManager.success("REFUND_DISPATCHED").pause(Duration.ofHours(24));
----

* **立即释放线程与连接**：如同正向流程一样，StackSaga 会立即将事务快照持久化为暂停回滚状态 (`is_paused = 1`)，释放所有的工作线程与数据库连接，等待外部回调结果。
* **自动逆向链条续接**：当外部系统推送退款完成 Webhook 时，Controller 调用 `sagaTemplate.resume(txId, resumeKey).put("refundStatus", "SUCCESS").execute()`。SEC 引擎在 `ResumeContext` 中校验回调载荷，完成当前补偿步骤，并**自动驱动逆向链路继续向前续推执行此前各步骤的补偿**（如 `exe-2` -> `exe-1`）。

有关回滚等待状态的完整实现细节与生产级代码示例，请参阅 xref:#pausable-compensation[doRevert() 中的可暂停补偿]。
====

[[resume-context-in-executors]]
=== 正向等待状态 (`doProcess`)

在正向流程中，等待状态通过 **Saga 流程拓扑分离设计 (Topology Separation)** 实现：

1. **暂停步骤 (`InitiatePaymentCommandExecutor`)**：负责发起外部异步请求，并声明进入持久化等待。
2. **恢复步骤 (`ConfirmPaymentCommandExecutor`)**：在 Saga DAG 中被指定为暂停后的下游步骤，在事务恢复时被调度执行。

==== 步骤 A：发起并暂停的执行器 (`InitiatePaymentCommandExecutor`)

[source,java]
----
@SagaExecutor(executeFor = "payment-service", value = "initiatePaymentCommandExecutor")
@AllArgsConstructor
public class InitiatePaymentCommandExecutor implements CommandExecutor<OrderDomainEntity> {

    private final PaymentGatewayClient paymentGateway;

    @Override
    public @NonNull ProcessStepManager<OrderDomainEntity> doProcess(
            @NonNull OrderDomainEntity currentDomainEntity,
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext,
            @NonNull ProcessStepManager<OrderDomainEntity> stepManager
    ) throws RetryableExecutorException, NonRetryableExecutorException {

        // 1. 发起外部异步支付请求，透传 idempotencyKey 作为关联标识
        String intentId = this.paymentGateway.initiatePaymentIntent(
                currentDomainEntity.getOrderId(),
                currentDomainEntity.getTotalAmount(),
                idempotencyKey //<1>
        );

        // 2. 将支付意图 ID 持久化记录到聚合实体中
        currentDomainEntity.setPaymentIntentId(intentId);

        // 3. 暂停前向执行，等待外部 Webhook 回调
        return stepManager
                .success("PAYMENT_INTENT_DISPATCHED")
                .pause(Duration.ofHours(2)) //<2>
                .nextExecutor(ConfirmPaymentCommandExecutor.class); //<3>
    }

    @Override
    public @NonNull RevertStepManager doRevert(...) {
        return stepManager.success("PAYMENT_INTENT_CANCELLED").noPause();
    }
}
----

<1> 将 `idempotencyKey` 透传给外部支付网关，作为回调握手的凭证。
<2> `.pause(Duration.ofHours(2))` 将事务在事件存储中标记为 `PAUSED`，并立即释放线程。
<3> `.nextExecutor(ConfirmPaymentCommandExecutor.class)` 明确指定事务恢复时将由哪个执行器接管。

==== 步骤 B：恢复接管的执行器 (`ConfirmPaymentCommandExecutor`)

当外部网关回调且应用调用 `sagaTemplate.resume(...)` 后，SEC 引擎调度执行 `ConfirmPaymentCommandExecutor`：

[source,java]
----
@SagaExecutor(executeFor = "payment-service", value = "confirmPaymentCommandExecutor")
@AllArgsConstructor
public class ConfirmPaymentCommandExecutor implements CommandExecutor<OrderDomainEntity> {

    private final PaymentGatewayClient paymentGateway;

    @Override
    public @NonNull ProcessStepManager<OrderDomainEntity> doProcess(
            @NonNull OrderDomainEntity currentDomainEntity,
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext, //<1>
            @NonNull ProcessStepManager<OrderDomainEntity> stepManager
    ) throws RetryableExecutorException, NonRetryableExecutorException {

        // 1. 从 ResumeContext 中提取 Webhook 回调可能携带的参数
        Optional<String> authCode = resumeContext.get("authCode"); //<2>
        Optional<String> status = resumeContext.get("status");

        // 2. 验证支付结果（优先从载荷提取，或基于已有的 paymentIntentId 查询网关确认）
        boolean isSuccess = status
                .map("SUCCESS"::equalsIgnoreCase)
                .orElseGet(() -> this.paymentGateway.verifyPaymentStatus(currentDomainEntity.getPaymentIntentId()));

        if (isSuccess) {
            authCode.ifPresent(currentDomainEntity::setPaymentAuthCode);

            // 3. 推进至下一前向步骤
            return stepManager
                    .success("PAYMENT_CONFIRMED")
                    .noPause()
                    .nextExecutor(DispatchDeliveryExecutor.class); //<3>
        } else {
            // 支付被拒：触发补偿
            throw NonRetryableExecutorException
                    .buildWith(new PaymentDeclinedException("网关支付失败"))
                    .put("intentId", currentDomainEntity.getPaymentIntentId())
                    .build();
        }
    }

    @Override
    public @NonNull RevertStepManager doRevert(...) {
        this.paymentGateway.refundPayment(currentDomainEntity.getPaymentAuthCode());
        return stepManager.success("PAYMENT_REFUNDED").noPause();
    }
}
----

<1> `resumeContext` 包含恢复时传入的键值参数。
<2> 通过 `resumeContext.get(key)` 安全提取。执行器内部对该上下文严格只读。
<3> 成功确认后，通过 `.noPause().nextExecutor(...)` 连续推进后续流程。

[CAUTION]
.架构反模式警示：切勿使用 `resumeContext.isEmpty()` 判断执行阶段！
====
绝不要使用 `if (resumeContext.isEmpty())` 来判断执行器是“首次运行”还是“被恢复执行”。

*为什么？* 外部 Webhook 或人工恢复操作完全可能**不包含任何有效载荷**（例如管理员仅在后台点击了“批准”按钮，或者 Webhook 是一个无 Body 的简单 HTTP 200 Ping）。
在这种情况下，`resumeContext.isEmpty()` 为 `true`，**但它仍然是一次真正的恢复执行**！

*执行器应如何感知自身阶段？*
1. **基于 Saga 流程拓扑设计**：放置在 pause 步骤之后的执行器（如 `ConfirmPaymentCommandExecutor`）生来就是为了处理恢复后的验证。
2. **基于领域聚合根状态**：如需防范超时重入，直接检查 `currentDomainEntity.getPaymentIntentId() != null` 等业务状态，而非检查 Map 是否为空。
====

=== 保留期超时与幂等性管理 (Retention Timeout & Idempotency)

若外部系统故障或在配置的 `retentionDuration` 内始终未发送回调，将发生什么？

1. **自动重新触发暂停步骤执行器**：
+
* 超时到期后，StackSaga 重试环调度器将自动暴露该停滞事务。
* 引擎将**自动重新调用先前暂停的那个执行器 (`InitiatePaymentCommandExecutor`)**，并注入其初始的 `in_data` 聚合快照。
* *原因*：下游并未确认完成，而核实外部状态、重发通知或取消业务的逻辑全都封装在该暂停执行器内。

2. **严格的幂等性要求**：
+
* 由于该执行器在先前已成功返回 pause 的情况下被再次调用，执行器**必须严格保证幂等性**。
* 在发起新的外部调用前，必须先核查 `currentDomainEntity` 中是否已有外部单据号，或使用 `idempotencyKey` 先向外部查询。

3. **并发回调与防重竞态保护**：
+
* 若在超时重试触发的同时或之后，迟到的第一个 Webhook 回调抵达，会发生什么？
* StackSaga 提供了内建的并发控制：**仅接收并处理第一个有效的恢复请求；后续的迟到请求或重复请求将被安全拒绝**。

4. **针对人工介入的长周期等待**：
+
* 若业务涉及长时间的人工审批且不希望自动重试介入，可指定超长保留期，例如 `Duration.ofDays(365)`。

[[pausable-compensation]]
=== 逆向补偿中的等待状态 (`doRevert`)

在分布式事务回滚中，退款等操作往往需要与银行清算机构进行异步交互，可能需要数小时或数天才能确认。

StackSaga 原生支持在 `doRevert(...)` 中调用 `stepManager.success(...).pause(Duration retentionDuration)`：

[[pausable-compensation-example]]
[source,java]
----
@SagaExecutor(executeFor = "payment-service", value = "paymentCommandExecutor")
@AllArgsConstructor
public class PaymentCommandExecutor implements CommandExecutor<OrderDomainEntity> {

    private final PaymentGatewayClient paymentGatewayClient;

    @Override
    public @NonNull ProcessStepManager<OrderDomainEntity> doProcess(...) {
        String paymentRef = this.paymentGatewayClient.charge(currentDomainEntity.getTotalAmount(), idempotencyKey);
        currentDomainEntity.setPaymentRef(paymentRef);
        return stepManager.success("PAYMENT_CHARGED").noPause().nextExecutor(ReserveStockExecutor.class);
    }

    @Override
    public @NonNull RevertStepManager doRevert(
            @NonNull NonRetryableExecutorException primaryExecutionException,
            @NonNull OrderDomainEntity finalDomainEntityState,
            @NonNull RevertHintStore revertHintStore, //<1>
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext,
            @NonNull RevertStepManager stepManager
    ) throws RetryableExecutorException {

        // 检查持久化的 RevertHintStore 以明确当前的补偿阶段：
        if (!revertHintStore.containsKey("refundSessionId")) { //<2>
            // --- 1. 首次补偿执行 ---
            // 发起异步退款请求，透传 idempotencyKey
            String refundSessionId = this.paymentGatewayClient.initiateAsyncRefund(
                    finalDomainEntityState.getPaymentRef(),
                    idempotencyKey
            );
            revertHintStore.put("refundSessionId", refundSessionId); //<3>

            // 暂停补偿，等待银行清算回调：
            return stepManager
                    .success("REFUND_INITIATED")
                    .pause(Duration.ofHours(24)); //<4>
        }

        // --- 2. 恢复补偿执行 ---
        // Webhook 回调到达！从 resumeContext 或向网关查询确认退款状态：
        String refundStatus = resumeContext.get("refundStatus")
                .orElseGet(() -> this.paymentGatewayClient.checkRefundStatus(revertHintStore.get("refundSessionId")));

        if ("SUCCESS".equalsIgnoreCase(refundStatus)) {
            // 退款成功，终结当前步骤的补偿
            return stepManager
                    .success("REFUND_COMPLETED")
                    .noPause(); //<5>
        } else {
            // 外部处理中：触发重试核验
            throw new RetryableExecutorException("银行网关清算中，稍后重试核验");
        }
    }
}
----

<1> `revertHintStore` 是在补偿重试和暂停之间持久保存线索的可靠存储。
<2> 使用 `!revertHintStore.containsKey("refundSessionId")`（而不是 `resumeContext.isEmpty()`）明确区分是首次发起退款还是回调恢复。
<3> 将退款会话 ID 存入 `revertHintStore`。
<4> 调用 `.pause(Duration.ofHours(24))` 暂停补偿。
<5> 确认退款完成后，调用 `.noPause()` 结束该步骤补偿，SEC 将自动调度前一步骤的回滚。

'''

== 执行器设计原则

在设计 Saga 执行器时，请遵循以下核心准则：

. **一个执行器 = 一个原子事务**：绝不在单个执行器中混合多个外部写操作。将其拆分为独立的命令执行器或子执行器。
. **严格保证幂等性**：始终向下游透传 `idempotencyKey`，并将重复执行响应作为正常成功处理。
. **清晰解耦连续与可暂停模式**：在可暂停流程中，将发起暂停的步骤与接收恢复的步骤作为独立执行器在 Saga DAG 中组织。
. **切勿使用 `resumeContext.isEmpty()` 做阶段分支**：依靠 Saga 拓扑与领域实体状态跟踪业务进度，依靠 `RevertHintStore` 跟踪补偿阶段。
. **遵循命名规范**：事件名称必须符合框架正则标准 (`^[A-Za-z0-9]+(?:_[A-Za-z0-9]+)*$`)，即由单下划线分隔的字母数字标识（如 `ORDER_CREATED`、`PAYMENT_SUCCESS`、`STOCK_RESERVED`）。禁止使用连字符、空格或连续下划线（如 `ORDER__CREATED`）。记录所有外部调用异常与重试策略。
