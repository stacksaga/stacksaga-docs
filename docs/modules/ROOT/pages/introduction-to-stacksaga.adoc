= Introduction to StackSaga

== Overview

StackSaga is an enterprise-grade, orchestrator-based Saga ecosystem designed to solve distributed transaction consistency across microservice architectures.

In distributed systems, traditional single-database transactions (ACID / 2-Phase Commit) cannot scale across autonomous microservices.
StackSaga provides the architectural foundation to execute **Long-Running Transactions (LRT)** reliably through orchestrated primary executions and their automated compensating (rollback) actions.
Beyond basic orchestration, StackSaga delivers a comprehensive cloud-native platform encompassing **Event Sourcing**, **distributed retry scheduling**, and **real-time transaction observability**.

== What is StackSaga?

StackSaga is an entire ecosystem rather than just a single library, engineered to implement, observe, and maintain Saga-based distributed transactions in production environments:

. *xref:implementations:engine-overview.adoc[Multi-Transport Orchestration Engines]* +
Pluggable orchestration engines supporting both synchronous request/response (REST, gRPC, GraphQL) and asynchronous event-driven (Apache Kafka) communication styles.
. *xref:stacksaga-database-support:overview/database-support-overview.adoc[Zero-Infrastructure Event Sourcing]* +
Built-in event-sourcing capabilities that use your existing relational database (MySQL, PostgreSQL, Oracle) as the event store—eliminating the need to deploy and manage a dedicated event-store cluster.
. *xref:retry-ring-coordinator:transaction-retrying-with-retry-coordinator.adoc[Distributed Retry Subsystem]* +
A resilient transaction retry subsystem utilizing Murmur3 token ring partitioning and the Ring Coordinator to schedule and self-heal stalled transactions without cluster race conditions.
. *xref:trace-window:stacksaga-trace-window.adoc[Visual Transaction Tracing (Trace Window)]* +
A developer and operator dashboard to visualize every transaction span in real time, inspect domain snapshots, trace execution timelines, and trigger manual operational interventions.

== Why Choose StackSaga?

When transitioning to microservices, organizations encounter the **Distributed Consistency Dilemma**: how to maintain business integrity across independent service databases without introducing fragile ad-hoc plumbing or distributed deadlocks.

StackSaga provides distinct advantages over DIY solutions and traditional workflow engines:

=== 1. Domain-Centric Orchestration (No Dedicated Orchestrator Infrastructure)
Traditional orchestration systems often require deploying a heavy, centralized external server or dedicated "orchestrator service" that acts as an enterprise bottleneck and single point of failure.

StackSaga eliminates this anti-pattern completely through **Domain-Centric (Service-Embedded) Orchestration**:

* **No Dedicated Orchestration Servers**: You do not build or deploy standalone orchestration servers. Instead, any standard microservice simply adds `stacksaga-spring-boot-starter` to become the orchestrator for its own business domain.
* **Per-Domain Centralization**: For example, `order-service` embeds StackSaga to orchestrate the "Place Order" saga across downstream services. If `payment-service` has its own complex multi-step clearing or settlement workflow, `payment-service` independently embeds StackSaga to orchestrate that payment domain. A single microservice can orchestrate one or multiple business domains.
* **Zero-Dependency Downstream Utility Services**: Only the microservice acting as the domain orchestrator carries the StackSaga framework dependency. Downstream participating services (e.g., `inventory-service`, `user-service`) remain standard microservices exposing ordinary REST, gRPC, or GraphQL APIs without a single line of StackSaga code. Adoption is clean, incremental, and non-invasive.

=== 2. Dual Long-Running Transaction (LRT) Models
Real-world enterprise processes require different execution dynamics:
* *Continuous LRT (Straight-Through Processing - STP)*: For fully automated, high-throughput workflows that run unbroken from start to finish (e.g. e-commerce checkout, financial payment processing).
* *Pausable LRT (Wait-States & Human-in-the-Loop - HITL)*: Intentionally pauses transactions at business milestones—such as waiting for external asynchronous payment webhooks, restaurant physical order confirmations, or manager/KYC manual approvals—releasing 100% of CPU worker threads while safely sleeping in the Event Store.

NOTE: Both Continuous LRT (STP) and Pausable LRT (HITL) execution models are first-class capabilities across *both* the *Synchronous (REST/HTTP)* and *StackSaga-Kafka (Event-Driven)* implementations.

=== 3. Durable Event Sourcing & Pristine State Restoration
Every state transition of the `SagaDomainEntity` is immutably recorded in the Event Store.
If an orchestrator node crashes or is redeployed mid-transaction, execution is resumed with zero data loss.
Furthermore, if a paused executor re-executes after a timeout, the engine discards uncommitted in-memory mutations and restores the domain entity to its pristine original snapshot, guaranteeing deterministic idempotency.

=== 4. Self-Healing Distributed Retries
Transient network blips and downstream service downtime are handled automatically.
The Ring Coordinator partition topology coordinates retry schedules across all active orchestrator nodes, ensuring that stalled spans are self-healed without duplicate execution or thread starvation.

=== 5. Spring Boot Native (Imperative & Reactive)
StackSaga is purpose-built for the Spring Boot ecosystem.
It offers first-class support for both imperative (Spring MVC / blocking) and reactive (Spring WebFlux / Project Reactor `Mono`/`Flux`) paradigms through unified, fluent APIs (`SagaTemplate`).

=== 6. Enterprise Observability & Compliance
Every transaction carries a complete audit trail: which service was invoked, what payload was sent, exact timestamps, and compensation logs.
With the built-in Trace Window dashboard, operations and support teams gain instant visibility into live distributed transactions.
