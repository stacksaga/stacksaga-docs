== Classification of Saga Transactions

Based on runtime execution behavior and outcomes, we can classify Saga transactions into three primary categories:

* *Successful Transactions (Primary Execution Success)*
* *Compensating Success Transactions (Forward Failure with Successful Rollback)*
* *Compensating Failed Transactions (Rollback Exception / Permanent Fault)*

NOTE: `GET_USER_DETAIL` is not an atomic transaction; it is a read-only query operation used to retrieve customer data. See xref:idempotency.adoc#atomic-operations[Query Operations] for more details.

In this scenario, the workflow spans 4 execution spans (including 3 state-changing atomic transactions) across 4 microservices.
The entire business transaction completes once the 4th atomic execution succeeds.
When every primary execution completes without error, the transaction is classified as a *Successful Transaction*.

[[revert_success_transaction]]
=== icon:circle[role=yellow,1x] Compensating Success Transactions

image:stacksaga-diagram-revert-successfull-transaction.svg[alt="stacksaga diagram revert successful transaction"]

Here, an exception occurs during the `make-payment` execution.
The primary execution halts immediately, and the compensation sequence begins, rolling back all previously committed executions in reverse chronological order (`CANCEL_RESERVED_ITEMS`, `CANCEL_ORDER`).
Once the compensating steps complete, the system returns to a consistent state.

Although this represents a business failure (the order was not completed), from a Saga orchestration perspective it is an architectural success: the system maintained *eventual consistency* by cleanly undoing all intermediate changes.

=== icon:circle[role=red,1x] Compensating Failed Transactions

image:stacksaga-diagram-revert-failed-transaction.svg[alt="stacksaga diagram revert failed transaction"]

In this scenario, an exception occurs during the payment execution, triggering backward compensation.
However, during the rollback sequence, an unhandled exception or network fault also occurs while executing `CANCEL_ORDER`.

IMPORTANT: In distributed systems, compensating transactions must be strictly **idempotent** and **retryable**. They should only fail due to transient infrastructure issues (such as momentary network partitions or database unavailability). See xref:proportional-analysis-of-long-running-transactions-in-saga.adoc#compensation_failed_transactions[Transient Faults and Failure Probability] for an architectural analysis of these edge cases.

TIP: StackSaga's distributed retry subsystem and event-sourced state store automatically manage these recovery scenarios, ensuring transactions self-heal once downstream dependencies recover.
