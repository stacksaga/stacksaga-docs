= Atomic Transactions & Idempotency in LRT

== Overview

In xref:introduction-to-saga-design-pattern.adoc[the previous section], we explored how the Saga pattern manages distributed business workflows as a *Long-Running Transaction (LRT)* — breaking a global transaction into a sequence of smaller, locally committed steps.

To understand how a Saga works in practice, developers need to understand:

. *What is the discrete unit of work executed at each step?* — An *Atomic Operation* or *Atomic Transaction*.
. *What happens when a network call or service fails?* — The ambiguous outcome dilemma and the necessity of *Retries*.
. *What prevents a retried step from corrupting data?* — *Idempotency*.

This page covers the foundational relationship between atomic transactions and idempotency, providing the architectural foundation for building resilient, failure-tolerant microservice workflows.

Most of this page is about *step-level idempotency*: making each saga step safe to retry against its *downstream* service by forwarding a *step idempotency key*.
The last part, <<lrt-idempotency>>, looks at the same problem one level up: protecting the *entire LRT* from a duplicate trigger with a *transaction idempotency key*.

[[atomic-operations]]
== Understanding Atomic Operations and Atomic Transactions

In monolithic systems, a transaction is governed by database-level ACID guarantees: multiple operations across multiple tables either all commit or all rollback as a single unit.
In a microservices architecture with a database-per-service pattern, an LRT cannot span multiple databases in a single ACID transaction. Instead, the LRT is composed of discrete, service-local units of execution.

An *atomic execution* is an all-or-nothing unit of work executed within the boundary of a single service.
However, not every atomic execution is the same. There is a critical distinction between a *read-only atomic operation* and a *state-changing atomic transaction*.

image:implementations:executor/stacksaga-diagram-atomic-transaction.svg[alt="atomic operations of the place-order long-running transaction"]

Consider the `place-order` scenario illustrated above:

. *Fetching User Details (`user-service`)*:
This is a *read-only query operation*. It retrieves customer information to validate whether the order can proceed. It does not alter any data in the `user-service` database.
Therefore, it is an *atomic operation*, but it is *not an atomic transaction*.

. *Creating the Order (`order-service`)*:
Inserts the order record in a pending state. This modifies database state.

. *Checking and Reserving Inventory (`inventory-service`)*:
Decrements product stock. This modifies database state.

. *Processing Payment (`payment-service`)*:
Debits the user's account or charges their card. This modifies database state.

Steps 2, 3, and 4 are *atomic transactions*: each performs a state-changing operation governed by a local ACID transaction within its service's database.

[cols="1,2,2", options="header"]
|===
| Characteristic | Read-Only Atomic Operation | State-Changing Atomic Transaction
| *Purpose* | Queries data needed for the workflow | Modifies data within a service boundary
| *Database Effect* | None (read-only) | Mutates state (INSERT, UPDATE, DELETE)
| *Transactional Nature* | Read consistency | Service-local ACID transaction
| *Requires Compensation?* | No (nothing to reverse) | Yes (must have a compensating transaction)
| *Natural Idempotency* | Naturally idempotent | Must be designed to be idempotent
| *StackSaga Component* | `QueryExecutor` | `CommandExecutor`
|===

=== The Local Commit Boundary (The Point of No Return)

The most important takeaway for developers new to microservices is this:

*Once an atomic transaction commits to its local database, it stays committed.*

There is no external distributed transaction coordinator holding a global lock or issuing a database-level `ROLLBACK` across services.
If step 4 (`make-payment`) fails, step 2 (`create-order`) and step 3 (`reserve-inventory`) are already permanent in their respective databases.
The only way to undo them is by executing *compensating transactions* (e.g. `cancel-order` and `release-inventory`) that semantically reverse the previous changes.

[[network_timeouts_and_ambiguity]]
== The Distributed Challenge: Network Timeouts and Ambiguous Failures

Because microservices communicate over an unreliable network (a reality formalized by the *Fallacies of Distributed Computing*), executing atomic transactions across service boundaries introduces failure modes that do not exist in monolithic applications.

=== The Ambiguous Outcome Dilemma (Network Timeouts & Dropped Packets)

When a coordinator (or an upstream service) invokes an atomic transaction over HTTP/REST or via messaging, three outcomes are possible:

. *Success*: The request arrives, the service executes the transaction, and the success response is received.
. *Deterministic Failure*: The request arrives, the service rejects the transaction (e.g., insufficient balance), and returns an error response.
. *Ambiguous State (Timeout / Network Drop)*: The caller sends the request, but the connection drops, times out, or the target instance crashes.

image::stacksaga-diagram-distributed-transaction.svg[alt="distributed transaction network boundary"]

In the third case, the caller faces an unsolvable ambiguity from the network alone:

* Did the request drop *before* reaching the service (meaning the atomic transaction never ran)?
* Or did the service execute the transaction successfully, but the network failed *afterwards* while returning the response?

Because the caller cannot tell whether the remote state was modified or not, the outcome is completely ambiguous.

=== Why Retries Are Mandatory

To recover from transient network drops, socket timeouts, or momentary service restarts, the coordinator *must retry* the invocation:

* *Forward Recovery*: If a transient network glitch occurs while invoking `reserve-inventory`, the coordinator retries the step until confirmation is received.
* *Backward Recovery*: If a step fails permanently and compensation begins, compensating transactions (e.g., `release-inventory`) must also be retried if they encounter network blips.

NOTE: The ambiguity also reaches the compensation. If a step timed out, was retried, and then failed permanently, the earlier timed-out attempt may have been applied.
StackSaga therefore runs that step's own compensating transaction first (unless the step opts out), and it must tolerate a target that was never created.
See xref:implementations:stacksaga-sync/orchestrator/executor_architecture.adoc#non_retryable_after_retry[Non-Retryable Failure After a Retry].

=== The Hazard: Duplicate Execution

Retrying an operation across an unreliable network solves the problem of dropped connections, but it introduces a far more dangerous hazard: *duplicate execution*.

Suppose `make-payment` was actually processed successfully on the first attempt, but the response was lost due to a timeout:

* If the caller blindly retries `POST /payments/charge`, the service may charge the customer's credit card a second time!
* If `inventory-service` blindly retries `POST /stock/decrement`, stock levels will be decremented twice for a single order.
* If a message broker redelivers a `create-order` message due to an unacknowledged message (at-least-once delivery), multiple duplicate orders will be created.

This leads directly to the core requirement of distributed systems: *every retried atomic operation and compensating transaction must be idempotent*.

[[what_is_idempotency]]
== What is Idempotency?

*Idempotency* in a microservices architecture means that processing the *same operation multiple times* has the *same effect* as processing it once — whether that operation arrives as a repeated synchronous request (e.g. over HTTP/REST) or as a redelivered message from a broker (e.g. a Kafka record).

In practice:

* Whether an atomic transaction or compensation request arrives once, twice, or ten times — due to retries, network re-transmissions, or broker redeliveries — *the system state changes only once*.
* Subsequent duplicate requests are recognized, safely handled, and return the same deterministic result without repeating the underlying mutation.

[[idempotency-and-atomic-transactions]]
=== The Relationship: Granularity vs. Repeatability

Atomic transactions and idempotency are two complementary concepts that solve different aspects of distributed reliability:

[quote]
____
*Atomicity* defines the *unit of execution* (an all-or-nothing step within a service boundary). +
*Idempotency* defines the *safety of repeating that execution* across a network.
____

* The *Atomic Transaction* gives the Saga engine a clean, bounded step to advance or compensate.
* *Idempotency* ensures that when the Saga engine retries that step — or when it executes its compensation — it is completely safe from double-execution side effects.

== Examples: Idempotent vs. Non-Idempotent Operations

Idempotency is an inherent characteristic of how an operation modifies data — it is not tied to any single communication protocol. It applies equally to synchronous REST calls and asynchronous message consumers (Kafka, RabbitMQ).

=== Naturally Idempotent Operations

. *Read-Only Queries*:
* REST: `GET /users/456`
* Messaging: Querying a read-model from a topic
* *Effect*: Reading data does not alter system state. Calling it 1 time or 100 times produces no side effects.

. *Absolute State-Setting (Upsert / Fixed Value)*:
* REST: `PUT /orders/123/status` with payload `{"status": "CONFIRMED"}`
* Messaging: An `OrderConfirmedEvent` with explicit target state
* *Effect*: Setting an absolute value repeatedly results in the exact same state.

. *Deletions*:
* REST: `DELETE /orders/123`
* Messaging: An `OrderCancelled` tombstone message
* *Effect*: Deleting an entity once removes it; subsequent delete attempts leave it removed.

=== Non-Idempotent Operations

. *Blind Resource Creation*:
* REST: `POST /orders` (without an idempotency key)
* Messaging: Consuming a `CreateOrderCommand` without deduplication
* *Effect*: Every delivery creates a new database record, producing duplicates.

. *Relative State Changes*:
* REST: `POST /accounts/123/adjust-balance` with payload `{"delta": -50}`
* Messaging: An `AdjustBalanceCommand` with relative offset
* *Effect*: If delivered twice, the balance is deducted twice ($100 -> $50 -> $0).

These non-idempotent operations are precisely the operations that *must* be fortified with an idempotency mechanism before they can participate safely in a Long-Running Transaction.

== How to Implement Idempotency in Practice

To ensure that retried atomic transactions and compensations do not produce duplicate mutations, developers use several proven implementation strategies:

=== 1. Use Idempotency Keys (Correlation Identifiers)

The caller attaches a unique, deterministic identifier to each operation:

* In REST APIs, this is typically sent as an HTTP header: `Idempotency-Key: <saga-id>-<step-id>`.
* In event-driven systems (Kafka/RabbitMQ), this is placed in the record header (e.g. `correlationId` or `messageId`), or used as the message key.

When the service receives the request, it checks whether an execution with that key has already completed.

=== 2. Check-Before-Processing (The Idempotency Store Pattern)

The service maintains a record of processed idempotency keys (typically in a dedicated database table or fast distributed store):

[arabic]
. When a request arrives with an idempotency key, start a local database transaction.
. Query the idempotency table for the key:
* *If the key exists and status is COMPLETED*: Return the previously saved response immediately without re-executing the business logic.
* *If the key exists and status is IN_PROGRESS*: A concurrent request with the same key is currently running. Return a conflict (`409 Conflict`) or wait.
* *If the key does not exist*: Insert a new record with status `IN_PROGRESS`, execute the atomic transaction, save the response in the idempotency record, update status to `COMPLETED`, and commit the local transaction.

This guarantees that even if a network timeout causes the client to retry, the second attempt receives the cached result of the first attempt without re-running payment or stock deduction.

=== 3. Database Constraints (Unique Business Keys)

Leverage the database engine's unique constraints to prevent duplicates at the storage level:

* For orders: Place a unique constraint on `(customer_id, client_request_token)`.
* For payments: Place a unique constraint on `order_id` in the payment ledger table.

If a retried operation attempts to insert a second payment record for the same order, the database rejects the write with a unique key violation, preventing data corruption.

=== 4. Prefer Absolute State Transitions Over Relative Offsets

Whenever possible, design atomic transactions to be state-driven rather than relative:

* *Instead of*: `UPDATE accounts SET balance = balance - 100 WHERE id = 123`
* *Prefer*: Recording an immutable ledger entry with a unique transaction ID (`INSERT INTO ledger_entries (id, account_id, amount) VALUES ('tx-123', 123, -100)`), and calculating the current balance from the ledger or updating balance only if the transaction ID has not been processed.

== How StackSaga Applies These Principles

StackSaga translates these distributed concepts into clean, object-oriented abstractions in Spring Boot.
Everything in this section is about *step-level idempotency*, which protects the calls each step makes to its downstream service:

. *Executors Map to Atomic Units*:

* `CommandExecutor`: Encapsulates an **Atomic Transaction**. It defines both the *primary execution* (`doProcess`) and its corresponding *compensating execution* (`doRevert`).
* `QueryExecutor`: Encapsulates a **Read-Only Atomic Operation** (`doProcess`), ensuring no unnecessary rollback logic is generated for non-mutating steps.

. *Automatic State Tracking & Correlation*:
* Every saga execution instance is assigned a unique `SagaId` and state machine correlation context.
* StackSaga's event store tracks the outcome of each executor step by step. If a network fault causes a step to retry, StackSaga ensures the step is re-dispatched with consistent context.

. *Safe Retries & Self-Healing*:
* When a transient failure occurs, StackSaga's retry subsystem re-executes the executor.
* Because your executors implement idempotency keys and state checks, retries advance the workflow forward safely without double-processing risks.

[TIP]
====
*StackSaga Provides the Step Idempotency Key Automatically:* +
In traditional microservices development, generating and maintaining unique idempotency keys across distributed retries is cumbersome and error-prone.
StackSaga takes this responsibility completely off your shoulders: the orchestrator automatically generates a deterministic, collision-resistant `idempotencyKey` for every atomic step (both primary execution and compensation) and injects it directly into your executor methods (`doProcess` and `doRevert`).
This auto-generated key is the *step idempotency key*: there is one per step, and it is scoped to that step's call to its downstream service.
It is not the *transaction idempotency key* that guards the whole LRT; see <<lrt-idempotency>>.

All you need to do is forward that step idempotency key to the downstream service (e.g., via an HTTP header such as `Idempotency-Key` or a messaging header) to ensure safe, duplicate-proof execution across retries.

* To see how executors receive and use this key in code, refer to xref:implementations:stacksaga-sync/orchestrator/executor_architecture.adoc#command-executors[Saga Command Executors].
* To learn how the key is calculated or how to customize the generator, see xref:implementations:stacksaga-sync/orchestrator/domain-entity.adoc#generateIdempotencyKey[Generating Idempotency Keys in Domain Entity].
====

[[lrt-idempotency]]
== Idempotency for the Entire LRT (Transaction Idempotency Key)

So far, the orchestrator has been the *caller* and each microservice has been the *downstream*.
The step idempotency key protects every individual call the orchestrator makes.
It does nothing, however, to stop the *whole LRT* from being started twice.
That is the job of a separate key: the *transaction idempotency key*.

IMPORTANT: Do not confuse the two keys. The *step idempotency key* is generated by StackSaga for each step and forwarded by you to a downstream service. The *transaction idempotency key* is chosen by you once per LRT and checked by StackSaga itself before the transaction starts.

=== The Reversed Viewpoint: The Orchestrator as the Downstream

Every saga is started by something: a REST request, a broker message, a webhook, a scheduled job, or a step of another saga.
From the point of view of that trigger, the *orchestrator is the downstream service*.
Everything this page says about ambiguous outcomes and retries applies again, one level up:

* The trigger sends "place order" and times out, so it sends it again.
* A broker redelivers an `OrderPlaced` event because the consumer's acknowledgement was lost.
* A payment provider retries a webhook because your endpoint answered too slowly.

Without protection, each duplicate trigger starts a *complete, independent LRT*.
Every step of the second transaction gets its own fresh step idempotency keys, so the downstream services see *new* requests, not retries.
The result is two orders, two inventory reservations and two charges, and step-level idempotency cannot catch it.

=== One Key for the Whole LRT

The transaction idempotency key closes that gap:

* *One key per LRT.* It identifies the business intent behind the whole transaction (for example, "place order `A-1001`"), not an individual step.
* *Checked once, at admission.* StackSaga checks the key when the transaction is admitted, before the first step runs.
* *A duplicate resolves to the existing transaction.* If a transaction already holds the key, `execute()` starts nothing and returns the ID of the transaction that already holds it. The caller gets the same answer as the first attempt, exactly like the check-before-processing (idempotency store) pattern described earlier on this page.

=== When It Matters Most

The transaction idempotency key is most valuable when the saga is not started directly by a person, because the trigger then retries on its own:

* *Event-started sagas.*
** A Kafka or RabbitMQ consumer starts the saga. At-least-once delivery means the same event can arrive again after a rebalance, a consumer crash or a lost acknowledgement.
** A payment or shipping provider calls your webhook. Providers retry deliveries until they receive a success response, and may deliver the same notification more than once.
* *Sagas started as part of another execution.*
** A step of another saga starts this saga. When that outer step is retried, it starts this saga again unless the key stops it. The outer step's step idempotency key is a natural transaction idempotency key here.
** A scheduled job starts the saga for each pending record. If the job runs twice, overlaps itself, or restarts halfway, the same record is picked up again.
** An upstream service calls your endpoint and retries on timeout, exactly like the ambiguous outcome dilemma in <<network_timeouts_and_ambiguity>>.

In all of these cases the orchestrator is in the same position as any downstream service, and the same reasoning applies: it must be idempotent.

=== When It Matters Less

When a person starts the saga by clicking a button, duplicates are usually rarer, and a duplicate is often visible to the user straight away.
It is still not risk-free:

* *Double submit.* The user clicks "Place order" twice, or presses Enter while the first request is still running.
* *Client resend.* A browser retries a request after a dropped connection, or a mobile app resends after the network switches from Wi-Fi to cellular.
* *Retrying gateways.* A load balancer or API gateway in front of your service retries a request that timed out.

Whether these risks are acceptable is a *business decision*.
A duplicate "subscribe to newsletter" saga may be harmless; a duplicate "transfer money" saga is not.

=== Choosing by Trigger Source

[cols="2,3,3", options="header"]
|===
| Trigger source | Duplicate risk | Recommended choice
| *Broker event* (Kafka, RabbitMQ)
| High. At-least-once delivery redelivers events after rebalances, crashes and lost acknowledgements.
| `idempotencyKey(String)` derived from the event ID.
| *Webhook* (payment, shipping or other provider)
| High. Providers retry until they get a success response.
| `idempotencyKey(String)` derived from the provider's delivery or event ID.
| *Another service or saga*
| High. The caller retries on timeout, and a retried saga step starts the saga again.
| `idempotencyKey(String)` derived from the upstream request ID, or from the calling step's step idempotency key.
| *Scheduled job*
| Medium to high. Overlapping runs, restarts and re-scans pick up the same record again.
| `idempotencyKey(String)` derived from the record being processed (for example, the order number and the business date).
| *User action* (button click, form submit)
| Low to medium. Double submits and client resends are possible.
| A business decision. Prefer `idempotencyKey(String)` with a client request token or the order number; use `withoutIdempotency()` only when a duplicate LRT is harmless.
|===

=== The StackSaga Team's Recommendation

The StackSaga team recommends maintaining a transaction idempotency key *as much as possible*.

Derive the key from something *stable in the trigger*, so that every redelivery or retry of the same trigger produces the same key:

* the event ID of a broker message,
* the provider's delivery or event ID for a webhook,
* the upstream request ID (or the calling step's step idempotency key) for a call from another service or saga,
* a business identifier such as the order number.

WARNING: Never use a random per-attempt value, such as a fresh `UUID.randomUUID()` or the current timestamp, as the transaction idempotency key. Each retry would then carry a different key, and every duplicate would start a new LRT.

=== How to Set It

The transaction idempotency key is set when the saga is started, in the required idempotency choice of `sagaTemplate.init(..).configure(..)`.

*Option 1: `idempotencyKey(String)`*: the key you derived from the trigger. It must not be blank, must be at most 255 characters, and must be unique per domain entity.

[source,java]
----
.configure(config -> config
        .transactionLifetime(Duration.ofHours(24))
        .defaultRestoreOnCrashDelay(Duration.ofMinutes(5))
        .idempotencyKey("order-placed:" + event.getEventId()))
----

*Option 2: `idempotentOnTransactionId()`*: records the framework-generated transaction ID as the key, so every transaction can be looked up the same way.
Every `init(..)` creates a new transaction ID, so this option does *not* recognise a repeated trigger.

[source,java]
----
.configure(config -> config
        .transactionLifetime(Duration.ofHours(24))
        .defaultRestoreOnCrashDelay(Duration.ofMinutes(5))
        .idempotentOnTransactionId())
----

*Option 3: `withoutIdempotency()`*: no transaction idempotency key. Duplicate triggers start duplicate LRTs.

[source,java]
----
.configure(config -> config
        .transactionLifetime(Duration.ofHours(24))
        .defaultRestoreOnCrashDelay(Duration.ofMinutes(5))
        .withoutIdempotency())
----

For the full API, validation rules and examples, see xref:implementations:stacksaga-sync/orchestrator/stacksaga_template.adoc#transaction-idempotency[Transaction Idempotency in SagaTemplate].

[CAUTION]
====
*Current limitation:* The event stores do not enforce transaction idempotency keys yet.
Choosing `idempotencyKey(String)` or `idempotentOnTransactionId()` makes `execute()` fail with `UnsupportedOperationException` instead of silently starting duplicate transactions.
Until enforcement is available, use `withoutIdempotency()`.
====

=== Step Idempotency Key vs. Transaction Idempotency Key

[cols="1,2,2", options="header"]
|===
| Aspect | Step Idempotency Key | Transaction Idempotency Key
| *Scope*
| One step (primary execution or compensation) of one LRT
| The entire LRT
| *Who generates it*
| StackSaga, automatically and deterministically for every step
| You, from something stable in the trigger (or the transaction ID with `idempotentOnTransactionId()`)
| *Who checks it*
| The downstream service you forward it to
| StackSaga, once, when the transaction is admitted
| *What it protects against*
| A retried step executing twice in a downstream service
| A duplicate trigger starting the whole LRT twice
| *Where it is set*
| Injected into `doProcess` and `doRevert`; you forward it in a header or message
| `sagaTemplate.init(..).configure(..)` when the saga is started
|===

== Summary: Mental Model for Developers

[cols="1,2,2", options="header"]
|===
| Concept | Role in Microservices | Key Rule
| *Atomic Operation* | The discrete execution step in an LRT | May be read-only (query) or state-changing (transaction).
| *Atomic Transaction* | A state-changing step committing locally to a service database | Commits permanently; cannot be rolled back by 2PC — must be compensated.
| *Compensating Transaction* | The semantic reversal of an atomic transaction | Must be idempotent and retryable until consistent.
| *Idempotency* | The safety guarantee for repeating operations | Ensures retrying an atomic transaction or compensation never produces duplicate side effects.
| *Step Idempotency Key* | The per-step key StackSaga generates and injects into `doProcess` and `doRevert` | Forward it to the downstream service so a retried step is applied only once.
| *Transaction Idempotency Key* | The key for the entire LRT, set in `configure(..)` when the saga is started | Derive it from something stable in the trigger so a duplicate trigger resolves to the existing transaction instead of starting a second LRT.
|===
