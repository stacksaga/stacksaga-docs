= StackSaga Dependencies and Relations

image::implementations:overview/stacksaga-dependencies-and-relations.svg[]

The diagram above illustrates the primary dependencies and architectural relations within the StackSaga ecosystem.

* **StackSaga Framework** (`stacksaga-spring-boot-starter`) provides unified saga orchestration, natively coordinating both synchronous request/response (REST, gRPC, local DB) and asynchronous event-driven messaging (Apache Kafka, RabbitMQ) within the exact same saga workflow.

== Key Dependencies

=== 1. Orchestrator Service
The domain service coordinating the saga adds the following core dependencies:
* xref:implementations:stacksaga-sync/index.adoc#stacksaga-spring-boot-starter[`stacksaga-spring-boot-starter`]: Core saga engine, `SagaTemplate`, `CommandExecutor`, `QueryExecutor`, and step managers.
* xref:stacksaga-database-support:overview/database-support-overview.adoc[`stacksaga-database-support`]: Database-specific event store adapter for persisting domain entity state and execution snapshots (e.g., `stacksaga-mysql-support`, `stacksaga-postgres-support`, `stacksaga-cassandra-support`).
* `stacksaga-environment-support`: Cloud and container topology resolution (see xref:ROOT:saga-region-resolver.adoc[SagaRegionResolver]).

=== 2. Retry Subsystem (Ring Coordinator)
For automated distributed self-healing:
* `stacksaga-ring-coordinator-connector`: Embedded in orchestrator instances to participate in token-ring retry partitioning.
* `stacksaga-ring-coordinator`: Standalone coordinator managing Murmur3 token sub-ranges across orchestrator clusters (see xref:retry-ring-coordinator:transaction-retrying-with-retry-coordinator.adoc[Retry Ring Coordinator]).

=== 3. Downstream Services
* Participating downstream utility services require **zero StackSaga dependencies**. They expose standard REST, gRPC, or messaging endpoints without any framework intrusion.
