= StackSaga Orchestration Engine (SEC): Overview & Core Concepts

== Executive Overview & Mental Model

The **StackSaga Orchestration Engine** (`stacksaga-spring-boot-starter`) is the reactive distributed execution platform at the core of the StackSaga ecosystem.
It coordinates distributed transactions across microservices by executing Saga workflows — sequences of local atomic transactions and their automated compensating actions — to guarantee eventual consistency across distributed boundaries.

The engine natively unifies **both synchronous execution (REST over HTTP, gRPC over HTTP/2, GraphQL, local database operations) and asynchronous event-driven messaging (Apache Kafka, RabbitMQ, AWS SQS)** within the **exact same saga workflow**.

```
                        [Inbound Client Request]
                                   │
                                   ▼
                    Order Service (Saga Orchestrator)
                embedded with stacksaga-spring-boot-starter
                                   │
        ┌──────────────────────────┴──────────────────────────┐
        ▼                                                     ▼
[Synchronous Spans: .asSync()]              [Asynchronous Spans: .asAsync()]
• Direct REST / gRPC call                   • Apache Kafka / RabbitMQ Produce
• Local Database (JPA/R2DBC)                • Two-Stage Model: Commit State First
• Immediate .noPause() or .pauseUntilResume • Mandatory .pauseUntilResume()
        │                                                     │
        │                                               [Broker Topic]
        │                                                     │
        │                                           [Downstream Consumer]
        │                                                     │
        │                                              [Event Callback]
        │                                                     │
        ▼                                                     ▼
[Next Synchronous Step] ◄────────────────────── [sagaTemplate.resume(resumeKey, duration)]
```

=== The Domain-Centric Orchestration Principle

Traditional orchestration systems typically require deploying heavy, centralized external orchestration servers (such as BPMN engines or standalone workflow servers) that introduce single points of failure, network bottlenecks, and administrative overhead.

StackSaga replaces this anti-pattern with **Domain-Centric (Embedded) Orchestration**:

* **No Dedicated Orchestrator Servers**: You do not build or manage dedicated orchestration server clusters. Any standard microservice simply adds `stacksaga-spring-boot-starter` to orchestrate sagas for its own business domain (e.g. `order-service` for order fulfillment, or `payment-service` for multi-step clearing and settlement).
* **Zero-Dependency Downstream Utility Services**: Downstream participating services (such as `inventory-service` or `user-service`) remain standard microservices exposing ordinary REST, gRPC, or message-driven endpoints. They have **zero StackSaga dependencies** and require no saga awareness.
* **Reactive & Non-Reactive Parity**: While the engine operates reactively under the hood using Project Reactor, it offers first-class support for both imperative (blocking/Spring MVC) and reactive (WebFlux) applications via the `SagaTemplate` and `ReactiveSagaTemplate` entry points.

== The StackSaga Execution Coordinator (SEC) [[SEC]]

Because StackSaga follows the Saga orchestration pattern, a central runtime component drives workflow progression, span dispatch, commit barriers, reverse compensation, and transient fault recovery.
In StackSaga, this engine component is called the **StackSaga Execution Coordinator (SEC)**.

=== The SEC Execution Loop

At every step of a transaction, the SEC enforces a deterministic two-step reliability loop:

1. **Execute Span**: The active executor runs its atomic business operation against a utility service, local database, or message broker.
2. **Event-Store Commit Barrier**: The SEC records the domain entity mutation, span status, and navigation instructions into the Event Store *before* advancing to the next step.

=== The 7-Step SEC Execution Lifecycle

Consider a distributed E-Commerce checkout saga coordinating across `user-service`, `inventory-service`, `payment-service`, and message brokers:

[cols="1,2,3",options="header"]
[.properties-table.google-anno-skip]
|===
| Phase | Action | SEC Engine Behavior

| **Inbound Trigger**
| `POST /orders` request arrives at `order-service`.
| Controller initializes an `OrderDomainEntity` and invokes: +
`sagaTemplate.init(() -> domainEntity).configure(...).startWith(CheckEligibilityExecutor.class).fireAndForget().execute();` +
(see xref:stacksaga-sync/orchestrator/stacksaga_template.adoc#configuring-transactions[Configuring the Transaction])

| **Initial Span Dispatch**
| SEC kicks off the saga.
| SEC instantiates `CheckEligibilityExecutor`, validates the starting contract, and creates the root transaction record in the Event Store.

| **Programmatic Navigation**
| Executor queries customer credit limits.
| The executor executes business logic and returns staged navigation instructions via `ProcessStepManager`: +
`return stepManager.success("ELIGIBILITY_CONFIRMED").asSync().noPause().toNextExecutor(ReserveInventoryExecutor.class);`

| **Hybrid Execution**
| Direct RPC vs Message Broker.
| *Synchronous Spans (`.asSync()`)* execute inline. +
*Asynchronous Spans (`.asAsync()`)*: For external brokers (Kafka/RabbitMQ), the executor registers an `AsyncInvoker`. The SEC commits state to the Event Store *first*, lazily fires the broker message, and marks the transaction `PAUSED`.

| **Intentional Pausable Sleep**
| Business wait-state reached.
| The SEC releases 100% of CPU worker threads while the transaction safely sleeps in the Event Store awaiting external confirmation.

| **Callback Resumption**
| Webhook or Kafka consumer receives reply.
| Controller or message listener invokes `sagaTemplate.resume(resumeKey, retentionDuration)`, and the SEC restores the domain entity and resumes execution directly at the designated target executor.

| **Symmetrical Rollback**
| Permanent failure occurs.
| If any executor throws `NonRetryableExecutorException`, the SEC halts forward progress and executes `doRevert()` on all previously completed command executors in reverse chronological order.
|===

[TIP]
====
**How Step-Level Commit Timing Drives the Integration Patterns** +
The two-step loop above — *Execute → Persist* — is the foundation of the xref:stacksaga-sync/orchestrator/unified-saga-patterns.adoc[Unified Saga Integration Patterns (USIP)].
The exact moment the SEC commits the span status to the Event Store relative to when the external call is made determines which of the 11 integration patterns applies.
See xref:stacksaga-sync/orchestrator/unified-saga-patterns.adoc[Unified Saga Orchestration Patterns (USIP & USNP)] for the complete catalog.

== Core Terminology & Building Blocks (Glossary)

The following terms represent the architectural building blocks of StackSaga.
Familiarizing yourself with them will make understanding the technical guides seamless:

[cols="1,3",options="header"]
[.properties-table.google-anno-skip]
|===
| Term | Definition

| *LRT (Long-Running Transaction)*
| A business transaction that spans multiple services or systems and may take milliseconds, minutes, hours, or days to complete.
LRTs require durable state persistence, distributed coordination, and automated compensation for partial failures.

| *Saga Domain*
| A specific category of LRT identified by its `DomainEntity` subclass (e.g. all order fulfillments belong to `OrderDomainEntity`).
The class type itself serves as the discriminator in the Event Store.

| *Span*
| A single atomic execution step within a saga.
Each span is performed by one executor on the orchestrator, invoking an operation on a downstream utility service, local database, or message broker.

| *SEC (Saga Execution Coordinator)*
| The internal engine component responsible for driving the saga: invoking executors, navigating transitions, persisting state, lazily firing asynchronous invokers, and triggering compensations.

| *Domain Entity*
| The aggregate root and payload carrier for a saga instance.
Annotated with `@SagaDomainEntity`, it carries all accumulated business data. Every state transition immutably records a domain snapshot to the Event Store.

| *Executor*
| The orchestrator-side handler encapsulating the logic for a single span: +
• `CommandExecutor`: State-changing operations requiring compensation (`doProcess()` and `doRevert()`). +
• `QueryExecutor`: Read-only queries with zero side effects; has no `doRevert()` compensation. +
• `Pre-Executor / Post-Executor`: Additional rollback steps executed before (`PreExecutor`) or after (`PostExecutor`) a command executor's core revert.

| [[glossary-step-manager]]*Step Manager*
| The staged fluent builder passed into each executor to drive execution and routing: +
• **Forward Navigation (`ProcessStepManager<DE>`)**: `.noPause().toNextExecutor(...)`, or `.pauseUntilResume(duration).resumeToNextExecutor(...)`, or `.complete()`. +
• **Compensation Navigation (`RevertStepManager`)**: `.noPause().toNextDefaultExecutor()`, or `.pauseUntilResume(duration).resumeToNextDefaultExecutor()`. The destination is not developer-selectable: the engine routes to the preceding command in history. +
• **Pre-Compensation Navigation (`PreStepManager<DE, E>`)**: `.noPause().toNextDefaultExecutor()` (hands off to the parent `doRevert`) or `.toNextPreExecutor(...)`. +
• **Post-Compensation Navigation (`PostStepManager<DE, E>`)**: `.noPause().toNextDefaultExecutor()` (concludes the step rollback) or `.toNextPostExecutor(...)`.

| *Idempotency Key & Correlation Key*
| A deterministic, stable unique key generated per span.
Guarantees that retrying an executor invocation produces zero duplicate side effects.
In Pausable LRTs, this key also serves as the `correlationKey` sent to external systems and brokers.

| [[glossary-resume-context]]*Resume Context*
| A key-value metadata store (`ResumeContext`) capturing external callback or webhook payload data supplied during transaction resumption via `sagaTemplate.resume()`, delivered directly into the resumed executor.

| *Event Store*
| The persistent storage layer holding all state transitions and domain entity snapshots, provided by `stacksaga-database-support` using your primary database (MySQL, PostgreSQL, Cassandra — _Oracle coming soon_).

| *Ring Coordinator*
| A standalone service (`stacksaga-ring-coordinator`) managing Murmur3 token ring partitioning, distributing retry ownership across orchestrator instances without distributed locks.
|===

== Long-Running Transaction (LRT) Models: The Unified Hybrid Approach

In enterprise microservice architectures, real-world business workflows naturally exhibit two behavioral patterns:
* **Continuous LRT (Straight-Through Processing - STP)**: Automated, unbroken pipelines progressing sequentially through microservices without intentional delays. Transient infrastructure faults are automatically retried by the Ring Coordinator.
* **Pausable LRT (Wait-States, Callbacks & Human-in-the-Loop - HITL)**: Workflows with intentional business wait states (e.g. 3D-Secure bank redirects, Kafka worker replies, Uber food preparation delays, KYC officer approvals, or pausable refunds). The SEC commits state to the Event Store and releases 100% of CPU worker threads while sleeping.

[NOTE]
====
**A Unified Engine for Mixed-Style LRTs**: Continuous vs. Pausable is an industry mental model, **not an either/or framework choice**.
StackSaga is an innovative industry solution engineered to manage **Mixed-Style LRTs** — seamlessly executing unbroken STP spans and pausable wait-states within the **exact same saga workflow** without any mode switches.
====

TIP: For the comprehensive architectural deep dive, full flow diagrams, and 5 enterprise real-world domain use cases, see the dedicated platform guide: **xref:ROOT:lrt-transaction-models.adoc[Transaction Execution Models: Continuous (STP) & Pausable (HITL)]**.

=== Comparison: Continuous vs. Pausable LRT

[cols="1,2,2",options="header"]
[.properties-table.google-anno-skip]
|===
| Dimension | Continuous Long-Running Transaction | Pausable Long-Running Transaction

| *Execution Continuity*
| Unbroken; advances sequentially from span to span without intentional delay.
| Suspended at business milestones; sleeps safely in the Event Store until resumed.

| *Industry Equivalents*
| Straight-Through Processing (STP), Non-Wait-State Flow, Synchronous Pipeline.
| Wait-State Transaction (BPMN), Callback Pattern (`waitForTaskToken`), Signal-Driven Workflow, Human-in-the-Loop (HITL).

| *Pause Nature*
| **Infrastructure Pause**: Only occurs on transient network faults (`RetryableExecutorException`), recovered automatically by the Ring Coordinator.
| **Business Pause**: Intentional domain requirement (broker callbacks, customer 3D-Secure redirects, kitchen prep, compliance reviews).

| *Thread Utilization*
| Worker threads held only for the duration of the active span.
| 100% of CPU worker threads released during wait states; zero thread starvation.

| *Executor Navigation*
| Forward: xref:stacksaga-sync/orchestrator/executor_architecture.adoc#stepManager_navigation[`stepManager.success(...).asSync().noPause().toNextExecutor(...)`] +
Revert: xref:stacksaga-sync/orchestrator/executor_architecture.adoc#revert-step-manager-util[`stepManager.success(...).asSync().noPause().toNextDefaultExecutor()`]
| Forward: xref:stacksaga-sync/orchestrator/executor_architecture.adoc#stepManager_pause[`stepManager.success(...).pauseUntilResume(duration)`] +

== State Decoupling & Ingestion: `ResumeContext` & Correlation

A critical architectural consideration in Pausable LRTs is how external callback data (e.g. payment gateway transaction IDs, webhook verification codes, fraud scores) is ingested into the saga.

=== The Problem with Direct Entity Mutation
Allowing external webhook controllers or Kafka listeners to directly mutate fields on the `DomainEntity` breaks domain encapsulation and invites race conditions, as external payloads would bypass the executor's state transition validation.

=== StackSaga's Solution: `ResumeContext`
When an external system fires a callback, the controller or event listener attaches the raw payload to `sagaTemplate.resume()`:

[source,java]
----
// Webhook Controller:
@PostMapping("/callbacks/payment")
public ResponseEntity<Void> handlePaymentCallback(@RequestBody PaymentCallbackDTO callback) {
    this.sagaTemplate.resume(callback.getResumeKey(), Duration.ofMinutes(15))
            .put("gatewayPaymentId", callback.getGatewayPaymentId())
            .put("settlementStatus", callback.getStatus())
            .execute();
    return ResponseEntity.ok().build();
}
----

StackSaga persists this metadata in the Event Store alongside the paused tryout row.
When the paused executor is resumed, the framework passes this `ResumeContext` directly into the executor method parameters:

[source,java]
----
public ProcessStepManager<OrderDomainEntity> doProcess(
        ProcessContext<OrderDomainEntity> context,
        ProcessStepManager<OrderDomainEntity> stepManager) {
    OrderDomainEntity currentDomainEntityState = context.currentDomainEntityState();

    // Safely extract and validate external callback data
    String gatewayId = context.resumeContext().get("gatewayPaymentId", String.class);
    currentDomainEntityState.setPaymentReference(gatewayId);

    return stepManager.success("PAYMENT_CONFIRMED")
            .asSync()
            .noPause()
            .toNextExecutor(DispatchOrderExecutor.class);
}
----

This guarantees that **only the executor contains the domain logic to interpret and validate external callback payloads**, keeping the domain aggregate strictly guarded.

=== Correlation Binding: `idempotencyKey` as the `correlationKey`

To prevent mismatched resumptions and duplicate callback processing:
1. In `doProcess(...)`, the framework generates a deterministic, stable `idempotencyKey` for the span.
2. The orchestrator sends this `idempotencyKey` to the downstream service or message broker.
3. The downstream service returns this exact key in its callback payload.
4. StackSaga validates that the supplied `correlationKey` matches the active resume key registered in the Event Store before resuming execution.

=== Pristine State Restoration on Re-Execution

A fundamental architectural advantage of StackSaga's Event Sourcing engine is that when an executor is re-invoked following a timeout, the `DomainEntity` is restored to its **exact pristine state prior to entering that executor**:

* If an executor mutates domain entity fields in memory and then times out while waiting for a callback, StackSaga's retry engine re-invokes the paused executor.
* Upon re-execution, the framework **discards all uncommitted in-memory mutations** and reconstructs the domain entity cleanly from the Event Store up to the checkpoint preceding this executor.
* This prevents dirty state leakage and guarantees deterministic, idempotent execution across all retries.

== Architectural Discipline: The CHES & D Layering

To maintain separation of concerns in enterprise Spring Boot microservices, StackSaga introduces the **CHES & D layered architecture** (extending Spring's standard 3-layer architecture):

* **C - Controller Layer**: Receives external REST/GraphQL/Webhook requests and invokes Handlers or `sagaTemplate.resume()`.
* **H - Handler Layer**: Orchestrates business entry points, initializes the `DomainEntity`, and starts the saga with `sagaTemplate.init(...).configure(...)`.
* **E - Executor Layer**: Encapsulates atomic saga spans (`CommandExecutor` and `QueryExecutor`), staged navigation, and compensating logic (`doRevert()`).
* **S - Service Layer**: Standard Spring business domain services invoked by executors (zero StackSaga awareness).
* **D - Data Access Layer**: Standard Spring Data repositories (JPA, JDBC, R2DBC) for local business persistence.

This architecture ensures that saga orchestration logic remains strictly contained within the **Executor layer**, keeping business services and domain models cleanly decoupled.
