= StackSaga Framework (Synchronous)

== Overview

*StackSaga Framework (Synchronous)* (`stacksaga-spring-boot-starter`) is the synchronous transport implementation of the StackSaga ecosystem.
It coordinates long-running distributed transactions (LRT) across microservices that already communicate over synchronous protocols — REST (over HTTP), gRPC (over HTTP/2), or GraphQL (over HTTP) — without introducing a message broker into your topology.

Unlike a choreography approach where each service reacts to events independently, StackSaga follows a *centralized orchestration* model: a single orchestrator service owns the full saga lifecycle, invokes the required operation on each participating service through that service's existing endpoint, and advances the saga based on the response it receives.
This gives you the deterministic control flow and auditability of the saga orchestration pattern while letting every participating service keep its existing synchronous API untouched.

The framework is built on top of Spring Boot and integrates with StackSaga's core engine for event sourcing, state management, retry scheduling, and cluster coordination.
Each saga execution is fully persisted — every state transition of the `SagaDomainEntity` (the saga's aggregate root and payload carrier) is written to the event store through `stacksaga-database-support` — so that any in-progress transaction can be recovered, retried, or inspected at any point in time.

NOTE: Even though the engine runs reactively under the hood, it is fully compatible with both *reactive* and *non-reactive* (imperative) Spring environments.
You choose your programming model with the `SagaTemplate` (blocking) or `ReactiveSagaTemplate` (reactive) entry point; the saga coordination behaves identically either way.

*Key capabilities:*

* *Synchronous saga orchestration* — the orchestrator invokes each step against a utility service through its existing REST/gRPC/GraphQL endpoint and advances the saga state based on the returned result, all coordinated by the Saga Execution Coordinator (SEC).
* *Forward and backward recovery* — built-in support for compensating transactions: when a step fails, the framework invokes `doRevert()` on each previously completed executor in reverse step order, triggering the rollback action for each affected service.
* *Zero-dependency utility services* — only the orchestrator carries a StackSaga dependency.
Participating utility services keep their existing endpoints and need no StackSaga code at all, so adoption is incremental and non-invasive.
* *Durable state via event sourcing* — the full `SagaDomainEntity` payload and status (`STARTED → IN_PROGRESS → COMPLETED | FAILED → COMPENSATING → COMPENSATED`) is persisted on every state transition, enabling point-in-time recovery and complete audit trails.
* *Distributed retry with token ring partitioning* — failed or stalled transactions are retried by the owning orchestrator instance as determined by Murmur3-based token ring partitioning, coordinated through the `stacksaga-ring-coordinator`.
* *Dual LRT execution models* — first-class support for both *Continuous LRT* (unbroken, straight-through execution across microservices) and *Pausable LRT* (business-condition wait states awaiting asynchronous callbacks, webhooks, or manual confirmations via `stepManager.pause()` and `SagaTemplate.resume()`).
* *Reactive and imperative support* — the developer-facing `SagaTemplate` / `ReactiveSagaTemplate` and the `CommandExecutor` / `QueryExecutor` abstractions support both blocking and reactive (`Mono`/`Flux`) handler implementations, giving application developers freedom to choose their programming model without affecting saga coordination.

== Glossary

The following terms are used throughout this documentation.
Familiarising yourself with them before reading the technical sections will significantly reduce the learning curve.

[cols="1,3",options="header"]
[.properties-table.google-anno-skip]
|===
| Term | Definition

| *LRT (Long-Running Transaction)*
| A business transaction that spans multiple services and may take seconds, minutes, or longer to complete.
LRTs require durable state management, distributed coordination, and compensation support for partial failures.

| *Saga Domain*
| A specific type of LRT identified by its `DomainEntity` subclass.
All saga instances of the same type (e.g., every `PlaceOrder` transaction) belong to the same saga domain.
The class type itself — not any field value — is the discriminator used to identify the domain.

| *Span*
| A single atomic execution step within a saga.
Each span is performed by one executor on the orchestrator, which invokes a single operation on a target utility service.
A saga is composed of one or more sequential spans in the primary flow, each with an optional corresponding compensation.

| *SEC (Saga Execution Coordinator)*
| The internal engine component responsible for driving a saga forward: invoking each executor, navigating to the next step, persisting state transitions, and triggering compensation when needed.
`SagaTemplate` / `ReactiveSagaTemplate` is the developer-facing entry point to the SEC.

| *Domain Entity*
| The aggregate root for a single saga instance.
Carries the full accumulated business payload and current execution state throughout the saga lifecycle.
Every state transition is persisted as a snapshot to the event store.
The framework uses the terms *Domain Entity* (`SagaDomainEntity`) as the core model representing the saga's domain state.

| *Executor*
| The orchestrator-side handler that executes the business logic for a single saga step.
Implemented as a `QueryExecutor` (read-only, no compensation), a `CommandExecutor` (state-changing, has a `doRevert()` compensation), or a *Sub Executor* (extra compensation steps that run before/after a command executor's revert).

| *Step Manager*
| The utility passed into each executor used to navigate the saga — `stepManager.next(NextExecutor.class, ...)` advances to the next span, `stepManager.pause(...)` halts execution at a business milestone awaiting an external callback, and `stepManager.complete(...)` finishes the saga.
Forward routing is expressed programmatically inside the executors rather than in a central routing table.

| *Continuous LRT*
| A long-running transaction that executes through all participating microservices sequentially without intentional business wait states. Pauses occur solely due to transient infrastructure errors handled by the retry subsystem. Equivalent to *Straight-Through Processing (STP)* or a *Non-Wait-State Transaction*.

| *Pausable LRT*
| A long-running transaction that intentionally enters a wait state (`stepManager.pause(...)`) at a business milestone, persisting its state and releasing execution threads until an external callback or event triggers resumption via `SagaTemplate.resume(...)`. Equivalent to a *Wait-State Transaction* or *Callback-Driven Saga*.

| *Correlation Key*
| The unique token used to correlate an incoming asynchronous callback with a paused transaction span. In StackSaga, the executor's deterministic `idempotencyKey` serves as the `correlationKey`.

| *Compensation*
| The reverse process that undoes previously completed steps when a saga fails.
Executed in reverse order via `doRevert()` on each completed `CommandExecutor`, optionally extended by sub-before and sub-after executors.

| *Event Store*
| The persistent storage layer for all saga state transitions and domain entity snapshots.
Provided by `stacksaga-database-support`.
Enables point-in-time recovery, retry, and full audit trails.

| *Revert Hint Store*
| A key-value store that carries metadata forward through the compensation sequence.
Values written during one `doRevert()` call are available to subsequent compensation steps.

| *Idempotency Key*
| A stable key generated per span so that re-invoking the same executor for the same transaction is safe.
The key is identical across every retry of the same executor invocation within a transaction.
In Pausable LRTs, this key also doubles as the `correlationKey` sent to downstream asynchronous services.

| *Ring Coordinator*
| A standalone service (`stacksaga-ring-coordinator`) that manages token ring partitioning for retry ownership.
Distributes Murmur3 token sub-ranges among orchestrator instances so each stalled transaction is retried by exactly one instance without distributed locking.

| *CHES & D Layered Architecture*
| The StackSaga design pattern that extends Spring's layered architecture with a *Handler* layer and an *Executor* layer — *C*ontroller, *H*andler, *E*xecutor, *S*ervice, and *D*ata Access.
See xref:stacksaga-sync/orchestrator/Saga-CHES-architecture.adoc[CHES & D layered architecture].

|===

[[supported-lrt-models]]
== Supported Long-Running Transaction (LRT) Models

In distributed microservice architectures, business transactions differ fundamentally in their operational continuity.
StackSaga categorizes long-running distributed transactions into two primary execution models:

. xref:#continuous-lrt[*Continuous Long-Running Transactions (Continuous LRT)*]
. xref:#pausable-lrt[*Pausable Long-Running Transactions (Pausable LRT)*]

Understanding the distinction between these two models ensures that developers choose the appropriate navigation pattern (xref:stacksaga-sync/orchestrator/executor_architecture.adoc#stepManager_navigation[`stepManager.next`] vs. xref:stacksaga-sync/orchestrator/executor_architecture.adoc#stepManager_pause[`stepManager.pause`]) and configure callback endpoints correctly.

[[continuous-lrt]]
=== 1. Continuous Long-Running Transactions (Straight-Through LRT)

A *Continuous Long-Running Transaction* (also known in enterprise and financial systems as *Straight-Through Processing (STP)* or a *Non-Wait-State Transaction*) is an end-to-end workflow designed to progress sequentially through every participating microservice without any intentional business pauses.

image::implementations:stacksaga-sync/continuous-lrt-flow.svg[Continuous LRT Flow,width=1000]

==== Execution Flow Example: E-Commerce Checkout

Consider a typical online order checkout that spans four microservices:

. `order-service` initializes the order and creates the domain state.
. `user-service` verifies customer account status and purchasing limits.
. `inventory-service` reserves the ordered product items.
. `payment-service` synchronously charges the customer's payment method.
. `delivery-service` schedules and dispatches the delivery.

From the moment the customer submits the order, the orchestrator executes each executor span one after another via xref:stacksaga-sync/orchestrator/executor_architecture.adoc#stepManager_navigation[`stepManager.next(...)`].
The transaction runs continuously until `stepManager.complete(...)` marks the saga as successfully finished.

==== Transient Infrastructure Errors vs. Business Pauses

Even in a continuous transaction, execution may temporarily halt if a downstream service times out or the network blips.
However:

* This delay is an *infrastructure pause*, not a business pause.
* When an executor catches a transient fault and throws `RetryableExecutorException`, StackSaga persists the transaction state in the event store.
* The xref:retry-ring-coordinator:transaction-retrying-with-retry-coordinator.adoc[Ring Coordinator] retry subsystem automatically re-invokes the stalled span according to the configured backoff schedule.
* No external callback or manual business signal is required; the framework self-heals the transaction automatically once the downstream service recovers.

[[pausable-lrt]]
=== 2. Pausable Long-Running Transactions (Wait-State / Callback-Driven LRT)

A *Pausable Long-Running Transaction* (known in workflow theory as a *Wait-State Transaction*, or the *Callback Pattern / Task Token* in cloud orchestrators) is a workflow designed with *deliberate business wait states*.
In this model, a step initiates an asynchronous process that cannot complete immediately, requiring the saga to intentionally pause and release compute resources until an external confirmation, webhook, or human action resumes it.

image::implementations:stacksaga-sync/pausable-lrt-flow.svg[Pausable LRT Flow,width=1000]

==== Real-World Use Cases

* *Uber / On-Demand Food Delivery*:
. Customer places an order; items and payment pre-authorization are reserved.
. The orchestrator notifies the restaurant (`restaurant-service`).
. *Intentional Business Pause*: The saga cannot dispatch a delivery driver immediately because food preparation takes 20–40 minutes. The executor calls xref:stacksaga-sync/orchestrator/executor_architecture.adoc#stepManager_pause[`stepManager.pause(DeliveryDispatchExecutor.class, "ORDER_PREPARING", Duration.ofHours(2))`]. The orchestrator persists the transaction and releases all worker threads.
. *Resumption via Callback*: When the kitchen marks the food "Ready", the restaurant system fires a callback webhook to the orchestrator. The orchestrator calls xref:stacksaga-sync/orchestrator/stacksaga_template.adoc#resuming-paused-transactions[`sagaTemplate.resume(transactionId, correlationKey).execute()`].
. The saga wakes up, restores domain entity state from the event store, and advances forward to `DeliveryDispatchExecutor` to assign and dispatch a courier.

* *Asynchronous Payment Gateways / Webhooks*:
A payment gateway (e.g., 3D-Secure bank redirects, asynchronous SEPA/ACH transfers, crypto confirmations) does not finalize synchronously.
The payment executor initiates the charge, forwards its `idempotencyKey`, and calls xref:stacksaga-sync/orchestrator/executor_architecture.adoc#stepManager_pause[`stepManager.pause(...)`].
Once the payment gateway notifies the orchestrator's webhook endpoint, the orchestrator resumes the saga with the callback payload via xref:stacksaga-sync/orchestrator/stacksaga_template.adoc#resuming-paused-transactions[`sagaTemplate.resume(...)`].

* *Human-in-the-Loop (HITL) Approvals*:
Corporate expense approvals, KYC compliance reviews, or high-value order sign-offs where the transaction waits days for a manager's decision before proceeding.

==== Key Architectural Mechanism: `idempotencyKey` as the `correlationKey`

To prevent race conditions, mismatched resumes, and duplicate callback processing, StackSaga integrates idempotency directly with correlation:

. In `doProcess(...)`, the framework generates a deterministic, stable `idempotencyKey` for the executor span.
. The developer forwards this `idempotencyKey` to the downstream asynchronous service (in the request body or HTTP header).
. The executor pauses the transaction:
+
[source,java]
----
// Wait indefinitely for external callback (no automatic retry exposure):
return stepManager.pause(DeliveryDispatchExecutor.class, "ORDER_PREPARING", null);

// OR wait up to a timeout duration before re-invoking the paused executor:
return stepManager.pause(DeliveryDispatchExecutor.class, "ORDER_PREPARING", Duration.ofHours(2));
----
. When the downstream service completes its asynchronous task, it invokes the orchestrator's callback endpoint (e.g., `POST /orders/callback`), supplying the `transactionId` and that exact `idempotencyKey`.
. The orchestrator's controller extracts the keys and resumes the saga:
+
[source,java]
----
// Blocking (Imperative):
this.sagaTemplate.resume(transactionId, correlationKey).execute();

// Non-blocking (Reactive):
this.sagaTemplate.resume(transactionId, correlationKey).executeAsync();
----
. StackSaga validates that the supplied `correlationKey` matches the paused span's `idempotencyKey`, safely restores the `SagaDomainEntity`, and resumes execution directly from the target executor (`DeliveryDispatchExecutor`).

==== Configurable Timeout Handling (`Duration`)

The third parameter of `stepManager.pause(...)` controls how the framework handles potential callback loss:

* *Passing `null`*: The transaction remains paused indefinitely without being exposed to the automatic retry scheduler. Use this when the business process has no fixed deadline and must wait strictly for the external callback or human intervention.
* *Passing a `Duration` (e.g., `Duration.ofHours(2)`)*: If the external system fails to deliver the callback within the specified duration, StackSaga's retry engine exposes the paused executor for re-invocation. This allows the executor to check the external system's status, re-trigger the request, or initiate compensation if the deadline expired.

=== Comparison: Continuous vs. Pausable LRT

[cols="1,2,2",options="header"]
[.properties-table.google-anno-skip]
|===
| Dimension | Continuous Long-Running Transaction | Pausable Long-Running Transaction

| *Execution Continuity*
| Unbroken; moves from step to step sequentially without intentional delay.
| Suspended at business milestones; enters a dormant wait state until an external trigger arrives.

| *Industry Equivalents*
| Straight-Through Processing (STP), Non-Wait-State Transaction, Request-Response Flow.
| Wait-State Transaction (BPMN), Callback Pattern (`waitForTaskToken`), Signal-Driven Workflow, Human-in-the-Loop (HITL).

| *Executor Navigation*
| xref:stacksaga-sync/orchestrator/executor_architecture.adoc#stepManager_navigation[`stepManager.next(NextExecutor.class, "EVENT_NAME")`]
| xref:stacksaga-sync/orchestrator/executor_architecture.adoc#stepManager_pause[`stepManager.pause(NextExecutor.class, "EVENT_NAME", duration)`]

| *Resumption Trigger*
| Immediate internal SEC thread scheduling.
| External API callback calling xref:stacksaga-sync/orchestrator/stacksaga_template.adoc#resuming-paused-transactions[`sagaTemplate.resume(transactionId, correlationKey)`].

| *Correlation Requirement*
| None (handled internally by SEC execution context).
| Downstream service must return the span's `idempotencyKey` as the `correlationKey`.

| *Pause Nature*
| *Infrastructure Pause*: Only occurs on transient errors (`RetryableExecutorException`) handled by the Ring Coordinator.
| *Business Condition Pause*: Intentional domain requirement (e.g. food preparation, payment webhook, KYC approval).
|===

== Why StackSaga Over Direct Service-to-Service Calls?

Wiring microservices together with direct synchronous calls (REST, gRPC, or GraphQL) does not by itself give you saga orchestration.
A hand-rolled topology requires every participating service — or the calling service — to understand the broader transaction context: which step it is in, what has already succeeded, what to roll back if something goes wrong, and how to track overall saga progress.
This logic inevitably leaks across services, making the system fragile and difficult to evolve.

The following comparison explains the specific gaps StackSaga closes.

=== Centralized Transaction State Management

[cols="1,2",options="header"]
[.properties-table.google-anno-skip]
|===
| Concern
| Detail

| *Raw synchronous calls*
| A direct call returns a response, but there is no concept of a business transaction that spans many calls. Nothing tracks that "step 2 of 5 has completed" or that a transaction is in a compensating state.

| *StackSaga*
| The orchestrator tracks the full saga lifecycle through well-defined states: `STARTED → IN_PROGRESS → COMPLETED \| FAILED → COMPENSATING → COMPENSATED`. The `SagaDomainEntity` is the single source of truth: it carries the transaction payload (all accumulated data from previous steps) and the current execution cursor. State transitions are persisted atomically to the event store on every step completion or failure.

| *Advantage*
| No saga coordination logic needs to be implemented in the participating utility services. The orchestrator is the sole authority on saga state.
|===

=== Resilience and Fault Tolerance

[cols="1,2",options="header"]
[.properties-table.google-anno-skip]
|===
| Concern
| Detail

| *Raw synchronous calls*
| When a downstream call fails or times out, the caller is left holding a partially completed transaction. Retry logic, timeout handling, and compensation decisions must be built — and kept consistent — by hand in every flow.

| *StackSaga*
| The framework implements configurable retry windows and automatic compensation invocation. If an executor signals a non-retryable failure, the saga engine immediately begins the reverse traversal, calling `doRevert()` for each completed forward step in reverse order. For transient failures (timeouts, resource unavailability) wrapped in a `RetryableExecutorException`, the retry subsystem re-invokes the saga from the last unacknowledged step using the Murmur3 token ring scheduler.

| *Advantage*
| Data consistency is maintained across services even under partial failures, without embedding retry or rollback logic in each service.
|===

=== Simplified Development

[cols="1,2",options="header"]
[.properties-table.google-anno-skip]
|===
| Concern
| Detail

| *Raw synchronous calls*
| Developers must implement state machine logic, idempotency checks, saga step routing, and compensation orchestration by hand in the service that drives the transaction.

| *StackSaga*
| The orchestrator-side abstractions (`SagaTemplate` / `ReactiveSagaTemplate`, `SagaDomainEntity`, and the `Executor` family) provide clear contracts for each role. Developers define what each step *does*, its compensation, and which step comes next; the framework handles persistence, retrying, and compensation sequencing. The xref:stacksaga-sync/orchestrator/Saga-CHES-architecture.adoc[CHES & D layered architecture] keeps these concerns in dedicated layers.

| *Advantage*
| Reduces boilerplate significantly and confines distributed transaction concerns to a small, testable layer.
|===

=== Operational Observability

[cols="1,2",options="header"]
[.properties-table.google-anno-skip]
|===
| Concern
| Detail

| *Raw synchronous calls*
| Per-service logs and metrics are available, but there is no concept of "transaction X is stuck at step 3" or "compensation for order Y failed" across the whole flow.

| *StackSaga*
| The `stacksaga-trace-window-connector` exposes APIs consumed by the xref:trace-window:stacksaga-trace-window.adoc[StackSaga Trace Window] UI, providing per-transaction step-level traces, execution timelines, failure points, retry counts, and compensation status.

| *Advantage*
| Operations teams can diagnose stalled or failed sagas at the business-transaction level, not just at the level of an individual service call.
|===

== Components

The synchronous framework overlays the *orchestrator* role onto an existing service via a single dependency.
In contrast to the StackSaga-Kafka transport — which adds a dependency to both the orchestrator and every worker — a synchronous deployment requires the StackSaga dependency only on the orchestrator.
The participating *utility services* are invoked through their existing synchronous endpoints and need no StackSaga dependency at all.

[[stacksaga-spring-boot-starter]]
=== stacksaga-spring-boot-starter

`stacksaga-spring-boot-starter` is the core runtime dependency added to the *orchestrator service* — the single service responsible for initiating and driving the saga lifecycle.
It provides the saga engine (SEC) and the developer-facing abstractions below.

* xref:stacksaga-sync/orchestrator/stacksaga_template.adoc[`SagaTemplate` / `ReactiveSagaTemplate`] — the entry point for starting a new saga execution or resuming a recovered one.
Accepts an initialized `SagaDomainEntity` and the first executor, then hands control to the saga engine.
* xref:stacksaga-sync/orchestrator/domain-entity.adoc[`SagaDomainEntity`] — the aggregate root for a saga instance.
Carries the accumulated business payload and the current execution state, and is serialized and persisted to the event store on every state transition.
* xref:stacksaga-sync/orchestrator/executor_architecture.adoc[Executors] — `CommandExecutor`, `QueryExecutor`, and Sub Executors that encapsulate each atomic step.
Each executor invokes the target utility service through its synchronous endpoint, navigates forward with `stepManager.next(...)`, and (for command executors) defines its compensation in `doRevert()`.
* xref:stacksaga-sync/orchestrator/event-listener.adoc[`TransactionEventListener` / `ReactiveTransactionEventListener`] — observe per-transaction state changes in real time for monitoring, notifications, and side effects.

To run your application as an orchestrator service, add the `stacksaga-spring-boot-starter` dependency to your project.

[source,xml,subs="attributes+"]
----
<dependencyManagement>
    <dependencies>
        <dependency> <!--Only for stacksaga dependencies version management-->
            <groupId>org.stacksaga</groupId>
            <artifactId>stacksaga-bom</artifactId>
            <version>{stacksaga-version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>org.stacksaga</groupId>
        <artifactId>stacksaga-spring-boot-starter</artifactId>
    </dependency>
</dependencies>
----

IMPORTANT: The engine is built internally using reactive programming principles, ensuring high scalability and performance.
Even though the framework operates reactively under the hood, it fully supports both reactive and non-reactive (imperative) application models through the `ReactiveSagaTemplate` and `SagaTemplate` entry points respectively.

Additionally, the orchestrator service must (or may) include:

* xref:stacksaga-database-support:overview/database-support-overview.adoc[stacksaga-database-support] _(required)_ — provides the event store integration (MySQL, Cassandra, or ScyllaDB depending on configuration) for persisting `SagaDomainEntity` snapshots and state transitions.
* xref:retry-ring-coordinator:transaction-retrying-with-retry-coordinator.adoc[stacksaga-ring-coordinator-connector] _(optional, required for retry)_ — connects the orchestrator instance to the `Ring Coordinator Service`, registers it as a retry node, and receives its assigned Murmur3 token sub-range.
Enables the retry subsystem to re-invoke failed transactions owned by this instance.
* xref:trace-window:stacksaga-trace-window.adoc[stacksaga-trace-window-connector] _(optional, required for monitoring)_ — exposes the internal APIs consumed by the StackSaga Trace Window UI for per-transaction traces, timelines, and compensation status.
* `stacksaga-env-support` _(optional)_ — provides environment-related geographical metadata (region, zone, instance ID, etc.) to the SEC, selected per deployment target (e.g., xref:stacksaga-environment-support:eureka-support/stacksaga-env-eureka-support.adoc[Eureka] or xref:stacksaga-environment-support:k8s-support/stacksaga_env_k8s_support.adoc[Kubernetes]).

[[utility-services]]
=== Utility services

A *utility service* is any service invoked by the orchestrator as a step in a saga — for example `user-service`, `payment-service`, or `inventory-service`.

Utility services do not interact with the event store, the ring coordinator, or any StackSaga abstraction.
They keep exposing their existing REST/gRPC/GraphQL endpoints and remain stateless with respect to the saga: the orchestrator's executor calls the endpoint, the service performs its business operation, and it returns a result.

NOTE: Because the saga logic (forward call, navigation, and compensation) lives entirely in the orchestrator's executors, the same utility service can participate in sagas owned by different orchestrators without any awareness of StackSaga.
