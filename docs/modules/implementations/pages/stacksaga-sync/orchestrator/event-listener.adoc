= Transaction Event Listener

[[event_listener_for_stage_change_events]]
== Transaction State Change Listeners

After handing over the transaction to the StackSaga engine by calling the `execute` or `executeAsync` method of the `StackSagaTemplate`, the transaction is being executed and updated the status time to time after each execution (primary and compensation) in the transaction flow.
so if you want to keep listening to the transaction status changes and perform any action based on that, framework provides the way to do that.

It also can be implemented based on the environment.

. `TransactionEventListener` for non-reactive environment.
. `ReactiveTransactionEventListener` for reactive environment.

If you want to get notified about the transaction status changes, there are two ways are available in the framework.

. Using `StackSagaTemplate.getCurrentState`
. Using `TransactionEventListener` or `ReactiveTransactionEventListener`.

IMPORTANT: using `StackSagaTemplate.getCurrentState` method to get the current state of the transaction by providing the transactionId approach is not efficient because when you call this method, the engine fetches the current state of the transaction from the event-store.
but if you are using the listeners, you will be notified about the transaction status changes after each execution in the transaction flow without the need to call any method to get the current state of the transaction because the current state of the transaction is being passed to the callback method of those listeners realtime.
due to it is happening realtime you don't want to poll the transaction state. for instance in the place-order example, after executing you can push the notification to update the user about the order status changes by using those listeners.
but in some cases you might want to get the current state of the transaction even after the transaction is completed. for instance after the user might need to see the details after placing order. then you can use the `SagaTemplate.getCurrentState` method to get the current state of the transaction by providing the transactionId.
The use cases are different for both approaches, so you can choose the one that is suitable for your use case.

[IMPORTANT]
====
*Sequential Execution and Latency Impact:*
While you are using the `onStateChanged` method of the listeners, be aware that the method is invoked sequentially as part of the transaction lifecycle after each span finishes. The next span in the saga flow is triggered only after the current `onStateChanged` completes. Avoid doing heavy computations or blocking I/O directly in this method because it directly delays the entire transaction flow. If heavy processing is required, offload it to a separate thread pool.

*At-Least-Once Notification in Pausable LRT (Duplicate Invocations):*
In xref:stacksaga-sync/index.adoc#pausable-lrt[Pausable LRTs], if an executor pauses awaiting an external callback with a timeout `Duration`, `onStateChanged` is invoked upon initial successful completion of that executor. If the external callback does not arrive before the timeout expires, the framework re-executes the paused executor, invoking `onStateChanged` **again** for the same step. See xref:stacksaga-sync/orchestrator/stacksaga_template.adoc#pausable-lrt-timeout-reexecution[Timeout Re-Execution Mechanics].

*Crucial Design Rule — Use a `QueryExecutor` for Business Logic:*
Never use `TransactionEventListener` to execute critical business state changes or non-idempotent operations. If an uncompensated operation must be performed following an executor (such as generating an internal receipt or audit record), model it as a formal **`QueryExecutor`** within the saga flow rather than placing it in a listener.
====

[[transaction_event_listener]]
=== TransactionEventListener

You can implement the `TransactionEventListener` interface to listen to the transaction events in a non-reactive environment as below.

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class PlaceOrderHandler implements TransactionEventListener<OrderDomainEntity> {
    @Override
    public void onStateChanged(TransactionState<OrderDomainEntity, SyncExecutionEvent<OrderDomainEntity>> state) {
        TransactionCompleteStatus currentStatus = state.getCurrentStatus();
        log.info("Current status of transaction: {}", currentStatus);
        NavigableMap<Integer, ? extends SyncExecutionEvent<OrderDomainEntity>> executionHistory = state.getExecutionHistory();
        log.info("Execution history of transaction: {}", executionHistory);
        OrderDomainEntity currentDomainEntity = state.getCurrentDomainEntity();
        log.info("Current domain entity state: {}", currentDomainEntity);
        ZonedDateTime startedDateTime = state.getStartedDateTime();
        log.info("Transaction started at: {}", startedDateTime.toLocalDateTime());
    }
}
----

NOTE: `onStateChanged` here is invoked on the framework's dedicated `blockingExecutionScheduler` — a bounded-elastic scheduler reserved for blocking, non-reactive listener code — never on the thread that drove the transaction step itself. This keeps a slow or blocking `TransactionEventListener` from delaying unrelated transactions. Tune it via `stacksaga.scheduler.blocking-execution.*`, see xref:stacksaga-sync/orchestrator/properties.adoc[Configuration Properties].

[[reactive_transaction_event_listener]]
=== ReactiveTransactionEventListener

You can implement the `ReactiveTransactionEventListener` interface to listen to the transaction events in reactive environment as below.

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class ReactivePlaceOrderHandler implements ReactiveTransactionEventListener<OrderDomainEntity> {
    @Override
    public Mono<Void> onStateChanged(TransactionState<OrderDomainEntity, SyncExecutionEvent<OrderDomainEntity>> transactionState) {
        return Mono
                .just(transactionState)
                .doOnNext(state -> {
                    TransactionCompleteStatus currentStatus = state.getCurrentStatus();
                    log.info("Current status of transaction: {}", currentStatus);
                    NavigableMap<Integer, ? extends SyncExecutionEvent<OrderDomainEntity>> executionHistory = state.getExecutionHistory();
                    log.info("Execution history of transaction: {}", executionHistory);
                    OrderDomainEntity currentDomainEntity = state.getCurrentDomainEntity();
                    log.info("Current domain entity state: {}", currentDomainEntity);
                    ZonedDateTime startedDateTime = state.getStartedDateTime();
                    log.info("Transaction started at: {}", startedDateTime.toLocalDateTime());
                })
                .flatMap(orderDomainEntityTransactionState -> {
                    //simulate some async processing here.
                    return Mono.delay(Duration.ofSeconds(1))
                            .then();
                });
    }
}
----

NOTE: No scheduler hop is inserted for `onStateChanged` here — it inherits the framework's shared, non-blocking `executionScheduler` that drives ongoing saga processing. Any blocking call made inside it can therefore starve unrelated transactions; keep this implementation fully reactive/non-blocking. Tune the scheduler via `stacksaga.scheduler.execution.*`, see xref:stacksaga-sync/orchestrator/properties.adoc[Configuration Properties].

== Recommended Handler Pattern

StackSaga team suggests to implement the saga transaction related things in a separate class called `Handler` that is responsible for starting, listening and checking the status of the saga transactions.
The below code snippet is showing the recommended architecture for the Handler.

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class PlaceOrderHandler implements TransactionEventListener<OrderDomainEntity> {

    private SagaTemplate<OrderDomainEntity> sagaTemplate;

    public String handle(String username, double amount, List<String> items) { //<1>
        return this
                .sagaTemplate
                .init(() -> {
                  //....
                })
                .....
    }

    public CustomOrderStatusView getCurrentState(String orderId) { //<2>
        return this
                .sagaTemplate
                .getCurrentState(orderId)
                ......

    }
    @Override
    public void onStateChanged(TransactionState<OrderDomainEntity, SyncExecutionEvent<OrderDomainEntity>> transactionState) { //<3>
        //....
    }
}
----

<1> The `handle` method is responsible for starting the saga transaction by using the `SagaTemplate` and providing the required parameters to start the transaction.
<2> Fetch the current state of the transaction by using the `SagaTemplate`
<3> Implement the `onStateChanged` method to listen to the transaction status changes by implementing the `TransactionEventListener` interface and override the `onStateChanged` method.
