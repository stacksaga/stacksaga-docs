= Saga Executors

== Overview

A Saga Executor in StackSaga is a specialized component responsible for encapsulating and executing a single atomic transaction within a distributed saga workflow.
It acts as the bridge between your business logic and the saga orchestration engine, ensuring that each step in a long-running transaction is performed reliably and consistently.

Saga Executors are categorized as either **Command Executors** (handling both primary and compensating executions for operations that modify state) or **Query Executors** (handling read-only operations).
By isolating each atomic transaction in its own executor, StackSaga enables precise control, automated retries, and compensation mechanisms, eliminating distributed data anomalies and guaranteeing eventual consistency across microservices.

IMPORTANT: If you are new to the saga pattern, it is recommended to read xref:foundations:idempotency.adoc[] to understand the concept of idempotency and atomic operations in distributed systems.

Typically, an atomic execution consists of two phases: **primary execution** and **compensating execution**.

1. **Primary Execution (Main Forward Execution)**:
The primary execution represents the core forward operation within a long-running transaction.
Each primary execution is a distinct step in the overall business workflow, advancing the process toward completion.
These operations are idempotent and isolated, ensuring they can be executed safely without unintended side effects.
+
For example, in a place-order workflow, primary executions might include fetching user details, initializing the order, performing pre-authorization, updating stock, and processing the final payment.
+
These primary executions move the process forward. [icon:arrow-circle-right[1x,role=green]]

2. **Compensating Execution (Revert Execution)**:
A compensating execution is designed to undo the effects of a previously completed primary execution if a subsequent step fails.
Each command execution has a corresponding compensating action to reverse its impact, ensuring the system returns to a consistent state upon failure.
+
Compensating executions move the process backward. [icon:arrow-circle-left[1x,role=green]]

[[conceptual-foundation]]
== Conceptual Foundation: Atomic Boundaries & Flow Management

Before examining Java interfaces and method signatures, it is essential to establish the architectural foundations: **why** Saga executors exist, **how** they manage distributed workflow chains, and **where** atomic transaction boundaries must be drawn.

=== The Real-World Business Scenario: E-Commerce Checkout Saga

Consider a typical e-commerce order checkout workflow where a customer purchases a \$1,500 laptop. To fulfill this single business request, the orchestrator must interact with 4 independent microservices:

1. **User Service** (`CheckCustomerEligibilityExecutor`): Validates customer account status and checks credit limits. (Read-only query).
2. **Order Service** (`CreateOrderCommandExecutor`): Initializes an order record in the `PENDING` state and persists order line items.
3. **Payment Service** (`ProcessPaymentCommandExecutor`): Communicates with an external payment gateway or bank to authorize and charge the customer's credit card.
4. **Inventory Service** (`ReserveStockCommandExecutor`): Deducts and reserves physical product stock units in the warehouse database.

=== Why Monolithic `@Transactional` Fails in Distributed Microservices

In a traditional monolithic architecture, this entire workflow lives inside a single Spring `@Transactional` method.
If the payment gateway rejects the card at Step 3, the local database transaction rolls back automatically: the order record is discarded, stock remains unchanged, and data consistency is preserved.

However, in a distributed microservice architecture:

* The Order Service writes to its own **PostgreSQL** database.
* The Inventory Service writes to an **Oracle** or **MySQL** database.
* The Payment Service calls an external third-party API (**Stripe, PayPal, or a Core Banking System**) over HTTP.

Because each service controls its own isolated persistence store, **a single distributed database transaction is physically impossible**.
Traditional distributed transaction protocols like Two-Phase Commit (2PC) or XA transactions require global locking across all participating services, introducing extreme latency, single points of failure, and severe fragility across network boundaries.

This is precisely the core architectural problem that **StackSaga Executors** solve.

=== The Atomic Transaction Boundary: "One Executor = One Atomic Operation"

In StackSaga, a **Saga Executor** is strictly defined as the encapsulation of **one single atomic transaction** within a single microservice boundary.

[IMPORTANT]
.The Fundamental Architectural Rule: One Executor = One Atomic Transaction
====
An executor should interact with **exactly one microservice or one database boundary**.
Never combine multiple state-changing external actions inside a single executor (e.g., creating an order AND charging a credit card within the same `doProcess()` method).
====

Why is strictly enforcing atomic boundaries essential?

1. **Fault Isolation and Blast Radius Control**:
If an executor creates an order record in the Order Service and then attempts to charge a card via Stripe within the same method, a network drop during the Stripe call leaves the system in an ambiguous state. StackSaga cannot know whether the card was charged or not.
By separating them into `CreateOrderCommandExecutor` and `ProcessPaymentCommandExecutor`, StackSaga knows with 100% certainty that Step 2 completed successfully and Step 3 failed.

2. **Granular Idempotency and Retries**:
Each executor receives its own deterministic `idempotencyKey` generated for that specific execution span.
If the Payment Service times out due to transient network congestion, StackSaga's retry engine can safely re-invoke `ProcessPaymentCommandExecutor` using its stable `idempotencyKey` without accidentally creating duplicate order records in the Order Service.

3. **Clean Compensating Boundaries**:
When compensation is triggered, StackSaga only needs to compensate the exact steps that succeeded.
If Step 3 (Payment) fails, the Inventory Service (Step 4) was never called, so no inventory rollback is needed. The SEC only invokes `CreateOrderCommandExecutor.doRevert()` to cancel the pending order.

=== How Executors Form and Steer the Saga Chain

In StackSaga, the execution chain is not defined in an external XML file, a rigid database table, or a central BPMN orchestrator. Instead, the Saga chain is formed **decentralized, programmatic, and type-safe**:

==== 1. Forward Chaining (Decentralized Programmatic Routing)
Every executor dictates the next step in the forward flow through the `ProcessStepManager`:

[source,java]
----
// Forward transition: Step 2 hands over to Step 3
return stepManager
        .success("ORDER_INITIALIZED")
        .noPause()
        .nextExecutor(ProcessPaymentCommandExecutor.class);
----

==== 2. Dynamic Conditional Branching
Because routing is programmatic, an executor can inspect the cumulative aggregate state in `currentDomainEntity` and dynamically branch the execution path at runtime:

[source,java]
----
// Dynamic routing based on domain state:
if (currentDomainEntity.isVipCustomer()) {
    // High-priority customers bypass standard queues:
    return stepManager
            .success("ORDER_INITIALIZED")
            .noPause()
            .nextExecutor(ExpressPaymentCommandExecutor.class);
} else {
    return stepManager
            .success("ORDER_INITIALIZED")
            .noPause()
            .nextExecutor(StandardPaymentCommandExecutor.class);
}
----

==== 3. Terminal Completion
The final executor in the forward chain signals the SEC that the entire business transaction has completed successfully:

[source,java]
----
// Terminal success: marks the saga complete in the event store
return stepManager
        .success("STOCK_RESERVED")
        .noPause()
        .complete();
----

==== 4. Automatic Reverse Compensation Chaining (Managed by the SEC)
A major architectural advantage of StackSaga is that **developers never write backward routing links**.
You do **not** configure "If payment fails, jump back to order cancellation".

**How does StackSaga coordinate rollback?**

1. As forward execution progresses, the Saga Execution Coordinator (SEC) commits an immutable, append-only log of every successfully executed command executor span into the event store (`es_transaction_execution_tryout`).
2. If any step throws a `NonRetryableExecutorException` (e.g. `PaymentDeclinedException`), the SEC immediately halts forward progression.
3. The SEC inspects the event log to identify all previously committed command executors and invokes their `doRevert()` methods **in reverse chronological order**:
+
[source,text]
----
Failed Step N ──> doRevert(Step N-1) ──> doRevert(Step N-2) ... ──> doRevert(Step 1)
----
+
4. For each step, the SEC restores the exact domain entity aggregate checkpoint that existed when that executor ran, ensuring the compensation logic operates on accurate historical data.

== Executor Types & Architecture

Based on the execution nature, saga executors in StackSaga are divided into core types and specialized sub-executors:

image:implementations:executor/stacksaga-diagram-executor-types-in-stacksaga.svg[alt="Stacksaga Executors types",width=100%,opts=interactive,scaledwidth=100%]

* **xref:#command-executors[Command Executors]** (`CommandExecutor` / `ReactiveCommandExecutor`): For state-changing operations that require compensation.
* **xref:#query-executors[Query Executors]** (`QueryExecutor` / `ReactiveQueryExecutor`): For read-only operations that require no compensation.
* **xref:#sub-executors[Sub Executors]**: For decomposing complex multi-action compensations into atomic steps:
** **xref:#sub-before-executors[Sub-Before Executors]** (`RevertBeforeExecutor` / `ReactiveRevertBeforeExecutor`)
** **xref:#sub-after-executors[Sub-After Executors]** (`RevertAfterExecutor` / `ReactiveRevertAfterExecutor`)

IMPORTANT: Each executor interface provides both blocking (imperative) and non-blocking (reactive via Project Reactor) implementations. You can freely choose or mix both paradigms within the same saga.

[TIP]
.Sealed Interface Foundation & Type Safety
====
All executor contracts in StackSaga are defined as modern Java 21 **sealed interfaces** rooted at `SagaExecutor<DE>`.
Intermediate contracts like `SagaCommandExecutor<DE>` unify synchronous (`CommandExecutor`) and reactive (`ReactiveCommandExecutor`) implementations, and serve as the generic target bound `<E extends SagaCommandExecutor<DE>>` for sub-executor hooks (`@RevertBefore` and `@RevertAfter`).
Similarly, `SagaQueryExecutor<DE>` unifies read-only queries, and `SagaReactiveExecutor<DE>` marks non-blocking Project Reactor pipelines.
====

=== Method Parameter Anatomy

StackSaga provides clean, compile-time typed method signatures across all executors.
Every primary execution (`doProcess`) receives 4 standardized parameters, and every command compensation (`doRevert`) receives 6 standardized parameters:

.Standard Method Signatures
[source,java]
----
// Forward Execution (CommandExecutor & QueryExecutor):
ProcessStepManager<DE> doProcess(
        @NonNull DE currentDomainEntity,
        @NonNull String idempotencyKey,
        @NonNull ResumeContext resumeContext,
        @NonNull ProcessStepManager<DE> stepManager
) throws RetryableExecutorException, NonRetryableExecutorException;

// Compensating Execution (CommandExecutor):
RevertStepManager doRevert(
        @NonNull NonRetryableExecutorException processException,
        @NonNull DE finalDomainEntityState,
        @NonNull RevertHintStore revertHintStore,
        @NonNull String idempotencyKey,
        @NonNull ResumeContext resumeContext,
        @NonNull RevertStepManager stepManager
) throws RetryableExecutorException;
----

* **`currentDomainEntity` / `finalDomainEntityState`**: The cumulative domain aggregate state restored from the event store up to this execution step.
* **`idempotencyKey`**: A deterministic, retry-stable unique key generated per execution span. Pass this key to downstream services (via body, headers, or query parameters) to guarantee idempotency across retries.
* **`resumeContext`**: An immutable key-value metadata store (`Map<String, String>`) carrying external callback payloads when a paused transaction is resumed via `sagaTemplate.resume(...)`.
* **`revertHintStore`** _(Compensation only)_: A persistent key-value store across compensation steps used to pass diagnostic hints or compensation tracking IDs (e.g., external refund request IDs).
* **`stepManager`**: The staged fluent builder interface used to declare execution results and control saga navigation.

To provide clear separation of concerns, StackSaga classifies executor usage into two foundational paradigms:

1. *xref:#usage-1-continuous-lrt[Usage Pattern 1: Continuous Long-Running Transactions (Continuous LRT)]* -- Straight-through, unbroken sequential execution.
2. *xref:#usage-2-pausable-lrt[Usage Pattern 2: Pausable Long-Running Transactions (Wait-State / Callback-Driven LRT)]* -- Deliberate wait states awaiting external callbacks or human interaction.

'''

[[usage-1-continuous-lrt]]
== Usage Pattern 1: Continuous Long-Running Transactions (Continuous LRT)

In a **Continuous Long-Running Transaction**, all steps execute sequentially from start to finish without entering a durable wait state.
This represents the vast majority of standard microservice orchestration flows (such as synchronous order creation, customer account debiting, and stock reservations).

In Continuous LRT:

* **Primary Execution**: Completes its work and immediately invokes `.noPause().nextExecutor(...)` or `.noPause().complete()`.
* **Compensating Execution**: Undoes state changes and immediately invokes `.noPause()`.
* **Resume Context**: Naturally empty (`resumeContext.isEmpty() == true`) because the transaction was never paused.

[[command-executors]]
=== Command Executors in Continuous LRT

If an atomic operation modifies system state and requires compensation if downstream steps fail, implement `CommandExecutor` (blocking) or `ReactiveCommandExecutor` (non-blocking).

[[blocking-command-executors]]
==== Blocking Command-Executor

[source,java]
----
@SagaExecutor(executeFor = "order-service", value = "initializeOrderExecutor") //<1>
@AllArgsConstructor
public class InitializeOrderExecutor implements CommandExecutor<OrderDomainEntity> { //<2>

    private final OrderService orderService;

    @Override //<3>
    public @NonNull ProcessStepManager<OrderDomainEntity> doProcess(
            @NonNull OrderDomainEntity currentDomainEntity,
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext,
            @NonNull ProcessStepManager<OrderDomainEntity> stepManager
    ) throws RetryableExecutorException, NonRetryableExecutorException {

        try {
            //<4>
            String orderId = this.orderService.initializeOrder(
                    currentDomainEntity.getUsername(),
                    currentDomainEntity.getProductItems(),
                    currentDomainEntity.getTotalAmount(),
                    idempotencyKey
            );
            currentDomainEntity.setOrderId(orderId);

            //<5>
            return stepManager
                    .success("INITIALIZED_ORDER")
                    .noPause()
                    .nextExecutor(ReserveItemsExecutor.class);

        } catch (OperationAlreadyExecutedException alreadyExecutedException) {
            //<6>
            return stepManager
                    .success("INITIALIZED_ORDER")
                    .noPause()
                    .nextExecutor(ReserveItemsExecutor.class);

        } catch (FeignException.ServiceUnavailable unavailableException) {
            //<7>
            throw RetryableExecutorException.of(unavailableException);

        } catch (FeignException.BadRequest badRequestException) {
            //<8>
            throw NonRetryableExecutorException
                    .buildWith(badRequestException)
                    .put("time", LocalDateTime.now())
                    .put("reason", "BadRequest")
                    .build();
        }
    }

    @Override
    @RevertBefore(startFrom = OrderInitializeSubBeforeExecutor.class) //<12>
    @RevertAfter(startFrom = OrderInitializeSubAfterExecutor.class) //<13>
    public @NonNull RevertStepManager doRevert(
            @NonNull NonRetryableExecutorException processException,
            @NonNull OrderDomainEntity finalDomainEntityState,
            @NonNull RevertHintStore revertHintStore,
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext,
            @NonNull RevertStepManager stepManager
    ) throws RetryableExecutorException {

        try {
            //<9>
            this.orderService.cancelOrder(finalDomainEntityState.getOrderId(), idempotencyKey);
            return stepManager
                    .success("CANCELLED_ORDER")
                    .noPause(); //<10>

        } catch (OperationAlreadyExecutedException alreadyExecutedException) {
            return stepManager
                    .success("CANCELLED_ORDER")
                    .noPause(); //<10>

        } catch (FeignException.ServiceUnavailable unavailableException) {
            //<11>
            throw RetryableExecutorException.of(unavailableException);

        } catch (FeignException.BadRequest badRequestException) {
            // Unrecoverable compensation error: log to revertHintStore and proceed without stalling rollback
            revertHintStore.put("InitializeOrderExecutor:FAILED", processException.getMessage());
            return stepManager
                    .success("CANCEL_ORDER_TOLERATED")
                    .noPause();
        }
    }
}
----

<1> `@SagaExecutor` registers the class as a Spring Bean and specifies metadata (`executeFor` service name and unique executor identifier).
<2> Implements `CommandExecutor<OrderDomainEntity>` bound to the saga's domain aggregate entity.
<3> Overrides `doProcess` accepting the 4 standard parameters.
<4> Executes primary business logic, forwarding `idempotencyKey` to downstream APIs.
[[stepManager_navigation]]
<5> **Staged Fluent Step Navigation (`stepManager`)**: +
*Stage 1*: `.success("INITIALIZED_ORDER")` records the completed execution event. +
*Stage 2*: `.noPause()` declares continuous forward execution without entering a wait state. +
*Stage 3*: `.nextExecutor(ReserveItemsExecutor.class)` designates the next executor in the saga. To complete the entire transaction successfully, call `.complete()`.
<6> **Handle Duplicate Executions Gracefully**: If the downstream service indicates the request was already executed (e.g., HTTP `409 Conflict`), return `stepManager.success(...).noPause().nextExecutor(...)`. Never throw an exception on already-processed operations.
<7> Throw `RetryableExecutorException.of(unavailableException)` for transient network blips to schedule automated retries.
<8> Throw `NonRetryableExecutorException` on permanent business rejections (e.g., invalid data, insufficient funds) to trigger backward rollback.
<9> Compensating logic in `doRevert`: reverses the effects of `doProcess`.
<10> Conclude compensation with `stepManager.success("CANCELLED_ORDER").noPause()`. The SEC automatically advances backward to the preceding command executor.
<11> Transient failures during compensation trigger automated retry via `RetryableExecutorException`.
<12> `@RevertBefore`: Optional hook to execute sub-before executors before this `doRevert()` runs.
<13> `@RevertAfter`: Optional hook to execute sub-after executors after this `doRevert()` runs.

[[reactive-command-executors]]
==== Non-Blocking (Reactive) Command-Executor

[source,java]
----
@SagaExecutor(executeFor = "order-service", value = "reactiveInitializeOrderExecutor")
@AllArgsConstructor
public class ReactiveInitializeOrderExecutor implements ReactiveCommandExecutor<OrderDomainEntity> {

    private final OrderService orderService;

    @Override
    @NonNull
    public Mono<ProcessStepManager<OrderDomainEntity>> doProcess(
            @NonNull OrderDomainEntity currentDomainEntity,
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext,
            @NonNull ProcessStepManager<OrderDomainEntity> stepManager
    ) {
        return this.orderService
                .createOrder(
                        currentDomainEntity.getUserData(),
                        currentDomainEntity.getOrderDetails(),
                        idempotencyKey
                )
                .map(orderId -> {
                    currentDomainEntity.setOrderId(orderId);
                    return stepManager
                            .success("INITIALIZED_ORDER")
                            .noPause()
                            .nextExecutor(ReactiveReserveItemsExecutor.class);
                })
                .onErrorResume(throwable -> {
                    if (throwable instanceof OperationAlreadyExecutedException) {
                        return Mono.just(stepManager
                                .success("INITIALIZED_ORDER")
                                .noPause()
                                .nextExecutor(ReactiveReserveItemsExecutor.class));
                    } else if (throwable instanceof ResourceUnavailableException) {
                        return Mono.error(RetryableExecutorException.of(throwable));
                    } else {
                        return Mono.error(NonRetryableExecutorException.buildWith(throwable)
                                .put("time", String.valueOf(System.currentTimeMillis()))
                                .put("reason", "BadRequest")
                                .build());
                    }
                });
    }

    @Override
    @NonNull
    public Mono<RevertStepManager> doRevert(
            @NonNull NonRetryableExecutorException processException,
            @NonNull OrderDomainEntity finalDomainEntityState,
            @NonNull RevertHintStore revertHintStore,
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext,
            @NonNull RevertStepManager stepManager
    ) {
        return this.orderService
                .cancelOrder(finalDomainEntityState.getOrderId(), idempotencyKey)
                .thenReturn(stepManager
                        .success("REVERTED_ORDER_INITIALIZATION")
                        .noPause())
                .onErrorResume(throwable -> {
                    if (throwable instanceof OperationAlreadyExecutedException) {
                        return Mono.just(stepManager
                                .success("REVERTED_ORDER_INITIALIZATION")
                                .noPause());
                    } else if (throwable instanceof ResourceUnavailableException) {
                        return Mono.error(RetryableExecutorException.of(throwable));
                    } else {
                        revertHintStore.put("InitializeOrderExecutor:FAILED", processException.getMessage());
                        return Mono.just(stepManager
                                .success("IGNORED")
                                .noPause());
                    }
                });
    }
}
----

IMPORTANT: In reactive executors, the pipeline must never return `null` or `Mono.empty()`. Always wrap results in `Mono.just(stepManager...)` or `Mono.error(...)`.

[[query-executors]]
=== Query Executors in Continuous LRT

Query executors represent read-only operations (e.g., fetching user profile data, verifying account limits, checking stock catalog).
Because read-only queries make no external state modifications, they do not require compensation: a Query Executor implements only `doProcess`.

[[blocking-query-executors]]
==== Blocking Query Executor

[source,java]
----
@SagaExecutor(executeFor = "user-service", value = "checkUserDetailsExecutor")
@AllArgsConstructor
public class CheckUserDetailsExecutor implements QueryExecutor<OrderDomainEntity> {

    private final UserService userService;

    @Override
    public @NonNull ProcessStepManager<OrderDomainEntity> doProcess(
            @NonNull OrderDomainEntity currentDomainEntity,
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext,
            @NonNull ProcessStepManager<OrderDomainEntity> stepManager
    ) throws RetryableExecutorException, NonRetryableExecutorException {

        try {
            UserDetailDto userDetail = this.userService.getUserDetails(currentDomainEntity.getUsername());
            currentDomainEntity.setUserDetail(userDetail);

            return stepManager
                    .success("FETCHED_USER_DETAILS")
                    .noPause()
                    .nextExecutor(InitializeOrderExecutor.class);

        } catch (FeignException.ServiceUnavailable unavailableException) {
            throw RetryableExecutorException.of(unavailableException);
        } catch (FeignException.BadRequest badRequestException) {
            throw NonRetryableExecutorException
                    .buildWith(badRequestException)
                    .put("time", LocalDateTime.now())
                    .put("reason", "BadRequest")
                    .build();
        }
    }
}
----

[[sub-executors]]
=== Sub-Executors in Continuous LRT

Sub-executors are specialized executors in StackSaga used for executing **extra compensating atomic transactions** in addition to the parent command executor's primary compensation (`doRevert`).

Remember the core rule: **One executor = One atomic transaction**.
If cancelling an order requires two distinct operations -- e.g., (1) voiding an internal reservation and (2) notifying an external third-party courier service -- implementing both inside a single `doRevert()` method violates atomic boundaries.
Sub-executors solve this challenge cleanly:

[source,text]
----
Sub-Before Executors (1..N) ──> Parent doRevert() ──> Sub-After Executors (1..N)
----

image:executor/Architecture-Stacksaga-command-executor-with-revert-executors.drawio.svg[alt="Stacksaga Executors",width=100%,opts=interactive,scaledwidth=100%]

[[sub-before-executors]]
==== Sub-Before-Executor

Runs *before* the parent command executor's `doRevert()`:

[source,java]
----
@SagaExecutor(executeFor = "order-service", value = "orderInitializeSubBeforeExecutor")
@AllArgsConstructor
public class OrderInitializeSubBeforeExecutor implements RevertBeforeExecutor<OrderDomainEntity, InitializeOrderExecutor> {

    private final OrderService orderService;

    @Override
    public @NonNull RevertBeforeStepManager<OrderDomainEntity, InitializeOrderExecutor> doProcess(
            @NonNull OrderDomainEntity finalDomainEntityState,
            @NonNull NonRetryableExecutorException processException,
            @NonNull RevertHintStore revertHintStore,
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext,
            @NonNull RevertBeforeStepManager<OrderDomainEntity, InitializeOrderExecutor> stepManager
    ) throws RetryableExecutorException {

        try {
            this.orderService.preCancelOrder(finalDomainEntityState.getOrderId(), idempotencyKey);
            return stepManager
                    .success("REVERTED_ORDER_INITIALIZATION_SUB_BEFORE")
                    .noPause()

        } catch (OperationAlreadyExecutedException alreadyExecutedException) {
            return stepManager
                    .success("REVERTED_ORDER_INITIALIZATION_SUB_BEFORE")
                    .noPause()
                    .noMoreRevertBeforeExecutors();
        } catch (FeignException.ServiceUnavailable unavailableException) {
            throw RetryableExecutorException.of(unavailableException);
        }
    }
}
----

[[usage-2-pausable-lrt]]
== Usage Pattern 2: Pausable Long-Running Transactions (Wait-State / Callback-Driven LRT)

In enterprise microservices, transactions often cannot execute unbroken from start to finish. Real-world workflows demand deliberate, durable wait states:

* **Payment Gateways**: Asynchronous 3D-Secure payment redirects or banking clearing delays.
* **Human-in-the-Loop**: Asynchronous human approvals (KYC verification, loan underwriting, manager authorization).
* **Physical Operations**: Slow physical operations (kitchen food preparation, warehouse parcel packing).

StackSaga provides native, first-class support for **Pausable Long-Running Transactions (Wait-State / Callback-Driven LRT)** via the `.pause(Duration retentionDuration)` operator on `stepManager`.

[[pausable_lrt_lifecycle]]
=== Real-World Mixed Saga Flow: Continuous & Pausable Orchestration

In production enterprise architectures, a single saga flow frequently combines both synchronous continuous execution and asynchronous pausable wait-states inside the same orchestrator service.

The diagram below illustrates how an `Order-service` orchestrator coordinates unbroken local and remote steps alongside asynchronous third-party callbacks using StackSaga:

The SEC wakes up the transaction and routes execution directly to the final executor (`exe-5`).

`FinalizeOrder (no pause)`

[NOTE]
.Symmetrical Wait-State Architecture: Pausable Compensation in `doRevert()`
====
The **Process -> Pause / Wait -> Callback Resumption** pattern demonstrated in the diagram above is not limited to forward execution (`doProcess()`).
StackSaga provides a completely symmetrical wait-state capability for reverse compensation (`doRevert()`):

* **Wait-States in Rollback**: If an atomic compensation step requires an asynchronous external operation (such as submitting an asynchronous refund request to a banking gateway or voiding an airline ticket through a global reservation system), `doRevert()` can return:
+
[source,java]
----
return stepManager.success("REFUND_DISPATCHED").pause(Duration.ofHours(24));
----

* **Immediate Thread & Lock Liberation**: Just like in forward execution, StackSaga immediately persists the transaction snapshot in a paused rollback state (`is_paused = 1`), releases all worker threads and database connections, and awaits the external confirmation callback.
* **Automatic Rollback Continuation**: When the external provider fires its refund webhook, your controller resumes the transaction via `sagaTemplate.resume(txId, resumeKey).put("refundStatus", "SUCCESS").execute()`. The SEC engine verifies the callback payload in `ResumeContext`, completes the step, and **automatically continues reverse compensation backward through the remaining preceding steps** (e.g., `exe-2` -> `exe-1`).

For in-depth code examples and complete configuration details of rollback wait-states, see xref:#pausable-compensation[Pausable Compensation in doRevert()].
====

[[resume-context-in-executors]]
=== Forward Wait-States (`doProcess`)

In forward execution, wait-states are achieved through **Saga Flow Topology (Separation of Concerns)**:

1. **Pausing Step (`InitiatePaymentCommandExecutor`)**: Initiates the external asynchronous process and requests a durable wait state.
2. **Resumed Step (`ConfirmPaymentCommandExecutor`)**: Designated as the downstream step in the Saga DAG, executing when the transaction resumes.

==== Step A: The Pausing Executor (`InitiatePaymentCommandExecutor`)

[source,java]
----
@SagaExecutor(executeFor = "payment-service", value = "initiatePaymentCommandExecutor")
@AllArgsConstructor
public class InitiatePaymentCommandExecutor implements CommandExecutor<OrderDomainEntity> {

    private final PaymentGatewayClient paymentGateway;

    @Override
    public @NonNull ProcessStepManager<OrderDomainEntity> doProcess(
            @NonNull OrderDomainEntity currentDomainEntity,
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext,
            @NonNull ProcessStepManager<OrderDomainEntity> stepManager
    ) throws RetryableExecutorException, NonRetryableExecutorException {

        // 1. Dispatch asynchronous request to external payment provider forwarding idempotencyKey
        String intentId = this.paymentGateway.initiatePaymentIntent(
                currentDomainEntity.getOrderId(),
                currentDomainEntity.getTotalAmount(),
                idempotencyKey //<1>
        );

        // 2. Persist intent reference into domain aggregate state
        currentDomainEntity.setPaymentIntentId(intentId);

        // 3. Pause forward execution awaiting external callback webhook
        return stepManager
                .success("PAYMENT_INTENT_DISPATCHED")
                .pause(Duration.ofHours(2)) //<2>
                .nextExecutor(ConfirmPaymentCommandExecutor.class); //<3>
    }

    @Override
    public @NonNull RevertStepManager doRevert(...) {
        // Compensation logic if cancelled before completion
        return stepManager.success("PAYMENT_INTENT_CANCELLED").noPause();
    }
}
----

<1> Forward `idempotencyKey` as the unique correlation identifier for the external service.
<2> `.pause(Duration.ofHours(2))` marks the transaction `PAUSED` in the event store and releases the worker thread.
<3> `.nextExecutor(ConfirmPaymentCommandExecutor.class)` designates the executor that the SEC will invoke upon resumption.

==== Step B: The Resumed Executor (`ConfirmPaymentCommandExecutor`)

When the external payment gateway calls back and the application triggers `sagaTemplate.resume(...)`, the SEC advances and executes `ConfirmPaymentCommandExecutor`:

[source,java]
----
@SagaExecutor(executeFor = "payment-service", value = "confirmPaymentCommandExecutor")
@AllArgsConstructor
public class ConfirmPaymentCommandExecutor implements CommandExecutor<OrderDomainEntity> {

    private final PaymentGatewayClient paymentGateway;

    @Override
    public @NonNull ProcessStepManager<OrderDomainEntity> doProcess(
            @NonNull OrderDomainEntity currentDomainEntity,
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext, //<1>
            @NonNull ProcessStepManager<OrderDomainEntity> stepManager
    ) throws RetryableExecutorException, NonRetryableExecutorException {

        // 1. Ingest optional payload from ResumeContext if provided by the callback webhook
        Optional<String> authCode = resumeContext.get("authCode"); //<2>
        Optional<String> status = resumeContext.get("status");

        // 2. Verify payment status (either from payload or by querying gateway using domain state)
        boolean isSuccess = status
                .map("SUCCESS"::equalsIgnoreCase)
                .orElseGet(() -> this.paymentGateway.verifyPaymentStatus(currentDomainEntity.getPaymentIntentId()));

        if (isSuccess) {
            authCode.ifPresent(currentDomainEntity::setPaymentAuthCode);

            // 3. Advance to the next forward step
            return stepManager
                    .success("PAYMENT_CONFIRMED")
                    .noPause()
                    .nextExecutor(DispatchDeliveryExecutor.class); //<3>
        } else {
            // Payment rejected: trigger compensation
            throw NonRetryableExecutorException
                    .buildWith(new PaymentDeclinedException("Payment declined by gateway"))
                    .put("intentId", currentDomainEntity.getPaymentIntentId())
                    .build();
        }
    }

    @Override
    public @NonNull RevertStepManager doRevert(...) {
        // Compensating refund if downstream delivery fails
        this.paymentGateway.refundPayment(currentDomainEntity.getPaymentAuthCode());
        return stepManager.success("PAYMENT_REFUNDED").noPause();
    }
}
----

<1> `resumeContext` contains the key-value data passed during `sagaTemplate.resume(txId, key).put("authCode", ...).execute()`.
<2> Safely extract values using `resumeContext.get(key)`. The context is strictly read-only within executors.
<3> Advance forward continuously via `.noPause().nextExecutor(...)`.

[CAUTION]
.Architectural Anti-Pattern: Do NOT use `resumeContext.isEmpty()` for Lifecycle Checking!
====
Never use `if (resumeContext.isEmpty())` to determine whether an executor is running for the first time or running after a resume.

**Why?** An external webhook or manual resume trigger might legitimately carry **no payload** (e.g., an administrator clicking "Approve" in a dashboard, or a webhook ping with an empty HTTP 200 body).
In such cases, `resumeContext.isEmpty()` is `true`, **yet the execution IS a resumed execution**.

**How do executors know their phase?**
1. **By Saga Flow Topology**: The executor positioned after a pause step (e.g. `ConfirmPaymentCommandExecutor`) is architecturally dedicated to handling post-resumption verification.
2. **By Domain Entity State**: If an executor must verify whether external work was already dispatched, inspect domain state (e.g. `currentDomainEntity.getPaymentIntentId() != null`), never whether `ResumeContext` contains keys.
====

=== Retention Timeout & Idempotency Management

What happens if the external system fails, crashes, or never calls back within the configured `retentionDuration`?

1. **Automatic Re-Invocation of the Pausing Executor**:
+
* Upon timeout expiry, StackSaga's Retry Ring Coordinator re-exposes the paused transaction.
* The engine **automatically re-invokes the pausing executor** (`InitiatePaymentCommandExecutor`) with its pristine input aggregate state (`in_data`).
* **Why?** Because downstream confirmation was never received, and the business logic to check status, resend notifications, or initiate cancellation resides inside that pausing executor.

2. **Mandatory Idempotency Requirement**:
+
* Because the same executor is re-invoked even though its primary execution had previously completed before pausing, the executor **must strictly maintain idempotency**.
* Before issuing a new charge or request, the executor should verify whether `currentDomainEntity.getPaymentIntentId()` already exists or query the external provider using `idempotencyKey`.

3. **Concurrency & Race Condition Protection**:
+
* What happens if the external webhook callback from the first attempt arrives *after* the timeout expired and the executor has already been re-invoked?
* StackSaga guarantees that **only the first valid resume request is processed; subsequent or duplicate resume requests are safely rejected**.

4. **Extended Pauses for Human-in-the-Loop**:
+
* If your workflow requires an indefinite wait (e.g., a manager approval that should never time out automatically), specify an extended duration such as `Duration.ofDays(365)`.

[[pausable-compensation]]
=== Backward Compensation Wait-States (`doRevert`)

Rollback operations in distributed microservices frequently cannot complete synchronously. For example, reversing a payment often requires an **asynchronous refund request** with a banking clearing house that confirms completion hours or days later via a webhook.

StackSaga natively supports wait-states inside `doRevert(...)` using `stepManager.success(...).pause(Duration retentionDuration)`:

[[pausable-compensation-example]]
[source,java]
----
@SagaExecutor(executeFor = "payment-service", value = "paymentCommandExecutor")
@AllArgsConstructor
public class PaymentCommandExecutor implements CommandExecutor<OrderDomainEntity> {

    private final PaymentGatewayClient paymentGatewayClient;

    @Override
    public @NonNull ProcessStepManager<OrderDomainEntity> doProcess(...) {
        // Continuous forward execution
        String paymentRef = this.paymentGatewayClient.charge(currentDomainEntity.getTotalAmount(), idempotencyKey);
        currentDomainEntity.setPaymentRef(paymentRef);
        return stepManager.success("PAYMENT_CHARGED").noPause().nextExecutor(ReserveStockExecutor.class);
    }

    @Override
    public @NonNull RevertStepManager doRevert(
            @NonNull NonRetryableExecutorException primaryExecutionException,
            @NonNull OrderDomainEntity finalDomainEntityState,
            @NonNull RevertHintStore revertHintStore, //<1>
            @NonNull String idempotencyKey,
            @NonNull ResumeContext resumeContext,
            @NonNull RevertStepManager stepManager
    ) throws RetryableExecutorException {

        // Check persistent RevertHintStore to determine compensation phase:
        if (!revertHintStore.containsKey("refundSessionId")) { //<2>
            // --- 1. INITIAL COMPENSATION ATTEMPT ---
            // Dispatch asynchronous refund request forwarding idempotencyKey:
            String refundSessionId = this.paymentGatewayClient.initiateAsyncRefund(
                    finalDomainEntityState.getPaymentRef(),
                    idempotencyKey
            );
            revertHintStore.put("refundSessionId", refundSessionId); //<3>

            // Pause compensation awaiting bank clearing webhook:
            return stepManager
                    .success("REFUND_INITIATED")
                    .pause(Duration.ofHours(24)); //<4>
        }

        // --- 2. RESUMED COMPENSATION ATTEMPT ---
        // Webhook arrived! Ingest refund result from resumeContext or query gateway:
        String refundStatus = resumeContext.get("refundStatus")
                .orElseGet(() -> this.paymentGatewayClient.checkRefundStatus(revertHintStore.get("refundSessionId")));

        if ("SUCCESS".equalsIgnoreCase(refundStatus)) {
            // Reversal completed: finalize this compensation step
            return stepManager
                    .success("REFUND_COMPLETED")
                    .noPause(); //<5>
        } else {
            // Transient gateway delay: retry verification
            throw new RetryableExecutorException("Refund clearing pending in banking gateway");
        }
    }
}
----

<1> `revertHintStore` is the durable storage for compensation metadata preserved across retries and pauses.
<2> Use `!revertHintStore.containsKey("refundSessionId")` (NOT `resumeContext.isEmpty()`) to cleanly distinguish between the initial refund dispatch and the resumed callback.
<3> Store the refund tracking identifier in `revertHintStore`.
<4> Pause compensation via `stepManager.success("REFUND_INITIATED").pause(Duration.ofHours(24))`.
<5> Conclude compensation with `.noPause()`. StackSaga then automatically proceeds to compensate preceding steps in reverse order.

== Guidelines for Creating Executors

When designing saga executors, follow these core architectural guidelines:

. **One Executor = One Atomic Transaction**: Never combine multiple state-changing external operations in a single executor. Decompose them into separate command executors or sub-executors.
. **Enforce Idempotency**: Always forward `idempotencyKey` to downstream APIs and handle already-executed responses as successful steps without throwing errors.
. **Separate Continuous vs Pausable Concerns**: In pausable transactions, keep the pausing executor (`Initiate...`) and the resumed executor (`Confirm...`) distinct in the Saga DAG.
. **Never Inspect `resumeContext.isEmpty()` for Lifecycle Phase**: Use flow topology and `currentDomainEntityState` for forward phase tracking, and `RevertHintStore` for compensation phase tracking.
. **Maintain Documentation Integrity**: Ensure event names match the framework regex format (`^[A-Za-z0-9]+(?:_[A-Za-z0-9]+)*$`): alphanumeric tokens separated by single underscores (e.g. `ORDER_CREATED`, `PAYMENT_SUCCESS`, `STOCK_RESERVED`). Hyphens, spaces, leading/trailing underscores, and consecutive underscores (e.g. `ORDER__CREATED`) are rejected by the framework. Document all external failure modes and retry policies.
