= Saga Executors: Component Reference & Implementation Guide

== Overview

In StackSaga, a **Saga Executor** is a specialized Spring-managed component responsible for encapsulating and executing a **single atomic transaction** within a distributed saga workflow.
It serves as the boundary between your business domain logic and the Saga Execution Coordinator (SEC), ensuring that every step in a long-running transaction (LRT) executes with strict fault isolation, automated retry capabilities, and deterministic compensation.

StackSaga classifies executors into three primary contracts:

1. **Command Executors** (`CommandExecutor` / `ReactiveCommandExecutor`): For state-modifying operations that require compensation (`doProcess` and `doRevert`).
2. **Query Executors** (`QueryExecutor` / `ReactiveQueryExecutor`): For read-only queries or non-compensable actions that require no rollback (`doProcess` only).
3. **Pre-Executors & Post-Executors** (`PreExecutor`, `PostExecutor` / `ReactivePreExecutor`, `ReactivePostExecutor`): For decomposing complex multi-action compensations into isolated atomic steps before and after the host command's core rollback.

[TIP]
====
**Concept Model vs. Component Reference**: +
This document provides the **practical component reference** for creating, configuring, and testing Saga Executors in Spring Boot.
For the foundational theory of the **Unified Saga Model (USM)**, the deep mechanics of external integration patterns (USIP: continuous, pausable wait-states, and commit barriers), and workflow graph routing (USNP: LIFO reverse autopilot and query pruning), see the companion architecture guide:
xref:stacksaga-sync/orchestrator/unified-saga-patterns.adoc[Unified Saga Orchestration Patterns (USIP & USNP)].

[[conceptual-foundation]]
== The Executor Contract: Rules Every Executor Must Follow

Before implementing any Java interface, recognize the two rules that apply to every Saga Executor, whatever its type.
Everything else on this page builds on them.

[[rule-one-atomic-transaction]]
=== Rule 1: One Executor = One Atomic Transaction

[IMPORTANT]
.The Fundamental Architectural Rule: One Executor = One Atomic Transaction
====
An executor must interact with **exactly one microservice or one local database boundary**.
Never combine multiple external state-changing actions inside a single executor's `doProcess()` method (for example, creating a database record AND charging a credit card in the same step).
====

==== Real-World Scenario: E-Commerce Checkout Saga

Consider an e-commerce order checkout where a customer places an order. The business transaction spans four distinct microservice boundaries:

1. **User Service** (`CheckCustomerEligibilityExecutor`): Queries customer account eligibility and credit limits (read-only query).
2. **Order Service** (`CreateOrderCommandExecutor`): Inserts a `PENDING` order record in the local Order database.
3. **Payment Service** (`ProcessPaymentCommandExecutor`): Connects over REST/gRPC to authorize and charge the payment gateway.
4. **Inventory Service** (`ReserveStockCommandExecutor`): Deducts and locks inventory in the warehouse database.

[[rule-idempotent-execution]]
=== Rule 2: Every Execution Must Be Idempotent

The engine guarantees that every executor runs *at least once* — not *exactly once*.
The same `doProcess()` or `doRevert()` can legitimately run more than once for the same step:

* *Transient failures*: when an executor throws `RetryableExecutorException`, the retry subsystem invokes it again.
* *Crashes*: the engine never wraps an executor in a database transaction, and it records the step result only after the method returns.
If the service stops between the external call and that record, the step runs again after recovery.
* *Wait-state timeouts*: when the callback of a paused step does not arrive in time, the step is invoked again.

[IMPORTANT]
.Make every repeated execution safe
====
* Forward the engine-provided `idempotencyKey` to the downstream service — as an `Idempotency-Key` HTTP header, a message key or header, or a unique business key in your database.
The key stays the same across every retry of the same execution, so the downstream service can recognize a repeat.
* Treat an "already processed" answer from the downstream service as success, not as a failure — see the `OperationAlreadyExecutedException` handling in the <<command-executors,canonical Command Executor>>.
====

For the theory behind this rule — ambiguous network outcomes, why retries cannot be avoided, and common idempotency techniques — see xref:foundations:idempotency.adoc#what_is_idempotency[What is Idempotency?].

=== Why These Rules Matter

Together, the two rules give the engine three operational guarantees:

1. **Fault Isolation**: If Step 3 (Payment) fails, the orchestrator knows with certainty that Step 2 (Order Creation) succeeded and Step 4 (Inventory) was never touched.
2. **Granular Idempotency & Retries**: Every execution span receives a deterministic `idempotencyKey`. If a network timeout occurs during Payment, the orchestrator safely retries only that step without generating duplicate orders.
3. **Clean Compensating Execution**: When failure occurs, the SEC unwinds only the steps that completed successfully. Developers never manually write reverse routing logic; the SEC coordinates compensation automatically via **Deterministic Reverse Autopilot** (see xref:stacksaga-sync/orchestrator/unified-saga-patterns.adoc#usnp-revert-step-manager[Unified Saga Navigation Patterns: USNP]).

[TIP]
.A direct consequence of Rule 1: no Transactional Outbox
====
Because a database write and a message publish always live in two separate executors, StackSaga applications do not need the Transactional Outbox Pattern.
See <<outbox-pattern-eliminated,Why StackSaga Eliminates the Transactional Outbox Pattern>> at the end of this page for the full explanation.
====

[source,java]

}
----

* **`value`**: The unique Spring Bean identifier for this executor instance.

[[method-signatures]]
== Method Signatures & Context Objects

Every executor method takes exactly two arguments:

* a **context** — everything the engine supplies to this execution (`ProcessContext` for forward execution, `RevertContext` for compensation), and
* a **step manager** — the builder the execution uses to report its outcome and choose where the saga goes next.

.Standard Method Signatures
[source,java]
----
// Forward execution (CommandExecutor & QueryExecutor):
ProcessStepManager<DE> doProcess(
        @NonNull ProcessContext<DE> context,
        @NonNull ProcessStepManager<DE> stepManager
) throws RetryableExecutorException, NonRetryableExecutorException;

// Compensation (CommandExecutor):
RevertStepManager doRevert(
        @NonNull RevertContext<DE> context,
        @NonNull RevertStepManager stepManager
) throws RetryableExecutorException;

// Compensation hooks around the host command's doRevert (PreExecutor / PostExecutor):
PreStepManager<DE, E> doRevert(
        @NonNull RevertContext<DE> context,
        @NonNull PreStepManager<DE, E> stepManager
) throws RetryableExecutorException;
----

The naming is deliberate: `doProcess` always moves the saga *forward*, and `doRevert` always runs during *compensation* — whether it is a command's own rollback or a Pre/Post hook around it.
Reactive executors use the same arguments and return the step manager wrapped in a `Mono`.

=== `ProcessContext` (forward execution)

1. **`currentDomainEntityState()`**:
   * The cumulative domain aggregate state, restored from the Event Store up to this execution step.
   * Mutate it with the response data of your external call; the SEC persists the updated snapshot when the step completes.

2. **`idempotencyKey()`**:
   * A deterministic, retry-stable key generated by the SEC for this execution. Every re-execution of the same step receives the same key.
   * Always forward it to the downstream service, as required by <<rule-idempotent-execution,Rule 2: Every Execution Must Be Idempotent>>.

3. **`resumeContext()`**:
   * An immutable key-value store (`ResumeContext`) delivered when a paused transaction is awakened via `sagaTemplate.resume(resumeKey, retentionDuration)`.
   * Read callback parameters with `context.resumeContext().get("key")` (returns `Optional<String>`).
   * When a step runs continuously without pausing, it is empty.

+
[CAUTION]
.Architectural Anti-Pattern: Never use `resumeContext().isEmpty()` for Lifecycle Checks
====
Never check `if (context.resumeContext().isEmpty())` to determine whether an executor is executing for the first time or running after a resume.
External webhooks or user approval clicks may legitimately deliver no body payload, leaving the resume context empty even though the execution is a resumption.
Instead, use **Saga Flow Topology** (separate pausing and resumed steps) or inspect domain entity state (`currentDomainEntityState.getPaymentSessionId() != null`).
====

=== `RevertContext` (compensation)

`RevertContext` is passed to a command's `doRevert` and to every Pre/Post hook of that command.

1. **`finalDomainEntityState()`**:
   * The exact historical snapshot of the domain aggregate at the time compensation started.
   * It is read-only during compensation; record compensation data in the `revertHintStore()` instead.

2. **`primaryExecutionException()`**:
   * The `NonRetryableExecutorException` that stopped forward execution and started compensation.

3. **`revertHintStore()`**:
   * A persistent key-value store scoped across the entire compensation pipeline of the transaction.
   * Used to pass intermediate compensation tokens (such as refund session IDs, cancellation tracking numbers, or error details) between retries, pre-executors, and post-executors.

4. **`idempotencyKey()`**:
   * The retry-stable key of *this compensating execution*. Forward it with the undo call so that a retried compensation is applied only once.

5. **`primaryExecutionIdempotencyKey()`**:
   * The key that the same step's `doProcess` received. In a Pre/Post hook, it is the key of the host command's `doProcess`.
   * Use it to address the remote operation the forward step created — for example, to look up, cancel, or refund that operation by the key it was submitted with.

6. **`resumeContext()`**:
   * Same as in `ProcessContext`: the callback data delivered when a paused compensation is resumed. See <<pausable-compensation,Implementing Pausable Compensation>>.

=== `stepManager`

The staged, fluent builder used to record step outcomes, declare execution modes (Sync vs. Async), configure wait-states, and specify workflow destinations.
See <<step-manager-navigation-reference,Step Manager Navigation Quick Reference>>.

[[command-executors]]
== Implementing Command Executors

Command Executors represent state-modifying actions requiring forward execution (`doProcess`) and backward compensation (`doRevert`).

=== Canonical Imperative Command Executor (`CommandExecutor`)

Below is a complete, production-ready implementation of `CommandExecutor<OrderDomainEntity>`:

[source,java]
----
@SagaExecutor(executeFor = "order-service", value = "createOrderExecutor")
@RequiredArgsConstructor
public class CreateOrderExecutor implements CommandExecutor<OrderDomainEntity> {

    private final OrderServiceClient orderClient;

    @Override
    public @NonNull ProcessStepManager<OrderDomainEntity> doProcess(
            @NonNull ProcessContext<OrderDomainEntity> context,
            @NonNull ProcessStepManager<OrderDomainEntity> stepManager
    ) throws RetryableExecutorException, NonRetryableExecutorException {
        OrderDomainEntity currentDomainEntityState = context.currentDomainEntityState();

        try {
            // 1. Invoke downstream service forwarding idempotencyKey
            OrderResponse response = orderClient.createOrder(
                    currentDomainEntityState.getOrderId(),
                    currentDomainEntityState.getItems(),
                    context.idempotencyKey()
            );

            // 2. Mutate domain entity with response data
            currentDomainEntityState.setTrackingNumber(response.getTrackingNumber());

            // 3. Staged navigation: Continuous Sync Advance (USIP Pattern 1)
            return stepManager
                    .success("ORDER_CREATED")
                    .asSync()
                    .noPause()
                    .toNextExecutor(ReserveInventoryExecutor.class);

        } catch (OperationAlreadyExecutedException ex) {
            // Idempotent recovery: already processed downstream, advance safely
            return stepManager
                    .success("ORDER_CREATED")
                    .asSync()
                    .noPause()
                    .toNextExecutor(ReserveInventoryExecutor.class);

        } catch (FeignException.ServiceUnavailable ex) {
            // Transient infrastructure fault: triggers automatic retry
            throw RetryableExecutorException.of(ex);

        } catch (FeignException.BadRequest ex) {
            // Permanent business failure: triggers reverse compensation
            throw NonRetryableExecutorException
                    .buildWith(ex)
                    .withEvent("ORDER_REJECTED")
                    .withDefaultReexposeOnUnexpectedCrash()
                    .compensateThisStep(true)
                    .put("reason", "Invalid order payload")
                    .build();
        }
    }

    @Override
    public @NonNull RevertStepManager doRevert(
            @NonNull RevertContext<OrderDomainEntity> context,
            @NonNull RevertStepManager stepManager
    ) throws RetryableExecutorException {
        OrderDomainEntity finalDomainEntityState = context.finalDomainEntityState();

        try {
            // Undo previous action using historical state snapshot
            orderClient.cancelOrder(finalDomainEntityState.getOrderId(), context.idempotencyKey());

            // Conclude compensation; SEC unwinds to preceding command in history
            return stepManager
                    .success("ORDER_CANCELED")
                    .asSync()
                    .noPause()
                    .toNextDefaultExecutor();

        } catch (OperationAlreadyExecutedException ex) {
            // Already cancelled: treat as successfully compensated
            return stepManager
                    .success("ORDER_CANCELED")
                    .asSync()
                    .noPause()
                    .toNextDefaultExecutor();

        } catch (FeignException.ServiceUnavailable ex) {
            // Retry transient rollback failure
            throw RetryableExecutorException.of(ex);
        }
    }
}
----

[NOTE]
====
In `doRevert()`, **only `RetryableExecutorException` is allowed**. `NonRetryableExecutorException` is strictly forbidden because in the Saga pattern there is no compensation for a compensation. If compensation fails permanently due to an unhandled exception, the saga becomes a Terminated Transaction requiring manual operator intervention. See xref:stacksaga-sync/orchestrator/stacksaga_template.adoc#advanced-architectural-faq[FAQ Q4: Compensation Error Handling & Terminated Transactions].
====

=== Supporting Pausable Wait-States (USIP Pattern 2)

When an operation requires an external callback, user redirect (3D-Secure, PayPal), or manual manager approval, configure a pausable wait-state using `.pauseUntilResume(duration)`:

[source,java]
----
// Forward wait-state awaiting payment webhook (e.g. 15-minute window):
return stepManager
        .success("PAYMENT_SESSION_INITIATED")
        .asSync()
        .pauseUntilResume(Duration.ofMinutes(15))
        .resumeToNextExecutor(CapturePaymentExecutor.class);
----

* The SEC marks the transaction as `PAUSED` (`is_paused = 1`), registers the unique `resumeKey` (formatted as `transactionId:tryoutId`), records the step with **`ExecutionStatus.NOT_YET`**, and **immediately frees the worker thread and DB connection**.
* The saga consumes zero CPU, threads, or memory while parked.
* **Parked Step Execution Status (`ExecutionStatus.NOT_YET`):** While parked waiting for external input, the active step event remains in `ExecutionStatus.NOT_YET`. It only transitions to `ExecutionStatus.SUCCESS` once the external callback arrives and the orchestrator successfully resumes the transaction to the destination executor.
* **Dual-Token Distinction:** The engine provides two tokens with separate responsibilities:
** **`idempotencyKey`** (Method Parameter): Business-level idempotency hash. Pass this to external APIs (e.g. in HTTP `Idempotency-Key` headers) to prevent duplicate side effects on the external service upon network retries.
** **`stepManager.getResumeKey()`** (`transactionId:tryoutId`): Runtime correlation token encapsulating the attempt-specific **Tryout UID**. Pass this in callback/webhook metadata so that late/stale callbacks from previous timed-out attempts are rejected automatically.
* When the webhook arrives, call `sagaTemplate.resume(resumeKey, retentionDuration)` (fluent `.put(...)` or `.withContext(resumeContext)`) to wake the saga and invoke `CapturePaymentExecutor`.
* **Timeout Re-Execution:** If the callback fails to arrive within the configured duration, the Retry Coordinator re-invokes this executor's `doProcess(...)` with a newly generated Tryout UID. See xref:stacksaga-sync/orchestrator/stacksaga_template.adoc#advanced-architectural-faq[FAQ Q1 & Q2: Re-Invocation of Succeeded Steps and Tuning Wait-State Duration].
* See xref:stacksaga-sync/orchestrator/unified-saga-patterns.adoc#usip-pattern-2-correlated-park-resume[USIP Pattern 2: Correlated Park-and-Resume] for complete thread lifecycle details.

=== Supporting Two-Stage Broker Dispatch with Commit Barrier (USIP Pattern 3)

When emitting command messages over **Apache Kafka, RabbitMQ, or AWS SQS**, enforce the Two-Stage Asynchronous Model via `.asAsync().invoker(...)`:

[source,java]
----
@Override
public @NonNull ProcessStepManager<OrderDomainEntity> doProcess(...) {
    // Stage 1: Preparation committed to Event Store BEFORE network send
    context.currentDomainEntityState().setShippingTrackingId(UUID.randomUUID().toString());

    return stepManager
            .success("SHIPPING_DISPATCH_COMMITTED")
            .asAsync()
            .invoker((de, ctx) -> {
                // Stage 2: Lazy dispatch executed strictly AFTER Event Store commit
                ShippingCommandMessage message = new ShippingCommandMessage(
                        de.getOrderId(),
                        de.getShippingTrackingId(),
                        context.idempotencyKey()
                );
                kafkaTemplate.send("shipping-commands", de.getOrderId(), message);
            })
            .pauseUntilResume(Duration.ofHours(2))
            .resumeToNextExecutor(ConfirmDeliveryExecutor.class);
}
----

* **Commit Barrier**: The SEC commits the `PAUSED` transaction record (`is_paused = 1`) to the Event Store *before* firing the lambda, recording the step in **`ExecutionStatus.NOT_YET`** and completely eliminating fast-callback race conditions.
* **Strict Rule**: Never mutate `currentDomainEntityState` inside the `invoker(...)` closure, as the entity snapshot is sealed prior to invocation.
* **Lifecycle Status**: The step remains in `ExecutionStatus.NOT_YET` while waiting for the downstream consumer's callback response; it transitions to `ExecutionStatus.SUCCESS` only after resumption.
* See xref:stacksaga-sync/orchestrator/unified-saga-patterns.adoc#usip-pattern-3-two-stage-lazy-dispatch[USIP Pattern 3: Two-Stage Lazy Dispatch] for architectural details.

=== Reactive Command Executor (`ReactiveCommandExecutor`)

For non-blocking reactive stacks (Spring WebFlux, Netty, R2DBC), implement `ReactiveCommandExecutor<DE>`:

[source,java]
----
@SagaExecutor(executeFor = "order-service", value = "reactiveCreateOrderExecutor")
@RequiredArgsConstructor
public class ReactiveCreateOrderExecutor implements ReactiveCommandExecutor<OrderDomainEntity> {

    private final WebClient webClient;

    @Override
    public Mono<ProcessStepManager<OrderDomainEntity>> doProcess(
            ProcessContext<OrderDomainEntity> context,
            ProcessStepManager<OrderDomainEntity> stepManager
    ) {
        OrderDomainEntity currentDomainEntityState = context.currentDomainEntityState();

        return webClient.post()
                .uri("/orders")
                .header("Idempotency-Key", context.idempotencyKey())
                .bodyValue(new CreateOrderRequest(currentDomainEntityState.getOrderId(), currentDomainEntityState.getItems()))
                .retrieve()
                .bodyToMono(OrderResponse.class)
                .map(response -> {
                    currentDomainEntityState.setTrackingNumber(response.getTrackingNumber());
                    return stepManager
                            .success("ORDER_CREATED")
                            .asSync()
                            .noPause()
                            .toNextExecutor(ReserveInventoryExecutor.class);
                })
                .onErrorResume(WebClientResponseException.class, ex ->
                        Mono.error(new RetryableExecutorException("Order service unavailable", ex)));
    }

    @Override
    public Mono<RevertStepManager> doRevert(
            RevertContext<OrderDomainEntity> context,
            RevertStepManager stepManager
    ) {
        OrderDomainEntity finalDomainEntityState = context.finalDomainEntityState();

        return webClient.delete()
                .uri("/orders/" + finalDomainEntityState.getOrderId())
                .retrieve()
                .toBodilessEntity()
                .thenReturn(stepManager
                        .success("ORDER_CANCELED")
                        .asSync()
                        .noPause()
                        .toNextDefaultExecutor());
    }
}
----

[[pausable-compensation]]
=== Implementing Pausable Compensation (Patterns 2 & 3 in Rollback)

Just as forward execution can park while awaiting external webhooks or asynchronous broker confirmations, **compensation (`doRevert`) fully supports pausable integration patterns**:

1. **Pattern 2 Revert (Sync-Paused)**: When reversing a step requires waiting for an asynchronous settlement or external webhook confirmation (such as an asynchronous banking refund or payment gateway refund callback), return `.pauseUntilResume(duration)`:
+
[source,java]
----
@Override
public @NonNull RevertStepManager doRevert(
        @NonNull RevertContext<OrderDomainEntity> context,
        @NonNull RevertStepManager stepManager
) throws RetryableExecutorException {
    OrderDomainEntity finalDomainEntityState = context.finalDomainEntityState();

    if (!context.revertHintStore().containsKey("refundInitiated")) {
        // First attempt: Request refund from external gateway
        String refundRef = paymentClient.requestAsyncRefund(finalDomainEntityState.getPaymentId(), context.idempotencyKey());
        context.revertHintStore().put("refundInitiated", refundRef);

        // Pause compensation awaiting webhook notification
        return stepManager
                .success("REFUND_DISPATCHED")
                .asSync()
                .pauseUntilResume(Duration.ofDays(1))
                .resumeToNextDefaultExecutor();
    }

    // Resumed attempt: Webhook callback arrived and resumeContext is populated
    String refundStatus = context.resumeContext().get("refundStatus").orElse("UNKNOWN");
    if (!"CONFIRMED".equalsIgnoreCase(refundStatus)) {
        throw new RetryableExecutorException("Refund not yet confirmed by gateway");
    }

    return stepManager
            .success("REFUND_COMPLETED")
            .asSync()
            .noPause()
            .toNextDefaultExecutor();
}
----

2. **Pattern 3 Revert (Async-Paused: Commit Barrier)**: When rollback requires emitting a compensating message to an external broker (e.g., publishing a `CancelShippingCommand` to Kafka), use `.asAsync().invoker(...)`:
+
[source,java]
----
@Override
public @NonNull RevertStepManager doRevert(...) {
    return stepManager
            .success("CANCEL_DISPATCH_COMMITTED")
            .asAsync()
            .invoker(
                    resumeKey -> {
                        kafkaTemplate.send("shipping-cancel-topic", context.finalDomainEntityState().getOrderId(), resumeKey);
                    },
                    Duration.ofMinutes(15),     // Tier 2 retry window on transient network failure
                    KafkaException.class        // Exception triggering scheduled retry
            )
            .pauseUntilResume(Duration.ofHours(2))
            .resumeToNextDefaultExecutor();
}
----

* **Uniform Resumption**: External webhooks resume compensating steps using the exact same API: `sagaTemplate.resume(resumeKey, duration).execute()`. The StackSaga Execution Coordinator (SEC) recognizes that the transaction is in `REVERTING` status, restores the rollback checkpoint, injects the `ResumeContext`, and re-invokes `doRevert(...)` to finalize compensation.
* **Transient Error Safety**: If the broker dispatch lambda throws the declared transient exception, the transaction remains parked (`is_paused = 1`) with transient retention, waiting for the Retry Subsystem to re-dispatch the cancellation event.
* For complete LIFO unwinding details and pre/post compensation cascades, see xref:stacksaga-sync/orchestrator/unified-saga-patterns.adoc#usnp-2-1-revert-to-core[Core Revert Navigation in Unified Saga Patterns].

[[query-executors]]
== Implementing Query Executors

Query Executors encapsulate read-only operations (e.g. checking customer credit, inspecting inventory, validating addresses) or non-compensable writes (e.g. appending security audit logs).
Because read-only queries make no external state mutations that need to be reversed, Query Executors **do not implement `doRevert()`**.

[TIP]
====
**Automatic Rollback Pruning**: During compensation, the SEC automatically skips historical `QueryExecutor` events. A query step will never break or complicate transaction rollback.
See xref:stacksaga-sync/orchestrator/unified-saga-patterns.adoc#usnp-query-pruning[Query State Pruning & Bypass Pattern].
====

[IMPORTANT]
.Architectural Best Practice: QueryExecutor vs. TransactionEventListener for Post-Step Invocations
====
If an operation must execute immediately following another executor (such as generating an internal receipt, recording an immutable audit ledger entry, or invoking a non-compensable verification) and must **never be skipped under any failure condition (including application crashes)**, model it as a formal **`QueryExecutor`** chained as the next step, rather than placing it inside a `TransactionEventListener`.

* *Why not an Event Listener?* As explained in xref:stacksaga-sync/orchestrator/stacksaga_template.adoc#at-least-once-listener-semantics[The Atomicity Mandate and the Crash Window], the SEC must durably persist executor state to the Event Store *before* notifying listeners to prevent phantom notifications. If the JVM process crashes immediately after state persistence, cluster restoration resumes execution directly from the *next* executor in the workflow, meaning any critical logic inside `onStateChanged` is permanently skipped and will never execute.
* *Why QueryExecutor?* `QueryExecutor` instances are first-class saga participants: they are **re-invokable by default**, tracked in the Event Store, self-healed by the xref:retry-ring-coordinator:transaction-retrying-with-retry-coordinator.adoc#retry-node[Retry Subsystem], and fully observable in the xref:trace-window:stacksaga-trace-window.adoc[Trace Window dashboard]. Because they do not implement `doRevert()`, the SEC's Reverse Autopilot prunes them automatically during backward compensation (see xref:stacksaga-sync/orchestrator/unified-saga-patterns.adoc#usnp-query-pruning[USNP Query Pruning Pattern]), delivering durability without rollback overhead.
* *Developer Decision Matrix:* To determine whether your logic should be a `QueryExecutor`, `CommandExecutor`, or `TransactionEventListener`, consult the xref:stacksaga-sync/orchestrator/stacksaga_template.adoc#at-least-once-listener-semantics[Developer Decision Matrix in the SagaTemplate Guide].
====

=== Blocking Query Executor

[source,java]
----
@SagaExecutor(executeFor = "user-service", value = "checkCreditQueryExecutor")
@RequiredArgsConstructor
public class CheckCreditQueryExecutor implements QueryExecutor<OrderDomainEntity> {

    private final CreditServiceClient creditClient;

    @Override
    public @NonNull ProcessStepManager<OrderDomainEntity> doProcess(
            @NonNull ProcessContext<OrderDomainEntity> context,
            @NonNull ProcessStepManager<OrderDomainEntity> stepManager
    ) throws RetryableExecutorException, NonRetryableExecutorException {
        OrderDomainEntity currentDomainEntityState = context.currentDomainEntityState();

        CreditScoreResponse response = creditClient.fetchScore(currentDomainEntityState.getCustomerId());
        currentDomainEntityState.setCreditApproved(response.isEligible());

        // Navigates directly to next command or query
        return stepManager
                .success("CREDIT_VERIFIED")
                .asSync()
                .noPause()
                .toNextExecutor(DebitAccountCommandExecutor.class);
    }
}
----

== Implementing Pre-Executors and Post-Executors (Pre & Post Compensation Hooks)

When compensating a step requires multiple actions across distinct systems (for example, releasing a distributed mutex before refunding, or sending a notification after cancelling), placing all logic inside one `doRevert()` method violates <<rule-one-atomic-transaction,Rule 1: One Executor = One Atomic Transaction>>.

StackSaga solves this by allowing developers to attach modular **Pre-Executors** and **Post-Executors** to any host `CommandExecutor`.
Because they run only during compensation, each hook implements `doRevert` and receives the same `RevertContext` as the host command, so `context.primaryExecutionIdempotencyKey()` gives a hook the key of the host command's forward execution:

image:implementations:executor/Architecture-Stacksaga-command-executor-with-revert-executors.drawio.svg[alt="Command Executor with Pre and Post Executors",width=100%,opts=interactive,scaledwidth=100%]

=== Declaring Hooks on Host Command Executor

Attach `@StartPreExecutor` and `@StartPostExecutor` directly to the `doRevert()` method of the host command:

[source,java]
----
@Override
@StartPreExecutor(AcquireRefundTokenPreExecutor.class)
@StartPostExecutor(SendCancellationEmailPostExecutor.class)
public @NonNull RevertStepManager doRevert(
        @NonNull RevertContext<OrderDomainEntity> context,
        @NonNull RevertStepManager stepManager
) throws RetryableExecutorException {
    OrderDomainEntity finalDomainEntityState = context.finalDomainEntityState();

    // Core payment refund compensation
    paymentClient.refund(finalDomainEntityState.getPaymentId(), context.idempotencyKey());
    return stepManager.success("PAYMENT_REFUNDED").asSync().noPause().toNextDefaultExecutor();
}
----

[[pre-executors]]
=== Pre-Executor (`PreExecutor`)

Executes *before* the parent command's core `doRevert()`. Use `.toNextDefaultExecutor()` to transition directly into the parent command's `doRevert()`:

[source,java]
----
@SagaExecutor(executeFor = "auth-service", value = "acquireRefundTokenPreExecutor")
@RequiredArgsConstructor
public class AcquireRefundTokenPreExecutor implements PreExecutor<OrderDomainEntity, PaymentCommandExecutor> {

    private final AuthServiceClient authClient;

    @Override
    public @NonNull PreStepManager<OrderDomainEntity, PaymentCommandExecutor> doRevert(
            @NonNull RevertContext<OrderDomainEntity> context,
            @NonNull PreStepManager<OrderDomainEntity, PaymentCommandExecutor> stepManager
    ) throws RetryableExecutorException {

        // Acquire cancellation token and save to hint store for parent doRevert()
        String token = authClient.acquireCancellationScopeToken();
        context.revertHintStore().put("CANCELLATION_TOKEN", token);

        // Hands control directly into PaymentCommandExecutor.doRevert()
        return stepManager
                .success("CANCELLATION_TOKEN_ACQUIRED")
                .asSync()
                .noPause()
                .toNextDefaultExecutor();
    }
}
----

To chain multiple pre-hooks, call `.toNextPreExecutor(SecondPreExecutor.class)`.

[[post-executors]]
=== Post-Executor (`PostExecutor`)

Executes *after* the parent command's core `doRevert()` completes. Calling `.toNextDefaultExecutor()` concludes compensation for this step, signaling the SEC to continue unwinding preceding commands in history:

[source,java]
----
@SagaExecutor(executeFor = "notification-service", value = "sendCancellationEmailPostExecutor")
@RequiredArgsConstructor
public class SendCancellationEmailPostExecutor implements PostExecutor<OrderDomainEntity, PaymentCommandExecutor> {

    private final EmailServiceClient emailClient;

    @Override
    public @NonNull PostStepManager<OrderDomainEntity, PaymentCommandExecutor> doRevert(
            @NonNull RevertContext<OrderDomainEntity> context,
            @NonNull PostStepManager<OrderDomainEntity, PaymentCommandExecutor> stepManager
    ) throws RetryableExecutorException {
        OrderDomainEntity finalDomainEntityState = context.finalDomainEntityState();

        emailClient.sendOrderCancellation(finalDomainEntityState.getCustomerEmail());

        // Step compensation fully completed; unwinds to preceding command step in history
        return stepManager
                .success("CANCELLATION_EMAIL_SENT")
                .asSync()
                .noPause()
                .toNextDefaultExecutor();
    }
}
----

To chain multiple post-hooks, call `.toNextPostExecutor(SecondPostExecutor.class)`.
For complete reverse handoff lifecycle rules, see xref:stacksaga-sync/orchestrator/unified-saga-patterns.adoc#usnp-pre-step-manager[Pre-Compensation] and xref:stacksaga-sync/orchestrator/unified-saga-patterns.adoc#usnp-post-step-manager[Post-Compensation] in Unified Saga Navigation Patterns.

== Exception Handling & Fault Classification

StackSaga classifies faults strictly into transient infrastructure issues and permanent business rejections:

.Exception Classification Matrix
[cols="30%,20%,25%,25%",options="header"]
|===
| Exception Type | Allowed in `doProcess` | Allowed in `doRevert` | Framework Behavior

| **`RetryableExecutorException`**
| ✔
| ✔
| **Transient Fault**: Indicates temporary network drops, HTTP 503s, or database lock contention. The engine automatically retries execution with exponential backoff via the Retry Ring Coordinator.

| **`NonRetryableExecutorException`**
| ✔
| ✖ _(Forbidden in rollback)_

[[building-non-retryable-exception]]
=== Building a `NonRetryableExecutorException`

A `NonRetryableExecutorException` is created with a staged builder.
Every value is required and is set in a fixed order, so the compiler only offers `build()` once all of them have been decided:

[source,java]
----
throw NonRetryableExecutorException
        .buildWith(badRequestException)                       // 1. the real error
        .withEvent("PAYMENT_DECLINED")                        // 2. the event recorded for this failure
        .reexposeOnUnexpectedCrash(Duration.ofMinutes(10))    // 3. the crash re-expose delay
        .compensateThisStep(true)                             // 4. compensation of the failing step
        .put("reason", "insufficient_funds")                  // optional, repeatable
        .build();
----

. **Real error** (`buildWith(...)`): the exception that caused the failure.
. **Event** (`withEvent(String)` or `withEvent(SagaExecutionEventName)`): the event recorded for this failure in the transaction history. Use `withDefaultEvent()` to record the framework's default error event.
. **Crash re-expose delay** (`reexposeOnUnexpectedCrash(Duration)`): how long the engine waits before it re-exposes the transaction if the instance crashes after this failure, before compensation has been handed over. Use `withDefaultReexposeOnUnexpectedCrash()` to apply the transaction's default restore-on-crash delay.
. **Compensation of the failing step** (`compensateThisStep(boolean)`): whether the failing step's own `doRevert()` runs when this failure happens on a re-execution of the step. See <<non_retryable_after_retry,Non-Retryable Failure After a Retry>>.
. **Metadata** (`put(key, value)`, optional): additional diagnostic details, available to listeners and compensating executors.

[IMPORTANT]
.Rollback Invariant: Non-Retryable Exceptions Forbidden in `doRevert()`
====
During compensation (`doRevert()`, `PreExecutor`, or `PostExecutor`), throwing unhandled non-retryable exceptions is prohibited because it would stall the rollback pipeline.
If an unrecoverable compensation error occurs that can be safely tolerated (e.g., account already closed):
1. Catch the exception and record diagnostic metadata in `context.revertHintStore().put("key", errorMsg)`.
2. Return `.success("REVERT_TOLERATED").asSync().noPause().toNextDefaultExecutor()` to permit rollback to proceed.
====

[[non_retryable_after_retry]]
=== Non-Retryable Failure After a Retry

When a `NonRetryableExecutorException` is thrown, the engine reverts the executors that completed *before* the failing one.
By default, the failing executor's own `doRevert()` is not part of that chain: a step that failed on its first attempt never completed, so there is nothing to undo.
One situation changes that.

==== The Scenario

A step can run more than once (see <<rule-idempotent-execution,Rule 2>>).
A transient failure (`RetryableExecutorException`) makes the engine invoke the same step again later, and the attempt that failed that way may *already have had an effect* on the remote service — for example, a timeout where the remote service applied the request but the response was lost.

. Attempt 1 calls the remote service and fails with a transient error. The engine schedules a retry.
. Attempt 2 of the same step fails with a *non-retryable* error (for example, the service now answers `400 Bad Request`).
. The transaction must now be compensated, but attempt 1 may have left an effect behind. Skipping the failing step's `doRevert()` would leave that effect in place.

A transient failure never starts compensation on its own.
The situation arises only for the sequence "one or more transient failures, then a non-retryable failure on the same step".

==== How StackSaga Handles It

The engine remembers whether a step was executed before the current attempt, and every `NonRetryableExecutorException` states with `compensateThisStep(boolean)` whether the failing step may be compensated (see <<building-non-retryable-exception,Building a `NonRetryableExecutorException`>>):

* If the step fails non-retryably on its *first* attempt, nothing was executed before, so its `doRevert()` is *not* run, whatever the value is. Compensation starts from the previous step.
* If the step fails non-retryably on a *re-execution* with `compensateThisStep(true)`, an earlier attempt may have had an effect, so the engine runs the failing step's own `doRevert()` *first*, and then continues in the normal reverse order.
* If the step fails non-retryably on a *re-execution* with `compensateThisStep(false)`, its `doRevert()` is *not* run. Use this for a step whose `doRevert()` must never run for its own failure.

[source,java]
----
throw NonRetryableExecutorException
        .buildWith(badRequestException)
        .withEvent("PAYMENT_DECLINED")
        .withDefaultReexposeOnUnexpectedCrash()
        .compensateThisStep(false)
        .build();
----

==== Writing a Safe `doRevert()`

Because `doRevert()` can be called for an attempt that was only *possibly* applied, write it so that it is safe in both cases:

* It must be idempotent (<<rule-idempotent-execution,Rule 2>>).
* It must tolerate a target that was never created — for example, treat "not found" as success.
* It must use `context.primaryExecutionIdempotencyKey()` — the key the forward attempts were submitted with — to address the same remote operation that the earlier attempt may have created.

== Guidelines for Creating Executors

When designing saga executors, follow these essential implementation best practices:

1. **One Executor = One Atomic Operation**: Never combine multiple external API or database writes in one executor (<<rule-one-atomic-transaction,Rule 1>>).
2. **Forward Idempotency Keys**: Always forward the engine-provided `idempotencyKey` to downstream services and handle already-processed requests idempotently (<<rule-idempotent-execution,Rule 2>>).
3. **Respect Invoker Immutability**: Never mutate `DomainEntity` inside `.asAsync().invoker(...)` or `.reactiveInvoker(...)` closures; state modifications belong strictly in the preparation phase.
4. **Enforce Event Naming Format**: Step event names must match the regex `^[A-Za-z0-9]+(?:_[A-Za-z0-9]+)*$` (e.g. `ORDER_CREATED`, `PAYMENT_AUTHORIZED`). Hyphens, spaces, and consecutive underscores (e.g. `ORDER__CREATED`) are rejected at runtime.
5. **Separate Continuous vs. Pausable Steps**: Keep initial request dispatches (pausing steps) and subsequent callback validations (resumed steps) cleanly separated in your saga topology.
6. **Tolerate Unrecoverable Rollback Errors**: Record diagnostic details in `context.revertHintStore()` rather than letting exceptions crash and stall compensating pipelines.

[[outbox-pattern-eliminated]]
== Why StackSaga Eliminates the Transactional Outbox Pattern

Developers coming from event-driven or choreography-based systems often ask how to implement the Transactional Outbox Pattern in StackSaga.
You do not need to: the <<conceptual-foundation,executor contract>> already gives the same guarantee, without the extra infrastructure.

=== The Dual-Write Problem

A service often has to do two things for one business action: write domain state to its database *and* publish an event to a message broker.
These are two different systems, so no single local transaction covers both.
If the service crashes after the database commit but before the publish, the state has changed but no one is told.

The Transactional Outbox Pattern solves this by writing the event into an `outbox` table in the same database transaction as the domain change, then running a separate relay process that reads the table and publishes its rows to the broker.
It works, but every service now owns an extra table, a relay process, and the retry and cleanup logic around them.

=== How the Executor Model Removes It

Under <<rule-one-atomic-transaction,Rule 1>>, the database write and the publish cannot share an executor.
They become two consecutive steps, each touching exactly one system:

[source,java]
----
// Step 1: writes to the local database only
@SagaExecutor(executeFor = "order-service", value = "saveOrderExecutor")
public class SaveOrderExecutor implements CommandExecutor<OrderDomainEntity> { ... }

// Step 2: publishes to the message broker only
@SagaExecutor(executeFor = "order-service", value = "publishOrderEventExecutor")
public class PublishOrderEventExecutor implements CommandExecutor<OrderDomainEntity> { ... }
----

`SaveOrderExecutor` returns `.toNextExecutor(PublishOrderEventExecutor.class)`, so the engine records that step 1 finished before step 2 is invoked.
No step contains a dual write any more: the gap between the two writes has become a step boundary that the engine tracks.

=== What Replaces the Outbox Machinery

[cols="1,1",options="header"]
|===
| Outbox Pattern | StackSaga
| `outbox` table written in the same transaction as the domain change | The Event Store, where the engine records the result of every step
| Custom relay or polling process | The built-in xref:retry-ring-coordinator:ring-coordinator.adoc[Retry Ring Coordinator], which resumes incomplete transactions
| Hand-written retry and cleanup logic | `RetryableExecutorException` and the transaction lifetime
| Manual undo when the publish can never succeed | `SaveOrderExecutor.doRevert()`, run by compensation
|===

A crash is covered on both sides of the step boundary:

* *Crash after step 1 is recorded*: the transaction resumes at `PublishOrderEventExecutor`; the order is not written again.
* *Crash before step 1 is recorded*: `SaveOrderExecutor` runs again. Because it forwards its `idempotencyKey` (<<rule-idempotent-execution,Rule 2>>), the repeated write does not create a second order.

=== Failure Behavior & Delivery Guarantee

* *Broker temporarily unavailable*: `PublishOrderEventExecutor` throws `RetryableExecutorException`, and the retry subsystem invokes it again within the xref:retry-ring-coordinator:disabled-and-terminated-transaction.adoc#transaction-lifetime[transaction lifetime].
* *Publish can never succeed* (for example, the broker rejects the message as invalid): the executor throws `NonRetryableExecutorException`, compensation starts, and `SaveOrderExecutor.doRevert()` undoes the database write.

Delivery is *at-least-once*, exactly as with an outbox relay: if the service crashes after the broker accepted the message but before the step was recorded, the message is published again.
Put the `idempotencyKey` in the message key or a header, and deduplicate on it in the consumer.

* To publish without waiting for a reply, see xref:stacksaga-sync/orchestrator/unified-saga-patterns.adoc#publish-without-waiting[Publishing an Event Without Waiting for a Reply].
* If the consumer replies to the orchestrator, use xref:stacksaga-sync/orchestrator/unified-saga-patterns.adoc#usip-pattern-3-two-stage-lazy-dispatch[Pattern 3: Two-Stage Lazy Dispatch], so the reply can never arrive before the step is recorded.
