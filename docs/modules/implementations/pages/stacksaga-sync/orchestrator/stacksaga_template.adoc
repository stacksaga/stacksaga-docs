= SagaTemplate and Event Listeners

[[stacksaga-template-usage]]
[[saga-template-usage]]
== SagaTemplate

`SagaTemplate` is the main entry point for interacting with the StackSaga engine (SEC) in an orchestrator service.
It provides a fluent builder API to initialize transactions, trigger execution (`fireAndForget`), and query the current state and execution history of any transaction.

`SagaTemplate` seamlessly supports both imperative (blocking) and reactive (non-blocking) application architectures.

[[stackSagaTemplate_usage_in_non_reactive_environment]]
[[sagaTemplate_usage_in_non_reactive_environment]]
=== SagaTemplate in a Non-Reactive Environment

In a traditional Spring MVC or blocking environment, use `SagaTemplate` to initiate saga transactions and retrieve transaction snapshots synchronously:

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class PlaceOrderHandler {

    private final SagaTemplate<OrderDomainEntity> sagaTemplate; //<1>

    public String handle(String username, double amount, List<String> items) {
        String transactionId = this.sagaTemplate
                //<2>
                .init(() -> {
                    OrderDomainEntity orderDomainEntity = new OrderDomainEntity();
                    {//initializing the domain entity with the required properties for the saga execution.
                        orderDomainEntity.setUsername(username);
                        orderDomainEntity.setTotalAmount(amount);
                        //...
                    }
                    return orderDomainEntity;
                })
                //<3>
                .peek(orderDomainEntity -> {
                    log.info("transactionId {}:", orderDomainEntity.getTransactionId());
                })
                //<4>
                .startWith(ValidateUserExecutor.class)
                //<5>
                .fireAndForget()
                //<6>
                .execute();
        log.info("Started place order saga with transactionId: {}", transactionId);
        return transactionId;
    }

    public void printCurrentState(String transactionId) {
        TransactionState<OrderDomainEntity, SyncExecutionEvent<OrderDomainEntity>> state = this
                .sagaTemplate
                //<7>
                .getCurrentState(transactionId)
                .fetch();

        TransactionCompleteStatus currentStatus = state.getCurrentStatus(); //<8>
        log.info("Current status of transaction {}: {}", transactionId, currentStatus);
        NavigableMap<Integer, ? extends SyncExecutionEvent<OrderDomainEntity>> executionHistory = state.getExecutionHistory(); //<9>
        log.info("Execution history of transaction {}: {}", transactionId, executionHistory);
        OrderDomainEntity currentDomainEntity = state.getCurrentDomainEntity(); //<10>
        log.info("Current domain entity state: {}", currentDomainEntity); //<11>
        ZonedDateTime startedDateTime = state.getStartedDateTime(); //<12>
        log.info("Transaction {} started at: {}", transactionId, startedDateTime.toLocalDateTime());
    }
}
----

<1> Inject `SagaTemplate` configured for your custom xref:stacksaga-sync/orchestrator/domain-entity.adoc#creating_custom_domain_entity[`DomainEntity`] type.
<2> Use `init()` to provide a `Supplier` creating the initial `DomainEntity`. The framework generates and assigns the unique `transactionId` during initialization.
<3> Use `peek()` (optional) to inspect or enrich the initialized `DomainEntity` before execution begins.
<4> Use `startWith()` to specify the initial xref:stacksaga-sync/orchestrator/executor_architecture.adoc[executor] that starts the transaction flow.
<5> Use `fireAndForget()` to select the fire-and-forget execution mode.
<6> Call `execute()` to initiate the transaction in a blocking manner. It returns the generated `transactionId` once initialized.
<7> Call `getCurrentState(transactionId).fetch()` to retrieve a synchronous snapshot of the transaction state from the event-store.
<8> Retrieve the overall completion status (`TransactionCompleteStatus`) of the transaction.
<9> Retrieve the chronological execution history (`NavigableMap<Integer, ? extends SyncExecutionEvent<DE>>`) containing every executed span (primary and compensation) with metadata and status.
<10> Retrieve the current domain entity snapshot representing all state mutations applied up to this point.
<11> Log the domain entity snapshot.
<12> Retrieve the start timestamp of the transaction.

NOTE: For real-time updates without polling, implement a xref:#event_listener_for_stage_change_events[State Change Listener].

=== SagaTemplate in a Reactive Environment

In a reactive environment (e.g., Spring WebFlux), `SagaTemplate` provides non-blocking operators across all lifecycle phases.

Calling `.fireAndForget().executeAsync()` hands the transaction off to the StackSaga engine in a non-blocking manner and returns a `Mono<String>` emitting the generated transaction ID once initialized:

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class PlaceOrderHandler {

    private final SagaTemplate<OrderDomainEntity> sagaTemplate;

    public Mono<String> handle(String username, double amount, List<String> items) {
        return this.sagaTemplate
                .init(() -> {
                    OrderDomainEntity orderDomainEntity = new OrderDomainEntity();
                    {//initializing the domain entity with the required properties for the saga execution.
                        orderDomainEntity.setUsername(username);
                        orderDomainEntity.setTotalAmount(amount);
                        //...
                    }
                    return orderDomainEntity;
                })
                .peek(orderDomainEntity -> {
                    log.info("transactionId {}:", orderDomainEntity.getTransactionId());
                })
                .startWith(ValidateUserExecutor.class)
                .fireAndForget()
                //<1>
                .executeAsync()
                .map(transactionId -> "Order placed successfully with transaction id: " + transactionId);
    }
}
----

<1> `executeAsync()` returns a `Mono<String>` that emits the transaction ID once the saga is initialised. The transaction continues running in the background; use `getCurrentState(transactionId).fetchAsync()` or the xref:#event_listener_for_stage_change_events[EventListener] to track its progress.

[[resuming-paused-transactions]]
=== Resuming Paused Transactions (Pausable LRT)

When a saga executor participates in a *xref:stacksaga-sync/index.adoc#pausable-lrt[Pausable Long-Running Transaction]* and delegates to an external asynchronous service (such as an asynchronous payment provider or human restaurant order confirmation), it intentionally halts forward execution by returning xref:stacksaga-sync/orchestrator/executor_architecture.adoc#stepManager_pause[`stepManager.pauseUntilResume(...)`].
Similarly, when a compensation step must undo a transaction via an asynchronous gateway or banking transfer, it halts compensation by returning xref:stacksaga-sync/orchestrator/executor_architecture.adoc#pausable-compensation[`stepManager.pauseUntilResume(...)`]. See xref:stacksaga-sync/index.adoc#dual-flow-pausable-lrt[Dual-Flow Pausable Workflows] for the conceptual background.

At the moment of pausing, the transaction enters an intentional business wait state:

* The `DomainEntity` state is persisted to the Event Store.
* The orchestrator marks the transaction as paused and registers the active correlation token (generated and accessible during execution via `stepManager.getResumeKey()`).
* CPU worker threads and database connections are freed immediately.

[NOTE]
====
**Retrieving the Resume Key:**  
During forward execution (`doProcess`) or compensation (`doRevert`), the executor invokes `stepManager.getResumeKey()` to obtain the unique correlation token. This token encapsulates the transaction ID and step idempotency metadata (e.g., `transactionId:idempotencyKey`). Pass this key to external webhooks, asynchronous payment providers, or message broker headers so that the callback can supply it back upon completion.
====

To wake up and continue the transaction once the external system completes its task, `SagaTemplate` provides the `resume(...)` operator.

[[fluent-resume-spec]]
==== The Fluent `ResumeSpec` Builder API

Calling `sagaTemplate.resume(resumeKey, retentionDuration)` returns a `SagaTemplate.ResumeSpec<DE>` fluent builder that configures callback metadata and initiates transaction resumption:

[source,java]
----
// Resuming synchronously with fluent key-value context entries:
this.sagaTemplate
        .resume(resumeKey, Duration.ofMinutes(15))
        .put("status", "SUCCESS")
        .put("gatewayReference", "REF-987654")
        .execute(); // Blocking (Spring MVC)

// Reactive non-blocking resumption:
Mono<Void> resumeMono = this.sagaTemplate
        .resume(resumeKey, Duration.ofMinutes(15))
        .put("status", "SUCCESS")
        .put("gatewayReference", "REF-987654")
        .executeAsync(); // Reactive (Spring WebFlux)
----

`sagaTemplate.resume(...)` requires two parameters:

* **`resumeKey`** (`String`): The unique correlation key that was generated for the paused span (retrieved via `stepManager.getResumeKey()`). It uniquely identifies the paused transaction and tryout checkpoint in the event store.
* **`retentionDuration`** (`Duration`): The duration to retain the transaction without being exposed for restoring by the Ring Coordinator's scheduled recovery workers (e.g., `Duration.ofMinutes(15)` or `Duration.ofHours(1)`). In case of an unexpected system termination during resumption, the transaction will be exposed for restoring only after this retention duration has elapsed.

`ResumeSpec<DE>` exposes the following fluent methods:

* **`.put(String key, String value)`**: Adds an individual key-value entry to the `ResumeContext`.
* **`.putAll(Map<String, String> map)`**: Adds all entries from the specified map to the `ResumeContext`.
* **`.withContext(ResumeContext resumeContext)`**: Supplies or replaces a pre-built `ResumeContext` (e.g., from `DefaultResumeContext.of(map)`).
* **`.execute()`**: Synchronously blocks until the transaction is resumed by the engine (for Spring MVC / imperative environments). Throws `InvalidTransactionResumeKeyException` if the resume key is invalid or unrecognized. Throws `IllegalStateException` if invoked from a non-blocking Reactor/Netty event-loop thread.
* **`.executeAsync()`**: Returns a `Mono<Void>` that completes asynchronously once resumption is processed (for Spring WebFlux / reactive environments). Signals `InvalidTransactionResumeKeyException` via `onError` if invalid.

NOTE: A convenient overloaded shortcut is also available: `sagaTemplate.resume(resumeKey, resumeContext, retentionDuration).execute()`.

[[uniform-resumption]]
==== Uniform Resumption: Seamless Handling of Forward and Compensation Flows

A major strength of StackSaga's architecture is that **resumption is completely uniform from the orchestrator's perspective**:

* You invoke the exact same method -- `sagaTemplate.resume(resumeKey, retentionDuration)` -- whether the saga paused during forward execution (`doProcess`) or during backward compensation (`doRevert`).
* The StackSaga Execution Coordinator (SEC) queries the Event Store, resolves the `resumeKey`, determines the transaction lifecycle status (`PROCESSING` vs `REVERTING`), restores the domain entity snapshot up to the paused checkpoint, clears the wait-state markers, and dispatches execution:
** **If paused in forward flow**: Advances to the target `NextExecutor` designated by xref:stacksaga-sync/orchestrator/executor_architecture.adoc#usage-2-pausable-lrt[`stepManager.success(...).asSync().pauseUntilResume(duration).resumeToNextExecutor(NextExecutor.class)`] (or `asAsync()`), invoking its `doProcess(...)` with the supplied `ResumeContext`.
** **If paused in compensation flow**: Re-invokes the paused `CommandExecutor`'s `doRevert(...)` with the supplied `ResumeContext`, allowing it to finalize reversal actions. See xref:stacksaga-sync/orchestrator/executor_architecture.adoc#pausable-compensation[Implementing Pausable Compensation].

[[callback-controller-pattern]]
==== Webhook / Callback Controller Pattern

The following example demonstrates how Spring REST controllers handle external callbacks for both forward business approvals and compensating refund confirmations:

===== Imperative Callback Controller (Spring MVC)

[source,java]
----
@Slf4j
@RestController
@RequestMapping("/orders/callbacks")
@RequiredArgsConstructor
public class OrderCallbackController {

    private final SagaTemplate<OrderDomainEntity> sagaTemplate;

    /**
     * Resumes forward execution (e.g., food preparation completed or 3D-Secure charge confirmed).
     */
    @PostMapping("/order-ready")
    public ResponseEntity<Void> onOrderReadyCallback(@RequestBody OrderReadyCallbackDto callbackDto) {
        log.info("Received order-ready callback for resumeKey: {}", callbackDto.getResumeKey());

        this.sagaTemplate
                .resume(callbackDto.getResumeKey(), Duration.ofMinutes(15))
                .put("kitchenStatus", callbackDto.getKitchenStatus())
                .put("readyTimestamp", callbackDto.getReadyTimestamp().toString())
                .execute();

        return ResponseEntity.ok().build();
    }

    /**
     * Resumes compensating execution (e.g., payment gateway asynchronous refund confirmation).
     */
    @PostMapping("/refund-confirmed")
    public ResponseEntity<Void> onRefundConfirmed(@RequestBody RefundWebhookDto refundDto) {
        log.info("Received refund webhook for resumeKey: {}", refundDto.getResumeKey());

        this.sagaTemplate
                .resume(refundDto.getResumeKey(), Duration.ofHours(1))
                .put("refundStatus", refundDto.getRefundStatus())
                .put("gatewayRefundRef", refundDto.getGatewayRefundReference())
                .execute();

        return ResponseEntity.ok().build();
    }
}
----

===== Reactive Callback Controller (Spring WebFlux)

[source,java]
----
@Slf4j
@RestController
@RequestMapping("/orders/callbacks")
@RequiredArgsConstructor
public class ReactiveOrderCallbackController {

    private final SagaTemplate<OrderDomainEntity> sagaTemplate;

    @PostMapping("/refund-confirmed")
    public Mono<ResponseEntity<Void>> onRefundConfirmed(@RequestBody Mono<RefundWebhookDto> refundDtoMono) {
        return refundDtoMono
                .flatMap(dto -> {
                    log.info("Received reactive refund webhook for resumeKey: {}", dto.getResumeKey());

                    return this.sagaTemplate
                            .resume(dto.getResumeKey(), Duration.ofHours(1))
                            .put("refundStatus", dto.getRefundStatus())
                            .put("gatewayRefundRef", dto.getGatewayRefundReference())
                            .executeAsync()
                            .thenReturn(ResponseEntity.ok().<Void>build());
                });
    }
}
----

When `resume(...)` is called:

. StackSaga resolves the `resumeKey`, validating and correlating the callback to the exact transaction ID and execution checkpoint registered in the Event Store.
. It durably records the serialized `ResumeContext` payload in the Event Store for complete auditing and tracing.
. It clears the transaction wait-state, ensuring subsequent duplicate callbacks with the same resume key are rejected.
. It restores the `OrderDomainEntity` with its pristine checkpoint state.
. It invokes the target executor's `doProcess(...)` or `doRevert(...)`, injecting the populated `ResumeContext`. See xref:stacksaga-sync/orchestrator/executor_architecture.adoc#usage-2-pausable-lrt[Pausable Long-Running Transactions in Executor Architecture] for how executors consume this data.

[[resume-context-contract]]
==== `ResumeContext` API & Contract

`ResumeContext` (`org.stacksaga.api.ResumeContext`) is the contract through which external callback data flows into executors:

* **Key-Value Store**: Implements `java.util.Map<String, String>` and `Serializable`.
* **Value Extraction (`get`)**: Provides `Optional<String> get(String key)` for safe retrieval:
+
[source,java]
----
String refundStatus = resumeContext.get("refundStatus").orElse("FAILED");
----

* **Immutability Guarantee**: Once passed into an executor (`doProcess` or `doRevert`), the `ResumeContext` is marked read-only. Calling modifying operations (`put`, `remove`, `clear`) throws `UnsupportedOperationException`. This prevents executors from accidentally mutating callback audit records.
* **Serialization & Event Sourcing**: Provides `prettyPrintAsString(ApplicationContext)` and `printAsString(ApplicationContext)` using the framework's configured JSON mapper bean.
* **Deep Comparison**: Provides `deepEquals(ResumeContext obj, ApplicationContext applicationContext)` for structural JSON equality checks.
* **Event Store Durability**: Durably serialized and recorded in the underlying Event Store, providing an immutable audit trail for every callback payload received by the system. See xref:stacksaga-sync/index.adoc#resume-context-concept[Decoupling External Callback Payloads].

[[pausable-lrt-timeout-reexecution]]
=== Timeout Re-Execution Mechanics (When No Callback Arrives)

When an executor pauses with a maximum duration (e.g., `stepManager.success("ORDER_PREPARING").asSync().pauseUntilResume(Duration.ofHours(5)).resumeToNextExecutor(DeliveryDispatchExecutor.class)`), the application expects an external callback to trigger `sagaTemplate.resume(...)` before the 5 hours expire.

However, in worst-case scenarios where the external system crashes, network connectivity is lost, or the callback is never delivered within the configured timeout:

* **Why the Framework Re-Executes the Paused Executor:**
The framework **cannot forcibly advance** to the next executor (`DeliveryDispatchExecutor`) because the downstream business operation was never confirmed.
Furthermore, the logic required to invoke the external target service, verify order or payment status, and initiate callbacks resides **inside that paused executor**.
Therefore, StackSaga's retry coordinator re-executes the transaction directly from the executor where it was paused (`MakePaymentExecutor`), even though its primary execution had previously succeeded before entering the pause.

* **Re-Invocation Flow:**
Upon timeout expiration, the retry coordinator claims ownership of the stalled transaction, safely reconstructs the pristine `DomainEntity` up to the checkpoint prior to that executor, and invokes `doProcess(...)` again. This gives the executor an opportunity to query the external system's status (e.g., checking if the payment went through), re-trigger the external call, or throw `NonRetryableExecutorException` to initiate compensation.

* **Impact on State Listeners:**
Because the paused executor is executed again, this directly affects registered state change listeners. See the detailed guidance in xref:#at-least-once-listener-semantics[At-Least-Once Notification in Pausable LRT] below.

[[event_listener_for_stage_change_events]]
== Observing Transaction State Changes

After initiating a transaction via `execute()` or `executeAsync()`, the StackSaga engine executes each step sequentially (forward commands/queries and backward compensations).

There are two distinct mechanisms to observe state changes:

. *xref:#state-change-listeners[State Change Listeners]* -- Push-based: The engine notifies your listener callback automatically after each executor step completes. Best for real-time reactions such as dispatching notifications, updating caches, or emitting events.
. *xref:#getcurrentstate-on-demand[`SagaTemplate.getCurrentState()`]* -- Pull-based: Queries the event-store on demand to retrieve the latest state snapshot for a given transaction ID. Best for user-facing status queries and post-completion audits.

[[state-change-listeners]]
=== Using State Change Listeners (Real-time)

State Change Listeners receive push notifications directly from the engine after every executor span completes (both forward execution and compensations).

Choose the listener interface matching your application architecture:

. `TransactionEventListener` -- For imperative / blocking environments.
. `ReactiveTransactionEventListener` -- For reactive / non-blocking environments.

[IMPORTANT]
====
*Sequential Execution and Latency Impact:*

The `onStateChanged` callback is executed sequentially as part of the transaction lifecycle.
Specifically, **the next span/executor step in the saga flow is triggered only after the current `onStateChanged` execution has completed**.

Performing heavy computations, slow I/O calls, or long-running operations inside `onStateChanged` directly blocks the progression of the transaction and increases total transaction latency.

*Best Practice:*
Keep `onStateChanged` lightweight (e.g., publishing a quick notification or logging status). If you need to perform heavy or time-consuming operations, offload the work to an asynchronous thread pool (using a snapshot or deep copy of `TransactionState` if needed), allowing the engine to immediately proceed with the next span of the transaction.
====

[[at-least-once-listener-semantics]]
[WARNING]
.Crucial: Atomicity, the Crash Window, and the Two Failure Hazards of Placing Business Logic in Listeners
====
While `TransactionEventListener` and `ReactiveTransactionEventListener` logically receive at-least-once notifications during normal workflow progression, developers must understand the technical lifecycle boundaries, the Event Store commit barrier, and failure semantics to avoid critical architectural bugs:

*1. The Atomicity Mandate: Why the Engine Persists State BEFORE Invoking Listeners*

A fundamental design invariant of the StackSaga Execution Coordinator (SEC) is: **The SEC immutably persists the executor's state transition and domain snapshot to the Event Store BEFORE invoking the `onStateChanged` listener callback.**

To understand why this sequence is mandatory, consider what would happen if the engine violated this rule and invoked the listener *before* persisting to the Event Store:

* Suppose the listener runs first and executes external side-effects (e.g. sending a customer SMS, email, or webhook confirmation: *"Your payment of $100 succeeded! Order #123 is confirmed"*).
* The user's phone receives the notification.
* A millisecond later, before the database write commits (or while the write is in progress), the JVM process suffers an Out-Of-Memory (OOM) kill, a node eviction, or a database connection timeout.
* **The Catastrophic Inconsistency (Phantom Notification):** When the cluster recovers, the Event Store contains **no record** of that payment or order confirmation. From the system's perspective, the step never happened (or will be rolled back). Yet the customer has already received an authoritative confirmation of success! This represents a total breach of atomicity and consistency.

Therefore, StackSaga enforces that **no step is considered complete until it is durably committed to disk in the Event Store**. The Event Store Commit Barrier must always precede listener notification.

*2. The Resulting Crash Window & The Silent Omission Hazard*

Because the Event Store commit barrier *must* precede listener execution to guarantee atomicity, there is an unavoidable physical window in distributed computing:

[source,text]
----
[1. Executor doProcess()] ──► [2. Event Store Commit Barrier] ──► [3. onStateChanged()] ──► [4. Next Executor]
                                                                     ▲
                                                        CRASH WINDOW: If JVM dies here,
                                                        Executor A is COMMITTED in Event Store.
                                                        On restore, saga resumes directly at [4]!
----

If the JVM process crashes (e.g. OOM kill, hardware fault, pod eviction, host power cut) immediately after step 2 or while step 3 is executing:

* The Event Store has already durably recorded that Executor A succeeded and committed its milestone snapshot.
* When the Retry-Node or dead-man's switch restore worker detects the stalled transaction and restores it, it inspects the Event Store and determines that Executor A is already `COMMITTED`.
* Consequently, the engine resumes transaction execution directly from **Executor B (the Next Executor)**.
* The framework **does NOT re-invoke the listener** for the already-committed Executor A!
* If a developer placed critical business logic inside `onStateChanged` (such as generating an invoice, decrementing another resource, or notifying a downstream ledger), **that critical invocation is permanently lost and will never execute**, without triggering any retry or compensation.

*3. Summary: The Two Failure Hazards of Listeners*

Placing business logic, financial operations, or state mutations in an event listener exposes the system to two complementary hazards:

[arabic]
. *Hazard 1: At-Least-Once Duplication (Timeout Re-Executions)* +
In a xref:#pausable-lrt-timeout-reexecution[Pausable LRT], if an executor pauses awaiting an external callback with a timeout `Duration` (e.g. 5 hours), the listener callback (`onStateChanged`) can be invoked **multiple times** for that same executor (once when entering the pause, and again upon timeout re-execution if no callback arrives). Non-idempotent logic will execute redundantly.
. *Hazard 2: Zero-Invocation Omission (The JVM Crash Window)* +
If the application crashes after the executor commits but before the listener completes, the listener will be invoked **zero times** for that attempt upon cluster restoration. Non-skippable logic will be dropped permanently.

*4. The Architectural Solution: The Re-Invokable Executor Pattern (`QueryExecutor` / `CommandExecutor`)*

If an invocation must run definitely as part of the Long-Running Transaction and must **never be skipped under any circumstance (including application crashes)**:

* **Rule 1: Never execute transactional or critical business logic inside `TransactionEventListener`.** Listeners are strictly reserved for ephemeral, non-transactional observations (pushing Prometheus metrics, emitting debug logs, or sending best-effort UI WebSocket updates).
* **Rule 2: Model and chain the invocation as a formal Executor as the immediate next step in your saga flow.**
** *If the operation is non-compensable* (e.g. creating an internal invoice, recording an immutable audit ledger, reading verification data, or dispatching a non-rollbackable receipt): implement it as a formal **`QueryExecutor`** (e.g. `stepManager.success("ORDER_PROCESSED").asSync().noPause().toNextExecutor(CreateInvoiceQueryExecutor.class)`).
** *If the operation is state-changing and requires rollback on failure*: implement it as a formal **`CommandExecutor`** with an appropriate `doRevert()` compensation method.

*Why Executors Guarantee Non-Skippability & Durability:*

. **Re-Invokable by Default:** Executors are first-class saga participants. If the JVM crashes before, during, or after an executor, StackSaga's Event Store and xref:retry-ring-coordinator:transaction-retrying-with-retry-coordinator.adoc#retry-node[Retry Subsystem] detect the uncommitted state, restore the pristine `DomainEntity` snapshot, and re-invoke the executor deterministically until completion.
. **Automatic Rollback Pruning for `QueryExecutor`:** Because `QueryExecutor` does not implement `doRevert()`, StackSaga's Reverse Autopilot automatically skips and prunes it during rollback (see xref:stacksaga-sync/orchestrator/unified-saga-patterns.adoc#usnp-query-pruning[USNP Query Pruning Pattern]). It provides durability without complicating the compensation path.
. **Trace Window Observability:** Unlike logic hidden inside listeners, every Executor span is fully visible in the xref:trace-window:stacksaga-trace-window.adoc[Trace Window] dashboard—including execution latency, domain entity snapshots before and after execution, and transient retry attempts.

==== TransactionEventListener

Implement `TransactionEventListener` to listen to transaction events in an imperative environment:

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class PlaceOrderHandler implements TransactionEventListener<OrderDomainEntity> {

    @Override
    public void onStateChanged(TransactionState<OrderDomainEntity, SyncExecutionEvent<OrderDomainEntity>> state) {
        TransactionCompleteStatus currentStatus = state.getCurrentStatus();
        log.info("Current status of transaction: {}", currentStatus);
        NavigableMap<Integer, ? extends SyncExecutionEvent<OrderDomainEntity>> executionHistory = state.getExecutionHistory();
        log.info("Execution history of transaction: {}", executionHistory);
        OrderDomainEntity currentDomainEntity = state.getCurrentDomainEntity();
        log.info("Current domain entity state: {}", currentDomainEntity);
        ZonedDateTime startedDateTime = state.getStartedDateTime();
        log.info("Transaction started at: {}", startedDateTime.toLocalDateTime());
    }
}
----

NOTE: Because `onStateChanged` is synchronous, blocking user code, the engine invokes it on a dedicated bounded-elastic scheduler (`blockingExecutionScheduler`) supplied by `AbstractSchedulerProvider`. This isolates listener execution from the engine's core reactive threads. The thread cap, queue capacity, and TTL can be tuned via the `stacksaga.scheduler.blocking-execution.*` configuration properties. See xref:stacksaga-sync/orchestrator/properties.adoc[Configuration Properties].

==== ReactiveTransactionEventListener

Implement `ReactiveTransactionEventListener` to listen to transaction events in a reactive environment:

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class ReactivePlaceOrderHandler implements ReactiveTransactionEventListener<OrderDomainEntity> {

    @Override
    public Mono<Void> onStateChanged(TransactionState<OrderDomainEntity, SyncExecutionEvent<OrderDomainEntity>> transactionState) {
        return Mono
                .just(transactionState)
                .doOnNext(state -> {
                    TransactionCompleteStatus currentStatus = state.getCurrentStatus();
                    log.info("Current status of transaction: {}", currentStatus);
                    NavigableMap<Integer, ? extends SyncExecutionEvent<OrderDomainEntity>> executionHistory = state.getExecutionHistory();
                    log.info("Execution history of transaction: {}", executionHistory);
                    OrderDomainEntity currentDomainEntity = state.getCurrentDomainEntity();
                    log.info("Current domain entity state: {}", currentDomainEntity);
                    ZonedDateTime startedDateTime = state.getStartedDateTime();
                    log.info("Transaction started at: {}", startedDateTime.toLocalDateTime());
                })
                .flatMap(state -> {
                    // simulate async non-blocking processing
                    return Mono.delay(Duration.ofSeconds(1)).then();
                });
    }
}
----

NOTE: Unlike `TransactionEventListener`, `ReactiveTransactionEventListener#onStateChanged` runs on the shared non-blocking `executionScheduler`. The returned `Mono<Void>` must be fully non-blocking; any blocking calls will starve worker threads and affect other concurrent transactions. Parallelism can be tuned via `stacksaga.scheduler.execution.parallelism`. See xref:stacksaga-sync/orchestrator/properties.adoc[Configuration Properties].

[[getcurrentstate-on-demand]]
=== Using SagaTemplate.getCurrentState() (On-demand)

`SagaTemplate.getCurrentState(String transactionId)` provides pull-based access to the complete state snapshot and execution history of any transaction by its ID.

Calling `getCurrentState(transactionId)` returns a `SagaTemplate.StateSpec<DE>` specification that provides two methods:

* **`fetch()`** -- Synchronous retrieval returning `TransactionState<DE, SyncExecutionEvent<DE>>`.
+
[WARNING]
====
Do not call `fetch()` on non-blocking Reactor or Netty event loop threads. The method performs a thread check (`Schedulers.isInNonBlockingThread()`) and throws an `IllegalStateException` if invoked from a non-blocking thread. In reactive applications, always use `fetchAsync()`.
====

* **`fetchAsync()`** -- Asynchronous retrieval returning `Mono<TransactionState<DE, SyncExecutionEvent<DE>>>`. Safe for use in Spring WebFlux and reactive event-loop threads.

==== Blocking State Retrieval (Imperative / Spring MVC)

[source,java]
----
TransactionState<OrderDomainEntity, SyncExecutionEvent<OrderDomainEntity>> state = 
        this.sagaTemplate
                .getCurrentState(transactionId)
                .fetch();

TransactionCompleteStatus status = state.getCurrentStatus();
NavigableMap<Integer, ? extends SyncExecutionEvent<OrderDomainEntity>> history = state.getExecutionHistory();
OrderDomainEntity entity = state.getCurrentDomainEntity();
----

==== Reactive State Retrieval (Reactive / Spring WebFlux)

[source,java]
----
Mono<TransactionState<OrderDomainEntity, SyncExecutionEvent<OrderDomainEntity>>> stateMono = 
        this.sagaTemplate
                .getCurrentState(transactionId)
                .fetchAsync();

stateMono.subscribe(state -> {
    log.info("Transaction status: {}", state.getCurrentStatus());
});
----

NOTE: Unlike State Change Listeners which receive pushed state events in memory as execution proceeds, `getCurrentState(transactionId)` queries the underlying event-store on every call. It is designed for on-demand queries, rather than high-frequency polling during active execution.

[[recommended-handler-pattern]]
== Recommended Handler Pattern

The StackSaga team recommends organizing saga transaction logic inside a dedicated `Handler` component that encapsulates transaction initiation, state queries, and lifecycle event observation.

=== Imperative Handler Pattern

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class PlaceOrderHandler implements TransactionEventListener<OrderDomainEntity> {

    private final SagaTemplate<OrderDomainEntity> sagaTemplate;

    public String handle(String username, double amount, List<String> items) { //<1>
        return this.sagaTemplate
                .init(() -> {
                    OrderDomainEntity orderDomainEntity = new OrderDomainEntity();
                    orderDomainEntity.setUsername(username);
                    orderDomainEntity.setTotalAmount(amount);
                    return orderDomainEntity;
                })
                .startWith(ValidateUserExecutor.class)
                .fireAndForget()
                .execute();
    }

    public CustomOrderStatusView getCurrentState(String orderId) { //<2>
        TransactionState<OrderDomainEntity, SyncExecutionEvent<OrderDomainEntity>> state = this
                .sagaTemplate
                .getCurrentState(orderId)
                .fetch();
        return new CustomOrderStatusView(state);
    }

    @Override
    public void onStateChanged(TransactionState<OrderDomainEntity, SyncExecutionEvent<OrderDomainEntity>> transactionState) { //<3>
        log.info("Transaction {} updated to status {}", 
                transactionState.getTransactionId(), 
                transactionState.getCurrentStatus());
    }
}
----

<1> The `handle` method initiates the saga transaction using `SagaTemplate` and returns the generated transaction ID.
<2> Retrieve the current transaction state on demand using `.getCurrentState(orderId).fetch()`.
<3> Implement `onStateChanged` from `TransactionEventListener` to handle real-time lifecycle notifications.

=== Reactive Handler Pattern

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class ReactivePlaceOrderHandler implements ReactiveTransactionEventListener<OrderDomainEntity> {

    private final SagaTemplate<OrderDomainEntity> sagaTemplate;

    public Mono<String> handle(String username, double amount, List<String> items) { //<1>
        return this.sagaTemplate
                .init(() -> {
                    OrderDomainEntity orderDomainEntity = new OrderDomainEntity();
                    orderDomainEntity.setUsername(username);
                    orderDomainEntity.setTotalAmount(amount);
                    return orderDomainEntity;
                })
                .startWith(ValidateUserExecutor.class)
                .fireAndForget()
                .executeAsync();
    }

    public Mono<CustomOrderStatusView> getCurrentState(String orderId) { //<2>
        return this.sagaTemplate
                .getCurrentState(orderId)
                .fetchAsync()
                .map(CustomOrderStatusView::new);
    }

    @Override
    public Mono<Void> onStateChanged(TransactionState<OrderDomainEntity, SyncExecutionEvent<OrderDomainEntity>> transactionState) { //<3>
        return Mono.fromRunnable(() -> 
                log.info("Transaction {} updated to status {}", 
                        transactionState.getTransactionId(), 
                        transactionState.getCurrentStatus())
        );
    }
}
----

<1> Non-blocking transaction initiation returning `Mono<String>` with the transaction ID.
<2> Non-blocking state query using `.getCurrentState(orderId).fetchAsync()`.
<3> Implement `onStateChanged` from `ReactiveTransactionEventListener` returning `Mono<Void>` for non-blocking event handling.

[[advanced-architectural-faq]]
== Advanced Architectural FAQ & Production Edge Cases

In distributed systems, workflow implementations often rely on intuitive assumptions that break down under real-world production conditions (such as network latency, late callbacks, pod evictions, and infrastructure timeouts).
The following Q&A addresses six critical, real-world edge cases to help architects and developers design resilient, bug-free sagas before encountering these scenarios in production.

=== Q1: Can an executor action (`doProcess()` or `doRevert()`) be re-invoked even after being marked as success?

*Yes.* In a xref:stacksaga-sync/index.adoc#pausable-lrt[Pausable Long-Running Transaction] where an executor enters a wait-state via `stepManager.pauseUntilResume(duration)`, the executor's initial execution is marked as `SUCCESS` and the transaction enters `PAUSED` status.

However, if the external callback (e.g. payment gateway webhook or courier confirmation) fails to arrive before the configured `duration` expires:
* The framework **cannot advance** to the next executor because the business operation remains unconfirmed.
* Furthermore, the domain logic to query the external system's status or re-trigger the call resides **inside that paused executor**.
* Therefore, the StackSaga xref:retry-ring-coordinator:transaction-retrying-with-retry-coordinator.adoc#retry-node[Retry Subsystem] re-executes the transaction directly from the executor where it was paused, **even though its initial execution previously succeeded before entering the pause**. See xref:#pausable-lrt-timeout-reexecution[Timeout Re-Execution Mechanics].

*Architectural Takeaway:* Any executor that returns `.pauseUntilResume(...)` must implement its `doProcess()` (or `doRevert()`) idempotently, so that a timeout re-execution does not generate duplicate business side-effects.

=== Q2: What happens if an external callback arrives after the wait-state timeout has expired, and how should duration be tuned?

When configuring a wait-state via `stepManager.pauseUntilResume(Duration duration)`, developers should tune the validity period based on the expected turnaround SLA and real-world response behavior of the target external system (e.g. 15 minutes for customer 3D-Secure redirects, 2 hours for restaurant kitchen preparation, or 24 hours for asynchronous bank clearing).

If the timeout duration expires before the callback arrives:
. The Retry Subsystem re-invokes the paused executor.
. When re-invoked, the executor may re-query or re-call the target service using the **exact same deterministic `resumeKey` / `idempotencyKey`** generated for that span, allowing the downstream system to match the operation idempotently.
. If a late callback arrives while re-invocation is underway or after compensation has commenced, `sagaTemplate.resume(resumeKey, retentionDuration)` may detect that the active resume token has expired or transitioned.

*Best Practice Recommendation:* Webhook controllers should handle late callbacks flexibly according to partner integration policies. Rather than throwing unhandled exceptions that cause third-party gateways to retry endlessly, controllers can inspect the current transaction state via `sagaTemplate.getCurrentState(orderId).fetch()` and acknowledge the callback (e.g. returning HTTP 200/202 with an informational audit log).

=== Q3: Why do in-memory field mutations on `DomainEntity` disappear upon timeout re-execution?

StackSaga enforces the **Event Sourcing** paradigm. State transitions are committed immutably to the Event Store only at completed execution milestones.

If an executor mutates in-memory fields on `currentDomainEntity` inside `doProcess()` and pauses, but the wait-state times out without a callback:
* The engine **discards all uncommitted in-memory mutations** from that paused tryout.
* Upon re-invocation, the engine reconstructs the `DomainEntity` cleanly from the Event Store up to the exact checkpoint preceding this executor (see xref:stacksaga-sync/index.adoc#pristine-state-restoration[Pristine State Restoration]).

*Architectural Takeaway:* Never rely on ephemeral in-memory object state across retries or pauses. Only domain state committed to the Event Store through successful tryout barriers is preserved.

=== Q4: Can `doRevert()` throw `NonRetryableExecutorException`? What happens if compensation encounters an error?

*No.* In StackSaga, `NonRetryableExecutorException` is **strictly forbidden in `doRevert()`** (see xref:ROOT:non_retryable_executor_exception.adoc[NonRetryableExecutorException]). Compensating transactions are allowed to throw `RetryableExecutorException` only.

*The Architectural Rationale:* In the Saga pattern, there is no compensation for a compensation. If a forward step fails, backward rollback must run until completion to guarantee eventual consistency.
* **Transient Rollback Errors:** If a downstream service is temporarily unavailable during compensation, throwing `RetryableExecutorException` pauses the rollback, and the Retry Subsystem will automatically re-attempt `doRevert()`.
* **Permanent Rollback Errors (The Risk):** If an unhandled `RuntimeException` occurs in `doRevert()`, the saga becomes a xref:retry-ring-coordinator:disabled-and-terminated-transaction.adoc#terminated-transactions[Terminated Transaction] (permanently frozen in partial compensation). The issue must be investigated and resolved via the xref:trace-window:stacksaga-trace-window.adoc[Trace Window] dashboard before restoring the transaction.

*Architectural Takeaway:* Write `doRevert()` methods defensively and idempotently. For example, if a downstream resource was never created in the forward step, `doRevert()` should treat cancellation as successful rather than throwing an error.

=== Q5: Why can `onStateChanged` be called multiple times, but also ZERO times during crashes?

State Change Listeners follow **At-Least-Once notification semantics** during normal operations, but have a physical **Crash Window**:
* **Multiple Invocations:** In a Pausable LRT, `onStateChanged` is invoked on the initial pause and **again** upon timeout re-execution.
* **Zero Invocations:** To guarantee atomicity and prevent phantom notifications (such as sending an SMS confirmation before data is committed to the database), the SEC persists state to the Event Store *before* calling listeners. If the JVM crashes after commit but before the listener finishes, cluster restoration resumes directly from the *next* executor, meaning the listener is never re-invoked for the completed step.

*Architectural Takeaway:* As summarized in the xref:#at-least-once-listener-semantics[Developer Decision Matrix], never place non-skippable transactional operations in `TransactionEventListener`. Always model critical post-step actions as formal xref:stacksaga-sync/orchestrator/executor_architecture.adoc#query-executors[`QueryExecutor`] steps.

=== Q6: Do we need a distributed lock (e.g. Redis / Redlock) to prevent multiple pods from retrying the same transaction?

*No.* Developers must **never** implement external distributed locks (such as Redis locks, Hazelcast mutexes, or database row locks) around StackSaga sagas or retry schedulers.

StackSaga eliminates distributed locking entirely through **Murmur3 64-bit Consistent Hashing Token Ring Partitioning** and **30-Second Forward Time-Window Publishing**:
* Every transaction ID is deterministically hashed into a 64-bit token (`-2^63` to `2^63 - 1`).
* The Retry-Coordinator Master and Slaves partition this token space into strictly non-overlapping sub-ranges assigned to active Retry-Nodes.
* Each Retry-Node holds exclusive ownership of its assigned sub-range for a defined one-minute time window, granted with the absolute UTC interval it covers.

Disjoint sub-ranges alone would not settle the question, because a system that reclaims an expired assignment must additionally *fence* the displaced holder to stop it writing.
StackSaga never reclaims: if a Retry-Node is lost mid-window its range is left uncovered until the next division rather than handed to a survivor, so a second claimant for the same range is never created — and no fencing token, row lock or distributed lock is needed anywhere.

See xref:retry-ring-coordinator:transaction-retrying-with-retry-coordinator.adoc#token-ring-partitioning[Token Ring Partitioning Architecture] and xref:retry-ring-coordinator:transaction-retrying-with-retry-coordinator.adoc#conflict-avoidance[Conflict Avoidance] for the full argument.
