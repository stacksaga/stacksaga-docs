= StackSagaTemplate and Event-Listener

[[stacksaga-template-usage]]
== StackSagaTemplate

`StackSagaTemplate` is the main entry point for accessing the StackSaga engine's (SEC) functionalities in the orchestrator service.
It provides the API to start new transactions, checking the status of existing transactions.

`StackSagaTemplate` can be used in both reactive(non-blocking) and non-reactive(blocking) programming models. if you are in non-reactive environment, it can be used as below.

[[stackSagaTemplate_usage_in_non_reactive_environment]]
=== StackSagaTemplate in a Non-Reactive Environment

This demonstrates how to use the `StackSagaTemplate` to start a new saga transaction for placing an order and also how to check the current state of the transaction.

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class PlaceOrderHandler {

    private final SagaTemplate<OrderDomainEntity> stacksagaTemplate;//<1>

    public String handle(String username, double amount, List<String> items) {
        String transactionId = this.stackSagaTemplate
                //<2>
                .init(() -> {
                    OrderDomainEntity orderDomainEntity = new OrderDomainEntity();
                    {//initializing the domain entity with the required properties for the saga execution.
                        orderDomainEntity.setUsername(username);
                        orderDomainEntity.setTotalAmount(amount);
                        //...
                    }
                    return orderDomainEntity;
                })
                //<3>
                .peek(orderDomainEntity -> {
                    log.info("transactionId {}:", orderDomainEntity.getTransactionId());
                })
                //<4>
                .startWith(ValidateUserExecutor.class)
                //<5>
                .fireAndForget()
                //<6>
                .execute();
        log.info("Started place order saga with transactionId: {}", transactionId);
        return transactionId;
    }

    public void printCurrentState(String transactionId) {
        TransactionState<OrderDomainEntity> state = this
                .stackSagaTemplate
                //<7>
                .getCurrentState(transactionId)
                .execute();

        TransactionCompleteStatus currentStatus = state.getCurrentStatus(); //<8>
        log.info("Current status of transaction {}: {}", transactionId, currentStatus);
        NavigableMap<Integer, SagaExecutionEvent> executionHistory = state.getExecutionHistory();//<9>
        log.info("Execution history of transaction {}: {}", transactionId, executionHistory);
        OrderDomainEntity currentDomainEntity = state.getCurrentDomainEntity(); //<10>
        log.info("Current domain entity state: {}", currentDomainEntity); //<11>
        ZonedDateTime startedDateTime = state.getStartedDateTime(); //<12>
        log.info("Transaction {} started at: {}", transactionId, startedDateTime.toLocalDateTime());
    }
}
----

<1> Autowire the `StackSagaTemplate` in your class. you have to provide the custom xref:stacksaga-sync/orchestrator/domain-entity.adoc#creating_custom_domain_entity[`DomainEntity`] as the generic parameter of the `StackSagaTemplate`.
<2> Use the `init` operator to initialize the transaction by providing a supplier of the custom DomainEntity. this method is used to create the initial state of the transaction by providing the required properties for the saga execution in the DomainEntity.
<3> Use the `peek` operator (optional) to perform any action with the initialized DomainEntity before starting the execution. the usage of this operator is that is to see the generated transactionId after initializing the DomainEntity because #the transactionId is generated and set in the DomainEntity by the framework at the time of passing via `init` operator#. therefore, you can use this operator to see the generated transactionId before starting the execution.
<4> Use the `startWith` operator to specify the first xref:stacksaga-sync/orchestrator/executor_architecture.adoc[executor] that should be triggered to start the transaction.

<5> Use the `fireAndForget` operator to start the execution of the transaction as fire-and-forget mode. that means the transaction totally runs in the background, and you don't have to wait for the execution to complete. it runs using the request thread only for initializing the transaction. after initializing the transaction, the request thread is released to serve other requests. the execution of the transaction runs in the background using a separate thread pool that is managed by the framework.

<6> Use the `execute` operator to start the execution of the transaction in blocking way.

<7> Use the `getCurrentState` operator to get the current state of the transaction by providing the transactionId. this method is used to retrieve the current state of the transaction at any point in time by providing the transactionId. yu can see all the details about the transaction state in the returned `TransactionState` object such as the current status of the transaction, the execution history, the current state of the domain entity, the started time and many more details.
<8> Get the current status of the transaction from the `TransactionState` object.
<9> Get the execution history of the transaction from the `TransactionState` object. the execution history is a navigable map that contains all the executed endpoints in the transaction flow (primary and compensation) with their metadata such as the execution status, completed time event name and more.
<10> Get the current state of the domain entity from the `TransactionState` object. this is the latest state of the domain entity after applying all the changes that are done by the executed endpoints in the transaction flow.
<11> Log the current state of the domain entity.
<12> Get the started time of the transaction from the `TransactionState` object and log it.

NOTE: There is another way to being updated about the transaction status changes by using the xref:#event_listener_for_stage_change_events[EventListener].

IMPORTANT: Go through the Javadoc of the `TransactionState` class to see all the features that are provided in the transaction state object to get more insights about the transaction.

=== StackSagaTemplate in a Reactive Environment

If you are in a reactive environment, you can use the `StackSagaTemplate` in a non-blocking way by using the reactive operators provided by the template.
There are two ways to execute a saga transaction in a reactive environment:

. *Fire-and-Forget* — Start the transaction and immediately get back a `Mono<String>` containing the transaction ID. The saga runs entirely in the background. Use this when you only need the ID and will rely on `getCurrentState` or the xref:#event_listener_for_stage_change_events[EventListener] to track progress.
. *Fire-and-Watch* — Start the transaction and observe every state transition in real-time as a `Flux`. Use this when you want to stream live execution events to a client (e.g., via Server-Sent Events).

==== Fire-and-Forget

The `fireAndForget()` operator hands the transaction off to the StackSaga engine and returns immediately.
Calling `.executeAsync()` on the resulting spec returns a `Mono<String>` that emits the transaction ID once the saga is successfully initialised and handed over.

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class PlaceOrderHandler {

    private final SagaTemplate<OrderDomainEntity> stacksagaTemplate;

    public Mono<String> handle(String username, double amount, List<String> items) {
        return this.stackSagaTemplate
                .init(() -> {
                    OrderDomainEntity orderDomainEntity = new OrderDomainEntity();
                    {//initializing the domain entity with the required properties for the saga execution.
                        orderDomainEntity.setUsername(username);
                        orderDomainEntity.setTotalAmount(amount);
                        //...
                    }
                    return orderDomainEntity;
                })
                .peek(orderDomainEntity -> {
                    log.info("transactionId {}:", orderDomainEntity.getTransactionId());
                })
                .startWith(ValidateUserExecutor.class)
                .fireAndForget()
                //<1>
                .executeAsync()
                .map(transactionId -> "Order placed successfully with transaction id: " + transactionId);
    }
}
----

<1> `executeAsync()` returns a `Mono<String>` that emits the transactionId once the saga is initialised. The transaction continues running in the background; use `getCurrentState(transactionId)` or the xref:#event_listener_for_stage_change_events[EventListener] to track its progress.

==== Fire-and-Watch

The `fireAndWatch(Duration waitTimeout)` operator starts the transaction and allows you to observe each state change in real-time.
Calling `.toFlux()` on the resulting spec returns a `Flux<TransactionState<DE, SyncExecutionEvent<DE>>>` that emits one item per executor step as the saga progresses — making it ideal for streaming live updates to a client (for example via Server-Sent Events).

[source,java]
----
@GetMapping(value = "/order/watch", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<TransactionState<OrderDomainEntity, SyncExecutionEvent<OrderDomainEntity>>> createOrderAndWatch() {
    return sagaTemplate
            .init(OrderDomainEntity::new)
            .peek(orderDomainEntity -> {
                log.info("Started Transaction ID: {}", orderDomainEntity.getTransactionId());
            })
            .startWith(ValidateUserExecutor.class)
            .fireAndWatch(Duration.ofSeconds(40)) //<1>
            .toFlux()
            .doOnNext(state -> {
                log.info("Received state change: {}", state);
            });
}
----

<1> The `waitTimeout` is the maximum duration the subscriber will wait for execution results before the pipeline is terminated with `WaitTimeExceededException`.

===== Key Behaviors and Error Handling

* *Timeout (`WaitTimeExceededException`)*: If the execution time exceeds the specified `Duration waitTimeout`, the pipeline signals a `WaitTimeExceededException` via `onError`. This **only terminates the subscription** — the underlying saga execution is not cancelled and continues asynchronously in the background.
After the subscription ends, you can still track the transaction in two ways:
** If you have implemented a xref:#event_listener_for_stage_change_events[State Change Listener] (`TransactionEventListener` or `ReactiveTransactionEventListener`), it will continue to receive state change notifications for every executor step as usual.
** Alternatively, you can manually query the current state of the transaction at any time using `getCurrentState(transactionId)`.

* *Execution Pause (`TransactionPausedException`)*: If a step encounters a retryable exception (such as a database outage or a custom `RetryableExecutorException`), the execution is paused and rescheduled. Because `TransactionState` has no notion of this internal pause, the pipeline stops emitting and signals a `TransactionPausedException` via `onError`. This does not mean the transaction has failed — it only means the live subscription is halted.
After the subscription ends, you can still track the transaction in two ways:
** If you have implemented a xref:#event_listener_for_stage_change_events[State Change Listener] (`TransactionEventListener` or `ReactiveTransactionEventListener`), it will continue to receive state change notifications once the execution resumes after the retry.
** Alternatively, you can manually check the current state of the transaction using `getCurrentState(transactionId)`.



[[event_listener_for_stage_change_events]]
== Observing Transaction State Changes

After handing over the transaction to the StackSaga engine by calling the `execute` or `executeAsync` method of the `StackSagaTemplate`, the transaction is executed step by step (primary executors and compensation executors).
There are two ways to observe and react to state changes during or after the transaction execution:

. *xref:#state-change-listeners[State Change Listeners]* — A push-based approach where the engine notifies your callback method in real-time after each executor step completes. Ideal for real-time use cases like pushing order status notifications to an end user.
. *xref:#getcurrentstate-on-demand[`StackSagaTemplate.getCurrentState()`]* — A pull-based approach where you query the full state of the transaction on demand at any point in time. Ideal for on-demand lookups, such as when a user wants to see the current status of their order.

[[state-change-listeners]]
=== Using State Change Listeners (Real-time)

State Change Listeners are the recommended way to track transaction progress in real-time.
The engine invokes the listener's `onStateChanged` callback after every executor step (both primary and compensation), passing the current `TransactionState` directly — so you never need to poll.

Listeners can be implemented based on your environment:

. `TransactionEventListener` — for non-reactive (blocking) environments.
. `ReactiveTransactionEventListener` — for reactive (non-blocking) environments.



[IMPORTANT]
====
*Sequential Execution and Latency Impact:*

The `onStateChanged` callback is executed sequentially as part of the transaction lifecycle.
Specifically, **the next span/executor step in the saga flow is triggered only after the current `onStateChanged` execution has completed**.

Performing heavy computations, slow I/O calls, or long-running operations inside `onStateChanged` directly blocks the progression of the transaction and increases total transaction latency.

*Best Practice:*
Keep `onStateChanged` lightweight (e.g., publishing a quick notification or logging status). If you need to perform heavy or time-consuming operations, offload the work to an asynchronous/separate thread pool (using a snapshot or deep copy of `TransactionState` if needed), allowing the engine to immediately proceed with the next span of the transaction.
====

==== TransactionEventListener

Implement the `TransactionEventListener` interface to listen to transaction events in a non-reactive environment.

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class PlaceOrderHandler implements TransactionEventListener<OrderDomainEntity> {
    @Override
    public void onStateChanged(TransactionState<OrderDomainEntity> state) {
        TransactionCompleteStatus currentStatus = state.getCurrentStatus();
        log.info("Current status of transaction: {}", currentStatus);
        NavigableMap<Integer, SagaExecutionEvent> executionHistory = state.getExecutionHistory();
        log.info("Execution history of transaction: {}", executionHistory);
        OrderDomainEntity currentDomainEntity = state.getCurrentDomainEntity();
        log.info("Current domain entity state: {}", currentDomainEntity);
        ZonedDateTime startedDateTime = state.getStartedDateTime();
        log.info("Transaction started at: {}", startedDateTime.toLocalDateTime());
    }
}
----

NOTE: Because `onStateChanged` here is plain synchronous, blocking-capable user code, the engine invokes it on a dedicated blocking scheduler — the `blockingExecutionScheduler` supplied by the orchestrator's `AbstractSchedulerProvider` — rather than on the Kafka consumer thread or the framework's shared non-blocking scheduler. That keeps blocking work in your listener from starving Kafka message consumption or the dispatch of other, unrelated transactions. It still delays the progression of *this* transaction until the method returns, and the scheduler's thread pool is finite, so avoid unbounded or very long-running work here regardless. This pool's thread cap, queue capacity, TTL and daemon flag can be tuned via the `stacksaga.kafka.orchestrator.scheduler.blocking-execution.*` properties.

==== ReactiveTransactionEventListener

Implement the `ReactiveTransactionEventListener` interface to listen to transaction events in a reactive environment.

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class ReactivePlaceOrderHandler implements ReactiveTransactionEventListener<OrderDomainEntity> {
    @Override
    public Mono<Void> onStateChanged(TransactionState<OrderDomainEntity> transactionState) {
        return Mono
                .just(transactionState)
                .doOnNext(state -> {
                    TransactionCompleteStatus currentStatus = state.getCurrentStatus();
                    log.info("Current status of transaction: {}", currentStatus);
                    NavigableMap<Integer, SagaExecutionEvent> executionHistory = state.getExecutionHistory();
                    log.info("Execution history of transaction: {}", executionHistory);
                    OrderDomainEntity currentDomainEntity = state.getCurrentDomainEntity();
                    log.info("Current domain entity state: {}", currentDomainEntity);
                    ZonedDateTime startedDateTime = state.getStartedDateTime();
                    log.info("Transaction started at: {}", startedDateTime.toLocalDateTime());
                })
                .flatMap(orderDomainEntityTransactionState -> {
                    //simulate some async processing here.
                    return Mono.delay(Duration.ofSeconds(1))
                            .then();
                });
    }
}
----

NOTE: Unlike `TransactionEventListener`, no dedicated blocking scheduler is used here: the engine subscribes to the returned `Mono` on the same shared, non-blocking `executionScheduler` supplied by `AbstractSchedulerProvider` that also drives dispatch of other, unrelated transactions. Because that scheduler is shared and fixed-size, this pipeline must be genuinely non-blocking — any blocking call here risks starving unrelated, concurrently-running transactions, not just delaying this one. This pool's parallelism can be tuned via the `stacksaga.kafka.orchestrator.scheduler.execution.*` properties.

[[getcurrentstate-on-demand]]
=== Using StackSagaTemplate.getCurrentState() (On-demand)

`StackSagaTemplate.getCurrentState(transactionId)` is a pull-based approach that lets you fetch the full state of a transaction at any point in time by providing the transaction ID.

This is useful when you need to look up the details of a transaction on demand — for example, when a user wants to view the current status of their order after it has been placed, or when you want to inspect the execution history after the transaction has completed.

NOTE: Unlike State Change Listeners, this method fetches the transaction state from the event-store on every call. It is not real-time and is not suitable for use as a polling mechanism during active execution. Prefer a State Change Listener for real-time tracking.


[[recommended-handler-pattern]]
== Recommended Handler Pattern

StackSaga team suggests to implement the saga transaction related things in a separate class called `Handler` that is responsible for starting, listening and checking the status of the saga transactions.
The below code snippet is showing the recommended architecture for the Handler.

[source,java]
----
@Slf4j
@Component
@RequiredArgsConstructor
public class PlaceOrderHandler implements TransactionEventListener<OrderDomainEntity> {

    private StackSagaTemplate<OrderDomainEntity> stackSagaTemplate;

    public String handle(String username, double amount, List<String> items) { //<1>
        return this
                .stackSagaTemplate
                .init(() -> {
                  //....
                })
                .....
    }

    public CustomOrderStatusView getCurrentState(String orderId) { //<2>
        return this
                .stackSagaTemplate
                .getCurrentState(orderId)
                ......

    }
    @Override
    public void onStateChanged(TransactionState<OrderDomainEntity> transactionState) { //<3>
        //....
    }
}
----

<1> The `handle` method is responsible for starting the saga transaction by using the `StackSagaTemplate` and providing the required parameters to start the transaction.
<2> Fetch the current state of the transaction by using the `StackSagaTemplate`
<3> Implement the `onStateChanged` method to listen to the transaction status changes by implementing the `TransactionEventListener` interface and override the `onStateChanged` method.
