= StackSaga Engine: Architecture & Components

== Overview

**StackSaga Engine** is a reactive distributed Saga orchestration framework built on top of Spring Boot.
It enables developers to coordinate complex distributed workflows by managing atomic step executions and their compensating actions, guaranteeing eventual consistency across microservice boundaries through the Saga design pattern.

The StackSaga Engine natively unifies **both synchronous execution (REST over HTTP, gRPC over HTTP/2, GraphQL, local database operations) and asynchronous event-driven messaging (Apache Kafka, RabbitMQ, AWS SQS)** within the **exact same saga workflow**.

NOTE: Even though StackSaga Engine runs reactively under the hood, it is fully compatible with both *reactive* (`Mono`/`Flux`) and *non-reactive* (imperative/blocking) Spring environments.

*Key features:*

* **Unified Hybrid Saga Orchestration**: Seamlessly interleave synchronous RPC calls and asynchronous message broker events in a single saga flow.
* **Two-Stage Asynchronous Execution Model (`asAsync()`)**: Guarantees event-store state persistence *before* dispatching messages to external event brokers (Apache Kafka, RabbitMQ) to eliminate race conditions between downstream callbacks and local event commits.
* **Dual Long-Running Transaction (LRT) Models**: Native support for both xref:stacksaga-sync/index.adoc#continuous-lrt[*Continuous LRTs*] (unbroken straight-through execution) and xref:stacksaga-sync/index.adoc#pausable-lrt[*Pausable LRTs*] (business wait states with callback correlation via xref:stacksaga-sync/orchestrator/executor_architecture.adoc#stepManager_pause[`stepManager.pauseUntilResume()`] and xref:stacksaga-sync/orchestrator/stacksaga_template.adoc#resuming-paused-transactions[`SagaTemplate.resume()`]).
* **Symmetrical Compensation (`doRevert()`)**: Backward compensation natively supports both synchronous endpoints and asynchronous broker dispatches.
* **Deterministic Idempotency**: Stable per-span idempotency keys eliminate duplicate execution side effects during retries.
* **Distributed Self-Healing Retries**: Ring coordinator partitioning distributes transaction retries conflict-free across orchestrator instances.
* **Zero-Infrastructure Event Sourcing**: Utilizes your existing relational or NoSQL database as the event store.
* **Visual Transaction Tracing**: Real-time distributed tracing via the StackSaga xref:trace-window:stacksaga-trace-window.adoc[Trace-Window].

=== Component Breakdown

* **`stacksaga-spring-boot-starter`**: The core framework dependency providing the Saga Execution Coordinator (SEC), `SagaTemplate`, `CommandExecutor`, `QueryExecutor`, and step managers.
* **`stacksaga-database-support`**: Database-specific event-store implementations (MySQL, PostgreSQL, Cassandra, Oracle) for persisting domain entity snapshots and execution histories.
* **`stacksaga-env-support`**: Provides geographical topology metadata (region, zone, instance ID) to the SEC in cloud and container deployments.
* **`stacksaga-ring-coordinator`**: Standalone coordinator managing Murmur3 token ring partitioning for cluster-wide retry ownership.
* **`stacksaga-trace-window`**: Cloud-hosted visual dashboard for real-time transaction inspection and manual operator interventions.

== Orchestration Service Architecture (Domain-Centric Orchestration)

A key architectural advantage of StackSaga is that you **never deploy a dedicated or standalone orchestration server**.
Instead, StackSaga follows a **Domain-Centric (Service-Embedded) Orchestration** model:

* **No Dedicated Orchestrator Infrastructure**: You do not build or maintain separate "orchestrator microservices". Instead, any standard microservice becomes an orchestrator simply by adding `stacksaga-spring-boot-starter` to it.
* **Per-Domain Centralization**:
  ** For an order placement workflow, add StackSaga to `order-service`. The `order-service` becomes the central orchestrator for that order domain.
  ** If your system also has a complex multi-step payment clearance, refund, or settlement saga, simply add StackSaga into `payment-service` to make it the orchestrator for the payment domain.
  ** A single microservice can orchestrate one or multiple business domains within its bounded context.
* **Zero Downstream Changes**: Microservices invoked by the orchestrator (such as `user-service` or `inventory-service`) remain standard utility services with zero StackSaga dependencies.

=== `stacksaga-spring-boot-starter` Dependency

`stacksaga-spring-boot-starter` is the core of the framework:

[source,xml,subs="attributes+"]
----
<dependency>
  <groupId>org.stacksaga</groupId>
  <artifactId>stacksaga-spring-boot-starter</artifactId>
  <version>{stacksaga-version}</version>
</dependency>
----

It provides the developer-facing abstractions:

* xref:stacksaga-sync/orchestrator/stacksaga_template.adoc[SagaTemplate and Event Listeners] — Entry point to initialize, watch, and resume sagas.
* xref:stacksaga-sync/orchestrator/domain-entity.adoc[Domain Entity] — To store the payload and execution state for the transaction.
* xref:stacksaga-sync/orchestrator/executor_architecture.adoc[Executors] — To create, execute, and pause each atomic step within the saga using staged synchronous (`.asSync()`) or asynchronous (`.asAsync().invoker(...)`) builders.

[[stacksaga-db-support]]
=== `stacksaga-database-support` Dependency

StackSaga persists execution snapshots to an Event Store hosted in your existing application database.
Add the database implementation matching your orchestrator's primary database:

* MySQL Database - xref:stacksaga-database-support:mysql-database-support/stacksaga-mysql-support.adoc[stacksaga-mysql-support]
* PostgreSQL Database - `stacksaga-postgres-support`
* Cassandra Database - xref:stacksaga-database-support:cassandra-database-support/stacksaga-cassandra-support.adoc[stacksaga-cassandra-support]
* Oracle Database - `stacksaga-oracle-support`

[[stacksaga-env-support]]
=== `stacksaga-env-support` Dependency

Provides environment-related geographical metadata (region, zone, instance ID) to the SEC.
Artifacts include `stacksaga-eureka-support`, `stacksaga-k8s-support`, and `stacksaga-consul-support` (see xref:ROOT:saga-region-resolver.adoc[Instance Region Resolution & SagaRegionResolver]).

[[agent_service_related_components]]
=== Retry & Cluster Coordination Components

To manage distributed transaction retrying without multi-node conflicts, StackSaga utilizes the Retry Subsystem coordinated via Murmur3 token ring partitioning.
Refer to xref:retry-ring-coordinator:transaction-retrying-with-retry-coordinator.adoc[Retry Subsystem Architecture] for complete deployment details.

=== StackSaga Trace-Window

StackSaga Trace-Window is the platform where you view transaction tracing details graphically.
There is nothing to implement for this component; you can visit https://trace.stacksaga.org[trace.stacksaga.org] and connect your instances.

== Low-Level Diagram (LLD)

Here you can see how the StackSaga Execution Coordinator (SEC) fits into the overall architecture:

image::ROOT:stacksaga-diagram-SEC.svg[alt="StackSaga Execution Coordinator (SEC) in StackSaga framework"]

. The request arrives at the orchestration service and is handed off to SEC.
. SEC picks up the request and starts execution from the configured starting point.
. Each step is executed based on programmatic staged navigation:
   - For direct calls, the executor runs synchronously and returns `.asSync().noPause().nextExecutor(...)`.
   - For broker messaging, the executor returns `.asAsync().invoker(...)`. SEC commits the domain entity state to the Event Store *first*, then lazily invokes the broker dispatch lambda, and marks the transaction `PAUSED`.
. Intermediate state snapshots are persisted in the event store for retrying, tracing, and point-in-time recovery.
. When an asynchronous callback or event arrives, `sagaTemplate.resume(txId, idempotencyKey)` awakens the saga, and SEC proceeds to the next executor.
. If any primary step throws `NonRetryableExecutorException`, SEC triggers compensating executions (`doRevert()`) in reverse order across both direct APIs and broker topics.
. If a transient fault occurs, SEC marks the transaction for retry, coordinated by the Ring Coordinator.
. Real-time telemetry is published to configured listeners and exposed to the Trace Window.

== Custom Configurations

=== Saga Scheduler Configuration

StackSaga provides a default scheduler configuration for saga execution that uses Project Reactor's `BoundedElastic` scheduler.
This configuration is automatically applied unless you provide a custom implementation.

==== Default Specifications

[cols="1,2"]
[.google-anno-skip]
|===
| Parameter | Value

| **Scheduler Type**
| `BoundedElastic`

| **Thread Pool Size**
| `availableProcessors() × 10`

| **Queue Capacity**
| `100,000`

| **Thread Name Prefix**
| `saga-exe`

| **Threading Timeout**
| `60 seconds`

| **Daemon Threads**
| `false`
|===

==== Customizing the Scheduler

To customize scheduler behavior, register an `AbstractSchedulerProvider` bean in your application context:

[source,java]
----
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.stacksaga.util.AbstractSchedulerProvider;
import reactor.core.scheduler.Scheduler;
import reactor.core.scheduler.Schedulers;

@Configuration
public class CustomSchedulerConfiguration {

    @Bean
    public AbstractSchedulerProvider customSchedulerProvider() {
        return new AbstractSchedulerProvider() {
            @Override
            protected Scheduler scheduler() {
                return Schedulers.newBoundedElastic(
                    50,              // Custom thread pool size
                    50_000,          // Custom queue capacity
                    "custom-saga",   // Custom thread name prefix
                    120,             // Custom timeout in seconds
                    true             // Daemon threads (optional)
                );
            }
        };
    }
}
----
