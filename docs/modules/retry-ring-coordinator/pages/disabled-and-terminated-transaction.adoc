= Disabled Transactions vs Terminated Transactions

The xref:transaction-retrying-with-retry-coordinator.adoc[retry subsystem] does not retry a transaction forever.
This page describes the two end states a transaction can reach when it stops being retried, and how to bring it back.

[[transaction-lifetime]]
== Transaction Lifetime

Every transaction carries a *lifetime*: the bounded period during which the retry subsystem will keep re-invoking it.
While the lifetime lasts, a transaction that fails with a retryable error is registered for another recovery window and attempted again.

The lifetime exists so that a transaction which can never succeed does not circulate through the retry subsystem indefinitely, consuming capacity that live recovery work needs.
What happens when a transaction stops depends on *how* it stopped:

* It ran out of lifetime without completing — a xref:#disabled-transactions[disabled transaction].
* It failed while compensating, which ends it immediately — a xref:#terminated-transactions[terminated transaction].

[[disabled-transactions]]
== Disabled Transactions

A transaction that is still incomplete when its lifetime expires is marked as a *disabled transaction*.
It is no longer picked up for retrying.

There are two common reasons a transaction reaches the end of its lifetime without completing.

. *An executor was removed or renamed while the transaction was still in flight.* +
Consider a transaction initiated on service version `1.0.0` that then spends time awaiting retry because a target service is unavailable.
If version `1.1.0` is deployed during that period and no longer contains the executor the transaction is waiting on, the transaction cannot proceed: each time it is passed for retrying, execution fails because the executor no longer exists.
It is rescheduled again and again until its lifetime runs out, at which point it becomes a disabled transaction.
+
NOTE: Rescheduling a transaction whose executor is missing is deliberate — it gives the team a window in which to recognise the problem and restore the executor before the lifetime expires. StackSaga reports this condition to the xref:trace-window:stacksaga-trace-window.adoc[StackSaga Trace Window] as soon as it occurs.

. *The target service host could not be resolved.* +
If the target host cannot be reached on every attempt until the lifetime is exceeded, the transaction becomes a disabled transaction.
+
NOTE: This case is not raised as a warning in the Trace Window. Resources being temporarily unavailable is an expected condition that the framework is designed to absorb, not a defect to report.

[[terminated-transactions]]
== Terminated Transactions

A transaction that *fails while reverting* is marked as a *terminated transaction*.

Compensation is not permitted to fail in StackSaga: the only exception a `doRevert()` method may throw is a retryable one.
A non-retryable failure during compensation therefore has no recovery path — there is no compensation for a compensation — so the transaction stops at once.

The distinction between the two end states is *when* they happen:

[cols="1,2,2",options="header"]
[.google-anno-skip]
|===
| | Disabled | Terminated

| Cause
| Lifetime expired before completion
| Compensation failed with a non-retryable error

| Timing
| At the end of the lifetime
| Immediately, without reaching the lifetime

| Flow
| Primary or compensation flow
| Compensation flow only
|===

== Restoring Disabled and Terminated Transactions

Both end states require the team to diagnose the underlying problem manually — a missing executor, an unreachable host, a defect in a `doRevert()` implementation.
Once the cause is fixed and the transaction can run to completion, it can be restored for retrying.

Two endpoints handle these transactions:

. *Fetching disabled and terminated transactions.* +
Collects the affected transactions so their errors can be analysed.

. *Restoring disabled and terminated transactions.* +
Returns a transaction to the retry subsystem by extending its lifetime.
