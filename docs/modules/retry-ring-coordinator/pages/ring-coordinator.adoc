= Ring-Coordinator

== Overview

As mentioned in the xref:transaction-retrying-with-retry-coordinator.adoc[previous section], the retry ring-coordinator is a separate service — distinct from your utility microservices — that runs as either a `master` or a `slave`, depending on how it is configured.
This section walks through how the retry ring-coordinator is set up and how it works.

IMPORTANT: The `Master` and `Slave` retry ring-coordinator instances can also be deployed within the same service instance.
Refer to the xref:transaction-retrying-with-retry-coordinator.adoc#ring-coordinator-deployment-topologies[deployment topologies] section for more details.

IMPORTANT: After adding the `stacksaga-ring-coordinator-spring-boot-starter` dependency to your project and configuring the retry ring-coordinator as `master` or `slave`, you can run the retry ring-coordinator as a Spring Boot application.

=== How Master and Slave Connect

Before configuring each role, it helps to see how a Master and a Slave find each other.
On startup, a Slave opens a persistent `RSocket` connection to the Master using the host and port configured via `stacksaga.coordinator.slave.target-master.*`.
The Master accepts the connection and adds the Slave to its registry — from its next 30-second publish cycle onward, the Master starts sending that Slave its token-range updates.

[[ring-coordinator-master]]
== Ring-Coordinator As `Master`

If the retry ring-coordinator is configured as `master`, it is responsible for managing the entire token ring and sharing partitions of it with every `slave` retry ring-coordinator connected to it within the same region and cluster.
Read more about the Master's responsibilities xref:transaction-retrying-with-retry-coordinator.adoc#ring-coordinator-master[here].

Add the `stacksaga-ring-coordinator-spring-boot-starter` dependency to your project as follows:

.pom.xml
[source,xml,subs="attributes+"]
----
<dependencyManagement>
    <dependencies>
        <dependency> <!--Only for stacksaga dependencies version management-->
            <groupId>org.stacksaga</groupId>
            <artifactId>stacksaga-bom</artifactId>
            <version>{stacksaga-version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>org.stacksaga</groupId>
        <artifactId>stacksaga-ring-coordinator-spring-boot-starter</artifactId>
    </dependency>
</dependencies>
----

[NOTE]
====
The `stacksaga-ring-coordinator-spring-boot-starter` includes a built-in reactive WebFlux and Thymeleaf engine that automatically provides the xref:#live-visual-dashboard[Real-Time Visual Dashboard], Terminal ASCII Banner, and Reactive SSE Live Stream out of the box.

If you are running the coordinator in a non-web environment or wish to disable the web UI endpoints completely, set `stacksaga.coordinator.dashboard.enabled=false`.

In production, you can additionally include `spring-boot-starter-actuator` to expose health probes (`/actuator/health`) and metrics (`/actuator/metrics`).
====

=== Configuration

The retry ring-coordinator can be configured via `application.properties` or `application.yml`.
Below is a minimal configuration for the retry ring-coordinator as `master`:

.application.properties
[source,properties]
----
#stacksaga-master coordinator configuration
stacksaga.coordinator.instance-type=master #<1>
stacksaga.coordinator.target-services=order-service #<2>

#stacksaga-instance configuration
stacksaga.instance.cluster=cluster1 #<3>
stacksaga.instance.region=us-east-1 #<4>
stacksaga.instance.zone=us-east-1a #<5>

#rsocket server configuration
spring.rsocket.server.port=1000 #<6>
spring.rsocket.server.address=localhost #<7>
spring.rsocket.server.transport=tcp #<8>

----

<1> Set `stacksaga.coordinator.instance-type` to `master`, since this instance runs as the Master.

<2> The target service(s) this Master coordinates retries for — `order-service` in this example.
This can be a comma-separated list when a single Master manages multiple services; see the xref:transaction-retrying-with-retry-coordinator.adoc#ring-coordinator-deployment-topologies[deployment topologies] section.

<3> The `cluster` this instance belongs to.
Only `slave` retry ring-coordinator instances and Orchestrators in the same cluster can connect to this Master — see the xref:transaction-retrying-with-retry-coordinator.adoc#virtual-cluster[Virtual Cluster] section.

<4> The `region` this instance belongs to.
Only `slave` retry ring-coordinator instances and Orchestrators in the same region can connect to this Master — see the xref:transaction-retrying-with-retry-coordinator.adoc#multi-region-deployment[Regional Deployment] section.

<5> The `zone` this instance belongs to.
It has no functional impact here, but should be set as per the StackSaga core specification.

<6> The `RSocket` server port. `slave` retry ring-coordinator instances connect to the Master over `RSocket` — backed by the default RSocket server provided by `spring-boot-starter-rsocket` — and Orchestrators use the same port to look up which `slave` instance to connect to.

<7> The `RSocket` network address that the server binds to.

<8> The `RSocket` transport protocol.
It must be `tcp` for retry ring-coordinator services.

[[ring-coordinator-slave]]
== Ring-Coordinator As `Slave`

If the retry ring-coordinator is configured as `slave`, it is responsible for connecting to the `master` retry ring-coordinator, subscribing to receive its assigned ring portion, and publishing sub-ring portions to the Orchestrator instances subscribed to it within the same region and cluster.
Read more about the Slave's responsibilities xref:transaction-retrying-with-retry-coordinator.adoc#ring-coordinator-slave[here].

Adding the `stacksaga-ring-coordinator-spring-boot-starter` dependency is exactly the same as for the xref:#ring-coordinator-master[Master] — both roles use the same starter.
Only the configuration differs, as shown below.

=== Configuration

.application.properties
[source,properties]
----
#stacksaga-slave coordinator configuration
stacksaga.coordinator.instance-type=slave #<1>
stacksaga.coordinator.target-services=order-service #<2>

#stacksaga-instance configuration
stacksaga.instance.cluster=cluster1 #<3>
stacksaga.instance.region=us-east-1 #<4>
stacksaga.instance.zone=us-east-1a #<5>

#rsocket server configuration
spring.rsocket.server.port=1001 #<6>
spring.rsocket.server.address=localhost #<7>
spring.rsocket.server.transport=tcp #<8>

#connecting to the master retry ring-coordinator
stacksaga.coordinator.slave.target-master.port=1000 #<9>
stacksaga.coordinator.slave.target-master.host=localhost #<10>

----

<1> Set `stacksaga.coordinator.instance-type` to `slave`, since this instance runs as a Slave.

<2> The target service(s) this Slave subscribes to on the Master, receiving their ring portion and publishing sub-ring portions to the subscribed Orchestrator instances.
This can be a comma-separated list when a single Slave subscribes for multiple services; see the xref:transaction-retrying-with-retry-coordinator.adoc#ring-coordinator-deployment-topologies[deployment topologies] section.
+
IMPORTANT: If a Slave supports multiple services, all of those services must also be supported by the Master.
Otherwise, the connection between the Master and Slave will not be established.

<3> The `cluster` this instance belongs to — same semantics as for the xref:#ring-coordinator-master[Master].
The Master, and any Orchestrator instances that want to subscribe to this Slave, must share this cluster name for the connection to succeed.

<4> The `region` this instance belongs to — same semantics as for the xref:#ring-coordinator-master[Master].
The Master, and any subscribing Orchestrator instances, must share this region for the connection to succeed.

<5> The `zone` this instance belongs to.
It has no functional impact here, but should be set as per the StackSaga core specification.

<6> The `RSocket` server port.
Orchestrator instances connect to this Slave over `RSocket` to receive their sub-range updates.

<7> The `RSocket` network address that the server binds to.

<8> The `RSocket` transport protocol.
It must be `tcp` for retry ring-coordinator services.

<9> The `RSocket` server port of the Master this Slave connects to, in the same region and cluster.

<10> The `RSocket` server host of the Master this Slave connects to, in the same region and cluster.

[[kubernetes-statefulset-deployment]]
== Automated Role Detection via Kubernetes StatefulSet

When deploying a Clustered Ring-Coordinator on Kubernetes, configuring separate Deployments for Master (`stacksaga.coordinator.instance-type=master`) and Slaves (`stacksaga.coordinator.instance-type=slave`) adds unnecessary operational overhead.
Instead, it is recommended to run the Ring-Coordinator cluster as a **Kubernetes StatefulSet**.

In a StatefulSet, each pod receives a deterministic, ordinal-indexed hostname:
----
<statefulset-name>-0  (e.g., ring-coordinator-0)
<statefulset-name>-1  (e.g., ring-coordinator-1)
<statefulset-name>-2  (e.g., ring-coordinator-2)
----

StackSaga can automatically determine the coordinator's role directly from this ordinal index using the `stacksaga.coordinator.deploy.index-based` property:

* **Pod Index `0`** is automatically designated as the **`master`** node.
* **Pod Index `> 0`** (e.g. index 1, 2, ...) are automatically designated as **`slave`** nodes.

=== Enabling Index-Based Role Resolution

To enable automatic role detection, set `stacksaga.coordinator.deploy.index-based=true`:

.application.properties
[source,properties]
----
# Enable index-based role detection for Kubernetes StatefulSet
stacksaga.coordinator.deploy.index-based=true #<1>

# Optional: instance-type does not need to be set; it is derived automatically #<2>

# Target service(s) coordinated by this cluster
stacksaga.coordinator.target-services=order-service,payment-service #<3>

# RSocket server settings
spring.rsocket.server.port=7777 #<4>
spring.rsocket.server.transport=tcp

# Target master connection (used by Slave pods when index > 0)
stacksaga.coordinator.slave.target-master.host=ring-coordinator-0.ring-coordinator-headless #<5>
stacksaga.coordinator.slave.target-master.port=7777 #<6>

# Cluster and region metadata
stacksaga.instance.cluster=cluster1
stacksaga.instance.region=us-east-1
stacksaga.instance.zone=us-east-1a
----

<1> Enables automated index-based role detection.
<2> `stacksaga.coordinator.instance-type` becomes optional. Pod `0` automatically runs as `master`, while pods `1..N` run as `slave`.
<3> The services coordinated by this ring-coordinator cluster.
<4> RSocket port used for communication.
<5> The hostname of the Master pod (pod `0`). In Kubernetes, this typically points to the headless service DNS of the Master pod (e.g., `<statefulset-name>-0.<headless-service-name>`). When pod `0` starts as Master, it ignores this property; when pods `1..N` start as Slaves, they use it to connect to pod `0`.
<6> The port of the Master pod.

=== Pod Identifier Resolution Order

When `stacksaga.coordinator.deploy.index-based=true` is set, StackSaga determines the pod index by inspecting the following sources in order:

1. `stacksaga.coordinator.instance-id` (explicit override if specified in configuration)
2. `POD_NAME` (standard Kubernetes downward API environment variable)
3. `HOSTNAME` (standard Kubernetes pod hostname environment variable)

The numeric index is extracted from the suffix after the last hyphen (`-`), ignoring any FQDN domain suffixes (e.g., `ring-coordinator-0.ring-coordinator-headless.default.svc.cluster.local` resolves index `0`).

[NOTE]
====
In standard Docker containers and standalone Linux environments, `stacksaga.coordinator.deploy.index-based` should remain `false` (the default).
When disabled, StackSaga will not attempt to parse container IDs or hostnames as StatefulSet ordinals, and will use the explicitly configured `stacksaga.coordinator.instance-type`.
====

[[live-visual-dashboard]]
== Real-Time Visual Dashboard & Observability

The Ring-Coordinator provides a built-in real-time dashboard and observability endpoints, allowing developers and operators to monitor live cluster activities, connected slave nodes, token range allocations, and connected microservice retry nodes (Orchestrators).

=== Accessing the Dashboard & Endpoints

When the Ring-Coordinator is running, the following endpoints are available:

[cols="2,2,4", options="header"]
|===
|Endpoint|Format|Description
|`/dashboard` (or `/`)|HTML|Interactive real-time web dashboard displaying live cluster topology, active slave nodes, assigned token ranges, and connected retry nodes.
|`/banner` (or `/`)|Plain Text|ASCII status banner providing instant cluster diagnostics via `curl` in terminal or CI/CD scripts.
|`/api/live/stream`|`text/event-stream`|Reactive Server-Sent Events (SSE) stream emitting real-time cluster state updates every second.
|`/api/live/snapshot`|`application/json`|Instant JSON snapshot of live coordinator state, slave connections, and token ranges.
|`/actuator/health`|`application/json`|Health check probe endpoint.
|`/actuator/metrics`|`application/json`|JVM and runtime metrics.
|===

=== Terminal Access Example

You can inspect the live status directly from your terminal using `curl`:

[source,bash]
----
curl -s http://localhost:8080/banner
----

[[docker-deployment]]
== Deploying with Docker & Docker Compose

Instead of building and maintaining a standalone Spring Boot project from scratch, developers and DevOps teams can deploy the official, pre-built **StackSaga Ring-Coordinator Docker image**.

=== Official Docker Image Flavors

The official images are published on Docker Hub and GitHub Container Registry:

[cols="2,1,1,4", options="header"]
|===
|Tag|Base OS|C Library|Recommended Use
|`stacksaga/ring-coordinator:latest`|Ubuntu Jammy|`glibc`|**Enterprise Production**: 100% compatible with APM profilers (Dynatrace, Datadog, New Relic) and native Netty epoll.
|`stacksaga/ring-coordinator:alpine`|Alpine Linux|`musl`|**Lightweight**: Minimal image footprint (~180MB) and hardened attack surface.
|===

IMPORTANT: Every coordinator container must maintain **NTP-class UTC clock discipline**. The official Docker image sets `TZ=Etc/UTC` by default. Ensure your host machine or Kubernetes worker nodes run active NTP synchronization (e.g., `chrony` or `systemd-timesyncd`).

=== Deployment Scenarios with Docker Compose

Below are copy-paste ready Docker Compose configurations for common deployment topologies.

[IMPORTANT]
====
The Docker Compose configurations below default to the lightweight **`stacksaga/ring-coordinator:alpine`** image for fast startup and minimal footprint (~180MB).

For **enterprise production environments**, switch the image tag to **`stacksaga/ring-coordinator:latest`** (Ubuntu Jammy / `glibc`), which provides full compatibility with enterprise APM profilers (Dynatrace, Datadog, New Relic) and native Netty epoll socket transport.
====

==== Scenario 1: Minimal Standalone / Hybrid (`master,slave`)

For local microservice development and single-host testing, running the coordinator in **Hybrid mode** combines the Master and Slave into a single container:

.docker-compose.minimal.yml
[source,yaml]
----
services:
  ring-coordinator:
    image: stacksaga/ring-coordinator:alpine
    container_name: stacksaga-ring-coordinator
    ports:
      - "7777:7777"   # RSocket server (Microservice Orchestrators connect here)
      - "8080:8080"   # HTTP Live Dashboard & Health Endpoints
    environment:
      - TZ=Etc/UTC
      - STACKSAGA_COORDINATOR_INSTANCE_TYPE=master,slave #<1>
      - STACKSAGA_TARGET_SERVICES=*                      #<2>
      - STACKSAGA_CLUSTER=dev-cluster
      - STACKSAGA_REGION=default
    volumes:
      - /etc/localtime:/etc/localtime:ro
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/actuator/health"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 10s
    restart: unless-stopped
----
<1> `master,slave` runs both the Master and Slave embedded in a single instance.
<2> `*` coordinates retries for all microservice domains.

Run with:
[source,bash]
----
docker compose -f docker-compose.minimal.yml up -d
----
Open `\http://localhost:8080/` in your browser to view the interactive live dashboard.

==== Scenario 3: Horizontally Scalable Cluster (`--scale coordinator-slave=N`)

In high-throughput enterprise deployments, a single Master coordinates a horizontally scalable pool of Slaves.
By omitting fixed host port mappings on the Slave service, Docker Compose can dynamically spawn any number of Slave instances:

.docker-compose.scalable.yml
[source,yaml]
----

    hostname: coordinator-master

      - "7777:7777"   # Master RSocket (Internal Slaves connect here)
      - "8080:8080"   # Master Live Dashboard (Open in browser)
    environment:
      - TZ=Etc/UTC
      - STACKSAGA_COORDINATOR_INSTANCE_TYPE=master
      - STACKSAGA_TARGET_SERVICES=*
      - STACKSAGA_CLUSTER=production-cluster
      - STACKSAGA_REGION=default

      - /etc/localtime:/etc/localtime:ro
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/actuator/health"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 10s
    restart: unless-stopped

  coordinator-slave:
    image: stacksaga/ring-coordinator:alpine
    depends_on:
      coordinator-master:
        condition: service_healthy
    environment:
      - TZ=Etc/UTC
      - STACKSAGA_COORDINATOR_INSTANCE_TYPE=slave
      - STACKSAGA_TARGET_SERVICES=*
      - STACKSAGA_CLUSTER=production-cluster
      - STACKSAGA_REGION=default
      - STACKSAGA_MASTER_HOST=coordinator-master
      - STACKSAGA_MASTER_PORT=7777
    volumes:
      - /etc/localtime:/etc/localtime:ro
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/actuator/health"]

----

Launch the cluster with 3 (or any desired number of) Slaves:
[source,bash]
----
docker compose -f docker-compose.scalable.yml up -d --scale coordinator-slave=3
----

Scale out to 5 Slaves on demand:
[source,bash]
----
docker compose -f docker-compose.scalable.yml up -d --scale coordinator-slave=5
----

===== How Dynamic Partitioning Works:
1. Each new Slave container boots up and connects to `coordinator-master:7777` over RSocket.
2. The Master registers the Slave in its active membership registry.
3. At the next **30-second boundary**, the Master recalculates token partition boundaries, dividing the Murmur3 64-bit token universe into `N` equal non-overlapping slices.
4. The Master broadcasts the updated ranges to all `N` Slaves for the upcoming 1-minute window (T+1 to T+2).
5. Visiting `\http://localhost:8080/` instantly reflects the new Slaves and their rebalanced token ranges on the dashboard.

|`Long.MAX_VALUE`
|`long`
|Maximum number of RSocket stream retry attempts before giving up. This governs recovery of the RSocket stream itself, and is distinct from the TCP `reconnect` attempts above. Defaults to `Long.MAX_VALUE` (effectively infinite), which is recommended in production so the stream is always eventually recovered.

|`stacksaga.coordinator.slave.target-master.retry.backoff-duration`
|`2s`
|`Duration`
|The initial backoff between RSocket stream retry attempts. After a failed attempt the Slave waits this long before retrying, growing on each subsequent attempt up to `max-backoff-duration`.

|`stacksaga.coordinator.slave.target-master.retry.max-backoff-duration`
|`6s`
|`Duration`
|The upper bound on the RSocket stream retry backoff. The growing backoff between retry attempts never exceeds this value.

|`stacksaga.coordinator.slave.target-master.retry.jitter`
|`0.5`
|`double`
|The jitter factor applied to the RSocket stream retry backoff. Randomizing the backoff avoids a thundering-herd problem when many Slaves reconnect to the Master at once. Must be between `0` (no jitter) and `1` (full jitter — a random value between 0 and the backoff duration).

|`stacksaga.coordinator.slave.lookup.ip-prefer`
|`false`
|`boolean`
|Controls what the Master hands back to Orchestrators when they look up the available Slaves to connect to. When `true`, the Master returns Slave IP addresses; when `false` (the default), it returns Slave hostnames.
