= Transaction Retry Architecture With Retry Coordinator

[.lead]
This article is the reference guide for the *Transaction Retry Architecture* of the StackSaga framework.
It is intended for *architects*, *DevOps engineers*, and *developers* who integrate, deploy, or operate StackSaga-based microservices.

== Introduction

In a distributed microservices architecture, transactions often span multiple services and databases, making them susceptible to failures, timeouts, and pauses.
The StackSaga framework addresses this challenge with a robust *transaction retry subsystem* that ensures reliability and consistency without risking duplicate processing or conflicts.

This subsystem detects paused transactions and re-invokes them safely across a cluster of microservice instances, using a combination of token ring partitioning, RSocket communication, and time-windowed publishing.
The result is high availability and resilience even in the face of transient failures, while guaranteeing that a stalled transaction is owned by exactly one node at a time.
Delivery semantics are *at-least-once*: a step may be re-invoked, so executors forward the engine-provided `idempotencyKey` downstream, which makes the result *effectively-once*.

=== Scope of This Document

This document focuses exclusively on the *transaction retry subsystem*.

Topics covered:

* Identifying retryable vs non-retryable errors
* Why instance-level retrying is insufficient
* Orchestrator Deployment modes: Standard-Node vs Retry-Node
* The three-component retry ecosystem: Orchestrator, Retry-Coordinator-Slave, and Retry-Coordinator-Master
* Token ring partitioning using Murmur3
* RSocket communication patterns between components
* Time-windowed token publishing and conflict avoidance
* Failure modes, reconnection behaviour, and deployment considerations
* Multi-region deployments
* Virtual cluster partitioning for massive-scale systems

== Foundational Concepts

Before diving into the architecture, two foundational concepts must be clear: what kinds of errors trigger retrying, and why retrying cannot simply be handled by the originating node.

=== Retryable vs Non-Retryable Errors

StackSaga distinguishes two classes of errors:

*Non-retryable error* — a business logic failure or permanent error condition.
These types of errors are not transient and cannot be resolved by retrying.
Examples include validation failures, authorization errors, or any condition that indicates a fundamental issue with the transaction itself.
These errors can occur in both the primary flow and the compensation flow.
In the primary flow, a non-retryable error triggers compensation; if it occurs during compensation, the transaction is marked as permanently failed.
In either case, the transaction *will not be retried*.
A step that was retried after a transient failure can still end with a non-retryable error. In that case, an earlier attempt may already have been applied, so the failing step's own compensation runs first (see xref:implementations:stacksaga-sync/orchestrator/executor_architecture.adoc#non_retryable_after_retry[Non-Retryable Failure After a Retry]).

*Retryable error* — a transient condition, such as a downstream service being unavailable, a database connection timeout, or a network partition.
The transaction is paused and will be replayed automatically.
Retryable errors can occur in both the primary flow and the compensation flow.
This is precisely where the retry subsystem comes into play, ensuring that the transaction is retried safely without duplication or conflict.

[[immediate-vs-asynchronous-retry]]
=== Immediate Retry vs Asynchronous Retry

A transient fault does not have to reach this subsystem at all.
StackSaga supports two distinct retry paths, and choosing between them is the developer's decision inside the executor.

*Immediate retry* — in-thread and developer-driven.
Inside `doProcess()`, the executor may re-attempt the failing call directly before deciding to give up on it — the request thread is still held, no state is committed, and the retry subsystem is never involved.
This is the right choice for a fault expected to clear within the lifetime of the request, and its latency is whatever the developer's own re-attempt costs.

*Asynchronous retry* — framework-driven, and the subject of this entire document.
It begins only once the executor throws `RetryableExecutorException`.
At that point StackSaga commits the in-flight state to the event store, releases the thread, and the transaction becomes the retry subsystem's responsibility: it is registered for a future recovery window and re-invoked later by whichever Retry-Node owns its token range at that time.

[NOTE]
====
The two paths are complementary, not alternatives to choose between once and for all.
Re-attempt in-thread while that is still cheap and likely to succeed; throw `RetryableExecutorException` once it is worth releasing the thread and letting the transaction be picked up later.

The latency figures discussed in <<costs-and-trade-offs>> describe the *asynchronous* path only.
They are not a limit on how quickly StackSaga can retry a transient fault.
====

=== Why Instance-Level Retrying Is Insufficient

At first glance it may seem easy to retry a transaction on the same node that originally processed it.
However, this approach has a critical flaw.

Standard nodes are *ephemeral* — they are short-lived, temporary, and designed to be created, destroyed, or replaced on-demand based on traffic.
This means that when the time comes to retry a transaction, the node that originally processed it may no longer be running.
The transaction then remains paused indefinitely with no node to reclaim it.

To make this concrete: imagine 3 instances are running and each has saved some transactions for retrying due to network issues.
If a scheduler is triggered on each instance to replay its own transactions, but one instance has since been terminated due to scale-down, the transactions it owned will never be picked up by the other instances.

image:ROOT:stacksaga-diagram-transaction-direct-retry-by-instance.drawio.svg[alt="why instance does not involve directly for retrying in StackSaga"]

StackSaga solves this by *decoupling transaction retrying from the originating node* entirely, using a three-component architecture described in the next sections.

[[orchestrator-deployment-modes]]
== Orchestrator Deployment Modes

Because orchestrator standard nodes are ephemeral, StackSaga defines two distinct deployment modes for an orchestrator service:

*Standard-Node*::
The regular orchestrator service (with StackSaga enabled) that processes transactions and handles business logic.
Standard nodes can be freely scaled up or down based on traffic.

*xref:#retry-node[Retry-Node]*::
A specialised node that handles transaction retries in addition to regular transaction processing.
Retry-Nodes are intended to be more stable and long-lived than Standard-Nodes, ensuring reliable retry management even as the rest of the cluster scales.

image::stacksaga-diagram-standard-node-vs-retry-node.svg[]

In a typical deployment you might have 5–1000 Standard-Nodes handling regular traffic and 2 Retry-Nodes that remain stable to manage retries.
There is no technical restriction on scaling Retry-Nodes up or down — the distinction is operational: they are simply the nodes you choose to keep stable.

[NOTE]
====
Retrying is the *worst-case* scenario for a transaction, not the regular flow.
See xref:foundations:proportional-analysis-of-long-running-transactions-in-saga.adoc[] for an analysis of retrying frequency and its weight relative to normal processing.
====

The next challenge is how retry responsibility is safely distributed across the cluster of Retry-Nodes without any two nodes conflicting over the same transaction.
This is where *Token Ring Partitioning* comes in.

[[token-ring-partitioning]]
== Token Ring Partitioning

=== Overview

StackSaga uses the *Murmur3 consistent hashing algorithm* to assign every transaction to a deterministic position in a 64-bit token ring.
This token is computed when the transaction is *initialised* (by any Orchestrator) and stored alongside the transaction record in the database, together with the *cluster name* and *region* of the originating Orchestrator.
The retry subsystem uses this stored token, cluster, and region to determine *which Orchestrator instance is responsible* for retrying a given transaction at any point in time.

The full token space spans from latexmath:[-2^{63}] to latexmath:[2^{63}-1]:

----
-9,223,372,036,854,775,808  →  9,223,372,036,854,775,807
----

The token ring is divided in *two levels*:

. *Master → Retry-Coordinator-Slave:* The Retry-Coordinator-Master divides the full ring equally across registered Retry-Coordinator-Slave nodes.
. *Retry-Coordinator-Slave → Orchestrator:* Each Retry-Coordinator-Slave further divides its slice equally across its registered Orchestrator instances.

== The Three-Component Retry Architecture

Token ring partitioning is managed collaboratively by three components.
Here is a brief orientation before the detailed descriptions:

[cols="1,3",options="header"]
[.google-anno-skip]
|===
| Component | Responsibility

| xref:#ring-coordinator-master[*Retry-Coordinator-Master*]
| Single authority for the domain.
Divides the full token ring equally across Retry-Coordinator-Slaves once per publish cycle.
Tells new Orchestrators which Retry-Coordinator-Slave to connect to (Round Robin).

| xref:#ring-coordinator-slave[*Retry-Coordinator-Slave*]
| Relay between Master and Orchestrators.
Receives its ring slice from the Master and divides it further across its connected Orchestrators.
Delivers each Orchestrator its personal sub-range once per publish cycle, granted for the window it covers.

| xref:#retry-node[*Orchestrator (Retry-Node)*]
| Holds its sub-range for the current minute.
Polls the database for paused transactions whose token falls in that sub-range and re-invokes them — without ever conflicting with another instance.
|===

Each component does one small job cleanly.
No component reaches into another's responsibility.
The result is a retry system that scales horizontally, tolerates partial failures, and guarantees that every paused transaction is eventually retried — by exactly one owner at a time.

[[ring-coordinator-master]]
=== Retry-Coordinator-Master

==== What It Is

The Retry-Coordinator-Master is the *single authority* for retry coordination within a microservice domain.
There is exactly *one Master per domain* (or per virtual cluster — see xref:stacksaga-database-support:cassandra-database-support/stacksaga-cassandra-support.adoc#virtual-clusters-cell-isolation[Horizontal Scaling via Virtual Clusters]).

The Master has no knowledge of your business logic and never touches the transaction database.
Its entire responsibility is coordination: dividing the token ring, tracking which Retry-Coordinator-Slaves are alive, and pointing new Orchestrators to the right Retry-Coordinator-Slave when they start up.

It is built on a *fully non-blocking Netty stack* via RSocket, which means a single Master instance can comfortably handle *thousands of concurrent Retry-Coordinator-Slave connections* — far beyond what most deployments will ever need.

==== Three Responsibilities

*Responsibility 1 — Maintain the Retry-Coordinator-Slave registry.*
Every Retry-Coordinator-Slave that starts up connects to the Master via a persistent RSocket `request-stream` and registers itself.
The Master keeps a live registry of all connected Retry-Coordinator-Slaves.
When a Retry-Coordinator-Slave disconnects (crashes, restarts), the Master notices immediately and updates its registry.

*Responsibility 2 — Publish token ring partitions once per minute.*
At the 30th second of every minute the Master fires a timer.
It looks at the current list of registered Retry-Coordinator-Slaves, divides the full 64-bit token ring equally among them, and pushes each Retry-Coordinator-Slave its assigned range, tagged as valid for the *next* full minute.
This 30-second lead gives the entire cluster time to receive and prepare the new assignments before they go live.

*Responsibility 3 — Direct new Orchestrators to a Retry-Coordinator-Slave.*
When a new Orchestrator instance starts up, it sends a one-shot `Request-Response` message to the Master asking: *"Which Retry-Coordinator-Slave should I connect to?"*
The Master picks a Retry-Coordinator-Slave using a *Round Robin* strategy — spreading Orchestrators evenly across available Retry-Coordinator-Slaves — and responds with the Retry-Coordinator-Slave's host and port.
After this single exchange the Orchestrator never contacts the Master again; all future communication goes through the Retry-Coordinator-Slave directly.

==== What It Knows and Does Not Know

Knows::
* The registered Retry-Coordinator-Slave nodes and their connection status.
* How to divide the 64-bit token ring equally using Murmur3 partitioning.
* Which Retry-Coordinator-Slave to assign to each new Orchestrator (Round Robin).

Does *not* know::
* Individual Orchestrator instances after the initial lookup.
* The transaction database.
* Your business logic or transaction structure.
* Other domain Masters — each Master is isolated to its own domain.

==== Master Node Failure

When the Master fails:

. All registered Retry-Coordinator-Slaves lose their connection to the Master.
. Retry-Coordinator-Slaves stop receiving token range updates.
Their *last known range remains cached* but expires at the next minute boundary.
. Orchestrators continue retrying using their last received sub-range until it expires.
. New Orchestrator instances starting up will fail to obtain a Retry-Coordinator-Slave assignment.

[NOTE]
====
A Master failure affects *only that domain's retry subsystem*.
Other microservice domains continue operating normally.
Primary transaction execution (new transactions) is unaffected by Master availability.

For systems where even this scoped failure window is unacceptable, see <<Virtual Clusters>>.
====

[[ring-coordinator-slave]]
=== Retry-Coordinator-Slave

==== What It Is

The Retry-Coordinator-Slave is a *dedicated infrastructure service* — a small, lightweight process deployed alongside your microservice.
It has no awareness of your business logic whatsoever.
It does not touch the transaction database.
It does not execute transactions.

Its entire purpose is to act as a *distribution bridge* between the Retry-Coordinator-Master and the Orchestrator instances: it receives a large token range from the Master and breaks it into smaller, non-overlapping sub-ranges, one for each connected Orchestrator.

==== Four-Step Routine

*Step 1 — Register with the Master.*
On startup, the Retry-Coordinator-Slave opens a persistent RSocket `request-stream` connection to the Master, announces itself, and waits for token range updates.

*Step 2 — Receive a token range slice.*
Once per minute, at the 30th second, the Master publishes updated ranges.
The Retry-Coordinator-Slave receives its slice — a contiguous portion of the full 64-bit ring — and is told which minute that slice is valid for.

*Step 3 — Accept Orchestrator registrations.*
When an Orchestrator starts up and connects, the Retry-Coordinator-Slave records it in its local registry.

*Step 4 — Divide and deliver.*
With its slice in hand and a list of connected Orchestrators, the Retry-Coordinator-Slave divides the slice equally — one non-overlapping sub-range per Orchestrator — and pushes each sub-range to the respective Orchestrator over the persistent stream.

This cycle repeats once per minute, keeping every connected Orchestrator informed of its current retry ownership window.

==== Why Have a Retry-Coordinator-Slave Layer At All?

Your service pods (Orchestrators) come and go frequently — they restart on deployments, scale up under load, scale down at night.
If the Master had to track every individual pod, it would be overwhelmed with registration and deregistration events and would constantly be recalculating the entire ring.

The Retry-Coordinator-Slave acts as a *buffer*.
The Master only needs to track a small, stable set of Retry-Coordinator-Slave nodes.
All the volatility of your application pods is absorbed by the Retry-Coordinator-Slave, which quietly adjusts its sub-range distribution whenever an Orchestrator joins or leaves — without disturbing the Master at all.

==== What It Knows and Does Not Know

Knows::
* The Master it is registered with (`stacksaga.coordinator.slave.target-master.host` / `.port`).
* The Orchestrator instances currently connected to it.
* The token range it has been assigned and how to divide it.

Does *not* know::
* Your business logic or transaction structure.
* The transaction database.
* Other Retry-Coordinator-Slave nodes — each Retry-Coordinator-Slave works independently.

==== Retry-Coordinator-Slave Node Failure

When a Retry-Coordinator-Slave crashes or becomes unreachable:

. All Orchestrators connected to that Retry-Coordinator-Slave lose their stream.
Their sub-ranges become stale; retry polling pauses for those instances.
. The Master detects the lost connection and applies a *lazy rebalance strategy*.
In no case is the lost range redistributed inside a window that is already in progress — redistribution happens only when a new division is computed at a publish cycle.
** The crashed Retry-Coordinator-Slave's token range is *frozen*: no Orchestrator covers it for the remainder of the current window.
** If the lost Retry-Coordinator-Slave is *not the last index* in the registry, the Master assumes it will be rescheduled shortly — which is the normal case in Kubernetes — and does not recompute the division around its absence.
It keeps sending the existing cached ranges to the remaining Retry-Coordinator-Slaves, so the surviving nodes' ranges do not shift underneath them.
** If the lost Retry-Coordinator-Slave *is* the last index, removing it does not disturb any other node's boundaries, so the next division simply excludes it and the remaining nodes divide the full ring between them.
. When the Retry-Coordinator-Slave restarts it reconnects to the Master and is treated as a *new registration*.
Like any late registration it receives no range for the window already in progress.
. At the next publish cycle the Master recalculates and redistributes ranges across all currently registered Retry-Coordinator-Slaves, including the restarted one.

[IMPORTANT]
====
During a Retry-Coordinator-Slave outage, transactions whose tokens fall within the frozen range are *not retried* until the range is covered again.
They remain safely stored in the event store and are not lost — this is the liveness cost described in <<costs-and-trade-offs>>.
====

[[retry-node]]
=== Orchestrator With Ring-Coordinator connector (Retry-Node)

Retry-Node stands for an Orchestrator instance that is deployed with the StackSaga xref:ring-coordinator-connector.adoc[] enabled to participate in the transaction retry ecosystem.
It is specialised node that handles transaction retries in addition to regular transaction processing.
Retry-Nodes are intended to be more stable and *long-lived* than Standard-Nodes, ensuring reliable retry management even as the rest of the cluster scales.

* To make a Standard-Node into a Retry-Node, simply add the `stacksaga-ring-coordinator-connector` dependency to the existing Orchestrator service and configure the connection properties.
* There is no technical restriction on scaling Retry-Nodes up or down — the distinction is operational: they are simply the nodes you choose to keep stable.
* Once configured as a Retry-Node, the Orchestrator automatically participates in the retry ecosystem. initially it connects to the Master to look up a Retry-Coordinator-Slave to be registered with, then it receives token sub-ranger(respective partition of the node) from the assigned Retry-Coordinator-Slave and starts retrying transactions that fall into the sub-range.

It runs two jobs side by side at all times.

==== Two Concurrent Jobs

*Job 1 — Execute transactions (regular orchestrator role).*
When a new business operation arrives (a customer places an order, for example), the Orchestrator creates a transaction, breaks it into *spans*, and executes them one by one — calling downstream services, updating databases, firing events.
If a span fails with a permanent error, it starts a *compensation* sequence to undo what was already done.

*Job 2 — Recover transactions that are no longer moving.*
Some spans stop advancing for reasons that have nothing to do with business logic.
StackSaga does not discard these transactions — it records them and re-invokes them later.
The Orchestrator checks the event store for the work it is currently *responsible for*, based on the token range it holds for the current window, and re-invokes each transaction's next pending span.
This is how StackSaga guarantees that multiple running instances never retry the same transaction at the same time.

[[what-a-retry-node-recovers]]
==== What a Retry-Node Recovers

Job 2 covers three distinct situations, all of which arrive through the same grant and the same token range:

[cols="1,3",options="header"]
[.google-anno-skip]
|===
| Situation | How it reaches the Retry-Node

| *Retryable failure*
| An executor threw `RetryableExecutorException`.
The in-flight state was committed and the transaction was registered for a future recovery window.
This is the path described throughout this document.

| *Expired wait-state (Pausable LRT)*
| An executor parked the saga with `.pauseUntilResume(duration)` and the expected callback never arrived within that duration.
The Retry-Node re-invokes the parked executor's `doProcess(...)` rather than waiting indefinitely.
See xref:ROOT:lrt-transaction-models.adoc[Long-Running Transaction Models] and xref:implementations:stacksaga-sync/orchestrator/stacksaga_template.adoc#advanced-architectural-faq[FAQ Q1 & Q2].

| *Silent crash (Restore)*
| The pod died mid-transaction — OOM kill, eviction, power loss — so no error was ever recorded anywhere.
Nothing distinguishes this transaction from one still running, which is why it is discovered by a separate mechanism rather than by looking for a failure.
See <<retry-vs-restore>>.
|===

[[retry-vs-restore]]
==== Retry vs Restore

*Retry* handles a failure the framework *knows about*: an executor reported a transient fault, so there is a record to act on.

*Restore* handles a failure nobody reported.
When a pod is killed mid-transaction there is no exception, no log entry and no status change — the transaction simply stops.
To catch this, a Standard-Node arms a *dead-man's switch* when a transaction starts: a watchdog record placed in a far-future recovery window, which is deleted when the transaction completes normally.
If the transaction never completes, the watchdog is never deleted, and when that future window eventually comes up for processing a Retry-Node finds it and re-invokes the transaction.

Both features share the same Retry-Node pool, the same token ring and the same ownership model — a Retry-Node does not run two schedulers.
In the Cassandra implementation they are kept apart inside the directory by bucket parity: even buckets carry Retry work and odd buckets carry Restore work, so a sweep of one never reads the other's partitions.
One Retry-Node — the holder of the lowest range, referred to as *Node-0* — additionally prunes completed windows from the directory while operating as a normal recovery worker.

See xref:stacksaga-database-support:cassandra-database-support/stacksaga-cassandra-support.adoc[Cassandra Support] for the directory layout, bucket parity and the compaction protocol.

NOTE: Restore detection is deliberately far-dated — the watchdog sits hundreds of windows ahead of the transaction that armed it, because it must not fire while the transaction is merely slow. That delay is configurable; see <<costs-and-trade-offs>>.

==== What It Knows and Does Not Know

Knows::
* Its own business logic and transaction spans.
* The token sub-range it currently holds (delivered by its Retry-Coordinator-Slave).
* The transaction database — it reads and writes transaction records directly.

Does *not* know::
* Other Orchestrator instances — there is no peer-to-peer communication between service instances.
* The Retry-Coordinator-Master — after the initial startup handshake, the Orchestrator never contacts the Master again (unless the Retry-Coordinator-Slave connection is lost and must be re-established).
* How the token ring works internally — it simply receives a range and uses it.

==== Orchestrator (Retry-Node) Failure

When an Orchestrator instance fails and restarts:

. It performs a fresh `Request-Response` lookup to the Master for an available Retry-Coordinator-Slave (potentially receiving a *different Retry-Coordinator-Slave* due to Round Robin).
. It opens a new persistent stream to the newly assigned Retry-Coordinator-Slave.
. It receives a range at the next publish cycle and resumes retrying.
As a late registration it is granted nothing for the window already in progress, and stays idle until that cycle.

Any transactions being actively retried at the moment of failure are *not* taken over by another instance during the current window.
The failed instance's range simply stays uncovered until that window ends, because a grant is never reclaimed.
Those transactions are re-attempted once a later division assigns that part of the ring to a live Orchestrator — see <<conflict-avoidance>>.

  orc -> db : resolve owned work for\n[subRangeStart, subRangeEnd]\nscoped by cluster + region
  db -> orc : transactions awaiting re-invocation
  orc -> orc : re-check UTC window,\nthen re-invoke next pending span
end

@enduml
----

=== Step-by-Step Description

==== Phase 1 — Retry-Coordinator-Slave Registration

. On startup, each Retry-Coordinator-Slave opens a persistent *RSocket `request-stream`* connection to the Retry-Coordinator-Master.
. The Master records the Retry-Coordinator-Slave in its registry.
. The Retry-Coordinator-Slave remains connected and passively waits for token range updates.

==== Phase 2 — Orchestrator Registration

. On startup, each Orchestrator sends a *RSocket `Request-Response`* message to the Master requesting an available Retry-Coordinator-Slave assignment.
. The Master applies *Round Robin* to select a Retry-Coordinator-Slave and returns the Retry-Coordinator-Slave's host and port.
+
NOTE: If the same Orchestrator instance restarts, it may receive a *different* Retry-Coordinator-Slave assignment, as the Round Robin pointer advances.
This ensures balanced Orchestrator distribution across Retry-Coordinator-Slaves over time.
. The Orchestrator opens a persistent *RSocket `request-stream`* connection to its assigned Retry-Coordinator-Slave and begins listening for sub-range updates.

==== Phase 3 — Token Range Distribution

. At the 30th second of every minute the Master fires its publish timer.
. The Master partitions the full token ring equally among all registered Retry-Coordinator-Slaves and sends each Retry-Coordinator-Slave its range, granted for the absolute interval from minute `T+1` until minute `T+2`.
. Each Retry-Coordinator-Slave divides its range equally among its registered Orchestrators and pushes sub-range updates downstream, carrying the same interval.
. Each Orchestrator stores the received grant, activates it at the start of minute `T+1`, and stops polling with it at the end of minute `T+1` — the grant carries its own expiry, so nothing has to revoke it.

==== Phase 4 — Retry Execution Loop

Once the granted window is active, each Orchestrator enters its retry loop:

. Resolve the granted token range to the transactions it owns, scoped by `cluster` and `region`.
How that resolution happens depends on the event-store implementation — see <<resolving-a-token-range-to-transactions>>.
. For each resolved transaction, re-check that the current UTC time is still inside the grant, then re-invoke the next pending span.
. Stop when the grant expires.
Expiry is part of the grant itself; nothing has to supersede or revoke it.

[[resolving-a-token-range-to-transactions]]
=== Resolving a Token Range to Transactions

The grant is identical in every deployment: a token range plus a UTC window, issued by the same two-level hierarchy.
What differs between event-store implementations is how a Retry-Node turns that range into a concrete set of transactions to re-invoke.

Both paths use Murmur3, and both honour the same grant.
Only the key being hashed for the lookup differs, and it differs because of how each database stores transactions.

*General model (SQL event stores)*::
Each transaction carries its own Murmur3 token, assigned at initialisation and stored on the record alongside `cluster` and `region`.
The Retry-Node queries the transaction store directly for records whose token falls inside its granted range:
+
[source,sql]
----
SELECT *
FROM   transactions
WHERE  token   BETWEEN :rangeStart AND :rangeEnd
AND    region  = :region
AND    cluster = :cluster
AND    status  = 'FAILED_WITH_RETRYABLE_ERROR';
----
+
The reactive batch-fetch and concurrency pipeline that executes this loop is tuned through the
`stacksaga.transaction.recovery-node.*` properties — see
xref:stacksaga-database-support:sql-database-support/stacksaga-sql-configuration-properties.adoc[SQL Configuration Properties].

*Cassandra*::
A flat table used as a polling queue is a documented Cassandra anti-pattern: there is no global index across partitions, and continuous insert-and-delete traffic buries live rows behind tombstones.
Cassandra therefore does not resolve the range against each transaction's own token.
Instead, a Standard-Node that hits a transient failure registers *itself* — its `instance_id` and `token(instance_id)` — into a recovery window, and the Retry-Node matches its granted range against `instance_id_token` to discover *which pods* have pending work.
It then descends a five-tier directory (day → UTC minute window → pod instances → buckets → transaction pointers) and hydrates each transaction lazily by `transaction_id`.
+
Every query along that path supplies a full composite partition key, so no range scan is ever issued.
See xref:stacksaga-database-support:cassandra-database-support/stacksaga-cassandra-support.adoc#cassandra-directory-architecture[Why Cassandra Requires a Directory-Based Architecture] for the mechanics.

[NOTE]
====
The ownership model in <<ownership-model>> is unaffected by this difference.
Whichever lookup an implementation uses, the Retry-Node acts only inside a granted range during a granted UTC window, and two nodes never hold the same range at the same time.
====

=== RSocket Communication Patterns

StackSaga uses https://rsocket.io[RSocket] for all inter-component communication, chosen for its support for persistent, reactive, bidirectional streams backed by a non-blocking Netty transport.

[cols="2,1,2",options="header"]
[.google-anno-skip]
|===
| Connection | Interaction Model | Description

| Retry-Coordinator-Slave → Master
| `Request-Stream`
| Persistent subscription. Retry-Coordinator-Slave registers with Master and keeps the stream open to receive token range updates.

| Orchestrator → Master
| `Request-Response`
| One-shot lookup. Orchestrator requests an available Retry-Coordinator-Slave node assignment from Master on startup.

| Orchestrator → Retry-Coordinator-Slave
| `Request-Stream`
| Persistent subscription. Orchestrator subscribes to its assigned Retry-Coordinator-Slave and keeps the stream open to receive sub-range updates.
|===

[[ownership-model]]
== The Ownership Model

Token ring partitioning decides *what* each node is responsible for.
This section describes *how* that responsibility is held, which is the part of the design that makes retrying safe without a single lock anywhere in the system.

=== The Publish Cycle

The Retry-Coordinator-Master runs a repeating timer that fires at the *30th second of every minute* — once per minute, not twice.
At each trigger the Master:

. Recalculates the token ring partition based on currently registered Retry-Coordinator-Slaves.
. Publishes the new token range to each Retry-Coordinator-Slave.
. Each Retry-Coordinator-Slave recalculates its sub-ranges and pushes updates to its registered Orchestrators.

The range is not merely *labelled* for the next minute — it is issued together with the absolute UTC interval over which it belongs to that node, as described in <<a-grant-is-a-range-plus-a-window>>.

=== Why the 30-Second Offset?

Publishing at the 30th second and granting the range for the *next* minute creates a *30-second preparation window*.
This window accounts for worst-case communication delays: Retry-Coordinator-Slave distribution, Orchestrator updates, and network latency in large clusters.

By the time minute `T+1` begins, all Orchestrators are guaranteed to have received their new sub-ranges and are ready to start polling.

----
Timeline example:

  Minute T, second 30 → Master publishes ranges (valid for T+1)
  Minute T, second 31–59 → Retry-Coordinator-Slaves and Orchestrators receive and cache new ranges
  Minute T+1, second 0  → Orchestrators begin polling with new ranges
  Minute T+1, second 30 → Master publishes ranges for T+2
  ...
----

[[a-grant-is-a-range-plus-a-window]]
=== A Grant Is a Range Plus a Window

A node is never given a token range on its own.
It is given a *grant*: a token range **together with** the absolute UTC interval over which that range belongs to it.

----
grant = { rangeStart, rangeEnd, validFrom, validUntil }   // validFrom / validUntil are UTC
----

Both levels of the hierarchy issue grants for the *same* window:

. The Master divides the full 64-bit ring across its registered Retry-Coordinator-Slaves for window `T+1`.
. Each Retry-Coordinator-Slave divides its own slice across its registered Orchestrators for that same window `T+1`.

A Retry-Node receives nothing beyond this.
There is no lock to acquire, no fencing token to present and no dispatcher to ask — the range and the interval are the entire contract.

=== Expiry Is Enforced by the Holder

Nothing revokes a grant.
The holder itself decides whether it is still inside the granted interval by reading its own UTC clock, and it makes that decision at *two* points:

. *Before polling* — the window must be current, or the node does not query the event store at all.
. *Before every single transaction invocation* — the check is repeated.
If the clock has passed `validUntil`, that transaction is *skipped without being retried*.

The second check is the load-bearing one.
A batch fetched while the window was still open but which crosses the boundary mid-processing *stops mid-batch*: the remaining transactions in that batch are skipped rather than retried under an expired grant.

[NOTE]
.Why the check is per invocation rather than once per window
====
There is no guarantee that the same token range returns to the same node in the next window.
A node therefore cannot assume that, because it owned a range a moment ago, it may finish its batch slightly past the boundary — past that boundary those tokens may already belong to another node.
The check has to sit immediately before the transaction is touched, which is the last possible moment at which it is still meaningful.
====

Skipping costs nothing at a normal boundary.
Because grants are published 30 seconds ahead, every node is *already holding* the next window's grant by the time the current one expires.
A transaction skipped at the boundary is therefore re-exposed immediately — to the same node if the new division gave it the same range, or to another node if that part of the ring moved.
Skipping is a handover, not a deferral.

IMPORTANT: Because each holder enforces its own expiry by reading its own clock, synchronised UTC time across every Master, Slave and Retry-Node is a deployment requirement rather than a recommendation. See <<costs-and-trade-offs>>.

=== Membership Is Closed for the Window

A division is computed from the nodes registered *at that instant*, and it is then fixed for the window it covers.

An Orchestrator or Retry-Coordinator-Slave that registers **after** a division has been computed receives no range from it.
It stays *idle* until a later division includes it.
This is why scaling Retry-Nodes up does not take effect within the window already in progress.

[[conflict-avoidance]]
=== Conflict Avoidance

Two Orchestrator instances can never claim responsibility for the same transaction, and no distributed locking is used to achieve it.

The guarantee does *not* follow from the sub-ranges being disjoint alone — disjointness closes only one of four routes to a conflict.
It follows from four separate properties of the protocol, which together leave no interval in which one range has two holders:

[cols="1,2",options="header"]
[.google-anno-skip]
|===
| Route to a conflict | Why it cannot occur

| *Reassignment during a window*
| A grant is never revoked.
If its holder is lost mid-window, the range is left *uncovered* until that window ends — the Master does not redistribute it among the survivors.

| *Admission during a window*
| A node that registers after a division has been computed receives no range from it.
It stays idle until a later division includes it.

| *A range outliving its window*
| Expiry is part of the grant, and the holder re-checks it against its own UTC clock before every transaction invocation.

| *Two sub-ranges of one division intersecting*
| Each division is a partition of the 64-bit ring — the sub-ranges are disjoint by construction.
|===

[IMPORTANT]
.Why no fencing token is needed
====
Systems that **reclaim** a work assignment when it expires must also *fence* the previous holder, because reclamation is what can produce two nodes that each believe they own the same work.
A fencing token — such as the `rangeID` used by Cadence and Temporal — exists to make the displaced holder's writes fail.

StackSaga never reclaims.
Declining to reassign a vacated range is precisely what guarantees that a second holder is never created, which is why no fencing token, row lock or distributed lock appears anywhere in this design.
====

The cost of this choice is paid in *liveness*, never in safety: transactions inside an uncovered range are not retried until a later division covers that part of the ring again.
They are never lost.
See <<costs-and-trade-offs>> for the full accounting.

[[multi-region-deployment]]
== Multi-Region Deployment

For systems deployed across multiple geographic regions, StackSaga uses the `region` property to scope retry ownership.
Every component — Master, Retry-Coordinator-Slave, and Orchestrator — is stamped with the region it belongs to.

=== How Region Scoping Works

When a transaction is created it inherits the region of the Orchestrator that created it.
That region value is stored in the transaction record in the database.

During the retry loop, each Orchestrator applies `region` as a mandatory scope alongside the token range.
In the general model that is a filter on the query itself:

.General model — region as a query filter
[source,sql]
----
SELECT *
FROM   transactions
WHERE  token   BETWEEN :rangeStart AND :rangeEnd
AND    region  = :region
AND    cluster = :cluster
AND    status  = 'FAILED_WITH_RETRYABLE_ERROR';
----

In Cassandra the same scope is enforced structurally instead: `region` is part of the composite partition key of every recovery directory table, so a query simply cannot reach another region's partitions.
See <<resolving-a-token-range-to-transactions>>.

Either way the guarantee is the same — an Orchestrator in `us-central` never picks up and retries a transaction that was originally created by an Orchestrator in `asia-south`, even when both regions share one globally replicated database.

== Virtual Clusters

=== Why Virtual Clusters?

In very large deployments the single-master-per-domain model presents two concerns as the system grows:

. *Scale* — a single Master must manage all Retry-Coordinator-Slave connections for the domain.
Although the Master's non-blocking Netty stack via RSocket can handle thousands of concurrent Retry-Coordinator-Slave connections, some extreme-scale deployments may want to distribute this coordination load further.

. *Fault isolation* — if the domain's single Master goes down, the entire domain's retry subsystem pauses until it recovers.
Some systems require that a partial infrastructure failure never affects more than a defined fraction of retry capacity.

Virtual clusters address both concerns by dividing a single physical deployment into *multiple independent master-slave groups*, each operating as a completely separate retry coordination unit within the same region.

[[virtual-cluster]]
=== What Is a Virtual Cluster?

A virtual cluster is a named group of Retry-Coordinator-Master, Retry-Coordinator-Slave, and Orchestrator instances that operate in full isolation from other groups.
The group identity is declared via the `stacksaga.instance.cluster` property.

All three components sharing the same cluster name form one logical retry cluster:

* The Master only accepts registrations from Retry-Coordinator-Slaves with a matching cluster name.
* The Retry-Coordinator-Slave connects only to the Master of its cluster (`stacksaga.coordinator.slave.target-master.host` / `.port`).
* The Orchestrator connects only to the Master of its cluster for the initial Retry-Coordinator-Slave lookup, and subsequently to the Retry-Coordinator-Slave assigned by that Master.
* Retry queries are filtered by cluster name in addition to token range and region.

Two virtual clusters running in the same physical Kubernetes cluster are *completely isolated* — they share no state, no connections, and no retry responsibility.

=== Deployment Topologies

*Multi-Region Single-Cluster*::
The simplest multi-region setup — one virtual cluster per region.
This is the baseline configuration for geographic distribution.

*Multi-Region Multi-Virtual-Cluster*::
For the highest levels of scale and fault isolation, each physical region can host *multiple virtual clusters*.
If any single Master fails, only the fraction of transactions belonging to that virtual cluster is affected — the remaining virtual clusters in the same region continue retrying normally.

=== Transaction Ownership Across Virtual Clusters

A transaction is permanently bound to the region and cluster of the Orchestrator that created it.
No other virtual cluster — even within the same region — will ever attempt to retry it.

Retry ownership always carries both `region` and `cluster` as mandatory scope, in addition to the token range:

.General model — region and cluster as query filters
[source,sql]
----
SELECT *
FROM   transactions
WHERE  token   BETWEEN :rangeStart AND :rangeEnd
AND    region  = 'us-central'        -- physical region
AND    cluster = 'us-central-c1'     -- virtual cluster
AND    status  = 'FAILED_WITH_RETRYABLE_ERROR';
----

This maps especially well onto Apache Cassandra, where `region` and `cluster` form part of the composite partition key of every recovery directory table.
There the isolation is physical rather than filtered: queries from two virtual clusters land in different partitions altogether, so the database routes each one directly to the correct nodes with no full-table scan.

[[costs-and-trade-offs]]
== Costs and Operational Trade-offs

The ownership model buys lock-free safety, and it is not free.
This section states what it costs, so the trade can be evaluated rather than discovered in production.

Almost every cost below is paid in *liveness* — work waits — and not in correctness.
That is the deliberate shape of the design: StackSaga would rather leave a range uncovered for a while than risk two nodes retrying the same transaction.

=== Paid in Liveness

*An uncovered range stays dark for up to two windows.*
When a Retry-Node is lost mid-window its range is not handed to a survivor, so the length of the gap depends on where in the cycle the loss happened.
A node lost at `T+1:20` is already absent when the next division is computed at `T+1:30`, so its tokens are covered again from `T+2:00` — a gap of roughly 40 seconds.
A node lost at `T+1:35`, *after* that division was computed, is still the grant holder for `T+2`, so its range stays dark for the remainder of `T+1` *and* the whole of `T+2`, and is only covered again at `T+3:00` — a gap of roughly 85 seconds.

The worst case is therefore just under two windows, and which case applies depends only on whether the loss happened before or after the publish cycle.

*A Retry-Coordinator-Slave outage freezes its entire slice.*
Losing an Orchestrator darkens one sub-range; losing a Slave darkens the whole slice that Slave was dividing, across all of its Orchestrators.
Lazy rebalance means the Master deliberately does not redistribute that slice, on the assumption the Slave will be rescheduled shortly.
This is the larger of the two failure modes.

*A Master outage across a window boundary stalls the subsystem.*
Nodes finish the window they already hold and then stop, because no new grants are issued and no new Orchestrator can register.
Primary transaction execution is unaffected, and nothing is lost — but retrying in that cluster pauses until the Master returns.

*New capacity is idle for up to a window.*
Membership is closed when a division is computed, so Retry-Nodes added to drain a backlog contribute nothing until the next division includes them.
This is worth knowing precisely because scaling up is the natural reaction to a backlog.

*A window boundary costs a re-read, not a stall.*
Rows already fetched in a batch that crosses the boundary are discarded and read again by whichever node owns them next.
Nothing waits for a later window: the next grant is published 30 seconds ahead, so a transaction skipped at the boundary is re-exposed at that same boundary.
The cost is the repeated read.

*An even ring split is not an even work split.*
The ring is divided into equal token ranges, not into equal amounts of work.
A range that happens to contain a disproportionate share of pending work leaves one Retry-Node saturated while its peers sit idle, and there is no work-stealing to correct it — stealing would require reclaiming a range, which the model forbids by design.
Scaling out helps at the next division; it does not rebalance the window in progress.

=== Paid in Latency

*Asynchronous retry carries a floor of roughly 10 to 70 seconds.*
A transient failure is registered into the *next* window rather than the current one, which gives a service that is restarting time to come back before anything retries it.
A retry that fails again is registered forward once more, so each successive attempt costs another window.

IMPORTANT: This floor applies to the asynchronous path only. A fault that should be retried in milliseconds belongs in an in-thread re-attempt inside the executor — see <<immediate-vs-asynchronous-retry>>.

*Silent-crash detection is far-dated by default.*
The Restore watchdog is armed hundreds of windows ahead of the transaction that set it — ten hours ahead in the default Cassandra configuration — because it must not fire while a transaction is merely slow.
A pod that dies silently is therefore recovered on the order of hours, not minutes, unless that delay is tuned down.
The delay is configurable per domain entity; see xref:stacksaga-database-support:cassandra-database-support/stacksaga-cassandra-support.adoc[Cassandra Support].

=== Required Operationally

*Every component must keep NTP-class UTC synchronisation.*
Each holder decides whether it is inside its granted window by reading its own clock, so clock discipline is a deployment requirement for the Master, every Slave and every Retry-Node — not a recommendation.

The degradation is bounded rather than sudden.
Window granularity is one minute, registration happens a window ahead, directory pruning re-checks the wall clock before deleting anything, and recovery windows are traversed chronologically, so sub-second to few-second drift — the normal case in a cloud VPC — is absorbed outright.
Severe drift of several minutes on a degraded pod causes it to register a window early or late; that window is still discovered and recovered later, rather than lost.
See xref:stacksaga-database-support:cassandra-database-support/stacksaga-cassandra-support.adoc[Cassandra Support] for the detailed analysis.

=== Paid in Operational Surface

*There is more to run.*
A Master and its Slaves have to be deployed, configured and monitored — or embedded into an existing service — for a code path that, by design, handles the worst case rather than the normal flow.
See xref:foundations:proportional-analysis-of-long-running-transactions-in-saga.adoc[] for how often that worst case actually occurs.
Retry-Nodes are additionally expected to stay stable and long-lived, which pulls against aggressive autoscaling of the same service.

*Cassandra deployments pay a write cost on the happy path.*
Registering a transient failure writes across five directory tiers, and *every* transaction — including every successful one — arms a watchdog row at start and deletes it on completion.
Successful transactions therefore carry part of the recovery machinery's cost, along with the resulting tombstone and compaction pressure.
This is the price of avoiding range scans on a database that cannot support a polling queue; see xref:stacksaga-database-support:cassandra-database-support/stacksaga-cassandra-support.adoc[Cassandra Support].

== Glossary

[cols="1,3",options="header"]
[.google-anno-skip]
|===
| Term | Definition

| *Span*
| A single, trackable unit of work within a distributed transaction.
A transaction is composed of one or more sequential spans.

| *Token*
| A 64-bit integer derived from the Murmur3 hash of a transaction ID.
Used to deterministically assign the transaction to a retry owner.

| *Token Ring*
| The full 64-bit integer space divided into contiguous, non-overlapping ranges.
StackSaga uses the Murmur3Partitioner model, identical in principle to Apache Cassandra's token ring.

| *Token Range*
| A contiguous subset of the token ring, granted to a Retry-Coordinator-Slave or Orchestrator for a given time window.

| *Grant*
| A token range together with the absolute UTC interval over which it belongs to a node (`validFrom` / `validUntil`).
A grant is never revoked or reclaimed; it expires on its own and the holder enforces that expiry against its own clock.
See xref:#ownership-model[The Ownership Model].

| *Time Window*
| The one-minute UTC interval of a grant, during which exactly one Orchestrator holds that sub-range.
Enforced by the holder reading its own clock, before polling and again before every transaction invocation.

| *Publish Cycle*
| The repeating event at the 30th second of every minute — once per minute — in which the Master computes a new division of the token ring for the following window.

| *Membership Closed*
| The rule that a division is computed from the nodes registered at that instant and then fixed for the window it covers.
A node that registers later receives no range from that division and stays idle until the next one.

| *Compensation*
| The rollback sequence executed when a non-retryable error occurs in the primary transaction flow.

| *Murmur3Partitioner*
| A consistent hashing scheme using the MurmurHash3 algorithm to evenly distribute keys across the token ring.

| *Region*
| A physical deployment boundary (e.g., `default`, `us-central`, `asia-south`).
Declared via `stacksaga.instance.region`. Stored on transactions (encoded as a 12-bit code in `SagaUUID`) and used as a mandatory retry query filter. See xref:ROOT:saga-region-resolver.adoc[`SagaRegionResolver`].

| *Virtual Cluster*
| A named logical group of Master, Retry-Coordinator-Slave, and Orchestrator instances that operate in complete isolation from other groups.
Declared via `stacksaga.instance.cluster`. Allows multiple independent retry units within the same physical region.

| *RSocket*
| A binary application-level protocol supporting four interaction models: `fire-and-forget`, `request-response`, `request-stream`, and `request-channel`. StackSaga uses `request-response` and `request-stream`.

| *Lazy Rebalance*
| The Master's strategy of deferring token ring recalculation until the next scheduled publish cycle,
rather than reacting immediately to Retry-Coordinator-Slave disconnections.

| *Standard-Node*
| An ephemeral Orchestrator instance that handles transaction processing and is scaled freely based on traffic.

| *Retry-Node*
| A stable, long-lived Orchestrator instance that handles both transaction processing and transaction retry management.
|===

=== Clustered Ring-Coordinator Deployment

In this topology, the master and slave instances are deployed as separate services(instances) for scalability and fault tolerance.
it can be further categorized into three modes.

[[shared-clustered-ring-coordinator-deployment]]
==== Shared Mode Of Clustered Ring-Coordinator Deployment

This is a bit more resource efficient deployment topology where a single Ring-Coordinator Cluster (one Master and multiple Slaves) is shared across multiple microservice domains within the same physical region.
For instance, if there are three microservice domains (Order, Payment, Inventory) in the `us-central` region, there will be one shared Ring-Coordinator Cluster (Shared-RC-Cluster) with one Master and multiple Slaves serving all three domains.

See the diagram below,

image::stacksaga-diagram-clustered-ring-coordinator-shared-mode.svg[]

[[dedicated-clustered-ring-coordinator-deployment]]
==== Dedicated Mode Of Clustered Ring-Coordinator Deployment

This is the maximally decoupled deployment topology where the Ring-Coordinator Master and Slave are deployed as separate services for each microservice domain separately.
This mode provides the highest level of isolation and fault tolerance, as each domain has its own dedicated Ring-Coordinator Cluster withing the same physical region.
For instance, if there are three microservice domains (Order, Payment, Inventory) in the `us-central` region, there will be three separate Ring-Coordinator Clusters (Order-RC-Cluster, Payment-RC-Cluster, Inventory-RC-Cluster), each with its own Master and Slaves.

See the diagram below,

image::stacksaga-diagram-clustered-ring-coordinator-dedicated-mode.svg[]

[[hybrid-clustered-ring-coordinator-deployment]]
==== Hybrid Mode Of Clustered Ring-Coordinator Deployment

This is a flexible deployment topology where some microservice domains have their own dedicated Ring-Coordinator Cluster, while others share a common Ring-Coordinator Cluster.
For instance, if there are three microservice domains (Order, Payment, Inventory) in the `us-central` region, the Order domain may have its own dedicated Ring-Coordinator Cluster (Order-RC-Cluster), while the Payment and Inventory domains share a common Ring-Coordinator Cluster (Shared-RC-Cluster).

[[kubernetes-statefulset-clustered-deployment]]
==== Kubernetes StatefulSet Deployment for Clustered Coordinators

In containerized Kubernetes environments, a Clustered Ring-Coordinator is recommended to run as a **StatefulSet**.

StatefulSets provide stable network identities and predictable ordinal indexing for each replica (`coordinator-0`, `coordinator-1`, `coordinator-2`, etc.).
StackSaga Ring-Coordinator natively leverages this through index-based deployment (`stacksaga.coordinator.deploy.index-based=true`):

* The replica with index **`0`** (`coordinator-0`) automatically boots as the **Master** node.
* All replicas with index **`> 0`** (`coordinator-1`, `coordinator-2`, etc.) automatically boot as **Slave** nodes.

This design enables operations teams to maintain a single unified StatefulSet manifest and ConfigMap for the entire coordinator cluster, eliminating the need to maintain separate deployment configurations for Master and Slave instances.

For full configuration guidelines and properties, see xref:ring-coordinator.adoc#kubernetes-statefulset-deployment[Automated Role Detection via Kubernetes StatefulSet in the Ring-Coordinator guide].

== When Retrying Stops

Retrying is not unbounded.
A transaction carries a *lifetime*, and the retry subsystem keeps re-invoking it only while that lifetime lasts.
A transaction that never completes within its lifetime becomes a *disabled transaction*, and one that fails while compensating becomes a *terminated transaction*.
Neither is retried again until an operator restores it.

See xref:disabled-and-terminated-transaction.adoc[] for what causes each case and how to restore them.
