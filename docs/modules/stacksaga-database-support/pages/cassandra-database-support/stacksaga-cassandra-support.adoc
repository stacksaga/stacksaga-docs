= StackSaga Cassandra Reactive Support

`stacksaga-cassandra-reactive-support` is the reactive (non-blocking) Cassandra adapter for the StackSaga engine, providing the Cassandra implementation of the xref:stacksaga-database-support:overview/database-support-overview.adoc[].
It handles two core concerns that every distributed transaction system must address:

* **Event Store** — persisting the transactional state, execution tryout history, and idempotency markers of every saga.
* **Recovery Engine** — an autonomous, tombstone-free 5-tier directory architecture that automatically recovers transactions that encountered transient network failures (**Retry**) or disappeared due to ungraceful server crashes (**Restore**), without developer intervention.

This guide covers both concerns comprehensively, starting with setup steps and progressing into a deep dive of the database schema, write protection mechanics, and the Recovery Engine internal architecture.

.StackSaga Cassandra Ecosystem Architecture
image::stacksaga-database-support:cassandra/stacksaga-ecosystem-overview.svg[alt="StackSaga Cassandra Ecosystem Architecture"]

The system operates across three interconnected environments:

<1> **Microservice Application Pod:** Live Spring Boot microservices (such as `order-service`) integrating `stacksaga-spring-boot-starter` and `stacksaga-cassandra-reactive-support`.
<2> **Apache Cassandra Cluster:** Distributed data tier storing both the Core Event Store (`es_transaction`, `es_transaction_tryout`) and the 5-Tier Recovery Directory.
<3> **StackSaga Trace Window:** Central web observability console connected via the StackSaga Agent sidecar for real-time visualization of saga execution state (see xref:trace-window:stacksaga-trace-window.adoc[]).

[IMPORTANT]
====
*Retry Ordering Guarantee (Murmur3 Token Order vs.
Strict FIFO):* +
In distributed architectures, transient retries occur when a downstream microservice is temporarily slow, restarting, or experiencing network latency.
In Cassandra, rows are distributed across cluster nodes via the **Murmur3 token hash**.

Within an individual 1-minute retry window, transactions are discovered by retry nodes (workers) in **token order** (via Murmur3 token range slicing), not by exact failure millisecond.
Across different minute windows and calendar days, retry processing is **strictly chronological** (earlier minute windows and earlier calendar dates are always traversed first).

*Architectural Recommendation for Strict Sequential FIFO Requirements:* +
For the vast majority of microservice domains (such as e-commerce, banking, logistics, and telecom), token order within a 1-minute retry window is standard and safe, because once the downstream dependency recovers, all failed transactions from that minute resolve successfully.
However, if your system contains a strict requirement for exact microsecond First-In, First-Out (FIFO) retry ordering between concurrent users (such as financial order-matching engines), StackSaga recommends using **one of the SQL database support modules** (xref:postgresql-database-support/stacksaga-postgresql-support.adoc[PostgreSQL] or xref:mysql-database-support/stacksaga-mysql-support.adoc[MySQL]) specifically for the event store.
====

[#step-2-create-keyspace-and-schema]
=== Step 2: Create the Keyspace and Schema

StackSaga uses **one shared keyspace** and **static table names** across all services and environments.
Multi-tenancy, service scoping, regional boundaries, and virtual clusters are isolated via composite Partition Keys (`PRIMARY KEY ((region, cluster, service_name, ...))`), eliminating the need for dynamic per-service table generation.

==== 1. Creating the Keyspace

For production deployments, always use `NetworkTopologyStrategy` configured with your local datacenter name and replication factor:

.Keyspace Creation Script
[source,sql]
----
CREATE KEYSPACE IF NOT EXISTS stacksaga_event_store
WITH replication = {
  'class': 'NetworkTopologyStrategy',
  'datacenter1': 3
}
AND durable_writes = true;
----

NOTE: For local development or isolated testing, you can use `'class': 'SimpleStrategy', 'replication_factor': 1`.

==== 2. Executing the Unified Schema Script

The unified schema script creates 9 static tables divided into two coordinated groups:

[cols="1,1,3",options="header"]
|===
| Group | Table Name | Purpose

.4+| *Core Event Store* (4 tables)
| `es_transaction` | Primary transaction state and metadata store (Single-Row Partition).
| `es_transaction_tryout` | Transaction step execution history, physically co-located by transaction ID.
| `es_frozen_transaction` | Quarantined transactions where compensation (rollback) failed unrecoverably.
| `es_execution_markers` | Step execution markers and idempotency leases for event streaming deduplication.

.5+| *5-Tier Recovery Engine* (5 tables)
| `es_days_by_year` | Tier 1: Directory of active calendar dates with pending retries or restores.
| `es_recovery_windows_by_day` | Tier 2: Directory of active UTC minute windows per day (0 to 1439).
| `es_instances_by_recovery_window` | Tier 3: Pod instance markers clustered by Murmur3 token hash for spatial slicing.
| `es_buckets_by_instance` | Tier 4: Sequential bucket index directory (even = Retry, odd = Restore).
| `es_recovery_transactions_by_instance` | Tier 5: Bounded recovery metadata partitions (< 50,000 rows, ~3–5MB).
|===

[TIP]
====
*Why does the default consistency level use `LOCAL_QUORUM` and not `QUORUM`?* +
`LOCAL_QUORUM` ensures strong consistency within the local datacenter only — reads and writes do not wait for confirmation from remote datacenters over high-latency WAN links.
In multi-datacenter deployments, using `QUORUM` would add 20–100ms of cross-region latency to every single database query.
For standard single-region and multi-region active-active deployments, `LOCAL_QUORUM` is the optimal choice.

== Part 2: The Event Store

Before examining the Recovery Engine, it is important to understand how StackSaga organizes and stores live transaction data.
The 4 Core Event Store tables operate independently of the Recovery Engine and are **never subjected to polling-queue range scans**.

=== `es_transaction` — The Primary Transaction Record

Every saga transaction has exactly one row in `es_transaction`, keyed by `transaction_id`.

*What happens if thousands of transactions are created simultaneously — won't a single Cassandra node become a hot spot?* +
`transaction_id` is a UUID uniformly distributed by Cassandra's Murmur3 partitioner across all cluster nodes with zero coordination.
Even under bursts of 100,000 concurrent writes, rows land uniformly across physical storage nodes, making hot spots structurally impossible:

.Managing High Write Throughput via Uniform Murmur3 Partitioning
image::stacksaga-database-support:cassandra/stacksaga-transaction-throughput.svg[alt="Managing High Write Throughput via Uniform Murmur3 Partitioning"]

<1> **High Inflow Requests:** Over 100,000 concurrent saga transactions initiated simultaneously across horizontally scaled application nodes.
<2> **Murmur3 Partitioner:** Cassandra's 64-bit Murmur3 hash uniformly scatters `transaction_id` across the token space with zero coordination and zero lock contention.
<3> **Even Cluster Scattering:** Writes land uniformly across physical nodes, ensuring CPU, memory, and disk I/O remain balanced without hot spots.

=== `es_transaction_tryout` — Step Execution History

Each saga step attempt (called a "tryout") is stored as an individual row under the same `transaction_id` partition key.

*Doesn't reading a transaction's execution history require touching multiple nodes across the network?* +
No.
Because `es_transaction` and `es_transaction_tryout` share the **identical composite partition key** `((region, cluster, service_name, transaction_id))`, Cassandra places the parent transaction and all of its step tryouts on the **exact same physical storage node**:

.Colocated Transaction Step History (`es_transaction_tryout`)
image::stacksaga-database-support:cassandra/stacksaga-tryout-colocation.svg[alt="Colocated Transaction Step History"]

<1> **Physical Cassandra Node Colocation:** Because `es_transaction` and `es_transaction_tryout` share the identical composite partition key `((region, cluster, service_name, transaction_id))`, all records for a given transaction reside on the exact same physical node.
<2> **Step Execution Clustering Rows:** Individual saga step attempts append as ordered clustering rows (`tryout_index ASC`) within the partition.
<3> **Zero-Hop Colocated Read:** Fetching a transaction and its full step history is always a single-node, zero-hop local read operation, maximizing performance.

=== `es_frozen_transaction` — The Quarantine Table

*What happens if even the compensation (rollback) step fails?
Does the transaction get lost?* +
No — it is safely quarantined. `es_frozen_transaction` stores transactions where an automated compensation step itself encountered an unrecoverable error, leaving the transaction in a partially compensated state.
These transactions are isolated to protect downstream systems from further side effects.
They require developer diagnosis and manual re-triggering via the administrative restore endpoint.

=== `es_execution_markers` — The Idempotency Lease Table

`es_execution_markers` stores step execution markers and idempotency leases to prevent duplicate saga step execution during Kafka consumer group rebalances or network re-deliveries.

*Partition lifecycle and storage cleanup:*

Each transaction's execution markers share the composite partition key `((region, cluster, service_name, transaction_id))` — the same as `es_transaction` and `es_transaction_tryout`.
Over the lifetime of a saga, each executed step appends one clustering row (`step_id`) to this partition.
When the transaction reaches a terminal state (`PROCESS_COMPLETED` or `REVERT_COMPLETED`), the engine issues a **single partition-level delete** against `es_execution_markers`:

[source,sql]
----
DELETE FROM es_execution_markers
WHERE region = :region AND cluster = :cluster
  AND service_name = :service_name AND transaction_id = :transaction_id;
----

Because this targets the full composite partition key, Cassandra writes a **single partition tombstone** — not one cell tombstone per step marker.
The entire partition (all step markers for that transaction) is dropped in O(1) time during SSTable compaction, regardless of how many steps the saga executed.
This guarantees that `es_execution_markers` storage is **self-bounded**: rows are written only during the active transaction window and fully reclaimed at transaction end, with no periodic cleanup job required.

== Part 3: Write Protection (Kafka Event Sourcing)

When using Kafka or similar streaming brokers for event-driven saga orchestration, guarding against duplicate step execution and race conditions is essential.

=== Why Duplicate Events Occur

StackSaga's Kafka messaging layer uses *at-least-once delivery semantics*.
Duplicate event deliveries naturally occur in distributed environments due to:

* Consumer group rebalances when pods scale up or down.
* Consumer node restarts before offset commits are acknowledged.
* Network timeouts and automated message retries.

Without protection, the same saga step could execute twice — charging a credit card twice, reserving duplicate inventory, or sending multiple customer confirmations.

=== STRICT Mode — Mutual Exclusion with Cassandra LWT

`STRICT` mode uses Cassandra Lightweight Transactions (Paxos-based LWT) to acquire an exclusive temporary execution lease before running any business logic:

[source,text]
----
STEP 1: INSERT INTO es_execution_markers ... IF NOT EXISTS USING TTL <leaseDuration>
         → If the row was NOT there: this pod holds the lease ([applied] == true). Proceed.
         → If the row WAS already there (TTL > 0): another pod is executing. Back off and retry.
         → If the row WAS already there (TTL = 0): already committed permanently. Skip safely.

STEP 2: Execute saga step business logic.

STEP 3: UPDATE es_execution_markers SET execution_state = 'COMMITTED', TTL = 0
         → Converts the temporary lease to a permanent marker.
         → All other pods now see TTL = 0 and terminate cleanly.
----

If a pod crashes between Step 1 and Step 3, the temporary lease expires when its TTL finishes, permitting another pod to retry and complete the saga step cleanly.

.STRICT Mode Write Protection Flow
image::stacksaga-database-support:cassandra/stacksaga-write-protection-strict.svg[alt="STRICT Mode Write Protection Flow"]

<1> **Kafka Event Inflow:** A saga step execution event arrives from Kafka with potential at-least-once duplicate delivery.
<2> **Paxos LWT Lease Acquisition:** The pod executes an atomic `INSERT ... IF NOT EXISTS USING TTL 5s` into `es_execution_markers`.
If a lease exists with `TTL > 0`, the pod backs off; if `TTL = 0`, it skips.
<3> **Mutual Exclusive Execution:** The single pod holding the active lease executes the saga business logic.
<4> **Permanent Marker Commit:** On success, the marker is committed with `TTL = 0`, conferring permanent duplicate immunity.

=== RELAXED_WITH_DEDUP Mode — Lightweight Read Check

`RELAXED_WITH_DEDUP` skips the Paxos LWT overhead entirely.
Before executing, the engine performs a fast read against `es_execution_markers`.
If a completed marker is found, execution is skipped.
This mode avoids Cassandra LWT round-trips, maximizing throughput.

.RELAXED_WITH_DEDUP Mode Execution Flow
image::stacksaga-database-support:cassandra/stacksaga-write-protection-relaxed.svg[alt="RELAXED_WITH_DEDUP Mode Execution Flow"]

<1> **Kafka Event Inflow:** Event received on high-throughput streaming pipelines where operations are inherently idempotent.
<2> **Non-Blocking Read Check:** Executes a fast read against `es_execution_markers` without Paxos consensus overhead.
If a marker exists, execution terminates immediately.
<3> **Atomic Batch Write:** Step results and execution markers are committed together in a single logged batch write.

*When to use `RELAXED_WITH_DEDUP`:*
* When downstream operations are naturally idempotent (e.g. setting an absolute value, updating a cache, writing to an audit log).
* When throughput is critical and duplicate execution carries zero business risk.

=== Domain-Level Configuration

Write protection can be configured globally and overridden per saga domain:

.Example `application.yml`
[source,yaml]
----
stacksaga:
  cassandra:
    write-protection:
      default-mode: RELAXED_WITH_DEDUP      # Default high-throughput mode
      default-lease-duration: 5s            # Default LWT lease TTL (for STRICT mode)
      domains:
        order-saga:
          mode: STRICT                      # Strict mutual exclusion for order creation
          lease-duration: 10s               # Custom lease TTL override
        payment-saga:
          mode: STRICT                      # Strict mode using default 5s lease
        notification-saga:
          mode: RELAXED_WITH_DEDUP          # High-throughput mode for notifications
----

== Part 4: The Recovery Engine & The 5-Tier Directory Architecture

The **Recovery Engine** is responsible for ensuring that no distributed transaction is permanently lost or abandoned due to infrastructure disruptions.
It provides two independent but architecturally unified capabilities:

[cols="1,2,2",options="header"]
|===
| Feature | When It Triggers | Root Cause

| **Retry**
| A saga step calls a downstream microservice and receives HTTP 503, connection timeout, or temporary network error.
| Downstream dependency is temporarily degraded. The transaction is deliberately scheduled for asynchronous re-invocation.

| **Restore**
| A pod crashes mid-transaction (power outage, OOM kill, forced Kubernetes pod eviction).
| The transaction was in progress when the process died. No error was recorded in any log or table.
|===

Both features share the **same 5-tier Cassandra directory structure** and the same pool of Retry-Nodes — differentiated only by even bucket indexes (Retry) and odd bucket indexes (Restore).

[#cassandra-directory-architecture]
=== Why Cassandra Requires a Directory-Based Architecture

In relational databases (PostgreSQL, MySQL), implementing a retry queue is straightforward:

[source,sql]
----
SELECT * FROM retry_queue
WHERE status = 'PENDING' AND retry_time <= NOW()
ORDER BY retry_time ASC LIMIT 100;
----

Relational engines use B-Tree indexes to locate pending rows in milliseconds, updating or deleting them in place.
In Cassandra, attempting to use a flat table as an active polling queue is a well-known distributed anti-pattern:

1. **Absence of Global Secondary Indexing for Queues:**
Cassandra distributes partitions across cluster nodes using partition key hashes.
There is no global B-Tree index across partitions.
Polling a flat table without knowing exact partition keys requires full cluster range scans (`ALLOW FILTERING`), creating catastrophic network I/O and query timeouts.
2. **The Queue Anti-Pattern & Tombstone Scanning:**
Cassandra SSTables are immutable.
Deleting a row writes a tombstone.
In a polling queue where tasks are continuously added and deleted, queries scanning for the next available tasks must read past all the tombstones of completed tasks before reaching live data.
If a scan crosses more than 100,000 tombstones, Cassandra aborts the query (`ReadFailureException`).
3. **Predictable Performance Requires Partition-Key Targeting:**
Cassandra is exceptionally fast when queries provide the exact composite partition key.

StackSaga solves this by modeling recovery discovery as a **hierarchical active directory** — a tree of narrow index tables where each level points to the next, so workers always query by exact partition key, never by blind range scan.

=== Core System Roles: Who Does What?

To understand how retries, restores, and compaction operate without distributed locks, it is important to distinguish the core components:

[cols="1,2,2",options="header"]
|===
| Component / Role | What It Is | Responsibility in Cassandra

| **Standard-Nodes** +
_(Live Traffic Pods)_
| Horizontally scaled microservice instances (e.g. Kubernetes pods running `order-service`) that serve live client requests and advance sagas. +
xref:retry-ring-coordinator:transaction-retrying-with-retry-coordinator.adoc#orchestrator-deployment-modes[Read more]
| **Writers (Retry):** On transient failure, writes ahead into window W+1, increments a JVM-local even `AtomicLong` counter to select a bounded even bucket, and registers the failure in the 5-tier directory — zero cross-pod coordination. +
**Writers (Restore):** On every transaction start, writes a watchdog row into a far-future restore window using an odd `AtomicLong` counter. On completion, deletes the watchdog row.

| **Retry-Nodes** +
_(Recovery Workers)_
| Dedicated orchestrator instances running with the StackSaga retry subsystem enabled, responsible for recovering stalled or orphaned transactions. +
xref:retry-ring-coordinator:transaction-retrying-with-retry-coordinator.adoc#orchestrator-deployment-modes[Read more]
| **Readers & Local Compactors:** Acquire an exclusive Murmur3 token lease from the Ring Coordinator, scan only sealed windows (<= W) for their assigned token range, re-invoke transactions, and drop completed bucket partitions with an O(1) partition delete.

| **RSocket Ring Coordinator**
| An independent, lightweight clustering service (`stacksaga-ring-coordinator`) deployed alongside your microservices. +
xref:retry-ring-coordinator:ring-coordinator.adoc[Read more]
| **Token Lease Authority:** Divides the 64-bit Murmur3 token ring (`-2^63` to `2^63 - 1`) into non-overlapping sector leases and issues time-bounded leases to active Retry-Nodes over persistent RSocket streams — eliminating database-level distributed locks.

| **Node-0** +
_(Compactor Overseer)_
| The Retry-Node holding the anchor (lowest) token lease from the Ring Coordinator. Operates as a normal recovery worker while also performing cluster-wide directory pruning.
| **Global Directory Compactor:** Runs two strict verification gates before deleting completed minute windows from Tier 2 and empty calendar dates from Tier 1.

| **Primary Event Store** +
(`es_transaction`)
| The permanent transactional database ledger.
| **Source of Truth:** Stores full saga state, execution history, and business payloads. Decoupled from the recovery directory — never subjected to polling queue range scans.
|===

[NOTE]
====
*Is the Ring Coordinator a single point of failure?* +
No.
Standard-Nodes (live traffic pods) **never communicate with the Ring Coordinator** — they write failure records directly to Cassandra regardless of coordinator availability.
Retry-Nodes continue executing on their current token lease during coordinator restarts.
The Ring Coordinator supports Master/Slave high-availability deployment; workers automatically reconnect and re-verify their token leases when it comes back online.
If the coordinator is briefly unavailable, only token rebalancing on worker join/leave is delayed — live transactions and ongoing recovery are completely unaffected.
====

=== The 5-Tier Directory Architecture at a Glance

The directory structure is organized as follows:

[source,text]
----
es_days_by_year                             ← Tier 1: Which calendar days have pending work?
  └── es_recovery_windows_by_day            ← Tier 2: Which UTC minute windows on that day?
        └── es_instances_by_recovery_window ← Tier 3: Which pod instances wrote work in that window?
              └── es_buckets_by_instance    ← Tier 4: Which bucket partitions did that pod create?
                    └── es_recovery_transactions_by_instance ← Tier 5: The actual transaction pointers.
----

Workers never scan empty tables.
Every query at every tier provides the full composite partition key of the tier above it, descending the tree until they discover `transaction_id` pointers to re-invoke.

.StackSaga 5-Tier Recovery Directory Hierarchy & Primary Event Store
image::stacksaga-database-support:cassandra/stacksaga-5tier-recovery-hierarchy.svg[alt="StackSaga 5-Tier Recovery Directory Hierarchy & Primary Event Store"]

The active directory tree operates through five coordinated tiers:

<1> **Tier 1 (`es_days_by_year`):** Tracks which calendar dates contain pending recovery transactions for a given service, preventing empty table scans.
<2> **Tier 2 (`es_recovery_windows_by_day`):** Divides each 24-hour day into discrete UTC minute windows (`0` to `1439`) processed in ascending chronological order (`minute_of_day ASC`).
<3> **Tier 3 (`es_instances_by_recovery_window`):** Pod instance markers clustered by Murmur3 token hash (`token(instance_id)`) for spatial worker slicing.
<4> **Tier 4 (`es_buckets_by_instance`):** Sequential bucket allocation directory (even = Retry, odd = Restore).
<5> **Tier 5 (`es_recovery_transactions_by_instance`):** Bounded recovery metadata partitions (< 50,000 rows, ~3–5MB) dropped via single partition tombstones in O(1) time.
<6> **Primary Event Store (`es_transaction`):** Decoupled heavy state hydrated lazily by `transaction_id`.

[NOTE]
====
*Wait — Tier 3 stores the Standard-Node's own `instance_id`.
But Standard-Nodes don't retry their own transactions — Retry-Nodes do.
Why store the writer pod's ID at all?* +
This is one of the most important design decisions in the architecture.
The writer pod's `instance_id` in Tier 3 serves three distinct purposes:

1. **Spatial sharding key:** `token(instance_id)` is the 64-bit Murmur3 hash used to distribute work across Retry-Nodes.
Every record written by `pod-order-a` is automatically routed to the Retry-Node whose token lease covers `token('pod-order-a')` — no central dispatcher needed.
2. **Decoupling:** The Standard-Node writes its ID and immediately returns to serving live traffic.
It has zero knowledge of which Retry-Node will pick up the work.
3. **Completion semaphore for Node-0:** When a Retry-Node finishes all buckets for an instance, it deletes that instance's Tier 3 marker.
Node-0 then queries Tier 3 across the whole cluster — when it returns 0 rows, Node-0 knows with 100% certainty that all recovery work for that minute window is globally complete.
====

'''

=== Feature 1: Retry

[#instance-level-local-bucketing]
==== Bounded Partitions: Instance-Level Local Bucketing

*What happens if a major downstream service goes down and thousands of pods all start failing simultaneously?
Won't they all write into the same Cassandra partition and blow past the 100MB limit?* +
In high-throughput microservice ecosystems, a widespread downstream outage can trigger hundreds of thousands of transaction failures within seconds across all running pods.
In Apache Cassandra, maintaining strictly bounded partitions (ideally under 50,000 rows and < 100MB) is vital to prevent JVM garbage collection pauses, read timeouts, and compaction hotspots.

StackSaga eliminates distributed counting bottlenecks entirely by combining **JVM-local atomic counters** with **Murmur3-based autonomous worker re-distribution**.
Instead of sharing global buckets across instances, the composite partition key of Tier 5 directly incorporates the writing instance's unique identity (`instance_id`):

[source,cql]
----
PRIMARY KEY (
  (region, cluster, service_name, date_of_year, minute_of_day, instance_id, bucket_index),
  transaction_id
)
----

Each live orchestrator pod independently manages its own bucket counter in local JVM memory without any cross-network coordination.
When a pod's local counter hits 50,000, only that specific pod increments its `bucket_index` to the next even value (`0` -> `2` -> `4`).
All writing pods write to completely isolated partitions simultaneously in O(1) time.

.Instance-Level Local Bucketing & Autonomous Worker Re-Distribution
image::stacksaga-database-support:cassandra/stacksaga-instance-local-bucketing.svg[alt="Instance-Level Local Bucketing & Autonomous Worker Re-Distribution"]

The mechanics operate through five stages:

<1> **Thousands of Ephemeral Orchestrator Pods (Live Writers):** Every live application pod maintains an in-memory `AtomicLong` counter per write window.
Incrementing takes ~2 nanoseconds without database locks.
<2> **Isolated Bounded Partitions (Tier 5 Metadata Store):** Partitions are strictly bounded to a maximum of 50,000 rows (~3MB to 5MB on disk), far below Cassandra's 100MB threshold.
<3> **Deterministic Spatial Mapping (`instance_id_token = token(instance_id)`):** Pods register their token hash in Tier 3, uniformly scattered across the continuous 64-bit token ring (`-2^63` to `2^63 - 1`).
<4> **Autonomous Worker Discovery & Re-Distribution:** Retry-Nodes sweep assigned token sector leases, claiming instances deterministically without cross-worker locking and purging completed partitions via O(1) partition tombstones.
<5> **Ephemeral Lifecycle Decoupling (Terminated Pod Recovery Guarantee):** Live pods can scale down, restart, or terminate immediately after writing failure records; 100% of pending retries are guaranteed to be recovered.

[NOTE]
====
*Writing to 5 tables per failure — doesn't that slow down my live API?* +
Not meaningfully.
Cassandra writes are append-only to an in-memory Memtable and sequential CommitLog — each write takes under 1 millisecond.
More importantly, Tiers 1–4 are written only **once per minute window** (idempotent upserts): if the same pod writes 10,000 failures in the same minute, only Tier 5 gets 10,000 new rows — Tiers 1–4 simply touch already-existing keys in memory.

*What if a Standard-Node pod restarts mid-window?
Its in-memory AtomicLong counter resets to 0 — does that overwrite or corrupt the old bucket?* +
No.
Each time the JVM starts, StackSaga generates a **new unique `instance_id`** for that runtime.
Because `instance_id` is embedded directly in the Tier 5 composite partition key, the restarted pod writes into a brand-new, uniquely keyed partition — it never touches the old pod's buckets.
The old pod's records remain safely registered under their original `instance_id` and are discovered and retried by Retry-Nodes.

*Why don't saga transaction payloads cause Tier 5 recovery partitions to exceed Cassandra's 100MB partition limit?* +
No — because **no business payload is stored in any of the 5 recovery tables**.
Whether a saga's state is lightweight (a few bytes) or complex, each Tier 5 row is strictly a minimal metadata pointer (~50–100 bytes).
The actual saga state and payload always remain in `es_transaction`.
A full 50,000-row bucket consumes only ~3MB to 5MB on disk, making it physically impossible for a recovery partition to violate Cassandra's 100MB limit regardless of payload size.
====

[#ternary-window-model]
==== The Ternary-Window Synchronization Model

*How do we prevent a Retry-Node from reading a window that a Standard-Node is still actively writing to, and where does silent crash recovery fit in?* +
Transaction processing operates across **three non-interfering temporal horizons**, cleanly dividing responsibilities between **Standard-Nodes** (writing ahead on failure and arming watchdogs) and **Retry-Nodes** (reading and compacting sealed windows).
This strict rule makes it structurally impossible for readers and writers to ever touch the same Cassandra partition simultaneously — without any distributed locks:

* **Sealed Read Windows (<= W):** Retry-Nodes read only sealed past windows, sweeping both transient retries (Even buckets) and triggered watchdogs (Odd buckets).
Zero phantom reads, zero row locks.
* **Immediate Write-Ahead Window (W+1):** Standard-Nodes encountering transient step failures always write into W+1 (the next scheduled minute window, never the current one), targeting Even buckets (`0, 2, 4`) with an automatic 10s–70s cooldown buffer.
* **Far-Future Watchdog Window (W+K):** When starting any transaction, Standard-Nodes register a Dead-Man's Switch watchdog in a far-future window (e.g. W + 600, 10 hours ahead) targeting Odd buckets (`1, 3, 5`), deleted in O(1) time upon normal transaction completion.

.Ternary-Window Synchronization Timeline: Writer, Reader, and Watchdog Isolation
image::stacksaga-database-support:cassandra/stacksaga-dual-window-timeline.svg[alt="Ternary-Window Synchronization Timeline"]

<1> **Active Write Window (W+1, Retry Horizon):** Standard-Nodes write transient failures into the immediate future window (Even buckets: `0, 2, 4`), completely isolated from active reader queries.
<2> **Sealed Read Windows (<= W, Reader Horizon):** Retry-Nodes read only completed, sealed windows.
Sweeps both expired retries and overdue watchdogs without phantom reads or lock contention.
<3> **Far-Future Watchdog Window (W+K, Restore Horizon):** Dead-man's switch watchdog row placed far ahead (e.g. W + 600 min) in Odd buckets (`1, 3, 5`).
Cancelled on normal transaction finish; survives only on ungraceful pod crash.
<4> **Automatic Cooldown Buffer:** Writing to W+1 provides an automatic cooldown buffer of 10 to 70 seconds before the first retry attempt, preventing workers from hammering a restarting service.
<5> **Midnight UTC Rollover:** Window 1439 wraps smoothly to minute 0 of the next calendar day (`date_of_year + 1`).

.Pseudocode: Ternary-Window Calculation & Midnight Rollover
[source,text]
----
constant TOTAL_WINDOWS_PER_DAY = 1440 // for 1-minute delay

function getCurrentReadWindow(utcTimestamp):
    minutesSinceMidnight = (utcTimestamp.hour * 60) + utcTimestamp.minute
    windowIndex = minutesSinceMidnight / delayInMinutes
    return Window(date = utcTimestamp.date, index = windowIndex)

function getImmediateRetryWriteWindow(utcTimestamp):
    readWindow = getCurrentReadWindow(utcTimestamp)
    nextIndex = readWindow.index + 1
    
    // Check midnight UTC rollover
    if nextIndex >= TOTAL_WINDOWS_PER_DAY:
        return Window(date = utcTimestamp.date + 1 day, index = 0)
    else:
        return Window(date = utcTimestamp.date, index = nextIndex)

function getFarFutureRestoreWindow(utcTimestamp, restoreDelayWindows = 600):
    readWindow = getCurrentReadWindow(utcTimestamp)
    targetIndex = readWindow.index + restoreDelayWindows
    daysOffset = targetIndex / TOTAL_WINDOWS_PER_DAY
    finalIndex = targetIndex % TOTAL_WINDOWS_PER_DAY
    return Window(date = utcTimestamp.date + daysOffset days, index = finalIndex)
----

[#spatial-worker-isolation]
==== Spatial Worker Isolation via Murmur3 Token Leases

When multiple Retry-Nodes run in parallel, they must each process a non-overlapping slice of the work without database row locks:

. Every Standard-Node registers its `instance_id` and `token(instance_id)` in Tier 3 (`es_instances_by_recovery_window`) upon failure.
. The Ring Coordinator divides the 64-bit token ring (`-2^63` to `2^63 - 1`) into non-overlapping sector leases and assigns one to each active Retry-Node.
. Each Retry-Node queries Tier 3 with its leased token bounds:

[source,sql]
----
SELECT instance_id, instance_id_token
FROM es_instances_by_recovery_window
WHERE region = :region AND cluster = :cluster AND service_name = :service_name
  AND date_of_year = :date AND minute_of_day = :window
  AND instance_id_token >= :lease_min_token
  AND instance_id_token <= :lease_max_token;
----

Because leases do not overlap, two Retry-Nodes never process the same instances.
Throughput scales **linearly** as more Retry-Nodes are added.
Every query verifies that the current timestamp is within the lease validity window; if a lease expires due to a network partition, execution terminates immediately, preventing split-brain processing.

.Murmur3 Token Ring Slicing & Spatial Worker Isolation
image::stacksaga-database-support:cassandra/stacksaga-spatial-token-ring.svg[alt="Murmur3 Token Ring Slicing & Spatial Worker Isolation"]

<1> **64-bit Murmur3 Token Ring:** Spans `-2^63` to `+2^63 - 1`.
<2> **Ring Coordinator:** Divides the token ring into non-overlapping sectors and issues time-bounded leases.
<3> **Worker Leases:** Each Retry-Node queries Tier 3 using its leased sector bounds (`WHERE token >= min AND token < max`).
<4> **Autonomous Slicing:** Linear horizontal scaling with zero duplicate processing and zero database row locks.

==== Processing a Retry Bucket: Step-by-Step

Once a Retry-Node identifies an `instance_id` in its leased token range, it executes:

1. **Read Tier 4** (`es_buckets_by_instance`) to discover all bucket indexes for this instance + window.
2. **Read Tier 5** (`es_recovery_transactions_by_instance`) for each even bucket to stream `transaction_id` pointers.
3. **Fetch the saga payload lazily** from `es_transaction` using `transaction_id`.
4. **Re-invoke the saga step** with controlled concurrency (`recovery.concurrency`, default: 100).
5. **Drop the bucket partition** from Tier 5 when all transactions in the bucket are dispatched:
+
[source,sql]
----
DELETE FROM es_recovery_transactions_by_instance
WHERE region = :region AND cluster = :cluster AND service_name = :service_name
  AND date_of_year = :date AND minute_of_day = :window
  AND instance_id = :instance_id AND bucket_index = :bucket_index;
----
+
Because the deletion targets the composite partition key, Cassandra writes a **single Partition Tombstone** rather than thousands of cell tombstones.
During SSTable compaction, Cassandra drops the entire partition in O(1) time.
6. **Delete the Tier 4 bucket index row** from `es_buckets_by_instance` immediately after the Tier 5 drop.
7. **Delete the Tier 3 instance marker** when all buckets for this instance are completed.

[NOTE]
====
*Crash-Between-Steps Idempotency:* +
If a Retry-Node crashes after dropping the Tier 5 bucket partition (step 5) but before deleting the Tier 4 bucket index row (step 6), the next worker to pick up that instance re-enters the traversal pipeline and reads Tier 4 — which still shows the stale bucket index entry.
It then reads Tier 5 for that bucket and gets **zero rows** (the partition is already gone).
The pipeline's empty-bucket path handles this identically to a normally completed bucket: it issues the Tier 5 drop as a no-op, deletes the stale Tier 4 index row, and advances cleanly to the next bucket.
No manual intervention is required — the pipeline is **fully idempotent** across all crash-between-steps scenarios.
====

[#safe-shutdown-guarantee]
==== Safe Shutdown & Zero Data Loss Guarantee

*What happens if Kubernetes kills a Retry-Node while it is halfway through processing 50,000 transactions?* +
The traversal pipeline enforces a strict shutdown invariant: a bucket partition is **never deleted unless 100% of its transactions have been dispatched**:

[source,text]
----
function onBucketBatchComplete(bucket, totalTransactions, executedCount):
    // If worker is stopping OR not all transactions were executed
    if isShutdownRequested() or executedCount < totalTransactions:
        log.info("Worker shutting down or partial execution. Preserving bucket in Cassandra.")
        return // Do NOT delete bucket partition!
        
    // Only delete partition when 100% of transactions were dispatched
    dropBucketPartition(bucket)
    deleteBucketIndex(bucket)
----

When a Retry-Node is killed mid-bucket, the partition stays intact in Cassandra.
Upon restart, the next worker picks up the bucket from row 1.
Execution markers (`es_execution_markers`) ensure that already-completed saga steps are detected as `COMMITTED` and skipped immediately without re-calling downstream APIs — only genuinely uncompleted steps are executed.

.Top-Down Traversal & Compaction Lifecycle Pipeline
image::stacksaga-database-support:cassandra/stacksaga-traversal-pipeline.svg[alt="Top-Down Traversal & Compaction Lifecycle Pipeline"]

<1> **Discovery:** Top-down sweep from Tier 1 down to Tier 4 without empty table scans.
<2> **Hydration:** Stream lightweight pointers from Tier 5 and lazily fetch payloads from `es_transaction`.
<3> **Dispatch:** Concurrent re-invocation up to `recovery.concurrency` (default: 100).
<4> **Safe Shutdown Barrier:** If a pod is killed mid-bucket, the partition is preserved in Cassandra; completed steps are skipped upon restart.
<5> **O(1) Compaction Drop:** When 100% dispatched, the entire bucket partition is dropped with a single partition tombstone.

[#deep-historical-recovery]
==== Deep Historical Recovery

*What if our entire service was offline for an entire weekend — do all those failed transactions get abandoned?* +
Never.
On startup, workers generate candidate dates going back multiple days based on `recovery.lookback-days` (default: `2`).
Workers traverse Tier 1 in ascending order (`date_of_year ASC`) and Tier 2 in ascending order (`minute_of_day ASC`), recovering Friday's, Saturday's, and Sunday's backlog chronologically before transitioning smoothly to the live stream.

.Deep Historical Lookback Across Calendar Days
image::stacksaga-database-support:cassandra/stacksaga-deep-historical-recovery.svg[alt="Deep Historical Lookback Across Calendar Days"]

<1> **Lookback Range Calculation:** On startup, workers calculate candidate dates based on `recovery.lookback-days`.
<2> **Ascending Day Sweep:** Workers traverse Tier 1 in ascending order (`date_of_year ASC`), recovering older backlog first.
<3> **Live Transition:** Once historical windows are processed, workers transition smoothly to the live minute stream (W).

=== Feature 2: Restore

==== The Problem: The Silent Crash

Retry handles failures that are detected — the step ran, the downstream service returned an error, and StackSaga recorded it.
But consider an ungraceful failure:

1. User places an order.
2. An `order-service` pod begins executing the saga — reserves stock in inventory.
3. Mid-flight, before calling payment, the host server suffers a catastrophic power outage or OOM kill.
4. The pod is gone.
No error was recorded.
No retry record was created.
5. When a replacement pod starts, it has no record of transaction `T-12345` ever existing in memory.

Without a dedicated mechanism, transaction `T-12345` is permanently orphaned in an inconsistent distributed state.
The **Restore** feature solves this with a **dead-man's switch pattern**: write a watchdog row at transaction start, delete it on completion.
If completion never occurs, the watchdog row survives and triggers automated recovery.

[#silent-crash-restore-watchdog]
==== How Restore Works: The Dead-Man's Switch

When a Standard-Node **starts processing** any transaction, it immediately:

1. Computes a **far-future restore window**:
+
[source,text]
----
restore_window = current_window + (recovery.restore.domains.<domain>.delay-windows * recovery.window-interval-minutes)

Example:
  window-interval-minutes = 1   (1-minute windows)
  restore.domains.default.delay-windows = 600
  → watchdog row is placed 600 minutes (10 hours) ahead in the directory
----
2. Writes a lightweight watchdog row into an **odd bucket** in Tier 5 at that restore window.
3. Durably saves the full partition path `(date, window, instance_id, odd_bucket_index)` inside the `es_transaction` record.

.The Restore Feature: Dead-Man's Switch Lifecycle
image::stacksaga-database-support:cassandra/stacksaga-restore-dead-mans-switch.svg[alt="The Restore Feature: Dead-Man's Switch Lifecycle"]

<1> **Transaction Start:** Standard-Node registers watchdog row at far-future window W + delay (e.g. +600 min).
<2> **Watchdog in Odd Bucket:** Written into Tier 5 odd bucket partition.
<3> **Path Stored in Ledger:** Partition path stored in `es_transaction` for targeted deletion.
<4> **Path A (Normal Completion):** Targeted O(1) delete removes watchdog row; window stays clean.
<5> **Path B (Pod Crash):** Watchdog row persists in Cassandra.
When window arrives, Retry-Node checks status and automatically re-invokes.

[cols="1,3",options="header"]
|===
| Outcome | What Happens

| **Transaction completes normally** +
_(success or compensation)_
| The Standard-Node reads the restore path from `es_transaction` and issues a direct partition-key `DELETE` against the watchdog row in Tier 5. The row is gone in O(1) time. The far-future restore window never appears in the directory as having active work.

| **Pod crashes mid-transaction** +
_(power outage, OOM kill, hardware fault)_
| The watchdog row was never deleted. When the far-future window eventually arrives and becomes a sealed read window (<= W), a Retry-Node discovers it through the normal 5-tier traversal, checks the status, and automatically re-invokes the transaction.
|===

==== Status Check on Restore Pickup

When a Retry-Node picks up a transaction from a restore bucket (odd `bucket_index`), the saga engine performs a **mandatory status check** against `es_transaction.running_status` before attempting re-invocation:

[source,text]
----
status = SELECT running_status FROM es_transaction WHERE transaction_id = :id

if status == PROCESS_COMPLETED or status == REVERT_COMPLETED:
    // Transaction already finished. The watchdog row delete must have failed
    // due to a network blip at completion time. Silently delete and skip.
    deleteRestoreRow(path)
    return

// Status shows transaction is still in-flight (or unknown). Re-invoke it.
reInvoke(transaction)
----

This guarantees **at-most-once re-invocation** for completed transactions and **at-least-once recovery** for genuinely orphaned ones.

[#odd-even-bucket-segregation]
==== Why Restore Buckets Use Odd Indexes

Restore records and Retry records share the **same Tier 5 table**, distinguished strictly by `bucket_index`:

* **Even bucket indexes (0, 2, 4 ...)** -> Retry records.
Written only on transient failure.
* **Odd bucket indexes (1, 3, 5 ...)** -> Restore records.
Written on every transaction start.

.Odd vs. Even Bucket Segregation & Tombstone Isolation
image::stacksaga-database-support:cassandra/stacksaga-odd-even-bucket-segregation.svg[alt="Odd vs. Even Bucket Segregation & Tombstone Isolation"]

<1> **Dual In-Memory Counters:** Independent `AtomicLong` counters for retry (even) and restore (odd).
<2> **Even Buckets (Pure Retry):** 0% cell tombstones.
High read performance, dropped via single partition tombstones.
<3> **Odd Buckets (Restore Watchdog):** Quarantines high-frequency cell tombstones from completed transactions away from retry reads, eliminating `ReadFailureException`.
<4> **O(1) Partition Tombstone:** Entire even bucket dropped in one metadata operation upon completion; retry workers never scan deleted rows.

*Why odd/even segregation is structurally essential:*
1. **Tombstone Isolation:** Restore rows are written for *every* transaction and deleted minutes later on success.
This produces heavy cell tombstone accumulation.
If restore rows were mixed into retry buckets, a Retry-Node scanning retry rows would have to read through thousands of tombstones, risking `ReadFailureException` (>100,000 tombstones).
Isolating restore to odd buckets keeps retry buckets 100% tombstone-free.
2. **Accurate Live-Row Counting:** The in-memory `AtomicLong` tracks rows written, not rows remaining after deletions.
Mixing them would cause partitions to roll over prematurely based on deleted rows.
3. **Independent Window Schedules:** Retry windows are 1 window ahead (W+1), while restore windows are hundreds of windows ahead (W + 600).
Separate counters prevent write rate skew between different points in time.

.Pseudocode: Dual Local In-Memory Counter Strategy (Retry + Restore)
[source,text]
----
// Two independent AtomicLong counters per instance, per write window
retryCounter  = AtomicLong  // for even bucket_index: 0, 2, 4 ...
restoreCounter = AtomicLong  // for odd  bucket_index: 1, 3, 5 ...

// ── ON TRANSACTION START (every transaction) ─────────────────────────────
function registerRestore(transaction):
    restoreWindow = computeRestoreWindow(UTC_NOW, delayWindows)  // far-future window
    slot  = restoreCounter.incrementAndGet()
    oddBucket = (slot / bucketSize) * 2 + 1                     // 1, 3, 5 ...

    insertDirectoryPath(restoreWindow, instanceId, oddBucket)    // idempotent upserts
    path = insertRestoreMetadata(restoreWindow, instanceId, oddBucket, transaction.id)
    storeRestorePathInTransaction(transaction.id, path)          // saved in es_transaction

// ── ON TRANSIENT FAILURE (retry path only) ──────────────────────────────
function registerRetry(transaction):
    retryWindow = computeWriteWindow(UTC_NOW)                    // W+1
    slot  = retryCounter.incrementAndGet()
    evenBucket = (slot / bucketSize) * 2                         // 0, 2, 4 ...

    insertDirectoryPath(retryWindow, instanceId, evenBucket)
    insertRetryMetadata(retryWindow, instanceId, evenBucket, transaction.id)

// ── ON TRANSACTION COMPLETION (success) ──────────────────────────────────
function onTransactionComplete(transaction):
    path = getRestorePathFromTransaction(transaction.id)
    deleteRestoreRow(path)   // O(1) targeted partition-key delete
----

[#virtual-clusters-cell-isolation]
=== Horizontal Scaling via Virtual Clusters & Cell Isolation

Instance-level bucketing bounds individual pod partitions to 50,000 rows.
However, ultra-large-scale microservice deployments face a cluster-wide ceiling: **the total number of active pods within a single minute window**.

[#tier-3-partition-sizing-guidance]
==== Tier 3 Partition Sizing Guidance: The 50,000 Pod Ceiling per Service

*Why is 50,000 pods the ceiling, and what scope does it apply to?* +
Recall the primary key structure of **Tier 3 (`es_instances_by_recovery_window`)**:

[source,sql]
----
PRIMARY KEY ((region, cluster, service_name, date_of_year, minute_of_day), instance_id_token, instance_id)
----

In Tier 3, each unique pod that registers a failure within a given minute window inserts a directory marker into the partition `((region, cluster, service_name, date_of_year, minute_of_day))`.
By default, all pods within a region belong to a single cluster named `default`.

[IMPORTANT]
====
*Critical Scope: 50,000 Pods of the SAME Orchestration Service, NOT the Entire Cluster:* +
Developers are sometimes alarmed when seeing the "50,000 pod ceiling," wondering if their entire Kubernetes cluster is near that limit.
It is essential to understand that **`service_name` is an integral component of the composite partition key**.
Cassandra physically isolates each microservice domain into its own independent partition space:

1. **Non-Orchestration Pods Do Not Count:** In a real-world Kubernetes cluster running 20,000 or 50,000 total pods, the vast majority are non-orchestration workloads (e.g., ingress controllers, API gateways, UI frontends, logging daemonsets, database/cache instances, or auxiliary microservices that do not use StackSaga).
These pods never interact with StackSaga's recovery tables.
2. **Independent 50,000 Limits per Service Entity:** If multiple distinct microservice entities in the same cluster use StackSaga orchestration (for example, `order-service` and `service-a` / `customer-service`), the 50,000-pod ceiling applies **completely separately to each service entity**:
* `order-service` has its own 50,000 pod budget: `((region, cluster, 'order-service', date, minute))`
* `service-a` has its own separate 50,000 pod budget: `((region, cluster, 'service-a', date, minute))`
Even if both services run in the exact same Kubernetes cluster and share the exact same Cassandra keyspace, their pod counts never sum together or consume each other's partition quota.
A cluster could have 30,000 `order-service` pods and 40,000 `service-a` pods (70,000 total StackSaga pods), and neither Tier 3 partition would come close to exceeding the 50,000 limit.
3. **The True Threshold:** A Tier 3 partition approaches Cassandra's recommended limit (< 50,000 rows / < 100MB) **only if 50,000 replicas of the EXACT SAME orchestration service (e.g., 50,000 pods of `order-service` alone)** all experience transient failures within the **exact same 60-second window**.

In practice, production microservices typically scale to tens, hundreds, or at most a few thousand replicas per service.
A single Tier 3 partition typically contains only tens to hundreds of rows under normal operations.
====

==== Cell Isolation via Virtual Clusters

For hyper-scale enterprise deployments that *do* operate 50,000+ replicas of a single orchestration service, StackSaga solves this scalability ceiling through **Virtual Clusters** without requiring separate physical database infrastructure:

.Horizontal Scaling via Virtual Clusters & Regional Cell Isolation
image::stacksaga-database-support:cassandra/stacksaga-virtual-clusters.svg[alt="Horizontal Scaling via Virtual Clusters & Regional Cell Isolation"]

<1> **Virtual Cluster Cell Isolation (`stacksaga.instance.cluster`):** Each virtual cluster forms a completely self-contained, autonomous processing cell.
Failures, network partitions, or high traffic spikes in `us-central-cluster-1` have zero operational impact on `us-central-cluster-2`.
<2> **Standard-Nodes (Live Traffic Writers):** The majority of orchestrator pods (e.g. 9,000 pods per cluster) handle live user-facing transactions.
On transient failure, they write forward into window W+1 of their assigned cluster partition using their local in-memory `AtomicLong` counter — no cross-cluster coordination required.
<3> **Strict 1:1 Ring Coordinator Mapping:** Each virtual cluster runs its **own dedicated Ring Coordinator cluster** (Master and Slaves).
There is **no cross-cluster coordinator traffic or shared state**.
The Ring Coordinator for `us-central-cluster-1` serves exclusively the Retry-Nodes configured with `cluster = us-central-cluster-1`, ensuring zero cross-cluster coordination overhead.
<4> **Retry-Nodes (Dual-Role: Readers & Forward Writers):** Retry-Nodes lease non-overlapping token sectors from their cluster's Ring Coordinator and scan sealed read windows (<= W).
Importantly, **Retry-Nodes are also forward writers**: when a retry attempt itself fails again, the Retry-Node atomically increments its local `AtomicLong` and re-registers the transaction into window W+1 of its own cluster — same write path as Standard-Nodes.
<5> **Shared Cassandra Keyspace (Physical Partition Separation):** All virtual clusters within the region connect to the **same Cassandra keyspace**.
Because Cassandra hashes the composite partition key `((region, cluster, service_name, date_of_year, minute_of_day))`, data from `us-central-cluster-1` and `us-central-cluster-2` lands in completely independent physical partitions.
Even with 50,000+ total pods active in the region, each virtual cluster's Tier 3 partition stays well under 10,000 rows — preserving optimal read latency and compaction efficiency.

By setting `stacksaga.instance.cluster` in `application.yml`, pods are assigned to isolated virtual clusters:

[source,yaml]
----
# Pods in virtual cluster 1
stacksaga:
  instance:
    region: us-central
    cluster: us-central-cluster-1

# Pods in virtual cluster 2
stacksaga:
  instance:
    region: us-central
    cluster: us-central-cluster-2
----

Each virtual cluster runs its **own dedicated Ring Coordinator deployment** with zero cross-cluster coordination overhead.
Because `cluster` is part of the composite partition key, data lands in completely separate physical partitions, preserving optimal read latency and compaction efficiency.

[#node-0-compactor-overseer]
=== Directory Compaction: Node-0 Compactor Overseer vs. Worker Responsibilities

When a Retry-Node finishes processing all buckets for an instance in a given window, it:
1. Drops each completed bucket partition from Tier 5 (single partition tombstone — O(1)).
2. Deletes the bucket index rows from Tier 4.
3. Deletes its instance marker from Tier 3.

*Who deletes the completed minute window from Tier 2 and the calendar date from Tier 1? Can every Retry-Node delete its own minute windows?* +
No — and this is a critical design point.
In StackSaga's retry architecture, **Node-0 is not a separate service or distinct binary**.
It is simply the active Retry-Node that holds the anchor (lowest) token range lease issued by the Ring Coordinator.

==== The Premature Deletion Hazard

Imagine two Retry-Nodes processing minute window 500:
* **Retry-Node 1** has 5 transactions and finishes in 100ms.
* **Retry-Node 2** has 40,000 transactions and is still running.

If Retry-Node 1 were allowed to delete minute 500 from `es_recovery_windows_by_day` immediately, the window would disappear from the directory.
If Retry-Node 2 then restarts (e.g. pod eviction by Kubernetes), it re-discovers its work by scanning Tier 2 — but minute 500 is gone, and those 40,000 transactions are permanently orphaned.

==== Responsibilities Breakdown

Compaction responsibilities are divided cleanly between general worker nodes and Node-0:

[cols="1,2,2",options="header"]
|===
| Responsibility | General Retry Workers (Node-1, Node-2, etc.) | Node-0 (Compactor Overseer)

| **Scope of Work**
| Handles only instances matching its assigned token lease.
| Inspects cluster-wide state across all token ranges.

| **Compaction Targets**
| - Tier 5: Bounded bucket partitions (`es_recovery_transactions_by_instance`) +
- Tier 4: Bucket index rows (`es_buckets_by_instance`) +
- Tier 3: Its own instance markers (`es_instances_by_recovery_window`)
| - Tier 2: Minute window records (`es_recovery_windows_by_day`) +
- Tier 1: Completed calendar dates (`es_days_by_year`)

| **Execution Timing**
| Runs immediately as each bucket or instance finishes.
| Runs on a periodic loop verifying sealed windows.
|===

[#node-0-two-gate-protocol]
==== Node-0's Two-Gate Verification Protocol

Before deleting any minute window from Tier 2, Node-0 must pass both gates:

* **Gate 1 (Cluster-Wide Quorum):**
Node-0 queries Tier 3 across the entire cluster without token filtering:
+
[source,sql]
----
SELECT instance_id FROM es_instances_by_recovery_window
WHERE region = :region AND cluster = :cluster AND service_name = :service_name
  AND date_of_year = :date AND minute_of_day = :window;
----
+
If any instance marker exists anywhere in the cluster, Node-0 waits.
* **Gate 2 (Wall-Clock Check):**
Node-0 verifies that current UTC time has progressed past the end of window W.
Even if all instance markers are clear, waiting ensures no late writes from Standard-Nodes cross into the window.

Only when **both gates pass** does Node-0 safely remove the minute window from Tier 2. Once all minute windows for a calendar date are cleared, Node-0 deletes the date from Tier 1.

.Directory Compaction: Node-0 Compactor Overseer Two-Gate Verification Protocol
image::stacksaga-database-support:cassandra/stacksaga-node0-compaction-gates.svg[alt="Node-0 Compactor Overseer Two-Gate Verification Protocol"]

<1> **Premature Deletion Hazard:** Uncoordinated worker deletion causes peer active transactions to be orphaned.
<2> **Node-0 Compactor Overseer:** Sole authority to delete shared upper tiers (Tier 2 and Tier 1).
<3> **Gate 1 (Cluster-Wide Quorum):** Full cluster query on Tier 3 must return 0 rows.
<4> **Gate 2 (Wall-Clock Check):** Verifies current UTC time has progressed past window end.
<5> **Safe Upper Pruning:** Safely deletes Tier 2 minute window and Tier 1 calendar date.

[#tier-3-tombstone-behavior]
==== Tier 3 Tombstone Behavior & Risk Profile

The Gate 1 scan surfaces a subtle but important Cassandra tombstone consideration that system engineers should understand.

*How tombstones accumulate in Tier 3:*

When a Retry-Node finishes all buckets for a given instance, it issues a targeted clustering-row `DELETE` against `es_instances_by_recovery_window`:

[source,sql]
----
DELETE FROM es_instances_by_recovery_window
WHERE region = :region AND cluster = :cluster AND service_name = :service_name
  AND date_of_year = :date AND minute_of_day = :window
  AND instance_id_token = :token AND instance_id = :id;
----

In Cassandra, deleting a clustering row writes a **cell tombstone** into the SSTable — not a partition tombstone like the O(1) Tier 5 bucket drops.
When Node-0 subsequently runs Gate 1 (a full partition scan of that `(date, window)` partition to verify 0 remaining instances), it must read through all accumulated cell tombstones before returning an empty result set.
Cassandra aborts any read that crosses more than 100,000 tombstones with a `ReadFailureException`.

*Why this is structurally self-limiting:*

Unlike Tier 5 restore rows (written for **every transaction start**), Tier 3 rows are only written when a pod **actually experiences a transient failure** — a much rarer event.
Several architectural constraints work together to keep tombstone accumulation well below the 100,000 threshold:

[cols="2,3",options="header"]
|===
| Constraint | Effect on Tier 3 Tombstone Accumulation

| **Failure-only writes**
| Tier 3 rows are inserted only on transient step failure — not on every transaction start.
In a healthy system the fraction of transactions that result in transient failures is small, so the number of unique `instance_id` markers written per minute window is far lower than total transaction throughput would suggest.

| **Virtual Cluster partitioning**
| The composite partition key includes `cluster`.
Pods assigned to `us-central-cluster-1` and `us-central-cluster-2` write into completely separate Tier 3 partitions.
The Virtual Cluster design bounds each partition to well under 10,000 rows — three orders of magnitude below the 100,000-tombstone threshold.
See <<tier-3-partition-sizing-guidance,Tier 3 partition sizing guidance>> and <<virtual-clusters-cell-isolation,Horizontal Scaling via Virtual Clusters & Cell Isolation>>.

| **Short lifecycle between deletion and Gate 1**
| Node-0's Gate 1 scan executes only after all Retry-Nodes have confirmed they finished a window.
In practice this is a short wall-clock interval — often within the same compaction cycle.
Cassandra's Memtable and recent SSTable flushes may have already partially absorbed or merged tombstones before Gate 1 executes, reducing the effective tombstone read count further.

| **Single-partition, exact-key scan**
| Gate 1 targets an exact composite partition key (`region + cluster + service_name + date_of_year + minute_of_day`).
Cassandra executes this as a single in-memory partition read without cross-node range scanning.
This is fundamentally different from the cross-partition `ALLOW FILTERING` anti-pattern described in <<cassandra-directory-architecture,Why Cassandra Requires a Directory-Based Architecture>>, and handles tombstones significantly more efficiently.
|===

*Risk assessment by deployment scenario:*

[cols="2,1,3",options="header"]
|===
| Deployment Scenario | Risk Level | Guidance

| Normal deployments — tens to hundreds of unique failing pods per minute window
| 🟢 Negligible
| Tombstone count is orders of magnitude below the 100,000 threshold. No tuning required.

| Large deployments with Virtual Clusters correctly configured
| 🟢 Low
| Each cluster's Tier 3 partition stays well under 10,000 rows by design. Standard `gc_grace_seconds` is sufficient.

| Very high pod churn — thousands of unique `instance_id`s failing per minute, sustained over many hours without compaction
| 🟡 Moderate
| Tombstones can stack across many windows if compaction does not keep pace.
Increase virtual cluster granularity (`stacksaga.instance.cluster`) and consider reducing `gc_grace_seconds` on `es_instances_by_recovery_window` to accelerate tombstone collection.

| Single cluster — 50,000+ actively failing pods of the same orchestration service, no Virtual Cluster separation
| 🔴 Risk
| This scenario already violates the documented <<tier-3-partition-sizing-guidance,Tier 3 partition sizing guidance>>.
Partition pods into virtual clusters immediately to bring each Tier 3 partition back within the safe row budget.
|===

[NOTE]
====
*Contrast with Tier 5 Odd Buckets:* +
The tombstone problem is explicitly solved at Tier 5 via odd/even bucket segregation and O(1) partition tombstone drops, because restore watchdog rows are written for *every* transaction start — producing cell tombstones at a rate directly proportional to total transaction throughput, which can be enormous. +
Tier 3 tombstones accumulate only at the rate of *transient failures across unique pods per minute*, which is structurally orders of magnitude smaller.
This is why the architecture provides a dedicated tombstone isolation mechanism for Tier 5 but relies on Virtual Cluster bounding — rather than a separate structural mitigation — for Tier 3.

=== Per-Domain-Entity Restore & Retry Delay Configuration

[#per-domain-delay-config]
Different saga types can have structurally different execution durations based purely on system-level factors — the number of downstream microservice hops, network round-trip times, and external API response times — not business-domain decisions.

For example:

* A `notification-saga` that calls one internal service completes in milliseconds.
A restore watchdog 10 hours ahead is unnecessarily distant — if the pod crashes, orphan detection is delayed far longer than necessary.
* An `order-saga` that orchestrates 8 downstream services across multiple regions may legitimately take 20–30 minutes under degraded network conditions.
With a short global restore delay, the watchdog could fire while the saga is still in-flight on a healthy pod, triggering a spurious status-check re-invocation cycle.

StackSaga provides **per-domain-entity overrides** for both restore and retry delay windows under `stacksaga.cassandra.recovery.retry.domains` and `stacksaga.cassandra.recovery.restore.domains`, with automatic fallback to the `default` entry:

.Example `application.yml` with Per-Domain Overrides
[source,yaml]
----
stacksaga:
  cassandra:
    recovery:
      retry:
        domains:
          default:
            delay-windows: 1            # Global default: W+1 (next window)
          order-saga:
            delay-windows: 3            # W+3 — longer cooldown for slow external APIs
          payment-saga:
            delay-windows: 1

      restore:
        domains:
          default:
            delay-windows: 600          # Global default: 10 hours ahead (600 × 1 min)
          order-saga:
            delay-windows: 1200         # 20 hours — multi-hop orchestration saga
          payment-saga:
            delay-windows: 300          # 5 hours — shorter lifecycle
          notification-saga:
            delay-windows: 60           # 1 hour — fast notification lifecycle
----

*Why the directory structure requires zero changes:*

The `delay-windows` value is consumed **only at write time** (when the Standard-Node writes ahead on failure or registers a watchdog row at transaction start).
Each transaction independently stores its full watchdog partition path (`restore_date`, `restore_window`, `restore_instance_id`, `restore_bucket`) in `es_transaction`.
Retry-Nodes discover and process watchdog and retry rows through the normal 5-tier traversal — they have no awareness of which domain entity a record belongs to.

This means:

* A `payment-saga` watchdog landing at `W+300` and an `order-saga` watchdog landing at `W+1200` coexist in the same Tier 5 table across different windows — processed by the same pipeline with zero structural changes.
* Domain-level fallback to `default` is seamless — any domain without an explicit override automatically inherits `domains.default.delay-windows`.
* No schema changes, no new tables, no new tiers required.

[#architectural-faq]
== Frequently Asked Questions: Architectural Deep-Dive

This section addresses architectural, operational, and database engineering questions frequently raised by developers, Cassandra DBAs, and platform SREs deploying StackSaga in high-throughput production environments.

=== Category 1: Cassandra Data Modeling & Partition Sizing

[#faq-q1]
==== Q1: Does the 50,000-pod ceiling in Tier 3 mean our entire Kubernetes cluster cannot exceed 50,000 pods?

**No.** The 50,000-pod threshold applies **exclusively per orchestration service** (`service_name`), not across the entire Kubernetes cluster.

1. **Non-Orchestration Pods Do Not Count:** In modern enterprise Kubernetes clusters running tens of thousands of pods, the vast majority represent non-orchestration workloads (e.g., API gateways, UI frontends, daemonsets, caching services, independent microservices not using StackSaga).
These workloads never write into StackSaga's recovery tables.
2. **Independent 50,000 Limits per Service Entity:** When multiple distinct orchestration services (`order-service`, `payment-service`, `shipping-service`) run in the same Kubernetes cluster and share the same Cassandra keyspace, each receives its **own independent 50,000-pod partition quota**.
This is because `service_name` is an explicit, mandatory component of Tier 3's composite partition key:
+
[source,sql]
----
PRIMARY KEY ((region, cluster, service_name, date_of_year, minute_of_day), instance_id_token, instance_id)
----
+
Data for `order-service` and `payment-service` hashes to completely different Cassandra nodes and physical SSTables.
A cluster running 30,000 `order-service` pods and 40,000 `payment-service` pods (70,000 total StackSaga pods) operates safely because neither service comes close to its individual 50,000 ceiling.
3. **The True Operational Threshold:** Tier 3 approaches Cassandra's recommended partition limit (< 50,000 rows / < 100MB) **only if 50,000 replicas of the exact same orchestration service** all experience transient failures within the **exact same 60-second window**.
Under normal operations, even large microservices scale to hundreds or a few thousand replicas, and only a fraction experience transient retries simultaneously.

See <<tier-3-partition-sizing-guidance,Tier 3 Partition Sizing Guidance>> and <<virtual-clusters-cell-isolation,Horizontal Scaling via Virtual Clusters & Cell Isolation>>.

[#faq-q2]
==== Q2: Why don't saga transaction payloads cause Tier 5 recovery partitions to exceed Cassandra's 100MB partition limit?

**Because zero business payloads or domain states are ever stored inside any of the 5 recovery directory tables.**

Whether a saga's payload is a 100-byte JSON order or a massive serialized domain entity graph, Tier 5 rows (`es_recovery_transactions_by_instance`) store strictly lightweight metadata pointers (~50 to 100 bytes): `transaction_id`, `running_status`, and target routing markers.

The actual saga state, step parameters, execution history, and serialized payloads reside exclusively in the core Event Store (`es_transaction` and `es_transaction_tryout`), which are partitioned individually by `transaction_id` (O(1) point lookups).

At ~50–100 bytes per metadata row:
* A 10,000-row bucket consumes only **~800KB**.
* A completely full 50,000-row bucket consumes only **~3MB to 5MB** on disk.

It is physically impossible for a recovery partition to violate Cassandra's 100MB limit regardless of how large your business transaction payloads are.

See <<instance-level-local-bucketing,Bounded Partitions: Instance-Level Local Bucketing>>.

[#faq-q3]
==== Q3: What happens if a major downstream service goes down and thousands of pods fail simultaneously—won't they hotspot a single Cassandra coordinator?

**No.** StackSaga deliberately avoids global shared partitions, global sequence generators, and centralized counters.

When thousands of pods experience downstream timeouts simultaneously:

. **Local Atomic Partitioning:** Each pod increments its own in-memory `AtomicLong` counter and writes into its **own instance-dedicated partition** in Tier 5 (`((region, cluster, service_name, date, window, instance_id, bucket_index))`):
+
[source,sql]
----
PRIMARY KEY ((region, cluster, service_name, date_of_year, minute_of_day, instance_id, bucket_index), transaction_id)
----
. **Ring-Wide Token Distribution:** Because Cassandra hashes partition keys using Murmur3, thousands of failing instances produce thousands of distinct token hashes across the Cassandra ring.
Write traffic is evenly distributed across every Cassandra node in the datacenter, eliminating coordinator hotspots.
. **Temporal Isolation:** Live pods write ahead into future window W+1.
Recovery workers read only from past sealed windows (<= W).
The write path and the recovery read path never touch the same partition at the same time.

See <<instance-level-local-bucketing,Bounded Partitions: Instance-Level Local Bucketing>> and <<ternary-window-model,The Ternary-Window Synchronization Model>>.

=== Category 2: Tombstones & Compaction Safety

[#faq-q4]
==== Q4: Why does StackSaga segregate Retries and Restores into Even and Odd buckets, and how does this prevent Cassandra `ReadFailureException`?

**Even and Odd bucket segregation isolates high-frequency cell tombstones generated by normal transaction completions away from pristine retry scan paths.**

* **Even Buckets (Pure Retries — 0, 2, 4...):** Written only when a transient failure occurs.
When all retries in a bucket finish, the entire partition is deleted in one metadata operation via an O(1) **partition tombstone**.
Retry workers reading even buckets scan **100% live rows with 0% cell tombstones**.
* **Odd Buckets (Restore Watchdogs — 1, 3, 5...):** Written on **every transaction start** as a dead-man's switch watchdog.
Under normal operating conditions, 99.9%+ of transactions complete successfully, resulting in targeted individual row deletions (`DELETE FROM ... WHERE transaction_id = :id`).
In Cassandra, individual row deletes write **cell tombstones**.
* **The Tombstone Hazard Prevented:** If Retries and Restores shared the same bucket partition, retry workers scanning 50,000 rows would encounter tens of thousands of cell tombstones from completed transactions.
Scanning over 100,000 tombstones in a single read query path causes Cassandra to abort with a fatal `ReadFailureException`.
* **The Solution:** By quarantining watchdogs into odd buckets, high-frequency cell tombstones never contaminate retry paths.
Even buckets remain 100% tombstone-free, ensuring predictable sub-millisecond recovery scans.

See <<odd-even-bucket-segregation,Why Restore Buckets Use Odd Indexes>>.

[#faq-q5]
==== Q5: When Retry-Nodes delete completed instances from Tier 3, why doesn't Node-0 encounter a tombstone storm during Gate 1 verification checks?

When a Retry-Node completes all buckets for an instance, it deletes that instance's clustering row from Tier 3 (`DELETE FROM es_instances_by_recovery_window WHERE ... AND instance_id = :id`), writing a cell tombstone.
When Node-0 executes Gate 1 (verifying 0 instances remain before pruning Tier 2), it scans that `(date, window)` partition.

This is structurally safe and will not trigger Cassandra's 100,000-tombstone ceiling because:
1. **Failure-Only Writes:** Tier 3 rows represent **unique pods that failed within that specific 60-second window**, not individual transactions.
In typical enterprise microservices, only tens or hundreds of unique pod instances experience transient errors per minute.
2. **Virtual Cluster Bounding:** The composite partition key includes `cluster`.
Workloads are bounded to well under 10,000 pods per cell—an entire order of magnitude below the 100,000-tombstone limit.
3. **Targeted Partition Scan:** Gate 1 targets an exact composite partition key (`region + cluster + service_name + date + minute`), reading a single in-memory partition without cross-node range scanning or `ALLOW FILTERING`.

See <<tier-3-tombstone-behavior,Tier 3 Tombstone Behavior & Risk Profile>> and <<node-0-two-gate-protocol,Node-0's Two-Gate Verification Protocol>>.

[#faq-q6]
==== Q6: Who cleans up completed minute windows and calendar dates, and what goes wrong if every worker node deletes its own windows?

Tier 2 (`es_recovery_windows_by_day`) and Tier 1 (`es_days_by_year`) are **shared directory indexes** traversed by all recovery workers.

* **The Premature Deletion Hazard:** If individual workers were permitted to delete Tier 2 minute windows as soon as their assigned token sector finished, an unrecoverable race condition would occur.
Suppose Worker A has 5 transactions and finishes in 50ms, while Worker B has 40,000 transactions and is still processing.
If Worker A deleted minute 500 immediately, the window would vanish from Tier 2. If Worker B then crashed and restarted, it would scan Tier 2, find minute 500 missing, and permanently abandon those 40,000 transactions.
* **The Node-0 Compactor Overseer Solution:** StackSaga designates **Node-0** (the active worker holding the anchor token lease) as the sole authority permitted to prune Tier 2 and Tier 1.
* **The Two-Gate Protocol:** Before deleting any minute window from Tier 2, Node-0 verifies:
1. **Gate 1 (Cluster-Wide Quorum):** Full cluster query on Tier 3 returns 0 remaining instance rows across all token ranges.
2. **Gate 2 (Wall-Clock Check):** Verifies current UTC time has progressed past the end of window W.
Only when both gates pass does Node-0 safely remove the minute window from Tier 2, followed by Tier 1 when the calendar day is complete.

See <<node-0-compactor-overseer,Directory Compaction: Node-0 Compactor Overseer vs. Worker Responsibilities>> and <<node-0-two-gate-protocol,Node-0's Two-Gate Verification Protocol>>.

=== Category 3: Concurrency, Locking, & Coordination

[#faq-q7]
==== Q7: How does StackSaga achieve distributed recovery across dozens of worker nodes without distributed locks (ZooKeeper, Redis, or Cassandra Paxos/LWT)?

StackSaga replaces runtime database locking with **Spatial Worker Isolation** based on Cassandra's native Murmur3 hashing ring:

1. **Token Registration:** During transient failure registration, every pod writes its `token(instance_id)` into Tier 3 as a clustering key alongside its `instance_id`.
2. **Mutually Exclusive Token Leases:** The RSocket Ring Coordinator divides the 64-bit Murmur3 integer space (`[-2^63 .. 2^63 - 1]`) into non-overlapping token sectors and leases them to connected Retry-Nodes.
3. **Partition-Filtered Queries:** When a worker queries Tier 3, it restricts its query using `WHERE instance_id_token >= :min AND instance_id_token < :max`.
4. **Zero Lock Contention:** Because each token lease is mutually exclusive, workers are physically incapable of claiming the same pod's recovery buckets.
Workers process transactions in parallel with zero lock contention, zero Paxos rounds, and zero external coordination infrastructure.

See <<spatial-worker-isolation,Spatial Worker Isolation via Murmur3 Token Leases>>.

[#faq-q8]
==== Q8: How does the Ternary-Window model prevent Retry-Nodes from reading transactions that Standard-Nodes are still actively writing?

The engine enforces a strict temporal firewall between readers and writers using three discrete time horizons:

1. **Past Sealed Windows (<= W):** The read-only zone.
Standard-Nodes never write here.
Only Retry-Nodes read from these windows.
2. **Active Write Window (W+1):** Standard-Nodes write transient failure retries here using local `AtomicLong` counters.
Retry-Nodes never read from W+1 because it has not yet elapsed and sealed.
3. **Far-Future Restore Horizon (W + delay):** Standard-Nodes arm silent crash watchdog rows here (e.g. +600 minutes / 10 hours ahead).

Because a minute window must fully elapse before being promoted to a sealed read candidate, writers and readers are physically separated by time and Cassandra partition keys.
This ensures zero dirty reads, zero phantom reads, and zero database-level locking.

See <<ternary-window-model,The Ternary-Window Synchronization Model>>.

=== Category 4: Fault Tolerance, Pod Crashes, & Disaster Recovery

[#faq-q9]
==== Q9: What happens if Kubernetes kills (OOM/evicts) a Retry-Node while it is halfway through processing a 50,000-transaction bucket?

StackSaga provides a strict **Safe Shutdown & Zero Data Loss Guarantee**:

1. **Atomic Compaction Barrier:** A bucket partition in Tier 5 and its pointer in Tier 4 are **never deleted until 100% of the bucket's transactions have been successfully dispatched**:
+
[source,text]
----
if isShutdownRequested() or executedCount < totalTransactions:
    log.info("Worker shutting down or partial execution. Preserving bucket in Cassandra.")
    return // Do NOT delete bucket partition!
----
2. **Preserved Work State:** If a Retry-Node is killed at transaction 25,000 out of 50,000, the bucket partition and its Tier 3 instance marker remain fully intact in Cassandra.
3. **Idempotent Step Skipping:** Upon worker restart (or reassignment of the token lease to a healthy node by the Ring Coordinator), the new worker re-scans the bucket from row 1. To prevent duplicate execution of the first 25,000 transactions, the engine inspects `es_execution_markers` before executing each saga step.
Completed steps are detected as `COMMITTED` and skipped immediately; only uncommitted steps are executed.

See <<safe-shutdown-guarantee,Safe Shutdown & Zero Data Loss Guarantee>>.

[#faq-q10]
==== Q10: What if an orchestrator pod crashes silently (kernel panic, power loss, `kill -9`) without executing its catch block or logging a failure?

Standard saga frameworks lose transactions during ungraceful terminations because the pod dies before writing a failure record or sending a heartbeat.

StackSaga solves this with the **Restore Dead-Man's Switch**:
1. When any transaction begins, the orchestrator writes a watchdog record into an odd bucket at a far-future window (W + delay, e.g. 10 hours ahead) and persists the partition pointer in `es_transaction`.
2. **Normal Path:** If the pod executes normally, it deletes the watchdog row in O(1) time upon transaction completion.
3. **Crash Path:** If the pod suffers a silent crash, it never completes, and the watchdog row remains in Cassandra.
Hours later, when the clock reaches that future window, the window seals and a Retry-Node automatically discovers the abandoned transaction.
4. **Mandatory Status Check:** When picking up a restore row, the engine queries `es_transaction.running_status`.
If the transaction is still in-flight, it is automatically re-invoked and carried forward to completion.

See <<silent-crash-restore-watchdog,How Restore Works: The Dead-Man's Switch>>.

[#faq-q11]
==== Q11: What if our entire microservice cluster or downstream dependencies were offline for a full weekend—do old failed transactions get abandoned?

**No.** StackSaga includes **Deep Historical Recovery**.

* **Multi-Day Scan on Boot:** When worker nodes boot, they do not merely start listening at the current clock minute.
They query Tier 1 (`es_days_by_year`) backwards by `recovery.lookback-days` (default: 2 days, configurable to any duration).
* **Ascending Chronological Traversal:** Workers traverse historical calendar days in ascending order (`date_of_year ASC`) and historical minute windows in ascending order (`minute_of_day ASC`), systematically processing Friday's, Saturday's, and Sunday's accumulated backlog before transitioning smoothly to live traffic.
* **Quarantine Safeguard:** Transactions older than `stacksaga.cassandra.transaction-lifetime` (default: 24h) are safely quarantined to `es_frozen_transaction` to prevent stale processing.

See <<deep-historical-recovery,Deep Historical Recovery>>.

[#faq-q12]
==== Q12: If an application pod restarts mid-window and its in-memory `AtomicLong` resets to 0, does it overwrite or corrupt existing bucket data?

**No.**
1. **Unique Instance Identity:** In modern container platforms like Kubernetes, when a container restarts or is rescheduled, it receives a new unique Pod UID / container identifier.
StackSaga uses this unique runtime identity for `instance_id`.
Therefore, a restarted pod writes into a completely distinct `instance_id` partition in Tier 5 and registers as a new clustering row in Tier 3.
2. **Clustering Key Isolation:** Even if an application framework reused the identical string ID across restarts, rows inside Tier 5 are keyed by `clustering key (transaction_id)`:
+
[source,sql]
----

----
+
Writes with different `transaction_id` values append new clustering rows rather than overwriting existing ones.

=== Category 5: Operations, Multi-Tenancy, & Consistency Tuning

[#faq-q13]
==== Q13: Can multiple distinct virtual clusters share the same Cassandra cluster and keyspace without interfering with each other?

**Yes.** StackSaga was designed specifically for multi-tenant and multi-cluster sharing on a single unified Cassandra keyspace.

* **Composite Partition Key Isolation:** All 5 directory tables include `region`, `cluster`, and `service_name` in their composite Partition Keys (`PRIMARY KEY ((region, cluster, service_name, ...))`):
+
[source,yaml]
----
stacksaga:
  instance:
    region: us-central
    cluster: us-central-cluster-1   # Cell A
----
* **Physical Ring Segregation:** Because Cassandra routes data based on the full hash of the partition key, writes and queries from `cluster: us-central-cluster-1` and `cluster: us-central-cluster-2` land in physically separate token ranges and SSTable partitions.
* **Zero Cross-Cluster Contention:** Each virtual cluster operates as an autonomous cell with its own dedicated Ring Coordinator and workers, with zero cross-cluster lock contention, zero noisy-neighbor partition scans, and zero data leakage.

See <<virtual-clusters-cell-isolation,Horizontal Scaling via Virtual Clusters & Cell Isolation>>.

[#faq-q14]
==== Q14: What Cassandra Consistency Level does StackSaga require, and does it survive a Cassandra node failure?

StackSaga defaults to `LOCAL_QUORUM` for both reads (`stacksaga.cassandra.read-consistency-level`) and writes (`stacksaga.cassandra.write-consistency-level`).

* **Strong Consistency:** In a typical 3-node or multi-datacenter Cassandra cluster with a Replication Factor of 3 (`RF=3`), `LOCAL_QUORUM` requires confirmation from floor(3/2) + 1 = 2 replicas in the local datacenter.
* **Overlap Invariant:** Because R + W = 2 + 2 = 4 > 3, this guarantees strong read-after-write consistency (the read set and write set always overlap by at least one replica node) while avoiding high-latency WAN round-trips to remote datacenters.
* **Fault Tolerance:** If a single Cassandra node fails or undergoes maintenance, reads and writes continue uninterrupted with full consistency.

See <<properties-reference,Properties Reference>>.

[#faq-q15]
==== Q15: What happens if there is NTP clock skew between different orchestrator pods or retry workers?

StackSaga is resilient to normal clock drift (sub-second or few-second discrepancies typical in cloud VPCs synchronized via NTP or AWS Time Sync / Google NTP):

1. **Coarse Window Granularity:** Window indexing operates at coarse 1-minute granularity (`minute_of_day = (hour * 60) + minute`).
A small sub-second drift does not impact window assignment.
2. **Forward Write Buffer:** Standard-Nodes write ahead into W+1, providing a minimum 60-second buffer before a window becomes eligible for reading.
3. **Node-0 Gate 2 Wall-Clock Check:** Node-0 requires the current UTC timestamp to strictly exceed the window boundary before deletion is considered, preventing premature pruning caused by slight clock differences.
4. **Chronological Recovery Guarantee:** If severe clock drift (several minutes) occurs on a degraded pod, it may register a window slightly early or late.
However, because both Tier 1 and Tier 2 are traversed chronologically, all windows are eventually discovered and recovered without data loss.

See <<ternary-window-model,The Ternary-Window Synchronization Model>> and <<node-0-two-gate-protocol,Node-0's Two-Gate Verification Protocol>>.
