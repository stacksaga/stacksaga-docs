= Stacksaga Cassandra Reactive Support

== Overview

`stacksaga-cassandra-reactive-support` is the *Cassandra reactive (non-blocking)* implementation of the xref:stacksaga-database-support:overview/database-support-overview.adoc[].
It provides all the facilities for accessing the Cassandra event store for the StackSaga engine, powering transaction persistence, asynchronous transient failure recovery, and exposing tracing details for the xref:trace-window:stacksaga-trace-window.adoc[].

It is deployed within the orchestrator service alongside any StackSaga orchestrator starter.
See xref:implementations:engine-overview.adoc[] for the full list of available implementations and their respective starters.

[IMPORTANT]
====
*Retry Ordering Guarantee (Murmur3 Token Order vs. Strict FIFO):* +
In distributed architectures, transient retries occur when a downstream microservice is temporarily slow, restarting, or experiencing network latency.
In Cassandra, rows are distributed across cluster nodes via the **Murmur3 token hash**.

Within an individual 1-minute retry window, transactions are discovered by worker instances in **token order**, not by exact failure millisecond.
Across different minute windows and calendar days, retry processing is **strictly chronological** (earlier minute windows and earlier calendar dates are always traversed first).

*Architectural Recommendation for Strict Sequential FIFO Requirements:* +
For the vast majority of microservice domains (such as e-commerce, banking, logistics, and telecom), token order within a 1-minute retry window is completely standard and safe, because once the downstream resource recovers, all failed transactions from that minute resolve successfully.
However, if your system contains a strict requirement for exact microsecond First-In, First-Out (FIFO) retry ordering between concurrent users (such as financial order-matching engines), StackSaga recommends using **one of the SQL database support modules** (PostgreSQL or MySQL) specifically for the event store.
====

=== Step 2: Keyspace & Schema Creation

Before starting your application, execute the CQL script in your Cassandra cluster.
The script creates the target keyspace along with all static tables required by both the **Core Event Store** and the **5-Tier Hierarchical Retry Engine**.

==== 1. Creating the Keyspace

For production deployments, always use `NetworkTopologyStrategy` configured with your local datacenter name and replication factor:

.Keyspace Creation Script
[source,sql]
----
CREATE KEYSPACE IF NOT EXISTS stacksaga_event_store
WITH replication = {
  'class': 'NetworkTopologyStrategy',
  'datacenter1': 3
}
AND durable_writes = true;
----

NOTE: For local development or isolated testing, you can use `'class': 'SimpleStrategy', 'replication_factor': 1`.

==== 2. Executing the Unified Schema Script

All tables in StackSaga use static names. Multi-tenancy, service scoping, regional boundaries, and virtual clusters are isolated via composite Partition Keys (`PRIMARY KEY ((region, cluster, service_name), ...)`), eliminating the need for dynamic per-service table generation.

.Unified Cassandra Schema Script (`schema.cql`)
[source,sql]
----
USE stacksaga_event_store;

-- ====================================================================
-- CORE EVENT STORE TABLES
-- ====================================================================

-- 1. Main transaction state store (Single-Row Partition)
CREATE TABLE IF NOT EXISTS es_transaction
(
    transaction_id          text PRIMARY KEY,
    aggregator_name         text,
    init_aggregator_version text,
    init_datetime           timestamp,
    instance_id             text,
    process_exception_json  blob,
    recent_retry_id         uuid,
    region                  text,
    cluster                 text,
    running_status          text,
    has_termination_error   int,
    termination_error_log   text,
    service_name            text,
    service_release_version text,
    target_retry_end_time   timestamp,
    zone_id                 text
);

-- 2. Transaction step (tryout) records (Multi-Row Partition co-located with parent transaction)
CREATE TABLE IF NOT EXISTS es_transaction_tryout
(
    transaction_id      text,
    span_key            text,
    executed_order      int,
    active_datetime     timestamp,
    duration            bigint,
    end_datetime        timestamp,
    executor_name       text,
    has_error           int,
    instance_id         text,
    process_error       text,
    span_type           text,
    start_datetime      timestamp,
    step_state          text,
    PRIMARY KEY (transaction_id, span_key, executed_order)
) WITH CLUSTERING ORDER BY (span_key ASC, executed_order ASC);

-- 3. Execution markers for idempotency and write protection
CREATE TABLE IF NOT EXISTS es_execution_markers
(
    service_name     text,
    transaction_id   text,
    span_key         text,
    execution_state  text,
    lease_owner      text,
    PRIMARY KEY ((service_name, transaction_id), span_key)
);

-- 4. Compensation failed transactions requiring manual intervention
CREATE TABLE IF NOT EXISTS es_frozen_transaction
(
    transaction_id         text PRIMARY KEY,
    freezing_datetime      timestamp,
    freezing_reason        text,

    cluster                text,

    process_exception_json blob
);

-- ====================================================================
-- 5-TIER HIERARCHICAL RETRY ENGINE TABLES

CREATE TABLE IF NOT EXISTS es_days_by_year
(

    service_name text,
    date_of_year date,

CREATE TABLE IF NOT EXISTS es_retry_windows_by_day
(
    region        text,
    cluster       text,
    service_name  text,
    date_of_year  date,
    minute_of_day int,
    PRIMARY KEY ((region, cluster, service_name, date_of_year), minute_of_day)
) WITH CLUSTERING ORDER BY (minute_of_day ASC);

-- Tier 3: Microservice instances clustered by Murmur3 token hash
CREATE TABLE IF NOT EXISTS es_instances_by_retry_window
(
    region            text,
    cluster           text,
    service_name      text,
    date_of_year      date,
    minute_of_day     int,
    instance_id_token bigint,
    instance_id       text,
    PRIMARY KEY ((region, cluster, service_name, date_of_year, minute_of_day), instance_id_token, instance_id)
) WITH CLUSTERING ORDER BY (instance_id_token ASC);

-- Tier 4: Sequential bucket allocation directory
CREATE TABLE IF NOT EXISTS es_buckets_by_instance
(
    region        text,
    cluster       text,
    service_name  text,
    date_of_year  date,
    minute_of_day int,
    instance_id   text,
    bucket_index  int,
    PRIMARY KEY ((region, cluster, service_name, date_of_year, minute_of_day, instance_id), bucket_index)

-- Tier 5: Bounded retry transaction metadata partitions
CREATE TABLE IF NOT EXISTS es_retry_transactions_by_instance
(
    region              text,
    cluster             text,
    service_name        text,
    date_of_year        date,
    minute_of_day       int,
    instance_id         text,
    bucket_index        int,
    transaction_id      text,
    added_datetime      timestamp,
    allocation_key      text,
    allocation_datetime timestamp,
    stacksaga_impl_type text,
    payload             blob,
    PRIMARY KEY ((region, cluster, service_name, date_of_year, minute_of_day, instance_id, bucket_index), transaction_id)
) WITH CLUSTERING ORDER BY (transaction_id ASC);

== How Transaction Data Is Stored in Cassandra

Cassandra stores data using a denormalized schema, partition key hashing, and immutable SSTables without centralized B-Tree indexing.
StackSaga divides its database architecture into two coordinated groups of tables:

[cols="1,2,2",options="header"]
|===
| Category | Table Name | Purpose

.4+| *Core Event Store*
| `es_transaction` | Primary transaction metadata store (Single-Row Partition).
| `es_transaction_tryout` | Step execution (tryout) store, co-located by transaction ID.
| `es_execution_markers` | Idempotency markers and write protection for event streaming.
| `es_frozen_transaction` | Quarantined transactions with permanent compensation failures.

.5+| *5-Tier Retry Engine*
| `es_days_by_year` | Tier 1: Directory of active calendar dates with pending retries.
| `es_retry_windows_by_day` | Tier 2: Directory of active 1-minute time windows per day.
| `es_instances_by_retry_window` | Tier 3: Pod instance markers clustered by Murmur3 token hash.
| `es_buckets_by_instance` | Tier 4: Sequential bucket indices per instance window.
| `es_retry_transactions_by_instance` | Tier 5: Bounded retry metadata partitions (< 100MB).
|===

=== `es_transaction` Table

`es_transaction` stores the primary state and metadata for every transaction, using `transaction_id` as the **Partition Key**.
Every transaction is saved as a **Single-Row Partition**.

Because transaction IDs are distributed uniformly across all Cassandra nodes via the partitioner hash, this approach enables sustained high throughput without creating database hot spots:

image:stacksaga-database-support:cassandra/stacksaga-diagram-cassandra-managing-throughput.drawio.svg[alt="StackSaga Cassandra Managing Throughput"]

=== `es_transaction_tryout` Table

`es_transaction_tryout` stores individual execution step records (tryouts) for each saga.
It uses `transaction_id` as the **Partition Key** with a **Multi-Row Partition** approach:

image:stacksaga-database-support:cassandra/stacksaga-diagram-cassandra-es-transaction-tryout-table.svg[alt="StackSaga Cassandra es_transaction_tryout table"]

Because tryouts share the exact same `transaction_id` partition key as the parent transaction, Cassandra places them on the **exact same physical storage node**.
This colocation minimizes network hops: queries reading a transaction and its tryout history are routed to a single node.

=== `es_frozen_transaction` Table

`es_frozen_transaction` stores transactions where an automated compensation step itself encountered an unrecoverable error, leaving the transaction in a partially compensated state.
These transactions are safely quarantined to protect downstream systems.
They require developer diagnosis and manual re-triggering via the administrative restore endpoint.

== The Cassandra Retry Challenge & The 5-Tier Directory Architecture

=== Why Cassandra Requires a Directory-Based Retry Architecture

In relational databases (PostgreSQL, MySQL), implementing a retry queue is straightforward:
[source,sql]
----
SELECT * FROM retry_queue
WHERE status = 'PENDING' AND retry_time <= NOW()
ORDER BY retry_time ASC LIMIT 100;
----
Relational engines use a B-Tree index to locate pending rows in milliseconds, and update or delete them in place.

In Cassandra, attempting to use a flat table as an active polling queue is a well-known distributed anti-pattern:

1. **Absence of Global Secondary Indexing for Queues:**
   Cassandra distributes partitions across cluster nodes using partition key hashes. There is no global B-Tree index across partitions.
   Polling a flat table for pending items without knowing partition keys requires full cluster range scans (`ALLOW FILTERING`), creating excessive network I/O and query timeouts.

2. **The Queue Anti-Pattern & Tombstone Scanning:**
   Cassandra data files (SSTables) are immutable. When records are deleted, Cassandra writes tombstones.
   In a polling queue where tasks are continuously added and deleted, queries scanning for the next available tasks must read past all the tombstones of completed tasks before reaching live data. If a scan crosses more than 100,000 tombstones, Cassandra aborts the query (`ReadFailureException`).

3. **Predictable Performance Requires Partition-Key Targeting:**
   Cassandra is exceptionally fast and scalable when queries provide the exact composite partition key.

=== The 5-Tier Directory Solution

Rather than treating retries as a flat polling queue, StackSaga models retry discovery as a **hierarchical active directory**:

* **Zero Blind Polling:** Workers never scan across empty tables. They only query partitions discovered through the active directory tree (`es_days_by_year` -> `es_retry_windows_by_day` -> `es_instances_by_retry_window`).
* **Partition-Level Compaction:** Transactions are grouped into bounded bucket partitions. When a bucket finishes, the entire partition is dropped at once (`DELETE ... WHERE ... bucket_index = :b`), creating a single partition tombstone that Cassandra cleans up in O(1) time during SSTable compaction.

.StackSaga 5-Tier Retry Directory Hierarchy & Primary Event Store
image:stacksaga-database-support:cassandra/stacksaga-diagram-cassandra-hierarchical-retry-schema.svg[alt="StackSaga 5-Tier Retry Directory Hierarchy & Primary Event Store"]

The numbered components of the architecture operate as follows:

<1> **Tier 1 (`es_days_by_year`) -- Active Calendar Dates:** +
Tracks which calendar dates contain pending retry transactions for a given service.
When a calendar day has no pending retries, its directory record is deleted.
Workers query active dates directly, eliminating empty table scans.

<2> **Tier 2 (`es_retry_windows_by_day`) -- UTC Minute Windows:** +
Divides each 24-hour day into discrete one-minute time windows (`minute_of_day`, `0` to `1439` UTC).
Workers process windows in ascending chronological order (`minute_of_day ASC`), ensuring older transient failures are retried before newer ones.

<3> **Tier 3 (`es_instances_by_retry_window`) -- Token-Partitioned Worker Slicing:** +
Records which microservice pods encountered failures in that minute window, clustered by their 64-bit Murmur3 token hash (`instance_id_token = token(instance_id)`).
Retry workers query only the instances whose token hash falls within their assigned token lease range.

<4> **Tier 4 (`es_buckets_by_instance`) -- Bucket Allocation Directory:** +
Maintains the sequential bucket indices (`0, 1, 2...`) allocated by an instance within that minute window.
Workers read this directory to discover active buckets without speculative queries.

<5> **Tier 5 (`es_retry_transactions_by_instance`) -- Bounded Metadata Partitions:** +
Stores lightweight retry metadata records inside strictly bounded partitions.
Crucially, when all transactions in a bucket are processed, the worker drops the **entire bucket partition at once**:
+
[source,sql]
----
DELETE FROM es_retry_transactions_by_instance
WHERE region = :region AND cluster = :cluster AND service_name = :service_name
  AND date_of_year = :date AND minute_of_day = :window
  AND instance_id = :instance_id AND bucket_index = :bucket_index;
----
+
Because the deletion targets the composite partition key, Cassandra writes a **single Partition Tombstone** rather than thousands of individual cell tombstones.
During background SSTable compaction, Cassandra drops the entire partition from disk in $O(1)$ time, completely preventing tombstone accumulation.

<6> **Primary Event Store (`es_transaction`) -- Decoupled Heavy State:** +
None of the 5 retry tables store business payloads.
Tier 5 holds strictly lightweight metadata pointers (~50 to 100 bytes per row).
When re-executing, the worker fetches the actual saga payload lazily from the primary event store using `transaction_id`, keeping memory usage low and constant.

=== Bounded Partition Sizing (< 100MB) via Local In-Memory Counters

If a major downstream outage generates 150,000 transaction failures in a single minute, placing all 150,000 records into one partition would create an oversized partition, triggering long garbage collection pauses and compaction pressure.

To prevent oversized partitions without burdening Cassandra with expensive `SELECT count(*)` checks, each application pod maintains an **atomic counter in local JVM memory** for the active minute window:

.Pseudocode: Local In-Memory Bucket Rollover
[source,text]
----
function registerFailure(transaction):
    currentWindow = computeTargetWindow(UTC_NOW)
    counter = getLocalWindowCounter(currentWindow)
    
    // Atomically increment local counter (takes ~2 nanoseconds)
    currentCount = counter.incrementAndGet()
    
    // Determine bucket index (default cap: 50,000 records per bucket)
    bucketIndex = currentCount / 50_000
    
    // Register directory path (idempotent upserts)
    insertDirectoryPath(currentWindow, instanceId, bucketIndex)
    
    // Insert lightweight retry pointer into bounded partition
    insertRetryMetadata(currentWindow, instanceId, bucketIndex, transaction.id)
----

* **Zero Read Latency on Writes:** Checking an in-memory counter takes 2 nanoseconds, adding no database read overhead to the live write path.
* **Safe Partition Sizing:** Each 50,000-row metadata partition consumes only ~3MB to 5MB on disk, remaining far below Cassandra's 100MB partition size limit.

== The Dual-Window Synchronization Model

Grouped time windows eliminate expensive range queries across timestamps by providing fixed, discrete partition keys.
To prevent race conditions between writers and readers, StackSaga enforces the **Dual-Window Model**:

.Dual-Window Synchronization Timeline: Writer & Reader Isolation
image:stacksaga-database-support:cassandra/stacksaga-diagram-cassandra-dual-window-timeline.svg[alt="Dual-Window Synchronization Timeline: Writer & Reader Isolation"]

The model operates through the following numbered mechanics:

<1> **Closed Read-Window ($\le W$):** +
Retry workers only read windows that have already closed (less than or equal to the current active read window $W$).
Window $W$ is sealed against new writes, guaranteeing stable, non-shifting query results.

<2> **Active Write-Window ($W+1$):** +
Live application pods experiencing failures **always write ahead into window $W+1$** (the next scheduled minute window).
No application thread will write to window $W$ while workers are reading or compacting it.

<3> **Live Application Pods (Write-Ahead Rule):** +
Because live writers write ahead to $W+1$, writers and readers never touch the same partition at the same time.
This complete separation eliminates write/read collisions and row lock contention without distributed locking.

<4> **Retry Workers (Sealed Read & Compaction):** +
Workers process completed windows without competing for row locks or encountering phantom reads.
Once all buckets in window $W$ are retried, the partition is dropped with a single tombstone.

<5> **Automatic Cooldown Period:** +
Writing to $W+1$ provides an inherent 10-second to 70-second cooldown buffer before retries begin.
This prevents the retry engine from immediately hammering a downstream service that is in the middle of a reboot or network blip.

.Pseudocode: Dual-Window Calculation & Midnight Rollover
[source,text]
----
constant TOTAL_WINDOWS_PER_DAY = 1440 // for 1-minute delay

function getCurrentReadWindow(utcTimestamp):
    minutesSinceMidnight = (utcTimestamp.hour * 60) + utcTimestamp.minute
    windowIndex = minutesSinceMidnight / delayInMinutes
    return Window(date = utcTimestamp.date, index = windowIndex)

function getCurrentWriteWindow(utcTimestamp):
    readWindow = getCurrentReadWindow(utcTimestamp)
    nextIndex = readWindow.index + 1
    
    // Check midnight UTC rollover
    if nextIndex >= TOTAL_WINDOWS_PER_DAY:
        return Window(date = utcTimestamp.date + 1 day, index = 0)
    else:
        return Window(date = utcTimestamp.date, index = nextIndex)
----

== Spatial Worker Isolation & Murmur3 Token Slicing

When multiple retry worker nodes run in parallel, they must process retries without fetching the same records and without relying on heavy distributed locks (such as Redis locks or Cassandra Paxos LWT).
StackSaga achieves this through **Murmur3 Token Range Leasing**:

.Murmur3 Token Ring Slicing & Spatial Worker Isolation
image:stacksaga-database-support:cassandra/stacksaga-diagram-cassandra-token-ring-instance-mapping.svg[alt="Murmur3 Token Ring Slicing & Spatial Worker Isolation"]

The numbered components operate as follows:

<1> **Murmur3 64-bit Token Ring:** +
Cassandra hashes partition keys into a continuous 64-bit integer space from `-9,223,372,036,854,775,808` to `9,223,372,036,854,775,807` (`-2^63` to `2^63 - 1`).

<2> **Ring Coordinator Non-Overlapping Leases:** +
An external RSocket Ring Coordinator divides the entire 64-bit token ring into mutually exclusive, non-overlapping segments and assigns one lease to each connected retry worker node (e.g. Node-0, Node-1, Node-2).

<3> **Deterministic Instance Routing (`token(instance_id)`):** +
When an application pod registers in Tier 3 (`es_instances_by_retry_window`), its clustering key includes `instance_id_token = token(instance_id)`.
Any pod's token hash falls deterministically into **exactly one** worker's assigned token range.

<4> **Spatial Isolation (Zero Lock Contention):** +
Workers query Tier 3 with their assigned token bounds:
+
[source,sql]
----
SELECT instance_id, instance_id_token
FROM es_instances_by_retry_window
WHERE region = :region AND cluster = :cluster AND service_name = :service_name
  AND date_of_year = :date AND minute_of_day = :window
  AND instance_id_token >= :lease_min_token
  AND instance_id_token <= :lease_max_token;
----
+
Because leases do not overlap, two workers never touch the same instance markers or bucket partitions.
Distributed locking is unnecessary, and throughput scales linearly as more worker nodes are added.

<5> **Lease Validity Guard (Failover Protection):** +
Every coordinator lease includes a validity timestamp window (`from` to `to` in epoch milliseconds).
Every database query and execution step verifies that the current timestamp falls within the lease window.
If a network partition causes a lease to expire, execution stops immediately, preventing split-brain execution while surviving nodes rebalance and take over the uncompleted ranges.

== End-to-End Traversal, Execution & Compaction Pipeline

The complete lifecycle from transaction failure to re-invocation and clean directory removal is structured as a top-down pipeline:

.Top-Down Traversal & Compaction Lifecycle Pipeline
image:stacksaga-database-support:cassandra/stacksaga-diagram-cassandra-traversal-pipeline.svg[alt="Top-Down Traversal & Compaction Lifecycle Pipeline"]

The numbered pipeline steps proceed in order:

<1> **Failure Detection & Target Window Calculation:** +
A saga step encounters a transient error. The pod calculates target write-window $W+1$ (handling UTC midnight rollover if needed).

<2> **Local In-Memory Counter Check:** +
The pod increments its local atomic counter for window $W+1$ to determine the active bucket index (0, 1, 2...).

<3> **Path Registration & Metadata Insertion:** +
The pod registers the path in Tiers 1 through 4, then inserts the lightweight metadata pointer into Tier 5 (`es_retry_transactions_by_instance`).

<4> **Worker Lease Acquisition & Lease Guard:** +
The retry worker acquires its token range lease from the coordinator and verifies lease validity.

<5> **Top-Down Traversal (Tiers 1, 2, 3):** +
The worker queries active calendar dates (`es_days_by_year`), picks the earliest eligible minute window (`es_retry_windows_by_day`), and filters instances matching its leased token range (`es_instances_by_retry_window`).

<6> **Bucket Discovery & Transaction Metadata Streaming:** +
The worker reads active bucket indices from Tier 4 (`es_buckets_by_instance`) and streams metadata records from Tier 5 (`es_retry_transactions_by_instance`).

<7> **Lazy Payload Fetching & Concurrent Re-Invocation:** +
Using the `transaction_id` metadata pointer, the worker fetches the full saga payload on demand from the primary transaction store and dispatches re-invocation with controlled concurrency.

<8> **Data Compaction (Partition Drop):** +
Once all transactions in the bucket have been dispatched, the worker executes a partition delete on Tier 5 and deletes the bucket index row from Tier 4.

<9> **Instance Marker Deletion:** +
When all buckets for an instance are completed, the worker deletes its instance marker from Tier 3 (`es_instances_by_retry_window`).

<10> **Node-0 Gate 1 & Gate 2 Verification:** +
The dedicated Compactor Overseer (Node-0) inspects Tier 3 across all token ranges to confirm zero pending instances remain across the whole cluster, and verifies that the window has elapsed into the past.

<11> **Node-0 Directory Compaction:** +
Node-0 safely deletes the completed minute window from Tier 2 (`es_retry_windows_by_day`), and deletes the calendar date from Tier 1 (`es_days_by_year`) once all minutes for that day are clear.

=== Safe Shutdown & Zero Data Loss Guarantee

If a retry worker pod is restarted while processing a 50,000-transaction bucket, deleting the partition prematurely would lose any transactions that had not yet run.

The traversal pipeline enforces a strict shutdown invariant:

.Pseudocode: Partial Batch Preservation on Shutdown
[source,text]
----
function onBucketBatchComplete(bucket, totalTransactions, executedCount):
    // If worker is stopping OR not all transactions were executed
    if isShutdownRequested() or executedCount < totalTransactions:
        log.info("Worker shutting down or partial execution. Preserving bucket in Cassandra.")
        return // Do NOT delete bucket partition!
        
    // Only delete partition when 100% of transactions were dispatched
    dropBucketPartition(bucket)
    deleteBucketIndex(bucket)
----

When a worker stops mid-bucket, the partition remains intact in Cassandra.
Upon restart (or when another worker takes over the token range), the remaining transactions are picked up and re-invoked safely.

=== Deep Historical Recovery

The retry scanner does not inspect only recent minutes. It is built for deep historical recovery after extended outages:

1. **Configurable Lookback:** On startup, workers generate candidate dates going back multiple days based on `start-digging-in-advance` (default: 2 days).
2. **Chronological Day Traversal:** Workers query Tier 1 (`es_days_by_year`) in ascending order (`date_of_year ASC`), processing older calendar days first.
3. **Chronological Minute Traversal:** Within each day, workers query Tier 2 (`es_retry_windows_by_day`) in ascending order (`minute_of_day ASC`).

If an application was offline throughout an entire weekend, workers systematically discover and process Friday's remaining windows, then Saturday's, Sunday's, and finally today's in chronological sequence.

== Directory Compaction: Node-0 Compactor Overseer vs. Worker Responsibilities

Compaction responsibilities are divided cleanly between general worker nodes and Node-0:

[cols="1,2,2",options="header"]
|===
| Responsibility | General Retry Workers (Node-1, Node-2, etc.) | Node-0 (Compactor Overseer)

| **Scope of Work**
| Handles only instances matching its assigned token lease.
| Inspects cluster-wide state across all token ranges.

| **Compaction Targets**
| - Tier 5: Bounded Bucket partitions (`es_retry_transactions_by_instance`) +
- Tier 4: Bucket index rows (`es_buckets_by_instance`) +
- Tier 3: Its own instance markers (`es_instances_by_retry_window`)
| - Tier 2: Minute window records (`es_retry_windows_by_day`) +
- Tier 1: Completed calendar dates (`es_days_by_year`)

| **Execution Timing**
| Runs immediately as each bucket or instance finishes.
| Runs on a periodic loop checking active windows.
|===

=== Why Node-0 Compaction Solves the Premature Deletion Problem

If every worker were allowed to delete minute windows from Tier 2, a fast worker with 5 transactions would delete minute 500 in 100 milliseconds, while a peer worker is still busy processing 40,000 transactions for that same minute.
The premature deletion would hide minute 500 from the directory, orphaning the remaining transactions.

Node-0 prevents this by passing **Two Strict Gates** before deleting directory records:

* **Gate 1 (Cluster-Wide Completion):**
  Node-0 queries Tier 3 across the entire cluster without token filtering:
  `SELECT instance_id FROM es_instances_by_retry_window WHERE minute_of_day = :window`.
  If any instance marker exists anywhere in the cluster, Node-0 waits.

* **Gate 2 (Time Moved into Past):**
  Node-0 checks that the clock has moved past the minute window. Even if all instance markers are gone, Node-0 waits until the window has elapsed to ensure no late writes occur.

Only when both gates pass does Node-0 safely remove the minute window from Tier 2.

== Write Protection & Duplicate Prevention (Kafka Event Sourcing)

When using Cassandra reactive support with event-driven streaming (such as Apache Kafka), guarding against duplicate execution and concurrent race conditions is essential.

=== Why Execution Markers Are Needed

StackSaga's Kafka implementation uses *at-least-once delivery semantics*.
Duplicate event deliveries can occur in distributed environments due to:

* Consumer group rebalances when pods scale up or down.
* Consumer node restarts before offset commits are acknowledged.
* Network timeouts and automated message retries.

To guarantee *idempotency*, StackSaga saves an *execution marker* in the `es_execution_markers` table.
Before processing, the engine inspects this table so that already-processed events are detected and skipped without side effects.

=== Consistency Modes & Overhead Trade-offs

StackSaga provides two consistency modes to balance strictness and throughput:

==== 1. STRICT Mode

* *When to use:* Recommended when you must strictly prevent duplicate side effects (such as customer notifications or non-idempotent third-party APIs) without writing custom deduplication code in your listeners.
* *How it works:*
1. **LWT Lease Acquisition:** Before running business logic, the worker acquires an exclusive temporary lock in Cassandra using Lightweight Transactions (LWT):
   `INSERT INTO es_execution_markers ... IF NOT EXISTS USING TTL <leaseDuration>`.
2. **Active Lease Wait:** If another worker is currently executing the same step (marker exists with `TTL > 0`), the second worker backs off for the remaining TTL duration and retries.
3. **Permanent Marker Commitment:** When the worker commits its batch, it updates the marker to permanent (`TTL = 0`). Concurrent workers see `TTL = 0` and terminate cleanly.
4. **Crash Recovery:** If a worker crashes mid-flight, the temporary lease expires when its TTL finishes, permitting another worker to retry and complete the saga step.

==== 2. RELAXED_WITH_DEDUP Mode

* *When to use:* Recommended when duplicate listener invocations are harmless (e.g. idempotent downstream consumers, cache evictions, loggers), or when you handle idempotency inside your listener logic.
* *How it works:* Before execution, the engine performs a lightweight read against `es_execution_markers`. If a completed marker is found, execution is skipped.
This avoids Cassandra LWT Paxos round-trips, maximizing throughput.

=== Domain-Level Configuration

Write protection can be configured globally and fine-tuned per domain:

.Example `application.yml`
[source,yaml]
----
stacksaga:
  cassandra:
    write-protection:
      default-mode: RELAXED_WITH_DEDUP      # Default high-throughput mode
      default-lease-duration: 5s            # Default LWT lease TTL (only for STRICT mode)
      domains:
        order-saga:
          mode: STRICT                      # Strict mutual exclusion for order saga
          lease-duration: 10s               # Custom lease TTL override
        payment-saga:
          mode: STRICT                      # Strict mode using default 5s lease
        notification-saga:
          mode: RELAXED_WITH_DEDUP          # High-throughput mode for notifications
----
