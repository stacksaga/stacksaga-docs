= StackSaga SQL Database Partition Support

== Overview

In high-throughput distributed systems using the Saga design pattern, the event-store tables—primarily `es_transaction` and `es_transaction_execution_tryout`—experience heavy sequential insert volumes as every transaction state and tryout execution is recorded.

To maintain optimal read/write query performance, rapid indexing, and predictable disk usage over time, these tables are partitioned by range (e.g. daily intervals based on the transaction timestamp).

`stacksaga-sql-partition-support` is a lightweight, non-blocking Spring Boot Starter designed to **automate the creation and maintenance of future partitions** across all SQL-based event-store databases in your ecosystem.

=== Architecture: A Dedicated Partition Runner

In a microservice architecture, each service embeds its respective database reactive starter (`stacksaga-mysql-reactive-support` or `stacksaga-pg-reactive-support`) to execute saga transactions. Partition maintenance, however, is handled by a separate dedicated runner — not by the microservices themselves.

[IMPORTANT]
====
*A dedicated runner, one per database engine*: +
Unlike the runtime database support modules that run inside every microservice instance, partition maintenance runs in a separate dedicated runner (a daemon or a scheduled job). Deploy **one runner per database engine** — one for MySQL and one for PostgreSQL — each serving all event-store databases of that engine.
====

Why run partition maintenance in a dedicated runner rather than inside the microservices?

1. **Avoids Multi-Instance DDL Conflicts & Lock Contention**:
If every replica or pod of every microservice attempted to execute `ALTER TABLE ... REORGANIZE PARTITION` or schema DDLs at application startup or on a cron trigger, database servers would suffer from metadata lock contention, connection spikes, and deadlocks.
2. **Strict Runtime Privilege Boundaries**:
Application microservices should run with minimal database privileges (DML only: `SELECT`, `INSERT`, `UPDATE`, `DELETE`). They do not need DDL or schema alteration rights. With a dedicated runner, only the partition runner is granted the necessary `ALTER` / `CREATE` privileges.
3. **One Runner Per Database Engine**:
A single runner handles **any number of datasources of the same engine** concurrently — e.g. one MySQL runner maintains the Order Service DB, the Inventory Service DB, and every other MySQL event-store at once. When your architecture mixes engines (some services on MySQL, others on PostgreSQL), deploy **one runner per engine**: one MySQL runner and one PostgreSQL runner. This keeps each runner's driver and database privileges scoped to a single engine. The pre-built Docker images (see <<docker-image>>) follow exactly this model — one image per engine.

image::stacksaga-database-support:stacksaga-diagram-sql-partition-architecture.drawio.svg[StackSaga SQL Partition Architecture]

==== Single Point of Failure (SPOF) Consideration: Why It Is Not An Issue

A common architectural question is: _"Does having a single partition runner per engine introduce a single point of failure?"_

The answer is **no**. In practice, this design is resilient and poses no risk to your production workloads:

* **Configurable Pre-Creation Buffer (`unit` + `ahead-count`)**:
When the runner triggers, it does not merely create a partition for the immediate day. Through `ahead-count` and `unit` (`DAYS`, `WEEK`, `MONTH`, `YEAR`), it pre-allocates partitions for multiple upcoming intervals in advance.
For example, configuring `unit: DAYS` with `ahead-count: 7` or `unit: MONTH` with `ahead-count: 2` guarantees that valid partitions already exist days or months ahead in your databases.
* **Completely Decoupled Runtime Transactions**:
Runtime microservices (`order-service`, `payment-service`, etc.) insert saga events directly into the database. They do *not* communicate with or depend on the partition runner during transaction execution.
* **Resilience to Runner Downtime**:
Even if a partition runner goes offline, encounters an infrastructure crash, or is undergoing extended maintenance for multiple days, your microservices continue writing events without interruption because future partition tables are already present in the database.
* **Automatic Catch-Up Upon Restart**:
As soon as the partition runner restarts or triggers next, it queries the database, detects any missing future intervals, and idempotently provisions them.

== Key Features

* **Startup & Cron Execution**:
Partitions are checked and pre-created immediately on application startup (`run-on-startup=true`) and periodically on a configurable schedule (`cron`, defaulting to `0 0 12 * * *` — 12:00 PM noon every day).
* **Multi-Datasource & Concurrency**:
Configures any number of datasources under `stacksaga.partitioning.sql.datasources.*`. All configured datasources are processed concurrently using Project Reactor's non-blocking `Flux.flatMap(concurrency = 4)`.
* **Unpooled On-Demand Connections**:
Because partition maintenance runs only on startup and once a day via cron, holding permanent idle connection pools in memory is unnecessary. The starter creates a direct, unpooled R2DBC connection on-demand, executes the partition DDLs, and closes the connection immediately.
* **Dialect Auto-Detection (MySQL & PostgreSQL)**:
The database type is automatically recognized from the R2DBC URL and connection metadata:
** **MySQL**: Dynamically reorganizes range partitions using the `p_max` catch-all boundary:
[source,sql]
----
ALTER TABLE es_transaction REORGANIZE PARTITION p_max INTO (
    PARTITION p2026_09_13 VALUES LESS THAN ('2026-09-14 00:00:00'),
    PARTITION p_max VALUES LESS THAN (MAXVALUE)
);
----
** **PostgreSQL**: Creates declarative child partitions:
[source,sql]
----
CREATE TABLE IF NOT EXISTS es_transaction_p2026_09_13 PARTITION OF es_transaction
    FOR VALUES FROM ('2026-09-13 00:00:00') TO ('2026-09-14 00:00:00');
----
* **Pre-Flight Validation**:
Validates database connectivity (`validate-on-startup=true`) and inspects user privileges (`validate-privileges=true`) at startup using `SHOW GRANTS` (MySQL) or `has_schema_privilege` (PostgreSQL), providing early warnings if the database user lacks permission.
* **Pre-Creation (`ahead-count`)**:
Configurable per datasource. Setting `ahead-count: 2` pre-creates partitions for today plus the next 2 days ahead, preventing data rejection when midnight arrives.

== How to Use: Two Options

There are two ways to use SQL Database Partition Support. Both run the exact same partition logic — choose
based on whether you want to build and operate your own service or just run a ready-made container.

[cols="1,3,3",options="header"]
|===
|Option|What you do|Best for

|<<option-a,*A — Build your own application*>>
|Create a small Spring Boot service, add the `stacksaga-sql-partition-support` dependency plus the matching
R2DBC driver(s), configure your datasources, and deploy it.
|Teams that want to embed and customize the runner — a custom `PartitionDefinitionProvider`,
`PartitionExecutionCompletedEvent` listeners, or extra application beans.

|<<docker-image,*B — Use the pre-built Docker images*>>
|Run the official `stacksaga/partition-runner-<engine>` image and inject datasources at runtime (environment

|Teams that just want partition maintenance running with zero code — a `docker run` daemon or a Kubernetes
CronJob.
|===

=== Base Images & Runtime

The images are built with and run on **Java 21** (Eclipse Temurin). The jar is built in CI and copied in, so
the images are small and multi-arch (amd64 + arm64). Both flavors run as a non-root user and pin
`TZ=Etc/UTC` so partition date boundaries never shift across hosts.

[cols="2,3",options="header"]
|===
|Flavor|Base image

|Production (`latest` / `<version>`)
|`eclipse-temurin:21-jre-jammy` (glibc)

|Alpine (`alpine` / `<version>-alpine`)
|`eclipse-temurin:21-jre-alpine` (musl)
|===

The runner is a self-contained container that talks to your databases over R2DBC, so your **database server
version is independent of the image**. The bundled drivers — `io.asyncer:r2dbc-mysql` and
`org.postgresql:r2dbc-postgresql`, at the versions managed by the StackSaga BOM for the release — connect to
current MySQL and PostgreSQL servers (verified against MySQL 8.x). Running a newer database or a newer JDK in
your own services does not affect these images.

=== Providing Datasources at Runtime

The image ships with **no datasources**. Inject them at run time with either environment variables or a
mounted config file.

**Option 1 — Environment variables** (relaxed binding; use lowercase-alphanumeric datasource names):

[source,bash]
----
docker run --rm stacksaga/partition-runner-mysql:1.0.0 \
  -e STACKSAGA_PARTITIONING_SQL_DATASOURCES_ORDERDB_URL=r2dbc:mysql://db-host:3306/order_db \
  -e STACKSAGA_PARTITIONING_SQL_DATASOURCES_ORDERDB_USERNAME=partition_admin \
  -e STACKSAGA_PARTITIONING_SQL_DATASOURCES_ORDERDB_PASSWORD=secret \
  -e STACKSAGA_PARTITIONING_SQL_DATASOURCES_ORDERDB_UNIT=DAYS \
  -e STACKSAGA_PARTITIONING_SQL_DATASOURCES_ORDERDB_AHEAD_COUNT=2
----

**Option 2 — Mounted `application.yml`** (cleaner for many datasources; keep passwords in env/secrets):

[source,yaml]
----
# my-datasources.yml  (mount at /app/config/application.yml)
stacksaga:
  partitioning:
    sql:
      datasources:
        orderdb:   { url: "r2dbc:mysql://db-host:3306/order_db", username: partition_admin, unit: DAYS, ahead-count: 2 }
        inventorydb: { url: "r2dbc:mysql://db-host:3306/inventory_db", username: partition_admin, unit: MONTH, ahead-count: 1 }
----

[source,bash]
----
docker run --rm \
  -v "$(pwd)/my-datasources.yml:/app/config/application.yml:ro" \
  -e STACKSAGA_PARTITIONING_SQL_DATASOURCES_ORDERDB_PASSWORD=secret \
  -e STACKSAGA_PARTITIONING_SQL_DATASOURCES_INVENTORYDB_PASSWORD=secret \
  stacksaga/partition-runner-mysql:1.0.0
----

TIP: The image bundles only one engine's driver, so the datasource URLs for a given runner must all target
that engine (all `r2dbc:mysql://...` for the MySQL image, all `r2dbc:postgresql://...` for the PostgreSQL image).

=== Daemon vs. Kubernetes CronJob

The same image serves both deployment modes described in <<Deployment Strategies>>. For the ephemeral
CronJob pattern, set `STACKSAGA_PARTITIONING_SQL_CRON=none` and
`STACKSAGA_PARTITIONING_SQL_EXIT_ON_COMPLETION=true` — the container runs once, exits `0` on success or `1`
on failure, and Kubernetes reclaims its resources. In the CronJob manifest under <<Deployment Strategies>>,
use `stacksaga/partition-runner-mysql:1.0.0` (or the `-postgres` image) as the container `image`.

=== Quick Start with Docker Compose

The following `docker-compose.yml` brings up a seeded MySQL and runs the partition runner against it as a
one-shot job. A ready-to-run copy also ships in the source repository at
`stacksaga-partition-runner/examples/docker-compose.yml`.

[source,yaml,subs="attributes+"]
----
name: stacksaga-partition-demo

services:
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: rootpw
      MYSQL_DATABASE: stacksaga_demo
      MYSQL_USER: partition_admin
      MYSQL_PASSWORD: partition_pw
    volumes:
      - ./init/mysql:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-uroot", "-prootpw"]
      interval: 5s
      timeout: 5s
      retries: 20

  partition-runner:
    image: stacksaga/partition-runner-mysql:{stacksaga-version}
    depends_on:
      mysql:
        condition: service_healthy
    restart: "no"
    environment:
      # Run once and exit (0 success / 1 failure) — the Kubernetes CronJob pattern.
      STACKSAGA_PARTITIONING_SQL_CRON: "none"
      STACKSAGA_PARTITIONING_SQL_EXIT_ON_COMPLETION: "true"
      # Datasource injected at runtime. The host is the compose service name 'mysql'.
      STACKSAGA_PARTITIONING_SQL_DATASOURCES_DEMODB_URL: "r2dbc:mysql://mysql:3306/stacksaga_demo"
      STACKSAGA_PARTITIONING_SQL_DATASOURCES_DEMODB_USERNAME: "partition_admin"
      STACKSAGA_PARTITIONING_SQL_DATASOURCES_DEMODB_PASSWORD: "partition_pw"
      STACKSAGA_PARTITIONING_SQL_DATASOURCES_DEMODB_UNIT: "DAYS"
      STACKSAGA_PARTITIONING_SQL_DATASOURCES_DEMODB_AHEAD_COUNT: "7"
----

The event-store tables must already exist as range-partitioned tables with a `p_max` catch-all (in production
they are created by the StackSaga MySQL/PostgreSQL reactive support). For this demo, seed them by placing the
file below at `init/mysql/01-schema.sql` next to the compose file — shown for one table; repeat the same
pattern for `es_transaction_execution_tryout`, `es_resume_context` and `es_terminated_transaction`:

[source,sql]
----
CREATE TABLE IF NOT EXISTS es_transaction (
    id                       BIGINT       NOT NULL AUTO_INCREMENT,
    transaction_tx_datetime  DATETIME     NOT NULL,
    payload                  VARCHAR(255) NULL,
    PRIMARY KEY (id, transaction_tx_datetime)
) ENGINE = InnoDB
PARTITION BY RANGE COLUMNS (transaction_tx_datetime) (
    PARTITION p_max VALUES LESS THAN (MAXVALUE)
);
----

Run it, then inspect the partitions that were created:

[source,bash]
----
docker compose up --abort-on-container-exit --exit-code-from partition-runner

# While MySQL is still up, list the created partitions:
docker compose up -d mysql
docker compose exec mysql mysql -upartition_admin -ppartition_pw stacksaga_demo \
  -e "SELECT table_name, partition_name FROM information_schema.partitions \
      WHERE table_schema='stacksaga_demo' AND partition_name IS NOT NULL ORDER BY 1,2;"
docker compose down -v
----

== Deployment Strategies

Because partition maintenance takes only a few seconds to verify and create tables, you can choose between two deployment strategies depending on your operational platform:

=== Strategy A: Persistent Daemon (Traditional VM / Long-Running Container)

In a traditional VM or standard Docker container environment:

* The application runs 24/7 as a background daemon.
* On startup, it performs connectivity checks, verifies user permissions (`validate-on-startup=true`), and pre-creates partitions (`run-on-startup=true`).
* After the startup run finishes, it sleeps idle in the background until the next scheduled trigger determined by `stacksaga.partitioning.sql.cron` (e.g. `0 0 12 * * *`).

=== Strategy B: Ephemeral Scheduled Job (Kubernetes CronJob)

In container orchestration environments such as **Kubernetes (k8s)**, maintaining a pod running continuously 24/7 can be inefficient, because after creating the partitions in a few seconds, the application simply sits idle doing nothing until the next scheduled day.

To optimize cluster resource utilization, you can deploy the partition runner as a **Kubernetes `CronJob`** (or container task on AWS ECS / GCP Cloud Run Jobs):

* **How It Operates**:
. Kubernetes triggers the CronJob pod at the desired schedule (e.g. daily at 12:00 PM).
. The pod starts up, Spring Boot initializes, and with `run-on-startup=true`, it immediately validates all datasources and creates upcoming partitions across all databases concurrently.
. The internal Spring cron scheduler is disabled by setting `stacksaga.partitioning.sql.cron=none` (or `-`).
. Enabling `stacksaga.partitioning.sql.exit-on-completion=true` commands the runner to automatically terminate the Spring Boot application and JVM once partition creation finishes:
+
* If all datasources succeed -> exits cleanly with code `0` (`Completed`).
* If any datasource fails -> exits with code `1` (`Error`/`Failed`), which causes Kubernetes to alert or retry according to your `restartPolicy`.
+
. Kubernetes releases all pod memory and CPU resources until the next scheduled interval.

*Example Kubernetes CronJob Manifest*:

[source,yaml]
----
apiVersion: batch/v1
kind: CronJob
metadata:
  name: stacksaga-partition-runner
  namespace: stacksaga
spec:
  schedule: "0 12 * * *"  # Trigger daily at 12:00 PM noon
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: partition-runner
              image: stacksaga/partition-runner-mysql:1.0.0  # one runner per engine; use -postgres for PostgreSQL
              env:
                # Execute partition creation immediately upon pod start
                - name: STACKSAGA_PARTITIONING_SQL_RUN_ON_STARTUP
                  value: "true"
                # Validate connectivity and permissions at startup
                - name: STACKSAGA_PARTITIONING_SQL_VALIDATE_ON_STARTUP
                  value: "true"
                - name: STACKSAGA_PARTITIONING_SQL_VALIDATE_PRIVILEGES
                  value: "true"
                # Disable the internal background cron since Kubernetes manages the schedule
                - name: STACKSAGA_PARTITIONING_SQL_CRON
                  value: "none"
                # Automatically exit with code 0 (or 1 on error) when finished
                - name: STACKSAGA_PARTITIONING_SQL_EXIT_ON_COMPLETION
                  value: "true"
              resources:
                requests:
                  memory: "256Mi"
                  cpu: "100m"
                limits:
                  memory: "512Mi"
                  cpu: "500m"
----

== Monitoring & Observability

`stacksaga-sql-partition-support` provides observability hooks to monitor partition execution results, record metrics, and trigger alerts on failures.

=== PartitionExecutionCompletedEvent

Whenever partition creation runs (both on application startup and on cron triggers), the runner automatically publishes a Spring `PartitionExecutionCompletedEvent`.

This event provides detailed execution telemetry:

[.scrollable-div]
--
[cols="1,1,<2"]
|===
|Method|Return Type|Description

|`isAllSuccessful()`
|`boolean`
|Returns `true` if all configured datasources were partitioned without any error.

|`getTotalDatasources()`
|`int`
|Total count of datasources evaluated during the execution.

|`getSuccessCount()`
|`int`
|Number of datasources successfully partitioned.

|`getFailureCount()`
|`int`
|Number of datasources that failed.

|`getDuration()`
|`Duration`
|Total elapsed execution time.

|`getReports()`
|`Map<String, DatasourceReport>`
|Per-datasource detailed reports containing table names, partition counts, and error causes (if any).
|===
--

=== Example: Listening for Partition Events & Alerting

Developers can register a Spring `@EventListener` to capture partition metrics, push alerts to Slack or PagerDuty, or export data to Prometheus:

[source,java]
----
import lombok.extern.slf4j.Slf4j;
import org.springframework.context.event.EventListener;
import org.springframework.stereotype.Component;
import org.stacksaga.partition.event.PartitionExecutionCompletedEvent;

@Component
@Slf4j
public class PartitionMonitoringListener {

    @EventListener
    public void onPartitionCompleted(PartitionExecutionCompletedEvent event) {
        if (!event.isAllSuccessful()) {
            log.error("ALERT: Partition creation failed for {}/{} datasources in {} ms!",
                    event.getFailureCount(), event.getTotalDatasources(), event.getDuration().toMillis());

            event.getReports().forEach((dsName, report) -> {
                if (!report.isSuccess()) {
                    log.error("Datasource '{}' failed: {}", dsName, report.getErrorMessage(), report.getError());
                    // Example: send alert to Slack, Discord, PagerDuty, or Email
                    // alertService.sendAlert("Partition failure on datasource: " + dsName);
                }
            });
        } else {
            log.info("SUCCESS: All {} datasources partitioned successfully in {} ms.",
                    event.getTotalDatasources(), event.getDuration().toMillis());
        }
    }
}
